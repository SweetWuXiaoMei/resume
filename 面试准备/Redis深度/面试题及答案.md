## 1. Redis 为什么这么快？

**面试官考察点**：对 Redis 性能原理的深度理解。

**参考答案**：

Redis 单线程 QPS 可达 10 万+，快的原因：

1. **纯内存操作**：所有数据在内存中，读写速度是纳秒级
2. **单线程模型**：避免多线程上下文切换和锁竞争，但 6.0 后引入多线程 IO（只用于网络读写，命令执行仍是单线程）
3. **IO 多路复用**：epoll/kqueue 同时监听多个连接
4. **高效数据结构**：SDS、ziplist、skiplist 等都是精心设计的
5. **RESP 协议简洁**：文本协议，解析开销低
6. **全局哈希表 + 渐进式 Rehash**：O(1) 查找，Rehash 非阻塞

**关键要点**：
- "单线程"是指命令执行线程，6.0 后网络 IO 是多线程的
- Redis 的性能瓶颈通常在网络带宽和内存带宽，而非 CPU

## 2. Redis 五种基本数据结构的底层实现？

**面试官考察点**：数据结构底层原理的扎实程度。

**参考答案**：

| 类型 | 底层实现 | 编码切换条件 |
|------|---------|-------------|
| **String** | SDS（简单动态字符串）| INT < EMBSTR < RAW（44 字节为界）|
| **Hash** | ziplist（压缩列表）→ hashtable | 元素 > 512 或单个 value > 64 字节 |
| **List** | quicklist（ziplist 链表，3.2+）| 统一使用 quicklist |
| **Set** | intset（整数集合）→ hashtable | 元素 > 512 或包含非整数 |
| **ZSet** | ziplist → skiplist + dict | 元素 > 128 或 member > 64 字节 |

**ZSet 的 Skiplist + Dict 双重结构**：
```
Skiplist：按 score 排序，支持范围查询 O(logN)
Dict：按 member 查找 score，O(1)

为什么两个结构？空间换时间
- 范围查询用 Skiplist
- 查单个 member 的 score 用 Dict
```

**关键要点**：
- 了解编码切换条件可以解释"为什么小数据量性能很好，数据量大了突然变慢"
- ziplist 是连续内存，CPU Cache 友好，小数据量下比 hashtable 快

## 3. Redis 持久化 RDB 和 AOF 的区别？混合持久化是什么？

**面试官考察点**：持久化方案的选型和原理。

**参考答案**：

| 维度 | RDB | AOF |
|------|-----|-----|
| 原理 | 快照，全量内存数据 | 写命令日志，增量追加 |
| 文件大小 | 小（压缩二进制） | 大（文本命令） |
| 恢复速度 | 快 | 慢（重放所有命令） |
| 数据安全 | 可能丢最后几分钟数据 | 可配置 fsync 策略 |
| 阻塞风险 | fork 子进程时可能短暂阻塞 | 无 |
| 重写 | 不需要（每次全量） | 需要 AOF Rewrite（BGREWRITEAOF） |

**混合持久化（Redis 4.0+）**：
```
AOF Rewrite 时：
- 前半部分：当前时刻的 RDB 快照数据（二进制，快速恢复）
- 后半部分：快照后的增量 AOF 命令

优势：恢复速度快（RDB 部分）+ 数据安全（AOF 部分）
```

**竞拍系统的选择**：
```
RDB：每小时一次快照（灾备，快速恢复）
AOF：everysec（保证最多丢 1 秒数据）
混合持久化：开启（兼顾恢复速度和数据安全）
```

**关键要点**：
- AOF Rewrite 期间也会 fork，和 RDB 一样有内存翻倍的风险
- 混合持久化是生产环境的最佳实践

## 4. 缓存穿透、缓存击穿、缓存雪崩的区别和解决方案？

**面试官考察点**：三大缓存问题的系统性应对方案。

**参考答案**：

| 问题 | 现象 | 根因 |
|------|------|------|
| **缓存穿透** | 查询不存在的数据，绕过缓存直接打 DB | 恶意攻击 / 业务查询 |
| **缓存击穿** | 热点 Key 过期瞬间，大量请求打 DB | 热点 Key 过期 |
| **缓存雪崩** | 大量 Key 同时过期，DB 瞬间过载 | 过期时间集中 |

**解决方案对比**：

**缓存穿透**：
```java
// 方案1：布隆过滤器（推荐）
BloomFilter<String> filter = BloomFilter.create(
    Funnels.stringFunnel(Charset.defaultCharset()),
    10000000,  // 预期元素数
    0.001      // 误判率
);

// 方案2：缓存空值（简单但有局限）
if (value == null) {
    redis.setex(key, 60, "NULL");  // 缓存空值 60 秒
}
```

**缓存击穿**：
```java
// 方案1：互斥锁（分布式锁）
public String getData(String key) {
    String value = redis.get(key);
    if (value == null) {
        String lockKey = "lock:" + key;
        if (redis.set(lockKey, "1", "NX", "EX", 10)) {
            try {
                value = db.query(key);
                redis.setex(key, 3600, value);
            } finally {
                redis.del(lockKey);
            }
        } else {
            Thread.sleep(50);
            return getData(key);  // 重试
        }
    }
    return value;
}

// 方案2：永不过期 + 异步更新
// 热点 Key 不设过期时间，通过业务逻辑异步更新
```

**缓存雪崩**：
```java
// 方案1：过期时间随机化
int expireTime = 3600 + ThreadLocalRandom.current().nextInt(600);  // 1h + 随机 0-10min

// 方案2：多级缓存
// L1: 本地缓存（Caffeine，永不过期但容量有限）
// L2: Redis 集群
// L3: 数据库

// 方案3：限流熔断
// Sentinel 在 DB 层面做限流保护
```

**关键要点**：
- 三个概念不要搞混，面试官必考
- 生产环境通常是多个方案组合使用

## 5. 缓存与数据库一致性方案？延迟双删怎么实现？

### 实战案例：支付系统缓存一致性

**面试官考察点**：缓存一致性的完整方案设计。

**参考答案**：

**推荐方案：Cache Aside + 双删 + Binlog 兜底**

```java
@Service
public class PaymentService {
    
    // 1. Cache Aside 模式
    public Payment getPayment(Long id) {
        // 先查缓存
        Payment payment = redis.get("payment:" + id);
        if (payment != null) return payment;
        
        // 缓存未命中，查数据库
        payment = db.findById(id);
        if (payment != null) {
            redis.setex("payment:" + id, 3600, payment);
        }
        return payment;
    }
    
    // 2. 更新：先删缓存，再更新 DB，再延时删缓存
    @Transactional
    public void updatePayment(Payment payment) {
        // 第一步：删除缓存
        String key = "payment:" + payment.getId();
        redis.del(key);
        
        // 第二步：更新数据库
        db.update(payment);
        
        // 第三步：延迟双删（异步，兜底并发问题）
        CompletableFuture.runAsync(() -> {
            try {
                Thread.sleep(200);  // 等待其他并发读请求完成
                redis.del(key);
            } catch (InterruptedException ignored) {}
        });
    }
}

// 3. Binlog 兜底（终极保障）
// Canal 监听 MySQL binlog → 数据变更 → 删除/更新缓存
// 保证即使应用层删除失败，最终也能一致
@Component
public class CanalListener {
    public void onBinlogEvent(DataChangeEvent event) {
        String key = "payment:" + event.getRowData().get("id");
        redis.del(key);  // 兜底删除
    }
}
```

**缓存一致性方案选择指南**：

| 一致性要求 | 推荐方案 |
|-----------|---------|
| 低（可容忍秒级不一致） | Cache Aside + TTL 过期 |
| 中（可容忍百毫秒） | Cache Aside + 双删 |
| 高（资金/库存类） | 不缓存，或 Cache Aside + 双删 + Binlog 兜底 |
| 极高（金融交易） | 不用缓存，直接读写数据库 |

## 6. Redis 哨兵模式（Sentinel）下如何处理脑裂？

### 实战案例：支付系统 Redis 脑裂排查

**面试官考察点**：Redis 高可用方案的故障处理经验。

**参考答案**：

**脑裂场景**：
```
初始状态：
┌──────────────────────────┐
│   Master (10.0.0.1:6379) │
│   ├── Slave-A             │
│   └── Slave-B             │
└──────────────────────────┘

网络分区后：
┌─────────────────┐    ┌─────────────────┐
│ Sentinel 1,2     │    │ Sentinel 3      │
│ 判定 Master 挂了  │    │ 仍连接 Master   │
│ 选 Slave-A 为新   │    │                 │
│ Master           │    │                 │
└─────────────────┘    └─────────────────┘

结果：两个 Master 同时接受写请求 → 数据不一致
```

**预防措施**：
```bash
# 1. Master 至少要有 1 个 Slave 才接受写入
CONFIG SET min-replicas-to-write 1
CONFIG SET min-replicas-max-lag 10  # Slave 延迟超过 10s 也不接受写入

# 2. Sentinel 配置优化
sentinel monitor mymaster 10.0.0.1 6379 2  # quorum = 2
# 注意：quorum 是"发现故障"的 Sentinel 数，"执行故障转移"需要 majority

# 3. 客户端/业务层防脑裂
# 写入前检查 master 角色
ROLE  # 返回 master/slave
INFO replication  # 查看连接状态
```

**脑裂后恢复**：
```
1. 确认真实 Master（看 Sentinel 日志和当前配置）
2. 通知业务方切换到正确 Master
3. 根据业务容忍度决定：丢弃脑裂期间旧 Master 的数据，或手动合并
4. 将旧 Master 以 Slave 身份重新加入集群
5. 同步完成后切换回原拓扑
```

**关键要点**：
- min-replicas-to-write 是预防脑裂数据丢失的关键参数
- quorum 和 majority 是两个不同概念，面试中经常被混淆

## 7. Redis 分布式锁怎么实现？Redlock 有什么问题？

**面试官考察点**：分布式锁的完整实现和理解。

**参考答案**：

**单 Redis 分布式锁**：
```java
// 加锁：SET key value NX PX 30000
String result = redis.set("lock:payment:123", requestId, "NX", "PX", 30000);

// 解锁：Lua 脚本保证原子性（验证 value 是自己加的锁）
String script = 
    "if redis.call('get', KEYS[1]) == ARGV[1] then " +
    "    return redis.call('del', KEYS[1]) " +
    "else " +
    "    return 0 " +
    "end";
redis.eval(script, Collections.singletonList(key), Collections.singletonList(requestId));
```

**单节点 Redis 锁的问题**：
- Master 宕机，从库提升，锁信息丢失
- 两个客户端同时获得同一把锁

**Redisson 看门狗机制（WatchDog）**：
```java
RLock lock = redisson.getLock("lock:payment:123");
lock.lock();  // 默认 30s 过期，每 10s 自动续期

// Redisson 的改进：
// 1. 自动续期（WatchDog）
// 2. 可重入（基于 Redis Hash 计数）
// 3. 公平锁（基于 Redis 队列）
// 4. 红锁（RedLock，多 Master 场景）
```

**Redlock 争议的要点**：
- GC stop-the-world 可能导致锁过期但客户端不知道
- 解决方案：Fencing Token（递增版本号，资源层校验）
- 竞拍系统没有使用 Redlock——用 Lua 原子操作代替了分布式锁

## 8. Redis Lua 脚本在竞拍系统中的实战应用

### 实战案例：竞拍出价引擎

**面试官考察点**：Lua 脚本的实际应用能力。

**参考答案**：

**为什么用 Lua 脚本？**
- 竞拍出价需要"校验余额 + 比较出价 + 更新排行 + 扣减资金"四步操作，必须原子执行
- 如果用 Java 代码 + 分布式锁，RT 太高（网络往返 + 锁开销）
- Lua 脚本在 Redis 服务端执行，彻底消除竞争条件

**竞拍出价 Lua 脚本**：
```lua
-- KEYS[1]: bid:auction:{auctionId}   -- 出价排行榜 ZSet
-- KEYS[2]: bid:lock:{auctionId}      -- 出价锁
-- KEYS[3]: balance:{bidderId}        -- 用户余额
-- ARGV[1]: bidderId                  -- 出价人 ID
-- ARGV[2]: amount                    -- 出价金额（分）
-- ARGV[3]: minBidAmount              -- 最小加价金额
-- ARGV[4]: maxBidAmount              -- 最大出价金额
-- ARGV[5]: timestamp                 -- 出价时间戳

-- 1. 检查余额
local balance = redis.call('GET', KEYS[3])
if not balance or tonumber(balance) < tonumber(ARGV[2]) then
    return {-1, 'INSUFFICIENT_BALANCE'}  -- 余额不足
end

-- 2. 检查出价金额
local currentMax = redis.call('ZREVRANGE', KEYS[1], 0, 0, 'WITHSCORES')
if currentMax[2] and tonumber(ARGV[2]) <= tonumber(currentMax[2]) then
    return {-2, 'BID_TOO_LOW'}  -- 出价过低
end

-- 3. 使用分数编码：价格(主) + 时间戳(次，取反以保证先到先得)
-- score = amount * 10^13 + (9999999999999 - timestamp)
-- 保证同价格下，先出价者排名更高
local score = tonumber(ARGV[2]) * 10000000000000 + (9999999999999 - tonumber(ARGV[5]))

-- 4. 更新排行榜
redis.call('ZADD', KEYS[1], score, ARGV[1] .. ':' .. ARGV[2])

-- 5. 扣减余额
redis.call('DECRBY', KEYS[3], ARGV[2])

-- 6. 返回成功
return {0, 'SUCCESS', currentMax[2] or 0}
```

**Java 端调用**：
```java
public BidResult placeBid(Long auctionId, Long bidderId, Long amount) {
    List<String> keys = Arrays.asList(
        "bid:auction:" + auctionId,
        "bid:lock:" + auctionId,
        "balance:" + bidderId
    );
    List<String> args = Arrays.asList(
        String.valueOf(bidderId),
        String.valueOf(amount),
        String.valueOf(minBidAmount),
        String.valueOf(maxBidAmount),
        String.valueOf(System.currentTimeMillis())
    );
    
    List<Long> result = (List<Long>) redis.eval(bidScript, keys, args);
    
    if (result.get(0) == 0) {
        // 出价成功，发送 MQ 事件异步通知 + 落库
        rocketMQ.send(new BidSuccessEvent(auctionId, bidderId, amount));
        return BidResult.success();
    } else {
        return BidResult.fail(result.get(1).toString());
    }
}
```

**关键要点**：
- Lua 脚本执行期间 Redis 是阻塞的，脚本不能太复杂
- 脚本需要纯函数式，每次执行结果可预测
- EVALSHA 缓存脚本 SHA，减少网络传输

## 9. Redis Cluster 的架构原理和运维经验？

**面试官考察点**：Redis 集群方案的理解。

**参考答案**：

**Cluster 核心设计**：
- **16384 个 Slot**：CRC16(key) % 16384 决定数据落在哪个 Slot
- **Gossip 协议**：节点间通过 Gossip 协议交换状态信息
- **MOVED/ASK 重定向**：客户端请求错误节点时，返回正确节点地址
- **主从模式**：每个 Slot 有一个 Master 和多个 Slave

**集群规划和扩容**：
```
初始：3 主 3 从，每个 Master 负责 5461 个 Slot
扩容到 6 主 6 从：
  1. 添加新节点
  2. redis-cli --cluster reshard → 迁移部分 Slot
  3. redis-cli --cluster rebalance → 重新均衡
  4. 为每个新 Master 添加 Slave
```

**常见运维问题**：
- Slot 迁移期间（MIGRATING/IMPORTING），Key 存在 ASK 重定向，客户端需要处理
- Cluster 要求所有节点之间能互通，否则脑裂
- 大 Key 迁移时间过长会导致迁移超时失败

## 附录：Redis 面试速查表

### 性能优化清单

```
□ 禁用危险命令：KEYS → SCAN, FLUSHALL → 重命名
□ 大 Key 拆分：> 10KB 或 > 10000 元素 → 拆分为多个小 Key
□ 热 Key 打散：热点 Key 复制多份 + 随机读取
□ 连接池：连接复用、最大连接数控制
□ Pipeline：批量操作，减少 RTT
□ 慢查询监控：slowlog-log-slower-than 10000（10ms）
□ 持久化：混合持久化 + everysec AOF
□ 内存淘汰策略：volatile-lru 或 allkeys-lru
```
