# 系统设计案例面试题及答案

> 本套面试题针对架构师岗位，每道题都是从 0 到 1 的完整架构设计，包含需求分析、技术选型、架构图、核心流程和容量评估。

---

## 题一：设计一个高并发实时竞拍系统

**面试官考察点**：高并发 + 强一致性 + 低延迟的综合架构设计能力。

### 一、需求分析

**功能需求**：
- 车商实时出价，出价必须高于当前最高价
- 所有在线车商实时看到最新出价排行 Top 10
- 出价成功后立即扣减保证金（防止恶意出价）
- 支持多场拍卖同时进行

**非功能需求**：
- 出价 P99 延迟 < 100ms，通知延迟 < 200ms
- 峰值 10 万+ 并发连接
- 出价成功率 100%（不允许超卖、排序错乱）
- 系统可用性 99.99%

### 二、架构设计

```
                          ┌──────────┐
      车商 App/Web ─────→ │   CDN    │ ← 静态化拍卖详情页
                          └──────────┘
                                │
              ┌─────────────────▼─────────────────┐
              │          Nginx (L4 LB)             │
              │    Keepalived VIP 高可用            │
              └─────────────────┬─────────────────┘
                                │
              ┌─────────────────▼─────────────────┐
              │      Netty 长连接网关集群           │
              │   ┌──────┐ ┌──────┐ ┌──────┐      │
              │   │Node 1│ │Node 2│ │Node N│ ...  │
              │   └──┬───┘ └──┬───┘ └──┬───┘      │
              │      │ WebSocket/Protobuf          │
              └──────┼────────┼────────┼──────────┘
                     │        │        │
              ┌──────▼────────▼────────▼──────────┐
              │         业务服务集群                │
              │  ┌──────────────┐                  │
              │  │ 出价服务      │ Dubbo RPC        │
              │  │ 保证金服务    │                  │
              │  │ 用户服务      │                  │
              │  └──────────────┘                  │
              └──────┬────────┬────────┬──────────┘
                     │        │        │
         ┌───────────▼──┐ ┌──▼────────▼──┐ ┌──────▼───────┐
         │  Redis       │ │  MySQL MGR   │ │  RocketMQ    │
         │  Cluster     │ │  组复制       │ │  DLedger     │
         │  3主3从      │ │              │ │              │
         │  Lua 出价引擎│ │  出价落库    │ │  事件通知    │
         └──────────────┘ └──────────────┘ └──────────────┘
```

### 三、技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 长连接 | Netty + WebSocket | Reactor 模型 10 万连接/节点 |
| 序列化 | Protobuf + Delta Encoding | 极致压缩，节省 80% 带宽 |
| 出价引擎 | Redis Cluster + Lua | 原子操作保证强一致性 |
| 消息通知 | RocketMQ 广播 | 解耦出价和通知，精准路由 |
| 注册中心 | ZooKeeper | 维护"车辆-服务器"映射 |
| 数据库 | MySQL MGR | 多主写入，自动故障切换 |

### 四、核心流程设计

```
出价流程：
1. 车商通过 WebSocket 发送出价请求
2. Netty 网关 → IP 限流 → 路由到出价服务
3. 出价服务 → 本地缓存快速校验（拦截无效出价）
4. Redis Lua 原子出价：
   a. 校验余额 >= 出价金额
   b. 比较出价 > 当前最高价
   c. 更新 ZSet 排行榜
   d. 扣减余额
5. 发送 RocketMQ 事件（异步落库 + 通知推送）
6. Netty 网关精准推送给关注该车辆的车商
```

### 五、关键难点与解决方案

**难点 1：出价排序的公平性**
- ZSet 的 score = 价格 + 时间戳编码
- 同价格时，时间戳取反（先出价 score 更高）
- 额外维护 FIFO 队列处理极端并发（同一纳秒多出价）

**难点 2：Redis 热点 Key**
- 热门拍卖品的出价榜是热点 Key
- 本地缓存 + Redis 二层架构
- 低于当前最高价的出价在本地直接拦截

**难点 3：灾备和恢复**
- AOF + RDB 双持久化
- 出价事件异步写入 MQ，MySQL 落库
- Redis 故障时，从 MQ 事件可以完整恢复状态

### 六、容量评估

```
峰值 QPS：10 万（出价 + 查询）
单机指标：
  - Netty 网关：5 万 QPS/节点 → 4 节点（含冗余）
  - 出价服务：1 万 QPS/节点 → 16 节点（含冗余）
  - Redis Cluster：10 万 OPS/节点 → 6 主 6 从
网络带宽：
  - 单连接：~1KB/s（心跳 + 推送）
  - 10 万连接：100MB/s → 至少千兆网卡
```

## 题二：设计一个短 URL 系统

**面试官考察点**：高并发读取 + 分布式 ID 生成 + 缓存策略的综合设计。

### 一、需求分析

- 支持 10 万级 QPS 短链重定向
- 亿级短链存储
- 短链唯一性保证
- 低延迟重定向（< 8ms）

### 二、架构设计

```
                    ┌──────────┐
    用户请求 ──────→│  Nginx   │
                    └────┬─────┘
                         │
              ┌──────────▼──────────┐
              │    短链服务集群       │
              │  (SpringBoot 无状态) │
              └──┬──────────┬───────┘
                 │          │
    ┌────────────▼──┐  ┌───▼──────────────┐
    │ L1: Caffeine  │  │ L2: Redis Cluster│
    │ (本地缓存)     │  │ (热点短链缓存)    │← BloomFilter 防穿透
    └───────────────┘  └───┬──────────────┘
                           │ 未命中
                    ┌──────▼──────┐
                    │   MySQL     │
                    │ 分库分表    │
                    └─────────────┘
```

### 三、短链生成方案

**方案对比**：

| 方案 | 优点 | 缺点 | 选择 |
|------|------|------|------|
| 哈希算法(MD5/SHA1) | 简单 | 碰撞风险 | × |
| 自增 ID + Base62 | 全局唯一 | 单点/暴露ID量 | × |
| 雪花算法 + Base62 | 趋势递增、高性能 | 时钟回拨 | **√ 采用** |

**Base62 编码**（10进制 → 62进制）：
```
字符集：0-9 + a-z + A-Z = 62 个字符
ID 123456789 → Base62 → "8m0Kx"
```

**预生成池优化**：
```
本地预生成池：批量生成 10000 个 ID 放入内存队列
使用率 > 70% → 异步预加载下一批
生成性能提升 3.7 倍
```

### 四、双层缓存架构

```
读取流程：
1. L1: Caffeine 本地缓存（10 万条，LRU）
2. L2: Redis Cluster（热点数据）
3. BloomFilter 判断：Key 不存在则直接返回 404
4. MySQL 查询 + 回写 Redis + 回写 Caffeine
```

### 五、容量评估

```
日生成：1000 万短链
总存储：1000 万 × 365 天 × 3 年 ≈ 110 亿条
QPS：10 万（90% 命中缓存）

Redis 存储：110 亿 × 512byte ≈ 5.6TB（保留 1 年热数据）
MySQL 存储：110 亿 × 200byte ≈ 2.2TB（全量分库分表）
```

## 题三：设计一个秒杀系统

**面试官考察点**：超大规模瞬时并发 + 库存扣减 + 削峰的整体方案。

### 一、需求分析

- 秒杀商品：库存有限（如 100 件），瞬时并发极高（10 万+ QPS）
- 不允许超卖
- 不允许少卖（库存必须卖出）
- 防黄牛：限购 1 件/人

### 二、架构设计

```
         ┌──────────┐
用户 ──→ │   CDN    │ ← 静态化秒杀页面（倒计时 JS）
         └────┬─────┘
              │
    ┌─────────▼─────────┐
    │  Nginx 多级限流    │ ← 第一级：IP 限流 + 验证码
    └─────────┬─────────┘
              │
    ┌─────────▼─────────┐
    │  秒杀网关          │ ← 第二级：令牌桶限流
    │  (动态 URL 防刷)   │
    └─────────┬─────────┘
              │
    ┌─────────▼─────────┐
    │  秒杀服务          │ ← 第三级：Redis Lua 扣库存
    │  Redis Lua 原子   │     只有成功者才进入下单流程
    └────┬─────────┬────┘
         │         │
    ┌────▼───┐ ┌──▼─────────┐
    │  Redis │ │ RocketMQ   │ ← 异步下单削峰
    │ 库存缓存│ │ 异步下单   │
    └────────┘ └──┬─────────┘
                  │
            ┌─────▼──────┐
            │  订单服务   │ ← 队列消费写入 DB
            │  MySQL     │
            └────────────┘
```

### 三、核心流程

**多级削峰漏斗**：
```
10 万 QPS → Nginx 限流(50%) → 5 万 QPS
5 万 QPS → 网关限流(50%) → 2.5 万 QPS
2.5 万 QPS → Redis Lua 扣库存 → 100 成功
100 成功 → MQ 异步下单 → DB 落库
```

**Redis Lua 扣库存**：
```lua
local stock = redis.call('GET', KEYS[1])
if not stock or tonumber(stock) <= 0 then
    return -1  -- 已售罄
end
redis.call('DECR', KEYS[1])
return 1  -- 秒杀成功
```

**防黄牛**：
```lua
-- 限购 1 件/人：使用 Set 判断是否已购买
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return -2  -- 已购买过
end
redis.call('SADD', KEYS[2], ARGV[1])
```

### 四、关键难点

| 难点 | 解决方案 |
|------|---------|
| 超卖 | Redis Lua 原子扣减 + 数据库唯一键(用户+商品) |
| 少卖 | 如果有退单，库存回补 + 通知排队用户 |
| 黄牛 | 限购 1 件 + 动态 URL + 验证码 |
| 削峰 | 三级限流漏斗 + MQ 异步下单 |
| 热点 Key | Redis 库存 Key 单实例 + 本地缓存兜底 |

## 题四：设计一个分布式 ID 生成器

**面试官考察点**：分布式系统的全局唯一 ID 设计。

### 一、需求分析

- 全局唯一、趋势递增（B+Tree 友好）
- 高性能（> 10000 ID/秒/节点）
- 高可用（99.99%）

### 二、方案选型

| 方案 | 原理 | 问题 |
|------|------|------|
| UUID | 随机生成 | 无序、空间大 |
| DB 自增 | 单表 auto_increment | 单点 |
| 号段模式 | 批量分配号段 | 号段用尽时阻塞 |
| 雪花算法 | 时间戳+机器ID+序列号 | 时钟回拨 |

### 三、优化版雪花算法设计

```
0 | 41bit: 时间戳(ms) | 5bit: 机房ID | 5bit: 机器ID | 12bit: 序列号
│                      │              │              │
│                      │              │              └─ 4096/ms
│                      │              └─ 32 台机器
│                      └─ 32 个机房
└─ 符号位

时钟回拨处理：
  < 50ms → 等待（2倍回拨时间）
  > 50ms → 切换备用机器 ID
  > 5s → 抛异常 + 告警
```

### 四、号段模式（美团 Leaf）

```
┌─────────────┐     ┌─────────────┐
│ 号段服务     │────→│   MySQL     │ ← 持久化号段分配
│             │     │             │
│ 双 Buffer   │     └─────────────┘
│ Buffer1:    │
│ [1001,2000] │← 当前使用
│ Buffer2:    │
│ [2001,3000] │← 异步预加载
└─────────────┘

当前 Buffer 使用 90% → 异步加载下一号段 → 无阻塞切换
```

## 附录：系统设计面试框架

### 通用回答模板

```
1. 需求澄清（2 分钟）
   - 功能需求有哪些？
   - 非功能需求：QPS/延迟/可用性/一致性？
   - 数据量级？

2. 高层设计（5 分钟）
   - 画出架构图（分层 + 组件）
   - 说明各层职责

3. 技术选型（3 分钟）
   - 关键组件选择 + 理由
   - 每个选择的 trade-off

4. 核心流程（3 分钟）
   - 主流程时序图
   - 异常流程处理

5. 关键难点（3 分钟）
   - 识别 2-3 个核心难点
   - 每个难点的解决方案
   - 踩过的坑 / 可能会遇到什么坑

6. 容量评估（2 分钟）
   - 算清楚：需要多少机器、多少存储、多少带宽
   - 留有冗余
```

### 面试官必追问的 5 个方向

```
1. "你这个方案最大的风险点是什么？" → 展示你对方案局限性的认知
2. "如果某个组件挂了会怎样？" → 展示你的高可用思考
3. "为什么选择 A 而不是 B？" → 展示你的技术选型能力
4. "如果数据量增加 10 倍/100 倍怎么办？" → 展示你的扩展性思考
5. "上线后第一个月你最担心什么？" → 展示你的运维思维
```
