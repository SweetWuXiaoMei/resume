## 1. Spring Boot 自动配置原理？如何自定义 Starter？

**面试官考察点**：对 Spring Boot 核心机制的理解。

**参考答案**：

**自动配置原理**：
```
@SpringBootApplication
  ├── @EnableAutoConfiguration
  │     └── @Import(AutoConfigurationImportSelector.class)
  │           └── 扫描 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
  │                 └── 加载所有自动配置类
  └── @ComponentScan  → 扫描当前包及子包
```

**自动配置类示例**（`@ConditionalOnXxx` 控制生效条件）：
```java
@AutoConfiguration
@ConditionalOnClass({RedisConnectionFactory.class})
@ConditionalOnProperty(name = "spring.redis.enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(RedisProperties.class)
public class RedisAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean
    public RedisTemplate<String, Object> redisTemplate(RedisConnectionFactory factory) {
        // ...
    }
}
```

**自定义 Starter 步骤**：
```
1. 创建 autoconfigure 模块
   ├── 定义 XxxProperties（@ConfigurationProperties）
   ├── 定义 XxxAutoConfiguration（@AutoConfiguration）
   └── 创建 spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

2. 创建 starter 模块（POM 依赖 autoconfigure）

3. 其他项目引入 starter 即可自动生效
```

**关键要点**：
- `@ConditionalOnMissingBean` 让用户可以用自定义 Bean 覆盖默认实现
- `spring.factories`（Spring Boot 2.x）→ `AutoConfiguration.imports`（Spring Boot 3.x）

## 2. Spring Cloud Gateway vs Zuul vs Nginx 网关对比？

**面试官考察点**：网关选型能力。

**参考答案**：

| 维度 | Spring Cloud Gateway | Netflix Zuul | Nginx/OpenResty |
|------|---------------------|-------------|-----------------|
| 架构 | 异步非阻塞（WebFlux） | Zuul 1.x 同步阻塞 | 异步事件驱动 |
| 性能 | 高（Reactor Netty） | 低（Servlet） | 极高（C 语言） |
| 功能 | 路由、限流、熔断、灰度 | 路由、过滤器 | 反向代理、限流、负载均衡 |
| 扩展性 | Java 代码扩展 | Java 代码扩展 | Lua 脚本（OpenResty） |
| 适用 | 微服务内部网关 | 旧项目 | 入口网关、静态资源 |

**竞拍系统的双层网关架构**：
```
                    互联网
                      │
              ┌───────▼───────┐
              │  Nginx (入口)  │  ← 限流、SSL 终结、静态资源
              └───────┬───────┘
                      │
              ┌───────▼───────────┐
              │  SCG (微服务网关)  │  ← 路由、鉴权、灰度、日志
              └───────┬───────────┘
                      │
              ┌───────▼───────┐
              │  业务微服务     │
              └───────────────┘
```

**SCG 核心配置**：
```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: bid-service
          uri: lb://bid-service
          predicates:
            - Path=/api/bid/**
          filters:
            - StripPrefix=1
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 10000
                redis-rate-limiter.burstCapacity: 20000
            - name: CircuitBreaker
              args:
                name: bidCircuitBreaker
                fallbackUri: forward:/fallback/bid
```

**关键要点**：
- SCG 基于 WebFlux，不要加入阻塞操作（如 JDBC 调用）
- 网关层不适合做复杂业务逻辑，只做横切关注点

## 3. 注册中心选型：Nacos vs Eureka vs ZooKeeper vs Consul？

**面试官考察点**：注册中心的深入理解和选型。

**参考答案**：

| 维度 | Nacos | Eureka | ZooKeeper | Consul |
|------|-------|--------|-----------|--------|
| CAP 模型 | AP/CP 可切换 | AP | CP | CP |
| 健康检查 | TCP/HTTP/MySQL | HTTP | TCP | TCP/HTTP |
| 配置中心 | 内置 | 无 | 无 | 内置 |
| 一致性协议 | 自研 Distro(AP) + Raft(CP) | Peer to Peer | ZAB | Raft |
| 雪崩保护 | 有 | 有 | 无 | 有 |
| 多数据中心 | 支持 | 支持 | 不支持 | 支持 |

**Nacos AP vs CP 模式**：
```
AP 模式（默认，注册中心场景）：
- 优先级：可用性 > 一致性
- 临时节点：服务下线自动删除

CP 模式（配置中心场景）：
- 优先级：一致性 > 可用性
- 持久节点：配置数据需要强一致
```

**关键要点**：
- Eureka 2.0 已停止维护，不要在新项目选 Eureka
- CAP 可切换是 Nacos 区别于其他注册中心的核心竞争力

## 4. Dubbo vs Spring Cloud 如何选型？混合架构怎么设计？

### 实战案例：Spring Cloud + Dubbo 混合架构

**面试官考察点**：微服务通信协议的选型能力。

**参考答案**：

| 维度 | Dubbo | Spring Cloud (Feign/HTTP) |
|------|-------|--------------------------|
| 协议 | TCP 二进制（性能高） | HTTP/JSON（可读性好） |
| 序列化 | Hessian2/Protobuf | JSON |
| 注册中心 | ZK/Nacos/Redis | Eureka/Nacos/Consul |
| 服务治理 | 负载均衡、容错、路由 | 负载均衡、熔断（Sentinel） |
| 生态 | Java Only | 跨语言友好 |
| 性能 | 高（TCP 长连接） | 中（HTTP 短连接） |

**混合架构设计（竞拍系统实际方案）**：
```
┌─────────────────────────────────────────────┐
│                 Nacos 注册中心               │
└────┬──────────────────────┬─────────────────┘
     │                      │
     ▼                      ▼
┌─────────────┐     ┌──────────────────┐
│ 内部服务调用  │     │  外部 API 调用     │
│   Dubbo     │     │   Feign/HTTP      │
│ (高性能场景) │     │ (跨语言/调试友好)   │
└──────┬──────┘     └────────┬─────────┘
       │                     │
       ▼                     ▼
  竞拍引擎/推送服务      对外接口/管理后台
（低延迟要求）          （可读性要求）
```

**为什么混合**：
- 竞拍出价核心链路：用 Dubbo RPC，TCP 长连接 + Protobuf，延迟更低
- 对外 API 和管理后台：用 Feign HTTP，方便调试和跨语言对接
- 两者共用 Nacos 注册中心，统一服务发现

## 5. 配置中心如何实现灰度发布？

**面试官考察点**：配置中心的进阶用法。

**参考答案**：

**Nacos 配置灰度模型**：
```
应用：bid-service
├── 公共配置（所有实例生效）
├── 灰度配置（特定 IP/Gra ID 生效）
└── 优先级：灰度配置 > 公共配置
```

**Apollo 配置模型**：
```
应用：bid-service
├── 公共 Namespace
├── 私有 Namespace
└── 灰度配置：按 IP/标签/版本号
```

**灰度配置实践**：
```java
// 灰度开关
@Value("${feature.fast-bid:false}")
private boolean fastBidEnabled;

public BidResult placeBid(BidRequest request) {
    if (fastBidEnabled) {
        return fastBidStrategy.execute(request);  // 新逻辑
    }
    return normalBidStrategy.execute(request);     // 旧逻辑
}

// 配合 Nacos 动态刷新
@RefreshScope
@RestController
public class BidController {
    @Value("${bid.limit.qps:10000}")
    private int qpsLimit;  // 无需重启即可调整限流阈值
}
```

**灰度发布流程**：
```
1. 先在 1-2 台机器开启灰度配置
2. 观察监控指标（RT/错误率/成功率）
3. 逐步扩大灰度范围：1% → 10% → 50% → 100%
4. 确认无问题后设为公共配置
5. 清理灰度配置
```

## 6. 微服务优雅上下线怎么做？

**面试官考察点**：微服务运维经验。

**参考答案**：

**优雅下线**：
```java
// 1. K8s PreStop Hook
# deployment.yaml
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 15"]  # 等待流量切换

// 2. Spring Boot 优雅关闭
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s

// 3. 摘除注册中心
@PreDestroy
public void destroy() {
    // 先从 Nacos 摘除自己（新请求不会路由到本机）
    nacosRegistry.deregister();
    
    // 等待已进入的请求处理完（优雅关闭 + 超时）
    Thread.sleep(10000);
}
```

**优雅上线**：
```java
// 1. 服务启动后延迟注册（等依赖初始化完成）
@Component
public class StartupListener implements ApplicationListener<ApplicationReadyEvent> {
    @Override
    public void onApplicationEvent(ApplicationReadyEvent event) {
        // ApplicationReadyEvent 在所有 Bean 初始化完成后触发
        // 此时注册到 Nacos 是安全的
        log.info("服务启动完成，开始接受流量");
    }
}

// 2. K8s Readiness Probe
# deployment.yaml
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
```

**关键要点**：
- 下线顺序：摘除注册中心 → 等待处理中的请求 → 关闭
- 上线顺序：启动 → 等待依赖就绪 → 注册 → 接受流量

## 7. 分布式链路追踪怎么实现？

**面试官考察点**：可观测性体系的建设经验。

**参考答案**：

**核心原理**：
```
请求链路：
Client → Service A → Service B → Service C
         TraceId: abc123 (全局唯一，贯穿所有服务)
         SpanId: 1 (Service A)
                   SpanId: 1.1 (调用 Service B)
                            SpanId: 1.1.1 (调用 Service C)
```

**SkyWalking 架构**：
```
业务服务 (Java Agent 探针，无侵入)
    ↓ 上报 Trace/Metrics
SkyWalking OAP Server
    ↓ 存储
    ├── ElasticSearch (Trace 数据)
    └── Prometheus (Metrics 数据)
    ↓ 展示
SkyWalking UI / Grafana
```

**关联日志**：
```log
# 每个服务都输出 TraceId，通过 ELK 串联整个调用链
2024-01-15 10:30:00 [traceId=abc123] [spanId=1.1] INFO BidService.placeBid - 出价成功
```

**关键要点**：
- 链路追踪必须有统一规范：所有服务输出 TraceId
- SkyWalking Agent 对代码零侵入，比 Spring Cloud Sleuth 更推荐

## 8. 50+ 微服务如何治理？

### 实战案例：微服务标准化治理

**面试官考察点**：大规模微服务治理的全局能力。

**参考答案**：

**治理体系框架**：

```
一、开发规范
├── 服务命名规范：{业务域}-{功能模块}-service
├── 接口规范：RESTful URL 设计、统一返回结构
├── 版本管理：API 版本号（v1/v2），向后兼容
└── 日志规范：TraceId、业务标识、脱敏

二、服务生命周期
├── 脚手架：统一 Archetype/Starter
├── CI/CD Pipeline：代码提交 → 构建 → 单测 → 镜像 → 部署
├── 上线审批：灰度 → 预发 → 生产
└── 下线流程：双写过渡 → 流量切走 → 观察 → 销毁

三、运行时治理
├── 注册中心：Nacos 集群
├── 配置中心：Nacos Config（开发/测试/生产环境隔离）
├── 网关：SCG + Nginx 双层
├── 限流熔断：Sentinel（控制台统一管理规则）
└── 链路追踪：SkyWalking（全链路可观测）

四、数据管理
├── 数据库拆分：一个服务一个数据库
├── 接口调用：避免直接访问其他服务数据库
├── 数据一致性：MQ 异步 + 最终一致
└── 分布式事务：Seata（仅关键场景）
```

**服务依赖管理**：
```
定期梳理服务依赖关系：
- 画出服务拓扑图（SkyWalking 自动生成）
- 识别循环依赖（绝对禁止）
- 识别强依赖/弱依赖（用于降级策略）
- 评估每个服务的调用量/SLA
```

## 附录：微服务面试速查表

### Spring Cloud 技术栈选型

```
注册中心：Nacos（一站式，注册+配置）
网关：Spring Cloud Gateway（异步非阻塞）
远程调用：OpenFeign + Dubbo（混合）
负载均衡：Spring Cloud LoadBalancer
熔断限流：Sentinel（比 Hystrix 更灵活）
配置中心：Nacos Config
链路追踪：SkyWalking（无侵入）
分布式事务：Seata
```

### 微服务拆分原则

```
1. 单一职责：一个服务只做一件事
2. 高内聚低耦合：相关功能放一起，不相关拆开
3. 数据独立：每个服务有自己的数据库
4. 团队对齐：服务边界对应团队边界
5. 演进式拆分：先单体 → 粗粒度服务 → 细粒度服务
```
