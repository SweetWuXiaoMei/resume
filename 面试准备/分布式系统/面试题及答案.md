# 分布式系统面试题及答案

> 本套面试题针对架构师岗位，结合竞拍系统、短URL系统、支付系统的实战场景，覆盖 CAP 理论、分布式事务、分布式锁、限流熔断等核心领域。

## 1. CAP 理论是什么？实际项目中如何取舍？

**面试官考察点**：是否真正理解 CAP 的工程含义，而非背诵定义。

**参考答案**：

**CAP 定义**：
- **C（Consistency）**：所有节点在同一时刻看到的数据一致
- **A（Availability）**：每个请求都能获得非错误的响应（不保证数据最新）
- **P（Partition Tolerance）**：系统在出现网络分区时仍能正常运作

**核心认知**：CAP 不能同时满足。P 在分布式系统中不可避免（网络不可靠），所以实际是 **CP vs AP** 的选择。

**实际取舍**：

| 场景 | 选择 | 案例 | 为什么 |
|------|------|------|--------|
| 支付扣款 | CP | 银行转账 | 宁可不可用也不能少钱 |
| 竞拍出价 | CP | 最高价必须一致 | 出价排序错乱 → 纠纷 |
| 商品库存显示 | AP | 电商库存数 | 显示 10 件实际 9 件，比不显示好 |
| 社交点赞数 | AP | 微博点赞 | 用户不关心里程碑式的精确值 |

**工程上如何应对 CAP**：
- 不是"要么 CP 要么 AP"，而是**不同模块不同策略**
- 例如 Nacos：注册中心优先 AP（不能因为一致性丢失服务），配置中心优先 CP（配置错了影响大）
- 最终一致性 = AP + 可收敛的时间窗口

**关键要点**：
- "我们选择了 AP，但对一致性做了补偿"是架构师的标准回答
- 不要把 BASE 理论省了——Basically Available, Soft state, Eventually consistent

## 2. 分布式事务的几种方案对比？你在项目中的选型逻辑？

**面试官考察点**：分布式事务的完整知识体系和选型能力。

**参考答案**：

| 方案 | 原理 | 一致性 | 性能 | 侵入性 | 适用场景 |
|------|------|--------|------|--------|---------|
| **2PC（XA）** | 协调者 + 两阶段提交 | 强一致 | 差 | 低 | 传统金融数据库 |
| **TCC** | Try-Confirm-Cancel | 最终一致 | 好 | 高 | 资金扣减 |
| **Saga** | 正向操作 + 补偿操作链 | 最终一致 | 好 | 高 | 长事务流程 |
| **本地消息表** | 业务 + 消息表本地事务 | 最终一致 | 中 | 中 | 异步解耦场景 |
| **事务消息（RocketMQ）** | 半消息 + 本地事务 + 回查 | 最终一致 | 中 | 中 | MQ 异步场景 |
| **Seata AT** | 自动生成回滚 SQL（Undo Log） | 最终一致 | 中 | 低 | 通用场景 |

**选型决策树**：
```
是否需要强一致性？
├── 是 → 2PC/XA（但接受性能代价）
└── 否 → 业务是否允许一定延迟？
    ├── 是 → 异步场景？
    │   ├── 是 → MQ 事务消息 / 本地消息表
    │   └── 否 → TCC / Saga / Seata AT
    └── 否 → 重新审视需求，是否真的需要分布式事务
```

**实战案例**：竞拍系统出价 + 冻结资金

```
// 场景：出价成功后需要扣减保证金
// 方案：MQ 事务消息（RocketMQ）

// 1. 发送半消息（对 Consumer 不可见）
// 2. 执行本地事务：扣减保证金
// 3. 根据本地事务结果：Commit 或 Rollback 半消息
// 4. RocketMQ 回查机制兜底
// 结果：保证金扣减和出价记录落库最终一致
```

**关键要点**：
- 一定要说"能不用分布式事务就不用"——这是架构师的成熟
- 多讲"用补偿代替回滚"的思路

## 3. 分布式锁的三种实现方式对比？Redlock 有什么争议？

**面试官考察点**：分布式锁方案的深入理解，是否关注过 Redlock 争议。

**参考答案**：

| 方案 | 实现 | 优点 | 缺点 |
|------|------|------|------|
| **Redis** | `SET NX PX` + Lua 释放 | 高性能 | 不可靠（主从切换可能丢锁） |
| **ZooKeeper** | 临时顺序节点 + Watch | 可靠（CP 系统） | 性能较低 |
| **etcd** | Lease + Txn | 可靠 + Watch | 性能中等 |

**Redis 单节点分布式锁的问题**：
```
1. Client A 获取锁 → Master
2. Master 挂了，锁还未同步到 Slave
3. Slave 提升为新 Master
4. Client B 可以获取"同一个锁" → 两个客户端同时持有锁
```

**Redlock 算法（Redis 作者 antirez 提出）**：
```
1. 获取当前时间
2. 依次向 N 个独立的 Redis Master 请求锁（SET NX PX）
3. 如果获得了 N/2+1 个锁，且总耗时 < 锁过期时间，则获取成功
4. 否则释放所有锁
```

**Martin Kleppmann 的质疑**：
- Redlock 假设了网络延迟和程序暂停有明确边界，但实际没有
- GC 导致的 "Stop-the-world" 可能让锁超时后客户端仍以为持有锁
- **核心论点**：Redlock 试图用基于时间的租约来保证正确性，但分布式系统中时钟不可靠

**Fencing Token 方案（Martin 推荐）**：
```
1. 锁服务每次返回一个递增的 Token
2. 共享资源（如数据库）拒绝比上次更小的 Token
3. 这样即使客户端 GC 后恢复，它的 Token 已经过期，操作会被拒绝
```

**实战选择**：
- 竞拍出价：不需要分布式锁，Redis Lua 原子操作即可
- 支付防重：基于数据库唯一键 + 状态机，比分布式锁更可靠
- 定时任务：Redisson 看门狗机制 + Redis 简单锁够用

**关键要点**：
- "不是所有并发问题都需要分布式锁"这句话会加分
- 能讨论 Redlock 争议说明你关注社区前沿

## 4. Redis 脑裂是什么？如何解决？

**面试官考察点**：是否经历过 Redis 集群故障。

**参考答案**：

**脑裂现象**：
```
Sentinel 集群因为网络分区分裂：
Sentinel A/B 认为 Master M 挂了 → 选出 Slave S1 为新 Master
Sentinel C/D 认为 Master M 正常
结果：两个 Master 同时接收写入 → 数据不一致
```

**排查方法**：
```bash
# 1. 查看集群状态
redis-cli -p 6379 -a xxx CLUSTER INFO
redis-cli -p 6379 -a xxx CLUSTER NODES

# 2. 查看是否出现脑裂（两个节点同时声称是 Master）
redis-cli -p 26379 -a xxx SENTINEL MASTERS

# 3. 检查网络
ping -c 100 <ip>
```

**解决方案**：
```bash
# 1. min-slaves-to-write：主库至少要有 N 个从库连接才接受写入
CONFIG SET min-replicas-to-write 1
CONFIG SET min-replicas-max-lag 10

# 2. Sentinel 配置优化
sentinel monitor mymaster 127.0.0.1 6379 2  # quorum=2，至少 2 个 Sentinel 同意
sentinel down-after-milliseconds mymaster 5000  # 适当调大，避免误判
sentinel failover-timeout mymaster 60000  # 故障转移超时
```

**关键要点**：
- quorum 和 majority 是两个概念——quorum 是"发现故障"的人数，majority 是"执行故障转移"的人数
- 脑裂恢复后，旧 Master 的数据会丢失（以新 Master 为准）

## 5. 限流算法有哪些？你在项目中如何实现？

**面试官考察点**：限流方案的完整设计和选型。

**参考答案**：

| 算法 | 原理 | 优点 | 缺点 | 适用 |
|------|------|------|------|------|
| **固定窗口** | 窗口内计数，超过阈值拒绝 | 简单 | 临界突刺 | 粗粒度 |
| **滑动窗口** | 窗口平滑移动 | 平滑 | 内存占用较高 | 较精确 |
| **漏桶** | 固定速率流出，队列缓存 | 平滑输出 | 不能应对突发 | 保护下游 |
| **令牌桶** | 固定速率放令牌，有令牌才能请求 | 允许突发 | 实现稍复杂 | 一般场景首选 |

**实战案例：竞拍系统多级限流**

```
第一级：Nginx 层
limit_req_zone $binary_remote_addr zone=bid:10m rate=100r/s;

第二级：Netty 网关层
// 基于 IP 的滑动窗口限流
ipRateLimiter.tryAcquire(ip, 100, TimeUnit.SECONDS)  // 每秒 100 次

第三级：Redis 层
// 基于 Lua 的分布式限流
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
if current > tonumber(ARGV[2]) then
    return 0  -- 限流
end
return 1  -- 放行
```

**Sentinel 实现限流熔断**：
```java
// 基于 QPS 的限流
FlowRule rule = new FlowRule();
rule.setResource("placeBid");
rule.setGrade(RuleConstant.FLOW_GRADE_QPS);
rule.setCount(10000);  // 单机限流 1 万 QPS
FlowRuleManager.loadRules(Collections.singletonList(rule));

// 基于 RT 的熔断
DegradeRule degradeRule = new DegradeRule();
degradeRule.setResource("placeBid");
degradeRule.setGrade(RuleConstant.DEGRADE_GRADE_RT);
degradeRule.setCount(100);  // RT 超过 100ms
degradeRule.setTimeWindow(10);  // 熔断 10s
```

**关键要点**：
- 多层限流 > 单层限流
- 限流要能动态调整（Apollo 配置中心下发）
- 令牌桶允许突发是优势不是劣势——正常业务就是有波峰波谷

## 6. 分布式 ID 生成方案对比？雪花算法有什么坑？

**面试官考察点**：分布式 ID 方案的深入理解。

**参考答案**：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **UUID** | 随机生成 | 无中心，性能好 | 无序（B+Tree 写入性能差）、占空间 |
| **数据库自增** | 单库自增 | 简单 | 单点瓶颈 |
| **号段模式** | 批量取号段，内存发放 | 高性能 | 需要数据库 |
| **雪花算法** | 时间戳+机器ID+序列号 | 趋势递增、高性能 | 时钟回拨问题 |
| **美团 Leaf** | 号段 + 雪花双模式 | 企业级 | 依赖 ZooKeeper |

**雪花算法标准结构（64bit）**：
```
1bit(保留) | 41bit(毫秒时间戳) | 10bit(机器ID) | 12bit(序列号)
  0         可存69年              1024台机器      4096/ms
```

**雪花算法的时钟回拨问题与解决**：
```java
public synchronized long nextId() {
    long current = System.currentTimeMillis();
    
    // 时钟回拨检测
    if (current < lastTimestamp) {
        long offset = lastTimestamp - current;
        if (offset <= 5) {
            // 回拨小于 5ms：等待
            Thread.sleep(offset << 1);
            current = System.currentTimeMillis();
        } else {
            // 回拨大于 5ms：使用备用机器 ID 或抛异常
            workerId = backupWorkerId;
        }
    }
    
    // ... 正常生成逻辑
}
```

**号段模式（双 Buffer 优化）**：
```
当前 Buffer 用完 90% → 另启线程加载下一个号段
等当前 Buffer 用完时 → 直接切换到新号段，无等待
```

## 7. 如何设计一个高可用的分布式系统？（30+ 节点集群管理经验）

### 实战案例：竞拍系统高可用设计

**面试官考察点**：完整的系统高可用设计能力。

**参考答案**：

**高可用设计原则**：

```
1. 故障预防（Prevent）：避免单点
   - 服务无状态：水平扩展
   - 数据有状态：主从/集群/分片
   
2. 故障发现（Detect）：快速感知
   - 健康检查：TCP/HTTP/自定义探针
   - 监控告警：Prometheus + Grafana + AlertManager
   
3. 故障恢复（Recover）：自动切换
   - 服务层：K8s 自动重启/驱逐
   - 数据层：主从自动切换
   - 流量层：熔断降级
   
4. 故障复盘（Postmortem）：持续改进
   - 故障记录、根因分析、改进措施
```

**竞拍系统高可用架构**：

```
┌──────────┐  ┌──────────┐  ┌──────────┐
│ Nginx LB │  │ Nginx LB │  │ Nginx LB │  ← Keepalived VIP
└────┬─────┘  └────┬─────┘  └────┬─────┘
     └──────────────┼──────────────┘
                    ▼
    ┌───────────────────────────────┐
    │    Netty 网关集群 (10 节点)    │  ← 无状态，可水平扩展
    └───────────────┬───────────────┘
                    ▼
    ┌───────────────────────────────┐
    │    业务服务集群 (20 节点)      │  ← Spring Cloud + Dubbo
    └───────┬───────┬───────┬───────┘
            ▼       ▼       ▼
      ┌────────┐┌──────┐┌──────────┐
      │ Redis  ││MySQL ││RocketMQ  │
      │Cluster ││MGR   ││DLedger   │
      └────────┘└──────┘└──────────┘
        3主3从    组复制    多副本
```

**各层高可用策略**：
| 层级 | 组件 | 高可用方案 | 故障切换时间 |
|------|------|-----------|-------------|
| 接入层 | Nginx | Keepalived VIP 漂移 | 1-3s |
| 网关层 | Netty | 无状态 + K8s 自动扩缩容 | 秒级 |
| 服务层 | Dubbo | 多副本 + 自动摘除 | 秒级 |
| 缓存 | Redis | Cluster 3主3从 | 秒级 |
| 数据库 | MySQL | MGR 组复制 | 10-30s |
| 消息 | RocketMQ | DLedger 多副本 | 秒级 |

## 8. 什么是缓存一致性？如何保证？

**面试官考察点**：缓存与数据库之间的一致性设计方案。

**参考答案**：

**缓存一致性问题的本质**：数据库更新了，缓存没更新（或反过来），导致读到脏数据。

**常见方案对比**：

| 方案 | 流程 | 一致性 | 缺点 |
|------|------|--------|------|
| **Cache Aside** | 先更新 DB，再删缓存 | 最终一致 | 存在短暂不一致窗口 |
| **Read/Write Through** | 缓存层代理 DB 读写 | 强一致 | 缓存层复杂度高 |
| **Write Behind** | 先写缓存，异步写 DB | 弱一致 | 缓存挂了丢数据 |
| **双删** | 删缓存 → 更新 DB → 延时再删 | 最终一致 | 第二次删除可能失败 |

**推荐的 Cache Aside + 双删 + 补偿**：

```java
public void updatePrice(Long auctionId, BigDecimal newPrice) {
    // 1. 删除缓存
    redis.delete("auction:" + auctionId);
    
    // 2. 更新数据库
    auctionDao.updatePrice(auctionId, newPrice);
    
    // 3. 延迟双删（兜底，异步）
    CompletableFuture.runAsync(() -> {
        Thread.sleep(200);  // 等待数据库主从同步
        redis.delete("auction:" + auctionId);
    });
}

// 4. Canal 监听 binlog，兜底删除
// Canal → RocketMQ → 消费者删除缓存
// 保证：即使第二步删除失败，最终 binlog 也能触发删除
```

**缓存不一致的容忍度**：
- 竞拍出价：不能容忍（出价金额不能错）→ 只缓存非关键信息
- 商品库存：可容忍短暂不一致（秒级）→ 过期时间兜底
- 短链跳转：几乎不需要更新 → Cache Aside 即可

**关键要点**：
- "不要过度设计"——不是所有数据都需要强一致性
- 删除缓存 > 更新缓存（避免并发写覆盖）

## 9. 如何排查线上分布式系统故障？请描述一次完整的排查经历。

**面试官考察点**：分布式系统故障排查的系统化能力。

**参考答案**：

**故障排查 SOP**：

```
1. 确认故障范围
   ├── 是单个服务还是全部服务？
   ├── 是单个节点还是全部节点？
   └── 是某个功能还是全部功能？

2. 快速止血（1分钟）
   ├── 重启？回滚？切流？
   └── 有预案的执行预案，没预案的降级

3. 定位根因（5分钟）
   ├── 监控面板：QPS/RT/错误率/CPU/Memory/GC
   ├── 日志平台：ERROR 日志、慢查询
   ├── 链路追踪：调用链中哪个环节慢/报错
   └── 变更记录：最近发布了什么？

4. 根治修复
   ├── 代码修复 + 回归测试
   ├── 配置热更新
   └── 灰度发布验证

5. 复盘总结
   ├── 故障原因
   ├── 影响范围
   ├── 发现时间 vs 恢复时间
   └── 改进措施（监控/预案/架构）
```

**关键工具链**：
| 工具 | 用途 |
|------|------|
| Prometheus + Grafana | 指标监控 |
| ELK | 日志聚合 |
| SkyWalking / Jaeger | 分布式链路追踪 |
| Arthas | 在线诊断 |
| Sentinel Dashboard | 限流熔断监控 |

## 10. 一致性哈希是什么？有哪些应用场景？

**面试官考察点**：分布式路由和数据分片的原理。

**参考答案**：

**原理**：将节点和数据都映射到同一个哈希环上。数据存储在顺时针方向遇到的第一个节点上。

**节点变更时**：只影响相邻节点之间的数据，其他数据不受影响。
```
新增节点：接收环上顺时针方向前一个节点的部分数据
删除节点：数据转移到顺时针方向的下一个节点
```

**虚拟节点**：解决数据倾斜问题。每个物理节点对应多个虚拟节点，均匀分布在环上。

**应用场景**：
- Redis Cluster：16384 个 Slot（本质上是一致性哈希的实现）
- Dubbo 负载均衡：ConsistentHashLoadBalance
- CDN 内容路由
- 分布式缓存扩容缩容

## 11. Raft 和 Paxos 的区别？

**面试官考察点**：对共识算法的了解程度。

**参考答案**：

| 维度 | Paxos | Raft |
|------|-------|------|
| 理解难度 | 极难 | 较易 |
| 工程实现 | 复杂 | 清晰 |
| 核心机制 | 两阶段提交 | 领导者选举 + 日志复制 |
| 代表性系统 | Chubby | etcd, Consul, TiKV |

**Raft 核心三要素**：
1. **Leader Election**：心跳检测 Leader 存活，超时触发选举
2. **Log Replication**：Leader 将日志复制到 Follower，多数派确认即提交
3. **Safety**：保证选举出的 Leader 拥有所有已提交的日志条目

**关键要点**：
- 日常开发不需要实现 Raft，但需要理解"多数派"的概念
- 面试如果被问，强调 Raft 相比 Paxos 的工程易用性即可

### 方案选择速查

```
并发扣库存  → Redis Lua 原子操作（不需要分布式锁）
并发扣余额  → 乐观锁（version 字段）或 TCC 分布式事务
防重提交    → 唯一键 + 状态机
分布式 ID   → 雪花算法（注意时钟回拨）
缓存一致性  → Cache Aside + 双删 + Canal 兜底
全局限流    → Redis Lua 滑动窗口
服务降级    → Sentinel 熔断降级
```

### 关键数字

```
30+ 节点集群 → ZooKeeper/Nacos 管理
10万+ QPS   → 多级缓存 + 限流 + 异步
99.99% 可用性 → 冗余 + 自动故障切换 + 监控
P99 < 50ms  → 本地缓存 + 异步化 + GC 调优
```
