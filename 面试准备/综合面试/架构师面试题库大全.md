## 一、Java 核心（并发 + JVM + 类加载）

| 序号 | 领域 | 题目 | 难度 | 考察目的 | 参考答案要点 |
|------|------|------|------|----------|-------------|
| 1 | Java并发 | AQS 的核心原理是什么？如何基于 AQS 实现一个自定义同步器？ | 高级 | 理解 JUC 底层基石，考察框架设计思维 | AQS 维护一个 volatile int state + CLH 双向队列。独占模式用 tryAcquire/tryRelease，共享模式用 tryAcquireShared/tryReleaseShared。ReentrantLock 的公平锁：先检查队列是否有等待者；非公平锁：先 CAS 抢一次。CountDownLatch 用共享模式，state=count，每次 countDown 减 1 并尝试唤醒。**深度追问**：AQS 的 Condition 队列和同步队列如何协作？signal() 把 Condition 队列的 head 移到同步队列尾部。 |
| 2 | Java并发 | synchronized 锁升级过程（偏向锁→轻量级锁→重量级锁）是怎样的？ | 高级 | 考察 JVM 底层锁机制的深入理解 | 偏向锁：Mark Word 记录线程 ID，同一个线程再次进入只需比对 ID。轻量级锁：CAS 将 Mark Word 指向栈帧中的 Lock Record，失败则自旋等待。重量级锁：自旋失败后膨胀，ObjectMonitor + 等待队列，涉及系统调用。**生产经验**：在低并发场景偏向锁有优势，高并发场景关闭偏向锁（`-XX:-UseBiasedLocking`）反而性能更好，因为偏向锁撤销有 STW 开销。竞拍系统关闭了偏向锁。 |
| 3 | Java并发 | ThreadLocal 内存泄漏的原因及解决方案？Netty 的 FastThreadLocal 做了什么优化？ | 高级 | 考察内存泄漏排查经验和框架理解 | 泄漏根因：ThreadLocalMap 的 Entry 是 WeakReference<ThreadLocal>，但 value 是强引用。ThreadLocal 被 GC 后 key 变 null，value 永远无法访问但不会被回收。解决：finally 中调用 remove()。FastThreadLocal 优化：用数组索引代替哈希表，O(1) 访问；不使用 WeakReference，配合 FastThreadLocalThread 使用；线程结束时自动清理。**实战案例**：竞拍系统中 Tomcat 线程池复用 + ThreadLocal 未清理，导致每个线程堆积了所有处理过的出价记录，最终 OOM。 |
| 4 | Java并发 | CAS 的 ABA 问题是什么？实际生产中你真的遇到过吗？ | 中级 | 考察 CAS 的边界理解 | ABA：线程 1 读到 A → 线程 2 改为 B 又改回 A → 线程 1 CAS 成功但不该成功。用 AtomicStampedReference 加版本号解决。**诚实回答**：大部分业务场景下 ABA 不是问题（比如计数自增），真正出问题的主要在无锁栈/队列等数据结构中。面试官喜欢听到"我不会过度设计"的态度。 |
| 5 | Java并发 | 一个线程的生命周期是怎样的？WAITING 和 BLOCKED 有什么区别？ | 中级 | 考察多线程调试和监控基础 | NEW → RUNNABLE → BLOCKED（等锁）/ WAITING（wait/join/park，需要其他线程唤醒）/ TIMED_WAITING → TERMINATED。WAITING vs BLOCKED：BLOCKED 是被动等 synchronized 锁，WAITING 是主动等待通知。jstack 中 BLOCKED 的线程状态是 "waiting for monitor entry"，WAITING 是 "in Object.wait()" 或 "parking"。 |
| 6 | JVM | CMS 和 G1 的详细对比？各自的适用场景和淘汰原因？ | 高级 | GC 选型能力和历史演进理解 | CMS：标记-清除，碎片化是致命伤。Concurrent Mode Failure 会退化为 Serial Old 单线程 Full GC，停顿秒级。JDK14 正式废弃。G1：Region 模型 + 标记-整理，停顿可控。RSet 维护跨 Region 引用，占约 5% 堆。Mixed GC 优先回收价值高的 Region。调优核心参数：MaxGCPauseMillis、IHOP。**追问题**：G1 和 ZGC 对比？ZGC 用染色指针 + 读屏障，停顿 < 1ms，适合 16G+ 堆；G1 更适合 4-16G 的中等堆。 |
| 7 | JVM | 一次 Full GC 的完整排查过程是怎样的？ | 高级 | 线上故障排查的完整方法论 | 第一步：确认现象（监控看到 GC 频繁 + STW 长）。第二步：拉 GC 日志分析（GCeasy/GCViewer，关注 Full GC 次数、触发原因、单次耗时）。第三步：`jstat -gcutil` 查看各区域使用率。第四步：如果是内存泄漏，`jmap` dump → MAT 分析 Dominator Tree → Path to GC Roots 找泄漏根因。第五步：修复 + 验证。**实战**：竞拍系统 G1 Full GC，根因是 Mixed GC 回收速度跟不上分配速度。方案：IHOP 从 45 降到 35，堆从 8G 扩到 12G，Full GC 消除。 |
| 8 | JVM | OOM 有哪些类型？分别怎么排查？ | 高级 | OOM 分型诊断能力 | ① Java heap space：MAT 分析 Dump → Dominator Tree 定位大对象 → Path to GC Roots。② Metaspace：jstat -gcutil MU 持续增长 → Arthas classloader 查看类加载器 → 可能是 CGLIB/Groovy 动态类未卸载。③ Direct buffer memory：jmap 看不到 → 查 NIO Buffer 使用情况 → 检查 -XX:MaxDirectMemorySize。④ unable to create new native thread：线程数超限 → 检查 -Xss 和 OS ulimit。⑤ GC overhead limit exceeded：GC 占 98% CPU 但回收 < 2% 堆 → 扩堆或查泄漏。 |
| 9 | JVM | 类加载的双亲委派模型及其被破坏的典型场景？ | 高级 | 类加载机制和实际问题经验 | 标准模型：Bootstrap → Extension → Application → Custom，自底向上检查，自顶向下加载。破坏场景：① SPI（JDBC 驱动）：ServiceLoader 使用线程上下文类加载器（TCCL），因为核心类在 Bootstrap，实现类在 Classpath。② Tomcat：WebAppClassLoader 优先加载自己的类，破坏委派实现隔离。③ OSGi：网状类加载。④ 热部署：需要绕过双亲委派。**GaussDB JDBC 关联**：JDBC 驱动的 DriverManager 注册就是通过 SPI + TCCL 实现的。 |
| 10 | JVM | JIT 编译中的逃逸分析是什么？对你的代码有什么实际影响？ | 高级 | JIT 优化机制的实战理解 | 逃逸分析判断对象作用域：不逃逸 → 栈上分配/标量替换/锁消除。影响：① 局部对象如果能被标量替换，堆分配变栈分配，减少 GC 压力。② 锁消除使 StringBuffer/StringBuilder 之争在单线程下无差别。**注意**：逃逸分析只是分析，JIT 不一定做优化。不要为了JIT优化写奇怪的代码，代码可读性优先。 |

| 17 | MySQL | InnoDB 的 MVCC 是如何实现的？RC 和 RR 级别的实现有什么区别？ | 高级 | 事务和 MVCC 的深度理解 | 三个隐藏列：DB_TRX_ID（最后修改的事务ID）、DB_ROLL_PTR（回滚指针指向 Undo Log）、DB_ROW_ID。ReadView 包含：m_ids（活跃事务列表）、min_trx_id、max_trx_id、creator_trx_id。可见性判断：trx_id < min → 可见；trx_id >= max → 不可见；在 min 和 max 之间 → 在 m_ids 中则不可见。RC vs RR：RC 每次快照读创建新 ReadView（可看到已提交的更新）；RR 第一次快照读创建 ReadView 后续复用（保证可重复读）。**注意**：RR 的快照读解决了不可重复读，但当前读（SELECT FOR UPDATE）仍可能幻读，需要 Next-Key Lock。 |
| 18 | MySQL | 一条 SQL 从 3s 优化到 50ms 的完整过程（以竞拍出价记录查询为例）？ | 高级 | 完整的 SQL 优化方法论 | 原始 SQL：SELECT bidder_id, amount, create_time, name FROM bid_record b JOIN user u ON b.bidder_id=u.id WHERE b.auction_id=? | 21 | MySQL | 分库分表方案设计：以竞拍系统为例，如何对出价记录表进行水平拆分？ | 高级 | 分库分表的完整设计能力 | 分片键选择：auction_id（出价记录查询总是带 auction_id）。分片算法：auction_id % 16 → 16 张表；库级：auction_id % 4 / 4 → 4 个库。中间件：ShardingSphere-JDBC（同城无中心化）vs ShardingSphere-Proxy（跨语言）。要解决的问题：① 全局唯一 ID → 雪花算法。② 跨分片分页 → 禁止深度分页，或用 ES。③ 扩容 → 一致性哈希或双倍扩容 + 数据迁移。④ 分布式事务 → 出价场景用 Redis Lua 保证原子性，DB 层用 MQ 异步落库，不需要强一致分布式事务。⑤ 数据迁移方案 → Canal binlog 同步 + 灰度切流。 |
| 22 | MySQL | 主从延迟的原因有哪些？如何监控和处理？ | 高级 | 高可用运维经验 | 原因：① 从库配置差/共享资源。② 从库承担大量读请求 CPU 竞争。③ 大事务（主库执行快，从库回放慢）。④ 从库单线程回放（5.6 前），5.7+ 开启并行复制。⑤ 网络延迟。监控：SHOW SLAVE STATUS → Seconds_Behind_Master。处理：① 并行复制（slave_parallel_workers=4）。② 半同步复制（主库等至少一个从库确认）。③ 一主多从 + 读写分离。④ 缓存前置（Redis 缓存热点数据，减少从库读压力）。⑤ 业务侧：主库强制读（关键操作读主库）。**竞拍系统**：出价结果查询读 Redis（不是 MySQL 从库），所以主从延迟不影响核心业务。 |

| 49 | 项目深挖 | 竞拍系统中，"车辆-服务器"路由注册中心的设计思路是什么？解决了什么问题？ | 高级 | 创新性架构设计能力 | **背景**：10 万+ 车商分布在 10 个 Netty 节点上。出价广播如果全量广播 → 每个节点遍历所有连接 → O(节点数×总连接数)。**方案**：基于 ZK 的动态映射。车商进入拍卖间 → 在 ZK 注册（auctionId → serverIp）。出价推送时：① 查 ZK 获取该车辆在哪些 Netty 节点有关注者 → ② 只发给这些节点 → ③ 节点查本地连接推送。**优势**：复杂度从 O(N²) 降到 O(N × 单一车辆关注者数)。**ZK 优势**：临时节点（Netty 宕机自动清除映射）+ Watch 机制（节点变更通知）。**创新性**：这个方案本质上是"用 ZK 做服务发现来实现精准路由"，避免了广播风暴和热点集中。 |
| 50 | 项目深挖 | 竞拍系统的 Delta Encoding 推送优化，具体怎么实现？节省了多少带宽？ | 高级 | 性能优化的量化思维 | **场景**：高频推送出价更新给 10 万+ 车商。每次都推完整数据：bidderId(8B)+amount(8B)+timestamp(8B) → 至少 24B。**Delta Encoding**：第一次推完整数据 → 后续只推差值（大部分差值在 ±255 以内 = 1B）。Protobuf 中新增 delta_amount 字段。Encoder 维护 lastAmount，计算 delta = current - last。Decoder 维护 lastAmount，累加 delta 得到当前价格。**效果**：90% 消息体从 ~50B → ~8B，带宽节省 80%。**风险**：① 丢包导致解码错乱 → 每 100 条消息发一次全量同步 + 客户端确认 ACK 机制。② 重连后状态丢失 → 恢复连接时先拉取全量快照。 |
| 51 | 项目深挖 | 竞拍系统中，如何保障出价的强一致性和公平性？ | 高级 | 分布式数据一致性的实战设计 | **强一致性**：Redis Lua 原子脚本完成 4 步操作（校验余额 → 比较出价 → 更新排行榜 → 扣减资金）。这 4 步必须原子执行，否则可能出现"出价排上了但余额没扣"或"余额扣了但出价没排上"。**公平性（FIFO）**：ZSet 的 score 编码 = 价格 * 10^13 + (9999999999999 - 时间戳纳秒)。同价格时时间戳取反 → 先出价的 score 更高 → 排前面。**边界处理**：纳秒级别并发（同一纳秒多个出价）→ 额外维护 FIFO 队列作为 ZSet 同 score 的 tiebreaker。**为什么不用数据库行锁**？竞拍 10 万 QPS，数据库行锁会严重瓶颈 → P99 > 3s → 不可接受。 |
| 52 | 项目深挖 | GaussDB JDBC 驱动的负载均衡和故障切换是怎么设计的？ | 高级 | JDBC 驱动层的高可用设计 | **负载均衡**：从协调节点（CN）获取集群拓扑信息（各数据节点 DN 的 IP/端口/权重）。Driver 内部维护"连接池 + 节点权重表"，每次获取连接时按加权轮询选择 DN。**故障切换**：① 连接失败 → 标记节点不可用 → 加入黑名单。② 异步心跳检测：每 10s 对黑名单节点做探测 → 恢复后移出黑名单。③ 切换过程对应用透明：重试另一个节点，不抛异常。④ 秒级切换。**读写分离**：parse SQL 判断读写类型 → SELECT 路由到只读副本，INSERT/UPDATE/DELETE 路由到主节点。允许 Hint 强制路由（`/*master*/` 或 `/*slave*/`）。**性能优化**：① 二进制协议编解码（比文本协议快 30%）。② ResultSet 流式读取（避免大数据量 OOM）。③ PreparedStatement 缓存（复用预编译语句）。 |
| 53 | 项目深挖 | 竞拍系统的灾备和容错设计是怎样的？如果 Redis 集群完全挂了怎么办？ | 高级 | 系统容灾和极端场景应对能力 | **Redis 高可用**：Cluster 3 主 3 从 + 自动故障转移（Sentinel/Gossip 检测 + 选举）。**Redis 完全故障**：① 出价事件全部写入 RocketMQ（事务消息）。② MySQL 中也有完整的出价记录（MQ 异步落库）。③ Redis 恢复后 → 从 MQ 回放事件重建排行榜状态 → 或从 MySQL 全量重建。④ 故障期间降级：提供"有损服务"——出价仍可提交（通过 MQ+DB），但排行榜查询可能不准确。**其他容错**：Netty 网关故障 → ZK 自动摘除 + 该节点上的车商重连到其他节点。业务服务故障 → Dubbo 自动 Failover。Sentinel 熔断降级 → 推送通知降级为轮询模式。**核心原则**：不完全依赖任何一个组件，每个组件都有兜底方案。 |
