## 1. B+Tree 为什么是 MySQL InnoDB 的默认索引结构？和 B-Tree、Hash、跳表的区别？

**面试官考察点**：对索引底层数据结构的理解，而非只是知道"B+Tree 好"。

**参考答案**：

| 维度 | B-Tree | B+Tree | Hash | 跳表（SkipList） |
|------|--------|--------|------|-----------------|
| 数据存储 | 所有节点都存数据 | 只有叶子节点存数据 | 桶+链表 | 多层链表 |
| 范围查询 | 需要中序遍历 | 叶子节点链表，天然支持 | 不支持 | 支持（O(logN)定位起点） |
| IO次数 | 较高 | 更低（非叶子节点只存 Key，单页放更多 Key） | 理想情况 O(1) | O(logN) |
| 插入性能 | 一般 | 较好（页分裂可控） | 扩容时 rehash 代价大 | 好（ConcurrentSkipListMap） |

**B+Tree 的核心优势**：
1. **高扇出（Fan-out）**：非叶子节点只存 Key + 指针，一个 16KB 页能放约 1200 个 Key，三层 B+Tree 可索引 1200^3 ≈ 17 亿行数据
2. **叶子节点有序双向链表**：天然支持范围查询和 ORDER BY
3. **查询稳定性**：任何查询都到叶子节点，路径长度相同

**关键要点**：
- "IO 次数少"是核心，因为磁盘 IO 是数据库最大的瓶颈
- 面试时要能算出"3 层 B+Tree 能存多少数据"

## 2. 什么是回表？如何避免回表？

**面试官考察点**：对索引原理的实际应用能力。

**参考答案**：

**回表**：普通索引叶子节点只存索引列 + 主键值。当查询列超出索引范围时，需要通过主键回到聚簇索引（主键索引）获取完整行数据。这个过程叫回表。

**避免回表的方法**：

```sql
-- 场景：用户表
CREATE TABLE user (
    id BIGINT PRIMARY KEY,
    name VARCHAR(64),
    phone VARCHAR(20),
    age INT,
    INDEX idx_phone(phone)
);

-- 回表查询（需要查 age，idx_phone 中不包含 age）
SELECT id, name, phone, age FROM user WHERE phone = '138xxx';

-- 覆盖索引（不回表）：查询列都在 idx_phone 中
SELECT id, phone FROM user WHERE phone = '138xxx';

-- 建立联合索引避免回表
CREATE INDEX idx_phone_name_age ON user(phone, name, age);
SELECT id, name, phone, age FROM user WHERE phone = '138xxx';
```

**实战案例**：支付系统账单查询优化

原始查询需要回表 200 万行：

```sql
-- 原始索引：idx_user_id(user_id)
-- 查询：SELECT id, amount, status, create_time FROM bill WHERE user_id = ? AND create_time > ?

-- 优化：创建覆盖索引
CREATE INDEX idx_user_time_amount_status ON bill(user_id, create_time, amount, status);

-- 优化后：Using index（覆盖索引），查询从 3s → 50ms
```

**关键要点**：
- EXPLAIN 中 `Extra: Using index` 表示覆盖索引
- `Using index condition` 是 ICP（索引条件下推），不一定避免了回表

## 3. 最左前缀原则是什么？哪些情况会导致索引失效？

**面试官考察点**：是否真正理解和写过联合索引。

**参考答案**：

**最左前缀原则**：联合索引 `(a, b, c)` 相当于创建了 `(a)`、`(a, b)`、`(a, b, c)` 三个索引（但不是 `(b)` 或 `(b, c)`）。

```sql
-- 联合索引：(a, b, c)
-- 走索引：
WHERE a = 1                    -- 使用 (a)
WHERE a = 1 AND b = 2         -- 使用 (a, b)
WHERE a = 1 AND b > 2 AND c = 3  -- 使用 (a, b)，c 部分走 ICP
WHERE a = 1 AND c = 3         -- 只使用 (a)，c 不能跳过 b
WHERE a = 1 AND b LIKE 'x%'   -- 使用 (a, b)

-- 不走索引：
WHERE b = 2                   -- 缺少 a
WHERE b = 2 AND c = 3         -- 缺少 a
WHERE a = 1 AND b LIKE '%x'   -- 范围后的模糊匹配
WHERE a = 1 OR b = 2          -- OR 中有非索引列
```

**常见索引失效场景**：
1. 对索引列使用函数：`WHERE DATE(create_time) = '2024-01-01'` → 改成 `WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'`
2. 隐式类型转换：`WHERE phone = 138xxx`（phone 是 VARCHAR）→ 改成 `WHERE phone = '138xxx'`
3. 负向条件：`!=`, `<>`, `NOT IN`, `NOT EXISTS` — 通常不走索引
4. `LIKE '%xxx'` — 以通配符开头
5. 联合索引不满足最左前缀

**关键要点**：
- EXPLAIN 的 key_len 可以看出实际使用了联合索引的哪几列
- ICP（Index Condition Pushdown）可以在存储引擎层过滤，减少回表

## 4. EXPLAIN 各字段含义及如何判断 SQL 是否需要优化？

**面试官考察点**：读执行计划的实际能力。

**参考答案**：

| 字段 | 含义 | 关注点 |
|------|------|--------|
| **type** | 访问类型 | system > const > eq_ref > ref > range > index > ALL，至少到 range |
| **key** | 使用的索引 | 是否用上了预期的索引 |
| **key_len** | 索引使用长度 | 联合索引用了哪几列 |
| **rows** | 扫描行数（估算） | 越小越好 |
| **Extra** | 额外信息 | Using index（覆盖）、Using filesort（需要排序优化）、Using temporary（需要临时表优化）、Using where、Using index condition（ICP） |

**需要优化的信号**：
- type = ALL（全表扫描）
- type = index（全索引扫描，通常也不好）
- Extra 中有 Using filesort 或 Using temporary
- rows 远大于实际返回行数
- key 为 NULL（没走索引）

**关键要点**：
- `type = index` 和 `type = ALL` 往往一样差
- `Extra: Using filesort` 不一定慢，但要关注排序数据量

## 5. 一条 SQL 从 3s 优化到 50ms 的完整过程

### 实战案例：竞拍出价记录查询优化

**面试官考察点**：完整的 SQL 优化方法论。

**参考答案**：

**背景**：竞拍系统需要查询"某场拍卖的车商出价记录排名"。

```sql
-- 原始 SQL（3s+）
SELECT b.bidder_id, b.amount, b.create_time, u.name, u.level
FROM bid_record b
LEFT JOIN user u ON b.bidder_id = u.id
WHERE b.auction_id = 12345
ORDER BY b.amount DESC
LIMIT 10;
```

**优化过程**：

**第 1 步：看执行计划**
```sql
EXPLAIN SELECT ...;
-- 结果：type=ALL，rows=500万，Extra=Using where; Using filesort
-- 问题：全表扫描 + 文件排序
```

**第 2 步：加索引**
```sql
-- 第一次尝试：单列索引
ALTER TABLE bid_record ADD INDEX idx_auction_id(auction_id);
-- 效果：3s → 1.2s，但 Extra 仍有 Using filesort
```

**第 3 步：联合索引（覆盖排序）**
```sql
-- 核心优化：联合索引覆盖 WHERE + ORDER BY
ALTER TABLE bid_record ADD INDEX idx_auction_amount(auction_id, amount);
-- 效果：1.2s → 200ms
-- 原理：B+Tree 叶子节点按 (auction_id, amount) 有序，ORDER BY amount 直接使用索引序
```

**第 4 步：覆盖索引（避免回表）**
```sql
-- 最终优化：覆盖索引避免 JOIN 回表
ALTER TABLE bid_record ADD INDEX idx_auction_amount_cover(auction_id, amount, bidder_id, create_time);
-- 效果：200ms → 50ms
-- 原理：所有需要的列都在索引中，不需要回表查聚簇索引
```

**第 5 步：业务优化**
```sql
-- 配合业务：拍卖进行中只需要当前排名，历史数据做归档
-- 将 500 万行全量数据拆分为热数据（当前拍卖）+ 冷数据（历史归档）
-- 热数据只有 2 万行，查询更高效
```

**优化总结**：
```
3s  → 全表扫描 + filesort
1.2s → 加单列索引，减少扫描行数
200ms → 联合索引利用索引序，消除 filesort
50ms → 覆盖索引消除回表，最终减少 JOIN 开销
```

## 6. MySQL 死锁如何排查和解决？

### 实战案例：竞拍系统死锁排查

**面试官考察点**：死锁的排查能力。

**参考答案**：

**死锁产生的四个必要条件**（缺一不可）：
1. 互斥：资源不能共享
2. 持有并等待：持有资源的同时等待其他资源
3. 不可剥夺：不能强行抢占
4. 循环等待：形成等待环

**排查方法**：

```sql
-- 1. 查看当前锁等待
SHOW ENGINE INNODB STATUS\G
-- 关注 LATEST DETECTED DEADLOCK 段

-- 2. 查看当前事务和锁
SELECT * FROM information_schema.INNODB_TRX;
SELECT * FROM information_schema.INNODB_LOCKS;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;

-- 3. 查看最近死锁日志
SHOW VARIABLES LIKE 'innodb_print_all_deadlocks';  -- 建议开启
```

**实战案例**：

```sql
-- 死锁场景：出价扣款
-- 事务 A：先扣保证金，再查钱包
UPDATE deposit SET amount = amount - 100 WHERE user_id = 1;  -- 持有 deposit 行锁
SELECT * FROM wallet WHERE user_id = 1 FOR UPDATE;           -- 等待 wallet 行锁

-- 事务 B：先扣钱包，再查保证金
UPDATE wallet SET balance = balance - 100 WHERE user_id = 1;  -- 持有 wallet 行锁
SELECT * FROM deposit WHERE user_id = 1 FOR UPDATE;           -- 等待 deposit 行锁

-- 结果：死锁
```

**解决方案**：
```sql
-- 方案1：统一加锁顺序（推荐）
-- 所有事务都先 lock deposit，再 lock wallet
-- 通过代码规范保证

-- 方案2：使用数据库死锁检测 + 重试
@Transactional
public void deduct(Long userId, BigDecimal amount) {
    int retry = 0;
    while (retry < 3) {
        try {
            depositDao.deduct(userId, amount);
            walletDao.deduct(userId, amount);
            break;
        } catch (DeadlockLoserDataAccessException e) {
            retry++;
            if (retry == 3) throw e;
        }
    }
}
```

**关键要点**：
- MySQL InnoDB 自动检测死锁并回滚代价最小的事务
- 死锁预防 > 死锁检测重试：统一加锁顺序是最佳实践

## 7. MySQL 主从延迟如何排查和解决？

**面试官考察点**：对 MySQL 复制机制和高可用方案的理解。

**参考答案**：

**主从延迟的常见原因**：
1. 从库机器性能差（最常见）
2. 从库承担了大量读请求，CPU/IO 竞争
3. 大事务：主库执行 1s，从库也要 1s，导致延迟累积
4. 从库是单线程 SQL 线程（MySQL 5.6 之前），5.7+ 支持并行复制
5. 网络延迟

**排查步骤**：
```sql
-- 1. 查看主从延迟秒数
SHOW SLAVE STATUS\G
-- 关注 Seconds_Behind_Master

-- 2. 查看复制线程状态
-- Slave_IO_Running: 拉取 binlog 的线程
-- Slave_SQL_Running: 执行 SQL 的线程
-- 哪个线程出问题，对应不同排查方向
```

**解决方案汇总**：

| 方案 | 适用场景 | 原理 |
|------|---------|------|
| 并行复制（5.7+） | 从库 SQL 线程跟不上 | `slave_parallel_workers=4`，按库/按事务并行回放 |
| 半同步复制 | 需要数据强一致 | 主库等待至少一个从库确认收到 binlog |
| 一主多从 + 读写分离 | 读压力大 | 主库只写，从库分担读 |
| 缓存前置 | 热点数据 | Redis 缓存热点数据，减少数据库读压力 |
| 分库分表 | 单库承载不了 | 水平切分，每个实例独立主从 |
| GTID + MGR | 高可用 | MySQL Group Replication，自动故障切换 |

**关键要点**：
- `Seconds_Behind_Master` 只是一个近似值，网络延迟也可能导致该值不准确
- 不要看到延迟就盲目切主——先确认 IO 线程还是 SQL 线程的问题

## 8. 分库分表的设计方案和经验

### 实战案例：竞拍 + 支付系统的分库分表

**面试官考察点**：分库分表的完整设计能力。

**参考答案**：

**什么时候需要分库分表？**
- 单表数据量超过 2000 万行（B+Tree 层级增加）
- 单库 QPS 超过 2000
- 单库容量接近磁盘上限

**分库分表策略**：

**垂直拆分**（按业务）：
```
原库 → 用户库 / 订单库 / 支付库 / 商品库
```

**水平拆分**（按数据）：
```sql
-- 使用 ShardingSphere 配置
# 广播表（每个库都有的小表）
sharding.broadcast-tables: t_config, t_dict

# 分片表（按 user_id 分片）
sharding.tables.t_order:
  actual-data-nodes: ds$->{0..3}.t_order_$->{0..15}
  database-strategy:
    standard:
      sharding-column: user_id
      algorithm-expression: ds$->{user_id % 4}
  table-strategy:
    standard:
      sharding-column: user_id
      algorithm-expression: t_order_$->{user_id % 16}
```

**分片键（Sharding Key）选择**：
- 竞拍系统选择 `user_id`：大部分查询带 user_id
- 支付系统选择 `merchant_id`：商户维度查询为主

**分片带来的问题与解决**：

| 问题 | 解决方案 |
|------|---------|
| 跨分片 JOIN | 冗余字段、应用层 JOIN、全局表 |
| 跨分片分页 | 禁止跨分片深度分页、用 ES 搜索 |
| 分布式 ID | Snowflake（参见分布式系统章节） |
| 扩容 | 一致性哈希、双倍扩容 + 数据迁移 |
| 分布式事务 | Seata AT 模式 |

**数据迁移方案**：
```
1. 存量数据：定时任务分批迁移 + 双写校验
2. 增量数据：Canal 监听 binlog → Kafka → 写入新库
3. 灰度切换：按 user_id 百分比逐步切流
4. 回滚方案：老库保留 7 天，出问题随时切回
```

## 9. MySQL 事务隔离级别及实现原理（MVCC）

**面试官考察点**：对事务和 MVCC 的深度理解。

**参考答案**：

**四种隔离级别**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 |
|---------|------|-----------|------|---------|
| READ UNCOMMITTED | √ | √ | √ | 无 MVCC，读最新 |
| READ COMMITTED | × | √ | √ | MVCC，每次快照读生成新 ReadView |
| REPEATABLE READ | × | × | ×(部分) | MVCC，事务开始生成 ReadView，Next-Key Lock 防幻读 |
| SERIALIZABLE | × | × | × | 所有 SELECT 加共享锁 |

**MVCC 核心机制（InnoDB）**：
- 每行数据有隐藏列：`DB_TRX_ID`（最后一次修改的事务ID）、`DB_ROLL_PTR`（回滚指针，指向 Undo Log）
- Read View：记录了当前活跃事务列表，用于判断数据版本的可见性
- **RC 和 RR 的区别**：RC 每次快照读生成新 ReadView，RR 事务开始时的第一个快照读生成 ReadView（之后复用）

**关键要点**：
- "RR 解决了幻读"只能说在快照读层面，当前读（`SELECT ... FOR UPDATE`）仍可能幻读，需要 Next-Key Lock
- Undo Log 是实现 MVCC 的关键，不是 Redo Log

## 10. SELECT 语句加锁分析（当前读 vs 快照读）

**面试官考察点**：对 MySQL 锁机制的深入理解。

**参考答案**：

```sql
-- 快照读（无锁，MVCC）
SELECT * FROM t WHERE id = 1;

-- 当前读（加锁）
SELECT * FROM t WHERE id = 1 FOR UPDATE;    -- 排他锁（X Lock）
SELECT * FROM t WHERE id = 1 LOCK IN SHARE MODE;  -- 共享锁（S Lock）

-- UPDATE/DELETE/INSERT 都是当前读
```

**加锁规则（InnoDB RR 级别）**：
- **主键等值查询**：Record Lock（行锁）
- **唯一索引等值查询**：Record Lock
- **普通索引等值查询**：Record Lock + Gap Lock（间隙锁）
- **范围查询**：Next-Key Lock（Record + Gap）
- **无索引列**：全表扫描 + 所有行加锁 → 近似表锁

**关键要点**：
- "快照读不加锁"只适用于普通 SELECT
- 间隙锁是为了防止幻读，只在 RR 级别有

## 11. 如何应对线上的大表 DDL 变更？

**面试官考察点**：大表运维经验。

**参考答案**：

**MySQL 5.6 之前**：DDL 会锁表，几千万行的大表可能锁几个小时。

**现代方案**：

| 方案 | 原理 | 工具 |
|------|------|------|
| Online DDL（5.6+） | InnoDB 在线加索引，不锁表 | `ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE` |
| pt-online-schema-change | 创建新表 → 复制数据 → 重命名 | Percona Toolkit |
| gh-ost | 类似 pt-osc，但基于 binlog 同步 | GitHub |

**gh-ost 原理与优势**：
```
1. 创建一张 ghost 表（新结构）
2. 从原表复制数据到 ghost 表
3. 同时监听 binlog，将增量变更同步到 ghost 表
4. 数据追平后，原子切换表名
```

**DDL 变更最佳实践**：
1. 业务低峰期操作
2. 控制复制速率，避免影响主库
3. 保留旧表一定时间便于回滚
4. 提前通知上下游

## 附录：MySQL 面试速查表

### EXPLAIN 快速诊断

```
type 优先级：system > const > eq_ref > ref > range > index > ALL
              ↑___________________优秀___________________↑  ↑_需优化_↑

Extra 重点关注：
- Using index          → 覆盖索引，好
- Using filesort       → 需要排序优化
- Using temporary      → 需要临时表，需优化
- Using index condition → ICP，减少回表
```

### 常用排查命令

```sql
-- 查看当前连接
SHOW PROCESSLIST;  -- 或 SELECT * FROM information_schema.PROCESSLIST;

-- 查看长时间运行的事务
SELECT * FROM information_schema.INNODB_TRX WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

-- 查看表锁等待
SELECT * FROM sys.innodb_lock_waits;  -- MySQL 5.7+

-- 查看表大小
SELECT table_name, ROUND((data_length + index_length) / 1024 / 1024 / 1024, 2) AS size_gb
FROM information_schema.TABLES WHERE table_schema = 'your_db';
```

### SQL 优化黄金法则

1. **最有效的优化 = 减少扫描行数**（加索引）
2. **其次 = 减少回表**（覆盖索引）
3. **再次 = 减少排序**（利用索引序）
4. **最后 = 减少网络传输**（只查需要的列，不用 SELECT *）
