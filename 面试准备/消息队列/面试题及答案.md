## 1. RocketMQ 的架构原理？

**面试官考察点**：对 RocketMQ 核心架构的理解。

**参考答案**：

```
┌──────────────────────────────────────────────┐
│                  NameServer                    │
│  (无状态集群，各节点独立，Broker/Topic 路由)    │
└──────┬───────────────────────────┬────────────┘
       │ 注册心跳                    │ 查询路由
       ▼                            ▼
┌──────────────┐          ┌──────────────────┐
│    Broker    │          │ Producer/Consumer │
│  ┌────────┐  │          │ (从 NameServer    │
│  │Master  │  │          │  获取 Broker 地址) │
│  ├────────┤  │          └──────────────────┘
│  │ Slave  │  │
│  └────────┘  │
└──────────────┘
```

**核心组件**：
- **NameServer**：路由注册中心，无状态，Broker 注册 + Producer/Consumer 查询路由。各节点不通信（和 ZooKeeper 根本不同）
- **Broker**：消息存储和转发，主从复制保证高可用。分为 Master/Slave
- **Producer**：消息生产者，从 NameServer 获取 Topic 路由，选择 MessageQueue 发送
- **Consumer**：消息消费者，Pull 模式长轮询拉取消息

**存储模型**：
```
CommitLog：所有消息按顺序写入同一个文件（顺序写）
    ├── TopicA-Queue0: ConsumeQueue（索引：CommitLog Offset + Size + Tag HashCode）
    ├── TopicA-Queue1: ConsumeQueue
    ├── TopicB-Queue0: ConsumeQueue
    └── TopicB-Queue1: ConsumeQueue
```

**关键要点**：
- NameServer 之间不通信！这是面试高频考点
- 所有 Topic 的消息混写同一个 CommitLog（顺序写保证性能）
- ConsumeQueue 只是索引文件，不是消息副本

## 2. 消息丢失的三种场景及如何做到零丢失？

### 实战案例：支付系统消息零丢失方案

**面试官考察点**：消息可靠性保证的完整方案。

**参考答案**：

**消息丢失的三个环节及对应方案**：

```
环节1：发送阶段（Producer → Broker）
丢失原因：网络问题，Producer 没收到确认
解决方案：
  - 同步发送 + 重试（retryTimesWhenSendFailed=3）
  - 异步发送 + 回调检查
  - 事务消息：半消息 + 本地事务 + 回查

环节2：存储阶段（Broker 内部）
丢失原因：Master 宕机，未同步到 Slave
解决方案：
  - 同步刷盘（性能差，不推荐）→ 异步刷盘 + 主从同步
  - Broker 集群：同步双写 / Raft（DLedger）

环节3：消费阶段（Broker → Consumer）
丢失原因：Consumer 自动提交 Offset，实际没处理完
解决方案：
  - 手动提交 Offset（处理成功后再提交）
  - 消费重试 + 死信队列兜底
```

**支付系统零丢失方案**：
```java
// 步骤1：发送事务消息（Producer）
TransactionMQProducer producer = new TransactionMQProducer("payment_group");
producer.setTransactionListener(new TransactionListener() {
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        try {
            // 执行本地事务：扣款
            paymentService.deduct((PaymentRequest) arg);
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }
    
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        // 回查：检查本地事务是否完成
        return paymentService.isDeducted(msg.getTransactionId()) 
            ? LocalTransactionState.COMMIT_MESSAGE 
            : LocalTransactionState.ROLLBACK_MESSAGE;
    }
});

// 步骤2：同步刷盘（Broker 配置）
# broker.conf
flushDiskType = SYNC_FLUSH       # 同步刷盘
brokerRole = SYNC_MASTER         # 同步主从

// 步骤3：手动提交 + 死信队列（Consumer）
consumer.registerMessageListener((MessageListenerOrderly) (msgs, context) -> {
    for (MessageExt msg : msgs) {
        try {
            paymentService.process(new String(msg.getBody()));
            // 只有处理成功才返回 SUCCESS，才会提交 Offset
        } catch (Exception e) {
            // 返回 SUSPEND → 触发重试 → 最终进死信队列
            return ConsumeOrderlyStatus.SUSPEND_CURRENT_QUEUE_A_MOMENT;
        }
    }
    return ConsumeOrderlyStatus.SUCCESS;
});
```

**关键要点**：
- 三个环节中任何一个出问题都丢消息，必须全链路保证
- 事务消息是 RocketMQ 独有的能力（Kafka 没有），这个是重要区分点

## 3. 消息积压如何处理？

### 实战案例：大促期间消息积压应急

**面试官考察点**：消息积压的应急处理能力。

**参考答案**：

**应急处理流程（4 阶段）**：

```
阶段1：快速止血（1分钟内）
  - 临时扩容 Consumer 实例（增加消费能力）
  - 如果 Topic 的 Queue 数量不够 → 先扩容 Queue
  - 如果是下游依赖慢 → 先限流下游

阶段2：紧急扩容（5分钟内）
  - 新增 Consumer 机器
  - 增加消费线程数
  - 如果消息不重要 → 先跳过积压消息，处理最新的

阶段3：批量消费（10分钟内）
  - 开启批量消费模式
  - 合并写操作（批量写 DB）

阶段4：事后修复
  - 分析根因：为什么消费速度跟不上生产速度？
  - 优化消费者逻辑（批处理、异步化、缓存）
  - 建立积压监控告警
```

**大促期间真实应急**：

```java
// 紧急代码：跳过旧消息，只处理最近 5 分钟的出价
consumer.registerMessageListener((msgs, context) -> {
    for (MessageExt msg : msgs) {
        long delay = System.currentTimeMillis() - msg.getBornTimestamp();
        if (delay > 300_000) {  // 超过 5 分钟
            log.warn("丢弃过期消息: {}", msg.getMsgId());
            continue;  // 跳过，直接标记消费成功
        }
        // 正常处理
        bidService.process(msg);
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
});
```

**预防措施**：
```bash
# 1. 积压监控告警
group_diff = 生产量 - 消费量 > 阈值 → 告警

# 2. 容量规划
消费速率 >= 生产速率 × 1.5 → 留够 buffer

# 3. 限流兜底
生产端配置限流，超过阈值拒绝或排队
```

**关键要点**：
- 积压时不要重启 Consumer（重启期间完全不消费，积压更多）
- 不要只调大消费线程数（要考虑下游 DB/Redis 能否承受）
- 建立死信队列机制，异常消息自动隔离

## 4. 顺序消息如何实现？有什么限制？

**面试官考察点**：顺序消息的原理和适用边界。

**参考答案**：

**实现原理**：
- Producer 将同一类型的消息发送到同一个 MessageQueue
- Consumer 对同一个 MessageQueue 使用单线程消费

```java
// Producer：通过选择器将同一拍卖品的消息发到同一个 Queue
producer.send(msg, new MessageQueueSelector() {
    @Override
    public MessageQueue select(List<MessageQueue> mqs, Message msg, Object arg) {
        Long auctionId = (Long) arg;
        int index = (int) (auctionId % mqs.size());
        return mqs.get(index);
    }
}, auctionId);

// Consumer：顺序消费监听器（单线程）
consumer.registerMessageListener((MessageListenerOrderly) (msgs, context) -> {
    for (MessageExt msg : msgs) {
        processSequentially(msg);
    }
    return ConsumeOrderlyStatus.SUCCESS;
});
```

**局限性**：
- 不能水平扩容 Consumer 超过 Queue 数量（多余的 Consumer 空闲）
- 单 Queue 消费成为瓶颈（不能并行）
- 消费失败后挂起，整个 Queue 暂停消费（单点阻塞）

**竞拍系统为什么用 RocketMQ 做推送但不用顺序消息？**
- 推送场景不需要严格顺序（先到的出价可能不是最终成交价）
- 排序逻辑在 Redis Lua 中完成，MQ 只负责通知

**关键要点**：
- 顺序消息和全局有序是不同的：RocketMQ 只能保证分区有序
- 顺序消息有显著性能代价，能不用就不用

## 5. 事务消息的实现原理？

**面试官考察点**：事务消息的深入理解。

**参考答案**：

**事务消息执行流程**：
```
1. Producer 发送 Half Message（半消息，对 Consumer 不可见）
2. Broker 存储 Half Message 成功 → 返回确认
3. Producer 执行本地事务
4. Producer 发送 Commit/Rollback 给 Broker
5. Broker 根据 Commit/Rollback：
   - Commit → 消息对 Consumer 可见
   - Rollback → 删除消息
6. 如果 Broker 没收到确认（超时）→ 回查 Producer
7. Producer 的 checkLocalTransaction() 返回事务状态
```

**关键设计**：
- Half Message 存储在单独的 Topic（RMQ_SYS_TRANS_HALF_TOPIC），ConsumeQueue 中的 Tag 记录事务状态
- 回查机制保证最终一致性（至少一次回查，可能多次）
- 事务消息不会丢失（Broker 持久化后才返回成功）

**支付系统事务消息的使用**：
```
场景：保证金扣减 → 通知钱包服务更新可用余额
方案：事务消息保证扣减和通知的一致性
- Half Message: "保证金已扣减 100 元"
- 本地事务：扣保证金表 + 记录流水
- Commit：钱包服务消费此消息，更新可用余额
```

**关键要点**：
- 事务消息 ≠ 分布式事务，它只保证消息和本地事务的一致性
- 回查可能多次执行，checkLocalTransaction 必须幂等

## 6. RocketMQ vs Kafka 如何选型？

**面试官考察点**：MQ 选型的判断力。

**参考答案**：

| 维度 | RocketMQ | Kafka |
|------|----------|-------|
| 事务消息 | 原生支持 | 不支持（需额外实现）|
| 顺序消息 | 原生支持（Queue 维度）| 支持（Partition 维度）|
| 延时消息 | 原生支持 18 个级别 | 不支持 |
| 消息过滤 | Tag/SQL92 | 不支持（客户端过滤）|
| 吞吐量 | 10万级（单机）| 百万级（单机）|
| 可靠性 | 极高（同步刷盘/主从）| 高（ISR 机制）|
| 运维复杂度 | 低（NameServer 简单）| 高（ZooKeeper 依赖）|
| 生态 | Java 生态好 | 大数据生态好 |
| 适用场景 | 业务消息（订单/支付）| 日志/流计算/大数据 |

**选型决策**：
```
需要事务消息/延时消息/复杂业务消息 → RocketMQ
日志采集/流计算/大数据 Pipeline → Kafka
公司是 Java 技术栈为主 → RocketMQ（运维和排查方便）
公司已深度使用 Hadoop/Spark/Flink → Kafka
```

## 7. 消息重复消费如何保证幂等？

**面试官考察点**：幂等性设计能力。

**参考答案**：

**为什么会有重复消费**：
- Producer 重试（网络超时但实际已写入）
- Consumer Rebalance（Offset 没及时提交）
- Consumer 失败重试

**幂等方案（三道防线）**：

```java
// 第一道：业务唯一键（首选）
public void processPayment(MessageExt msg) {
    PaymentEvent event = JSON.parseObject(msg.getBody(), PaymentEvent.class);
    String bizId = event.getTransactionId();
    
    // 数据库唯一键保证幂等
    try {
        paymentDao.insert(event);  // transaction_id 是唯一键
    } catch (DuplicateKeyException e) {
        // 已处理过，跳过
        log.warn("重复消息: {}", bizId);
        return;
    }
}

// 第二道：Redis 去重（高并发场景）
public void processBid(MessageExt msg) {
    String msgId = msg.getMsgId();
    // SET NX 原子操作
    Boolean success = redis.setnx("msg:dedup:" + msgId, "1", 300);
    if (!success) {
        return;  // 已处理
    }
    // 业务处理
    bidService.process(msg);
}

// 第三道：状态机（复杂业务）
public void processOrder(MessageExt msg) {
    OrderEvent event = JSON.parseObject(msg.getBody(), OrderEvent.class);
    Order order = orderDao.findById(event.getOrderId());
    
    // 状态机判断
    if (order.getStatus() != OrderStatus.PAID) {
        log.warn("订单状态不正确，跳过: {}", order.getStatus());
        return;
    }
    // 更新状态 + 乐观锁版本号
    orderDao.updateStatus(event.getOrderId(), OrderStatus.PAID, OrderStatus.SHIPPED, order.getVersion());
}
```

**关键要点**：
- 不要依赖 MessageId 做去重（Broker 重启可能产生重复 ID）
- 业务唯一键（如 transaction_id）是最可靠的幂等依据

## 8. 竞拍系统如何实现 RocketMQ 的精准路由推送？

### 实战案例：竞拍通知混合推送

**面试官考察点**：MQ 在复杂场景下的架构设计。

**参考答案**：

**业务需求**：
- 10 万+ 在线车商，每场拍卖 500+ 人
- 出价事件需要推送通知给关注该车辆的车商
- 不能全量广播，不能热点集中

**架构设计**：
```
Producer（业务服务）:
  出价成功 → 发送 RocketMQ 消息 → Topic: BID_EVENT
                ↓ 广播模式（所有 Netty 节点都收到）
Consumer（Netty 网关集群，10 节点）:
  各节点本地判断 → 是否有该车辆的车商连接？
    有 → 查 Redis 获取关注列表 → 精准推送
    没有 → 丢弃（减少无效处理）

"车辆→服务器"映射维护：
  Znode: /bid/mapping/{auctionId} → {serverIps...}
  车商进入拍卖间 → 注册到映射表
  车商离开拍卖间 → 从映射表移除
```

**效果**：O(n²) 复杂度降为 O(n × 节点上该车辆关注者数)，推送 QPS 提升 10 倍。

## 附录：MQ 面试速查表

### 消息可靠性保障清单

```
Producer 端：
□ 同步发送 / 事务消息
□ 发送重试（至少 3 次）
□ 失败告警

Broker 端：
□ 同步刷盘 / 异步刷盘 + 主从同步
□ 主从自动切换（DLedger）
□ 磁盘使用率监控

Consumer 端：
□ 手动提交 Offset
□ 消费重试 + 死信队列
□ 幂等处理
□ 消费进度监控
```

### 消息积压排查清单

```
1. Consumer 实例数是否够？
2. Consumer 线程数是否够？
3. 下游依赖（DB/Redis/API）是否慢？
4. Queue 数量是否需要扩容？
5. 消费逻辑是否可以优化（批量、异步）？
6. 非关键消息是否可以降级丢弃？
```
