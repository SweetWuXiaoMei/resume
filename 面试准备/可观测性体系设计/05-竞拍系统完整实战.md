# 05 — 竞拍系统可观测性完整实战

> 本章将前面四章的所有概念落地到竞拍系统。面试时，你可以把这一章的内容当作"我主导设计的可观测性体系"来讲。

## 5.1 竞拍系统的架构背景

在讲可观测性之前，先快速回顾竞拍系统的架构——因为可观测性设计必须从架构推导。

```
车商 App/Web
    │ WebSocket
    ▼
Netty 长连接网关 × 10 节点（单节点 5 万连接）
    │ Dubbo RPC
    ▼
出价服务 × 20 节点
    ├──→ Redis Cluster（Lua 出价引擎）
    ├──→ RocketMQ（事件通知）
    └──→ MySQL MGR（出价落库）

推送服务 × 8 节点
    ├──→ RocketMQ（消费出价事件）
    └──→ Netty 网关（精准推送 WebSocket）
```

**可观测性的设计目标**：
1. 出价成功率下降 → **1 分钟内**发现（告警）
2. 慢出价根因 → **5 分钟内**定位（指标 + Trace + 日志串联）
3. 推送延迟异常 → 能看到是 MQ 积压还是 Netty 推送慢
4. 业务方能看懂自己的业务指标（不只是技术指标）

## 5.4 代码埋点实战

### 关键路径埋点清单

竞拍系统的一条出价请求，哪些地方需要埋点：

```
□ 网关接入层
  ├── WebSocket 连接建立耗时
  ├── 协议解析耗时
  └── 当前连接数

□ 出价服务层
  ├── 本地缓存校验耗时（拦截无效出价）
  ├── Redis Lua 脚本执行耗时 ★ 核心
  ├── Lua 脚本结果（成功/余额不足/出价过低）
  └── MQ 发送耗时

□ 推送服务层
  ├── MQ 消费延迟（消息产生时间 - 消费开始时间）
  ├── ZK 映射查询耗时
  ├── Netty 推送耗时（分节点统计）
  └── 推送目标数量

□ 业务层
  ├── 每场拍卖的在线车商数
  ├── 每场拍卖的出价 QPS
  └── 出价排行榜 Top10 计算耗时
```

### 使用 Micrometer 统一埋点

```java
// ===== 1. 网关埋点 =====
public class GatewayMetrics {
    private final Counter wsConnectTotal;       // WebSocket 连接总数
    private final Gauge wsActiveConnections;     // 当前活跃连接数
    private final Timer protoDecodeTime;        // 协议解析耗时
    
    @PostConstruct
    public void init() {
        wsActiveConnections = Gauge.builder("gateway.ws.connections.active",
                channelGroup, ChannelGroup::size)
            .register(registry);
    }
}

// ===== 2. 出价服务埋点 =====
@Service
public class BidService {
    
    private final Timer bidTotalTimer;          // 总耗时
    private final Timer redisLuaTimer;          // Redis Lua 耗时
    private final Counter localCacheHit;        // 本地缓存命中（拦截无效出价）
    private final Timer localCacheCheckTime;   // 本地缓存校验耗时
    private final Counter[] bidResults;         // 出价结果分布
    
    @PostConstruct
    public void init() {
        // 出价总耗时 + 分布
        this.bidTotalTimer = Timer.builder("bid.total.time")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);
        
        // Redis Lua 耗时（核心指标）
        this.redisLuaTimer = Timer.builder("bid.redis.lua.time")
            .publishPercentiles(0.5, 0.95, 0.99, 0.999)
            .register(registry);
        
        // 出价结果分布
        String[] results = {"success", "insufficient_balance", "bid_too_low", "auction_ended"};
        this.bidResults = new Counter[results.length];
        for (int i = 0; i < results.length; i++) {
            bidResults[i] = Counter.builder("bid.result")
                .tag("outcome", results[i])
                .register(registry);
        }
    }
    
    public BidResult placeBid(BidRequest request) {
        return bidTotalTimer.record(() -> {
            // 本地缓存快速拦截
            boolean cachedPass = localCacheCheckTime.record(() -> {
                boolean pass = localCache.isHigherThanCurrentMax(request);
                if (!pass) localCacheHit.increment();
                return pass;
            });
            if (!cachedPass) {
                bidResults[2].increment();  // bid_too_low
                return BidResult.tooLow();
            }
            
            // Redis Lua 核心引擎
            BidResult result = redisLuaTimer.record(() -> 
                redisBidEngine.execute(request)
            );
            
            // 记录结果
            switch (result.getOutcome()) {
                case SUCCESS -> bidResults[0].increment();
                case INSUFFICIENT_BALANCE -> bidResults[1].increment();
                case AUCTION_ENDED -> bidResults[3].increment();
            }
            
            return result;
        });
    }
}

// ===== 3. 推送服务埋点 =====
@Component
public class PushService {
    
    private final Timer pushTotalTime;          // 推送总耗时
    private final Timer mqConsumeDelay;         // MQ 消费延迟（端到端）
    private final Counter pushTargetCount;      // 推送目标数量
    private final Counter pushSuccessCount;     // 推送成功数
    private final Counter pushFailCount;        // 推送失败数
    
    @PostConstruct
    public void init() {
        this.pushTotalTime = Timer.builder("push.total.time")
            .publishPercentiles(0.5, 0.95, 0.99)
            .register(registry);
        // MQ 消费延迟 = 消费开始时间 - 消息产生时间
        this.mqConsumeDelay = Timer.builder("push.mq.consume.delay")
            .publishPercentiles(0.5, 0.99)
            .register(registry);
    }
    
    public void onBidEvent(BidEvent event) {
        pushTotalTimer.record(() -> {
            // 记录 MQ 端到端延迟
            long mqDelay = System.currentTimeMillis() - event.getTimestamp();
            mqConsumeDelay.record(mqDelay, TimeUnit.MILLISECONDS);
            
            // 获取推送目标
            Set<Long> targets = routingService.getTargets(event.getAuctionId());
            pushTargetCount.increment(targets.size());
            
            // 推送
            for (Long target : targets) {
                try {
                    pushToGateway(target, event);
                    pushSuccessCount.increment();
                } catch (Exception e) {
                    pushFailCount.increment();
                }
            }
        });
    }
}
```

## 5.5 大促期间的可观测性策略

竞拍系统在大促期间（如双十一二手车节）流量是平时的 3-5 倍，可观测性策略需要调整：

### 采样策略动态调整

```java
@Component
public class AdaptiveSampler {
    
    // 配置中心动态下发
    @Value("${sampler.normal.rate:0.1}")
    private double normalRate;
    
    @Value("${sampler.peak.rate:0.02}")  // 大促期间降为 2%
    private double peakRate;
    
    @Value("${sampler.mode:normal}")     // normal / peak
    private String mode;
    
    public boolean shouldSample(SamplingContext ctx) {
        // 错误请求永远全采
        if (ctx.isError()) return true;
        // 慢请求永远全采
        if (ctx.getDurationMs() > 100) return true;
        
        // 根据模式调整采样率
        double rate = "peak".equals(mode) ? peakRate : normalRate;
        return ThreadLocalRandom.current().nextDouble() < rate;
    }
}
```

### 告警阈值动态上调

```
大促期间：
  - 出价 P99 告警阈值：100ms → 200ms
  - MQ 积压告警阈值：10 万 → 50 万
  - CPU 告警阈值：80% → 90%（正常的高负载）

大促结束后自动恢复到日常阈值
```

## 5.6 架构师面试完整话术

### 面试官问："你们系统怎么做监控的？"

> 普通回答："我们用了 Prometheus + Grafana，配了一些告警。"
>
> 架构师回答：
>
> "我主导设计了竞拍系统的可观测性体系。首先明确一点——监控不等于可观测性。监控告诉你 CPU 高了，可观测性告诉你为什么高。
>
> 我设计的是三大支柱：**指标（Metrics）+ 日志（Logging）+ 链路追踪（Tracing）**，通过 TraceId 串联。
>
> 指标分四层：基础设施（CPU/内存）→ 中间件（Redis/MQ/DB）→ 应用（出价 QPS/P99/成功率）→ 业务（在线车商数/热门拍卖品/推送延迟）。业务方能看懂自己的业务指标，不只是技术指标。
>
> 技术选型上，链路追踪选了 SkyWalking——因为我们是 Java 技术栈 + Dubbo RPC，SkyWalking 的无侵入 Agent 对 Dubbo 原生支持最好。指标用 Micrometer 统一 API + Prometheus 存储，日志用 ELK。
>
> 这个体系的价值不是"告警响了"，而是**把 MTTR（故障平均恢复时间）从 30 分钟降到 5 分钟**。怎么做到？告警响了 → 点开 Grafana 看到异常 TraceId → SkyWalking 看调用链哪个环节慢 → Kibana 搜 TraceId 看完整日志 → 5 分钟内定位根因。
>
> 还有两点可能和其他团队不一样：第一，我们定义了 SLO 和 Error Budget，发布节奏和错误预算挂钩——预算充足大胆迭代，预算紧张冻结发布。第二，告警分层——P0 电话 + 短信、P1 企业微信、P2 邮件。每条告警都绑定了 Runbook，让 oncall 的人知道第一步做什么。"

### 面试官追问："为什么选 SkyWalking 而不是 Jaeger 或 Zipkin？"

> "三个原因。第一，SkyWalking Agent 是 Java 无侵入的，加上 JVM Agent 参数就行，不需要改任何代码。Zipkin 需要 Brave SDK 入侵代码。第二，我们用 Dubbo 做服务间调用，SkyWalking 对 Dubbo 的支持是原生的、最好的，跨进程的 Trace 传递完全自动。第三，SkyWalking 内置了 JVM 指标采集、慢 SQL 检测、服务拓扑等能力，一套 Agent 解决多个问题。代价是 SkyWalking OAP 集群需要 3 台 4C8G 的机器，但这个成本完全可接受。"

### 面试官追问："可观测性体系花了多少钱？"

> "年度成本大概 1 万元人民币左右，但竞拍系统每分钟交易额 10 万元。曾经有一次，老系统没有可观测性，出价异常花了 25 分钟才定位到 Redis 热点。这套体系上线后，同类故障平均 5 分钟定位。单次故障节省 20 分钟 × 10 万 = 200 万。所以 ROI 至少 200 倍。老板从来没在可观测性预算上卡过我。"
