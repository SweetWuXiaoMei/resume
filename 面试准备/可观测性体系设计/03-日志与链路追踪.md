# 03 — 日志与链路追踪

> 日志和链路追踪是回答"为什么出问题"的关键。指标告诉你"有异常"，日志和 Trace 告诉你"异常在哪里"。

---

## 3.1 结构化日志规范

### 为什么需要结构化日志？

```
传统日志（人可读，机器难解析）：
2024-01-15 10:30:00 INFO BidService - 车商 12345 对拍卖品 67890 出价 100000 元成功

结构化日志（人可读 + 机器可解析）：
{"timestamp":"2024-01-15T10:30:00.123Z","level":"INFO","service":"bid-service",
 "traceId":"abc123def456","spanId":"span-001","userId":"12345",
 "auctionId":"67890","amount":100000,"event":"bid_success","duration_ms":35}
```

结构化日志投入 ELK 后，你可以搜：
- `event:bid_success AND amount:>50000` → 大额出价
- `traceId:abc123def456` → 串联整条调用链
- `duration_ms:>100` → 所有慢出价

### 竞拍系统日志规范

```java
// 统一的日志 Schema
@JsonInclude(JsonInclude.Include.NON_NULL)
public class LogEvent {
    private String timestamp;      // ISO 8601 时间戳
    private String level;          // INFO/WARN/ERROR
    private String service;        // bid-service / push-service
    private String traceId;        // 全局 TraceId
    private String spanId;         // 当前 Span
    private String event;          // 事件类型：bid_request / bid_success / bid_failed
    private String userId;         // 车商 ID
    private Long auctionId;        // 拍卖品 ID
    private Long amount;           // 出价金额
    private Long durationMs;       // 耗时
    private String errorCode;      // 错误码
    private String errorStack;     // 异常堆栈（仅 ERROR 级别）
    private Map<String, Object> extra; // 扩展字段
}

// 使用示例
@Slf4j
public class BidService {
    
    public BidResult placeBid(BidRequest request) {
        long start = System.currentTimeMillis();
        String traceId = TraceContext.getTraceId();
        
        // 1. 请求日志
        log.info(LogEvent.builder()
            .event("bid_request")
            .traceId(traceId)
            .userId(request.getBidderId())
            .auctionId(request.getAuctionId())
            .amount(request.getAmount())
            .build().toJson());
        
        try {
            BidResult result = doBid(request);
            long duration = System.currentTimeMillis() - start;
            
            // 2. 成功日志
            log.info(LogEvent.builder()
                .event("bid_success")
                .traceId(traceId)
                .userId(request.getBidderId())
                .auctionId(request.getAuctionId())
                .amount(request.getAmount())
                .durationMs(duration)
                .extra(Map.of("rank", result.getRank()))
                .build().toJson());
            
            return result;
            
        } catch (Exception e) {
            // 3. 失败日志（含完整上下文）
            log.error(LogEvent.builder()
                .event("bid_failed")
                .traceId(traceId)
                .userId(request.getBidderId())
                .auctionId(request.getAuctionId())
                .amount(request.getAmount())
                .errorCode(e.getClass().getSimpleName())
                .errorStack(ExceptionUtils.getStackTrace(e))
                .build().toJson());
            throw e;
        }
    }
}
```

### ELK 日志采集架构

```
Spring Boot App (JSON 日志 → stdout)
        │
        ▼
    Filebeat (采集 + 多行合并 + 解析)
        │
        ▼
    Kafka (缓冲，消峰填谷)
        │
        ▼
    Logstash (过滤 + 清洗 + 丰富)
        │
        ▼
    Elasticsearch (索引 + 存储)
        │
        ▼
    Kibana (搜索 + 可视化)
```

**保留策略**：
```
ES Hot 节点：7 天（SSD，快速检索）
ES Warm 节点：30 天（HDD，低频查询）
S3 归档：90 天（压缩，合规审计）
```

## 3.2 链路追踪设计

### SkyWalking 的竞拍系统配置

```yaml
# skywalking-agent.config
agent.service_name: ${SW_SERVICE_NAME:bid-service}
agent.sample_n_per_3_secs: -1  # -1 = 全量采样（开发环境）

# 生产环境采样策略
plugin.toolkit.sample_rate: 
  # 正常请求 10%，错误请求 100%
  default: 10
  error: 100
  
# Dubbo 插件（竞拍系统核心）
plugin.dubbo.trace_param: true  # 追踪 Dubbo 请求参数
```

### 如何在代码中让日志和 Trace 关联？

```java
// 方案：MDC (Mapped Diagnostic Context)
// SkyWalking Agent 自动将 TraceId 注入 MDC

// logback-spring.xml
<appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
        <!-- 自动包含 MDC 中的 traceId -->
        <includeMdcKeyName>traceId</includeMdcKeyName>
    </encoder>
</appender>

// 任何日志自动带上 traceId：
// {"timestamp":"...","level":"INFO","traceId":"abc123def456","message":"出价成功"}
```

**串联效果**：
```
1. 在 Grafana 看到出价成功率下降到 98% [指标]
2. 点击异常时间点 → 跳转到 SkyWalking → 看到大量慢 Trace [链路]
3. 选一条慢 Trace → 复制 TraceId → 跳转到 Kibana [日志]
4. 在 Kibana 搜索 traceId:abc123def456 → 看到完整的事件序列

从发现异常到定位根因：5 分钟以内
```

## 3.3 采样策略设计

全量采样成本太高，需要聪明的采样策略。

### 竞拍系统的自适应采样

```java
// SkyWalking 采样策略配置
@Bean
public SamplerConfig samplerConfig() {
    return SamplerConfig.builder()
        // 策略 1：错误请求 100% 采样
        .errorRate(1.0)
        // 策略 2：慢请求 100% 采样（超过 100ms 的都是慢请求）
        .slowThresholdMs(100)
        .slowRate(1.0)
        // 策略 3：正常请求 10% 采样
        .normalRate(0.1)
        // 策略 4：高频入口降采样
        .highFrequencyThreshold(1000)  // 超过 1000 QPS 的入口
        .highFrequencyRate(0.05)      // 只采样 5%
        .build();
}
```

### 采样对排查的影响

```
策略      | 存储成本 | 故障排查价值
全量      | 极高(30GB/天) | 完美（所有请求都有 Trace）
10% 固定  | 低(3GB/天)   | 差（90% 故障可能没被采样）
自适应    | 中(5GB/天)   | 好（关键请求全保留）
```

> **面试话术**："全量采样太贵，固定采样排查时缺数据。我们用自适应采样：正常请求只采 10%，但错误和慢请求 100% 保留。故障排查时从来不会缺关键 Trace。"

## 3.4 竞拍系统的日志分级与脱敏

### 日志分级策略

| 级别 | 用途 | 保留策略 | 示例 |
|------|------|---------|------|
| ERROR | 系统异常 | ES 30天 + S3 90天 | NPE、连接超时、OOM |
| WARN | 业务异常 | ES 7天 | 余额不足、出价过低 |
| INFO | 关键事件 | ES 7天 | 出价成功、拍卖结束 |
| DEBUG | 调试信息 | 不记录 | 方法入参、中间结果 |

### 敏感数据脱敏

```java
// 竞拍系统涉及的车商手机号、银行卡号必须脱敏
public class LogSanitizer {
    
    // 手机号脱敏：138xxxx0626
    public static String maskPhone(String phone) {
        if (phone == null || phone.length() < 7) return "***";
        return phone.substring(0, 3) + "****" + phone.substring(phone.length() - 4);
    }
    
    // 金额脱敏（审计日志不脱敏，业务日志脱敏）
    public static String maskAmount(Long amount) {
        return "***";  // 或保留量级：~10万
    }
}

// Jackson 序列化时自动脱敏
@JsonSerialize(using = PhoneMaskSerializer.class)
private String phone;

@JsonSerialize(using = AmountMaskSerializer.class)
private Long amount;  // 用于业务日志
```

**面试要点**：提到安全——"日志中的个人信息必须脱敏，尤其是手机号、身份证、银行卡号。这是 GDPR/个人信息保护法的合规要求。脱敏在序列化层统一做，不在业务代码中散落。"
