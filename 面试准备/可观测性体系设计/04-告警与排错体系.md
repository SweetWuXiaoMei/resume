# 04 — 告警与排错体系

> 告警不是越多越好。架构师的价值在于：设计一套"响了就有人处理、处理了能找到根因"的体系。

---

## 4.1 告警金字塔

```
                   ┌─────┐
                   │ P0  │  紧急：立即处理，全组响应
                   │ 3-5 │  例子：出价成功率 < 95%、Full GC > 0
                   ├─────┤
                   │ P1  │  严重：30 分钟内处理
                   │ 8-10│  例子：出价 P99 > 200ms、消息积压 > 10 万
                   ├─────┤
                   │ P2  │  一般：工作时间处理
                   │ 10+ │  例子：CPU > 80%、磁盘使用率 > 80%
                   ├─────┤
                   │ P3  │  提醒：可延后处理
                   │ N   │  例子：非核心服务异常、慢查询出现
                   └─────┘
```

### 竞拍系统告警规则设计

```yaml
# AlertManager 告警规则
groups:
  - name: auction_critical  # P0 告警
    rules:
      # 规则 1：出价成功率低于 99%
      - alert: BidSuccessRateLow
        expr: |
          rate(bid_request_total{result="success"}[5m]) / 
          (rate(bid_request_total{result="success"}[5m]) + 
           rate(bid_request_total{result="failure"}[5m])) < 0.99
        for: 1m  # 持续 1 分钟才触发（避免瞬时抖动）
        labels:
          severity: P0
          team: auction-core
        annotations:
          summary: "出价成功率低于 99%"
          description: "当前成功率 {{ $value | humanizePercentage }}，请立即检查"
          runbook: "https://wiki.internal/runbooks/bid-success-rate-low"
      
      # 规则 2：出现 Full GC
      - alert: FullGC
        expr: rate(jvm_gc_pause_seconds_count{action="end of major GC"}[5m]) > 0
        for: 0m  # 有一次就告警
        labels:
          severity: P0
        annotations:
          summary: "实例 {{ $labels.instance }} 发生 Full GC"
          runbook: "https://wiki.internal/runbooks/full-gc"

  - name: auction_warning  # P1 告警
    rules:
      # 规则 3：出价 P99 高于 200ms
      - alert: BidP99High
        expr: histogram_quantile(0.99, rate(bid_request_duration_bucket[5m])) > 0.2
        for: 5m
        labels:
          severity: P1
        annotations:
          summary: "出价 P99 超过 200ms"
          
      # 规则 4：消息积压
      - alert: MessageBacklog
        expr: rocketmq_group_diff > 100000
        for: 5m
        labels:
          severity: P1
        annotations:
          summary: "RocketMQ 消费积压超过 10 万条"

      # 规则 5：Redis 命中率低
      - alert: RedisHitRateLow
        expr: |
          rate(redis_keyspace_hits_total[5m]) / 
          (rate(redis_keyspace_hits_total[5m]) + 
           rate(redis_keyspace_misses_total[5m])) < 0.90
        for: 10m
        labels:
          severity: P1
```

### 告警分级和通知策略

| 级别 | 通知方式 | 响应时间 | 升级策略 |
|------|---------|---------|---------|
| P0 | 电话 + 企业微信 + 短信 | 5 分钟内 | 10 分钟无响应 → 通知 Leader → 20 分钟 → 通知总监 |
| P1 | 企业微信 + 邮件 | 30 分钟内 | 1 小时无响应 → 通知 Leader |
| P2 | 企业微信 | 工作时间（4 小时）| 下一个工作日 |
| P3 | 邮件 | 可延后 | 周报汇总 |

## 4.2 告警抑制与静默

告警太多 = 狼来了 = 没人看了。必须设计抑制规则。

```yaml
# AlertManager 告警抑制规则
inhibit_rules:
  # 规则 1：节点级别的告警抑制应用级别告警
  # 如果整个节点挂了，就别发"该节点上的服务异常"了
  - source_match:
      alertname: NodeDown
    target_match_re:
      alertname: "Service.*"
    equal:
      - instance

  # 规则 2：集群级别告警抑制单实例告警
  # 如果整个 Redis Cluster 不可用，就别为每个 Redis 实例发告警了
  - source_match:
      alertname: RedisClusterDown
    target_match:
      alertname: RedisInstanceDown
```

### 静默窗口

```
计划维护窗口：每周四凌晨 2:00-4:00 → 自动静默所有告警
大促活动：活动期间 → 提高告警阈值（QPS × 3 是正常的）
```

## 4.3 排错 Runbook 设计

告警响了但不知道怎么做 = 白搭。每条告警必须绑定 Runbook。

### Runbook 模板：出价成功率下降

```
┌── Runbook: 出价成功率下降 ──────────────────────────┐
│                                                       │
│ 触发条件：bid_success_rate < 99%，持续 1 分钟          │
│                                                       │
│ Step 1: 确认故障范围（30 秒）                          │
│   □ Grafana → 出价成功率面板 → 是所有拍卖品还是个别？  │
│   □ 如果是某个拍卖品 → 可能是该拍卖品 Redis 热点       │
│   □ 如果是全局 → 继续 Step 2                          │
│                                                       │
│ Step 2: 检查 Redis（1 分钟）                           │
│   □ Redis CPU 是否 > 80%？                            │
│   □ Redis 连接数是否接近上限？                         │
│   □ Lua 脚本是否有报错？                               │
│   □ 关键操作：redis-cli PING → 检查延迟               │
│                                                       │
│ Step 3: 检查下游依赖（1 分钟）                         │
│   □ MySQL 是否有死锁/慢查询？                          │
│   □ RocketMQ 是否有积压？                              │
│   □ 网络是否有丢包？                                   │
│                                                       │
│ Step 4: 应急止血（1 分钟）                             │
│   方案 A：如果 Redis CPU 高 → 切换到备集群              │
│   方案 B：如果是 DB 问题 → 开启只读模式 + 限流          │
│   方案 C：如果无法快速恢复 → 降级为"排队出价"模式      │
│                                                       │
│ Step 5: 复盘（故障恢复后）                              │
│   □ 记录时间线：发现 → 响应 → 止血 → 恢复              │
│   □ 根因分析（5 Why）                                  │
│   □ 改进措施 + 责任人 + 完成时间                       │
│                                                       │
│ 相关链接：                                             │
│   Grafana: https://grafana/d/auction-bid-dashboard    │
│   Wiki: https://wiki/bid-architecture                 │
│   Oncall 值班: @oncall-auction (企业微信)              │
└───────────────────────────────────────────────────────┘
```

## 4.4 故障排查的五步法（面试标准答案）

面试官问"线上出了问题你怎么排查"时，用这个框架回答：

```
1. 确认故障范围（30 秒）
   - 只看告警可能会被骗（单一指标波动）
   - 三个信号交叉验证：指标 + 日志 + Trace
   - "出价成功率下降" → 是所有拍卖品还是某一个？

2. 快速止血（1 分钟）
   - 重启？回滚？切流？限流？降级？
   - 有预案执行预案，没预案用最保守的手段
   - "先让系统恢复，再查根因"

3. 定位根因（5 分钟）★ 可观测性发挥作用的地方 ★
   - 指标：出价成功率下降的同时，Redis P99 从 2ms 涨到 50ms
   - Trace：慢请求都卡在 Redis Lua 脚本
   - 日志：搜索慢 Trace 的 TraceId → 发现 Lua 脚本中 ZADD 耗时长
   - 关联变更：有没有最近发布？有没有流量突增？

4. 根治修复（看复杂度）
   - 代码修复 / 配置调整 / 扩容
   - 灰度发布 + 对比监控

5. 复盘总结（事后）
   - 故障时间线、影响范围、MTTR
   - 根本原因（5 Why）
   - 改进的监控、告警、预案
```

## 4.5 竞拍系统常见的 3 类故障排查路径

### 故障 1：出价变慢

```
现象：用户反馈"出价要转圈很久"
指标：出价 P99 从 50ms → 500ms

排查路径：
  1. Grafana → 出价 P99 监控 → 确认异常时间点
  2. SkyWalking → 搜索该时段慢 Trace → 发现瓶颈在 Redis Lua
  3. 选择一条 Trace → 复制 TraceId
  4. Kibana → 搜索 TraceId → 发现日志 "Redis Lua script execution: 480ms"
  5. Redis 监控 → 发现该拍卖品的 Key 是热点 Key → CPU 单核 100%
  6. 根因：热门拍卖品 Redis 单实例热点
  7. 修复方案：
     a. 紧急：本地缓存拦截低于当前最高价的出价（减少 60% Redis 请求）
     b. 长期：热点 Key 多副本 + 轮询读取
```

### 故障 2：推送延迟飙升

```
现象：车商出价成功后，要等好几秒才看到排行榜更新
指标：推送 P99 > 2 秒

排查路径：
  1. RocketMQ 监控 → 消息积压 50 万条
  2. Consumer 监控 → 消费 TPS 从 5000/s 降到 500/s
  3. Consumer 日志 → MySQL 写入耗时 3s/条
  4. MySQL 监控 → 主库 CPU 90% → 死锁频繁
  5. 根因：出价落库使用了悲观锁，高并发下死锁率飙升
  6. 修复方案：
     a. 紧急：暂停历史数据写入，只保留 Redis 出价数据
     b. 长期：去掉悲观锁，改用 MQ 异步落库 + 乐观锁
```

### 故障 3：Netty 网关频繁重启

```
现象：K8s 监控显示 Netty 网关 Pod 每 10-30 分钟重启一次
告警：OOMKilled

排查路径：
  1. K8s Events → Pod 被 OOMKilled
  2. JVM 监控 → 堆使用率持续增长，Full GC 无法回收
  3. MAT Dump 分析 → 大量 PooledByteBuf 对象未释放
  4. 代码排查 → ChannelHandler 中 writeAndFlush() 后未 release ByteBuf
  5. 根因：Netty ByteBuf 引用计数泄漏
  6. 修复方案：
     a. 所有 writeAndFlush 后调用 ReferenceCountUtil.release()
     b. 开启 Netty 内存泄漏检测：-Dio.netty.leakDetectionLevel=PARANOID
     c. 添加 ByteBuf 泄漏监控指标
```
