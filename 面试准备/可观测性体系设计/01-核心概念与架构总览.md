# 01 — 核心概念与架构总览

---

## 1.1 监控 ≠ 可观测性

面试官如果问你"可观测性和监控有什么区别"，90% 的候选人答不清楚。

### 一句话区分

```
监控（Monitoring）：你知道系统会出什么问题，预设了指标去盯着它。
                    → "告警响了，CPU 超过 90%"

可观测性（Observability）：你不知道系统会出什么问题，但你有能力从
                           外部信号中推断出系统内部状态。
                           → "为什么 CPU 突然高了？让我看 Trace 和日志"
```

### 用竞拍系统举例

| 场景 | 监控能做到的 | 可观测性能做到的 |
|------|------------|----------------|
| CPU 飙高 | 告警通知：CPU > 90% | 关联 Trace → 发现是某个拍卖品的出价 Lua 脚本慢 → 关联日志 → 发现该拍卖品有 5000 人同时在出价 |
| 出价成功率下降 | 告警通知：成功率 < 99% | 链路追踪 → 发现瓶颈在 Redis 连接池耗尽 → 指标下钻 → 根因是某个 CN 节点故障导致连接泄漏 |
| 用户投诉"卡" | 不知道 | 用户 ID → 查 Trace → 发现他的 WebSocket 连接反复断开重连 → 看那台 Netty 节点的 GC 日志 → 发现 Full GC 频繁 |

### 核心洞察

> 监控告诉你"出事了"，可观测性告诉你"为什么出事"。
> 架构师的价值不是搭一套 Prometheus，而是设计一套**让陌生人能在 5 分钟内定位问题**的信号体系。

## 1.2 三大支柱

```
        ┌─────────────────────────────────────────────┐
        │              可观测性体系                      │
        ├─────────────────┬─────────────────┬─────────┤
        │     Metrics     │    Logging      │ Tracing │
        │     (指标)       │    (日志)        │ (链路)   │
        ├─────────────────┼─────────────────┼─────────┤
        │ "有什么异常？"    │ "异常的具体细节？"│ "在哪一环出的问题？"│
        │ CPU/内存/QPS/RT  │ 错误堆栈/请求参数 │ 调用链/耗时分布   │
        │ 聚合的、可告警    │ 详细的、可检索    │ 关联的、可下钻    │
        └─────────────────┴─────────────────┴─────────┘
                         ▲         ▲         ▲
                         └─────────┼─────────┘
                                   │
                          TraceId 串联三者
```

### Metrics（指标）

**是什么**：一段时间内聚合的数值。CPU 使用率、QPS、P99 延迟。

**特点**：
- 聚合的（不是单次请求）
- 占用空间小（一个时间序列点只需几个字节）
- 可以低成本存储很长时间（如保留 1 年）
- 适合做告警和趋势分析

**竞拍系统关键指标**：
```
出价 QPS、出价 P99 延迟、推送 P99 延迟
Redis Lua 执行时间、Netty 连接数、GC 次数
```

### Logging（日志）

**是什么**：离散的事件记录。每次出价的详细信息、错误堆栈。

**特点**：
- 每条日志是独立的（但可以通过 TraceId 关联）
- 占用空间大（需要索引和存储策略）
- 适合做详细排查（"这个出价为什么失败了？"）

**竞拍系统关键日志**：
```
出价请求日志（用户 ID、拍卖品 ID、出价金额、TraceId）
异常日志（完整堆栈 + 上下文）
慢查询日志（SQL + 耗时 + 执行计划）
```

### Tracing（链路追踪）

**是什么**：一次请求在分布式系统中经过的所有服务的调用链。

**特点**：
- 串联多个服务的日志和指标
- 可以发现性能瓶颈在哪个服务/方法
- 需要代码埋点或 Agent 自动注入

**竞拍系统一条 Trace**：
```
车商 App WebSocket 请求
  → Netty 网关(耗时 5ms)
    → 出价服务(耗时 2ms)
      → Redis Lua 出价引擎(耗时 15ms)
      → RocketMQ 发送事件(耗时 3ms)
    → 推送服务(耗时 8ms)
      → Netty 网关推送(耗时 2ms)
  → 总耗时: 35ms
```

## 1.3 可观测性的四个层次

作为架构师，你的指标体系要有分层思维：

```
第四层：业务指标（Business）
  "这个拍卖品有多少人出价？转化率是多少？"
  受众：产品经理、运营、老板
  例子：出价成功率、平均出价次数/人、拍卖成交率

第三层：应用指标（Application）
  "出价接口的 QPS 和延迟是多少？"
  受众：开发人员、架构师
  例子：接口 QPS、P99 延迟、错误率、TPS

第二层：中间件指标（Middleware）
  "Redis 的命中率？RocketMQ 的积压量？"
  受众：开发人员、DBA、SRE
  例子：Redis 缓存命中率、MQ 消费延迟、DB 连接池活跃数

第一层：基础设施指标（Infrastructure）
  "CPU、内存、磁盘、网络使用情况"
  受众：运维、SRE
  例子：CPU 使用率、内存使用率、磁盘 IO、网络流量
```

**面试重点**：架构师不仅关心下面两层（谁都会），更关心上面两层——**业务指标怎么定义、怎么让业务方看得懂**。

### 组件选型

| 层级 | 组件 | 竞拍系统选择 | 理由 |
|------|------|------------|------|
| 采集 | 链路追踪 | **SkyWalking Agent** | Java 无侵入，自动支持 Dubbo/Spring Cloud/Redis/MQ |
| 采集 | 指标暴露 | **Prometheus JMX Exporter** | JMX → Prometheus 标准格式，零代码改造 |
| 采集 | 业务指标 | **Micrometer** | Spring Boot 原生集成，统一指标 API |
| 采集 | 日志采集 | **Filebeat** | 轻量级，解析 Spring Boot JSON 日志 |
| 管道 | 日志缓冲 | **Kafka** | 消峰填谷，解耦采集端和存储端 |
| 存储 | 指标 | **Prometheus TSDB** | 时序数据原生存储，查询语言灵活 |
| 存储 | 日志 | **Elasticsearch** | 全文检索，配合 Kibana 可视化 |
| 存储 | 链路 | **Elasticsearch**（SkyWalking 后端） | 和日志统一存储 |
| 展示 | 统一看板 | **Grafana** | 一个平台展示 Prometheus + ES 数据 |
| 展示 | 链路 UI | **SkyWalking UI** | 开箱即用的拓扑图和调用链 |
| 告警 | 告警管理 | **AlertManager** | 告警分组、抑制、静默、多通道路由 |

### 为什么这样选？

面试时会被问到"为什么选 SkyWalking 而不是 Jaeger/Zipkin？"

| 维度 | SkyWalking | Jaeger | Zipkin |
|------|-----------|--------|--------|
| Java 无侵入 | ★★★★★ Agent 自动 | ★★ 需要 SDK | ★★★ 需要 Brave |
| Dubbo 支持 | ★★★★★ 原生 | ★★ | ★★ |
| 性能开销 | 低（字节码增强） | 中 | 中 |
| 指标集成 | 内置 | 需要外部 | 需要外部 |
| 社区 | Apache 顶级 | CNCF | CNCF |

选 SkyWalking 的核心原因：Java Agent 无侵入 + Dubbo 原生支持（竞拍系统的核心 RPC 是 Dubbo）。

## 1.5 可观测性的成本意识（架构师必答）

面试官到一定级别会问成本。你不能只报工具名，还得算账。

```
竞拍系统日请求量：500 万次出价 + 1000 万次查询 = 1500 万次请求

指标数据：
  1000 个时间序列 × 每 15s 一个点 × 一天 5760 个点 × 8B ≈ 46MB/天
  → 1 年约 17GB（极低成本）

链路数据：
  1500 万次 × 全量采样 × 每条 Trace 约 2KB ≈ 30GB/天
  → 1 年约 11TB（成本高！）
  → 方案：全量采样太贵，用 10% 采样率 → 3GB/天 → 1 年约 1TB

日志数据：
  1500 万次 × 5 条日志/次 × 200B ≈ 15GB/天（压缩前）
  → ES + 压缩 → 实际约 3GB/天
  → 保留策略：ES 热数据 7 天 + S3 冷数据 90 天

总存储成本（估算）：
  指标：17GB × $0.1/GB ≈ $2/年
  链路：1TB × $0.5/GB(Hot ES) ≈ $500/年
  日志：ES 1TB(Hot) × $0.5/GB + S3 10TB(Cold) × $0.02/GB ≈ $700/年
  ≈ $1200/年（合理）
```

> **面试加分话术**："全量 Trace 太贵，我们用 10% 自适应采样——正常请求 10%，错误请求 100% 采样。这样故障排查时从不缺数据，日常监控成本又可控。"

## 1.6 可观测性设计的三大原则

作为架构师，设计可观测性体系时遵循这三个原则：

### 原则 1：信号先行于故障

```java
// 不好的代码：出错了才记录
try {
    placeBid(request);
} catch (Exception e) {
    log.error("出价失败", e);  // 只有失败才记录
}

// 好的代码：正常流也埋点，出问题时有 baseline 对比
@Timed(value = "bid.place", extraTags = {"auction", "region"})
public BidResult placeBid(BidRequest request) {
    long start = System.nanoTime();
    try {
        BidResult result = doBid(request);
        meterRegistry.counter("bid.success").increment();
        return result;
    } catch (Exception e) {
        meterRegistry.counter("bid.failure", "reason", e.getClass().getSimpleName()).increment();
        throw e;
    } finally {
        timer.record(System.nanoTime() - start, TimeUnit.NANOSECONDS);
    }
}
```

### 原则 2：三个支柱必须能串联

孤立的数据价值有限。TraceId 是串联三者（Metrics / Logging / Tracing）的钥匙。

```
排查路径示例：
1. Grafana 看到 bid.success 指标下降 
2. 下钻到具体时间点 → 找到异常的 TraceId
3. 在 SkyWalking 中搜索这个 TraceId → 看到调用链慢在哪
4. 在 Kibana 中搜索这个 TraceId → 看到完整的请求日志和错误栈
5. 定位根因 → 修复
```

### 原则 3：成本与故障恢复时间（MTTR）成正比

可观测性也是一种投资。需要计算 ROI：
- 没有这套体系时，故障平均恢复时间（MTTR）= 30 分钟
- 有了这套体系后，MTTR = 5 分钟
- 竞拍系统每分钟交易额 = 10 万元
- 每次故障节省 = 25 分钟 × 10 万 = 250 万
- 可观测性年度成本 = 1200 美元（约 1 万人民币）
- **ROI = 250 万 / 1 万 = 250 倍**

> **面试话术**："我知道这套体系要花钱。但竞拍系统一旦出问题，每多停一分钟就是十万级别的损失。算清楚这笔账后，老板从来没在可观测性预算上卡过我。"
