# 02 — 指标体系设计

> 指标不是越多越好。架构师的核心能力是：**知道该度量什么，知道什么程度该告警**。

---

## 2.1 指标设计的 USE 和 RED 方法

### USE 方法论（面向资源）

原始由 Brendan Gregg 提出，适合基础设施和中间件：

| 维度 | 含义 | 竞拍 Redis 示例 |
|------|------|----------------|
| **U**tilization | 利用率 | Redis CPU 利用率 70% |
| **S**aturation | 饱和度 | Redis 连接队列等待数 |
| **E**rrors | 错误数 | Redis 连接超时次数 |

### RED 方法论（面向服务）

源自 Google 的四个黄金信号，适合应用层：

| 维度 | 含义 | 竞拍 API 示例 |
|------|------|-------------|
| **R**ate | 请求速率 | 出价接口 QPS = 8000 |
| **E**rrors | 错误率 | 出价失败率 = 0.1% |
| **D**uration | 延迟 | 出价 P99 = 75ms |

**面试要点**：讲完理论立刻带出实践——"我们出价接口用 RED，Redis 用 USE，两个方法互补。"

### 第三层：应用指标（重点）

这是业务开发最关心的，也是面试最容易出彩的：

```java
// Metric 1: 出价接口核心指标（RED 方法论）
@RestController
public class BidController {
    
    private final MeterRegistry registry;
    private final Timer bidTimer;
    private final Counter successCounter;
    private final Counter failureCounter;
    
    public BidController(MeterRegistry registry) {
        this.registry = registry;
        this.bidTimer = Timer.builder("bid.request.duration")
            .description("出价请求耗时")
            .publishPercentiles(0.5, 0.95, 0.99)      // P50/P95/P99
            .sla(Duration.ofMillis(50), Duration.ofMillis(100)) // 满足 SLA 的比例
            .register(registry);
        this.successCounter = Counter.builder("bid.request.total")
            .tag("result", "success")
            .register(registry);
        this.failureCounter = Counter.builder("bid.request.total")
            .tag("result", "failure")
            .register(registry);
    }
    
    @PostMapping("/bid")
    public BidResult placeBid(@RequestBody BidRequest request) {
        return bidTimer.record(() -> {
            BidResult result = bidService.placeBid(request);
            if (result.isSuccess()) {
                successCounter.increment();
            } else {
                failureCounter.increment();
            }
            return result;
        });
    }
}
```

### 第四层：业务指标（面试亮点的核心）

**大多数候选人止步于第三层，你讲到第四层立刻脱颖而出**。

```java
// 业务指标：不是技术指标，是业务方看得懂的指标
public class BusinessMetrics {
    
    // 业务指标 1：实时出价成功率（按拍卖品维度）
    private final MeterRegistry registry;
    
    public void recordBid(Long auctionId, boolean isSuccess, Long amount) {
        // Tag 加 auctionId 可以按拍卖品下钻
        registry.counter("business.bid.result",
            "auction_id", String.valueOf(auctionId),
            "result", isSuccess ? "success" : "fail"
        ).increment();
        
        // 出价金额分布
        registry.summary("business.bid.amount").record(amount);
    }
    
    // 业务指标 2：Top10 排行榜计算耗时
    public void recordTop10Calculation(Long auctionId, long durationMs) {
        registry.timer("business.top10.calc.time",
            "auction_id", String.valueOf(auctionId)
        ).record(durationMs, TimeUnit.MILLISECONDS);
    }
    
    // 业务指标 3：推送延迟（出价成功 → 车商收到通知）
    public void recordPushLatency(Long auctionId, long latencyMs) {
        registry.timer("business.push.latency",
            "auction_id", String.valueOf(auctionId)
        ).record(latencyMs, TimeUnit.MILLISECONDS);
    }
    
    // 业务指标 4：在线车商数
    public void recordOnlineBidders(int count) {
        registry.gauge("business.online.bidders", count);
    }
    
    // 业务指标 5：拍卖间热门程度
    public void recordAuctionRoomSize(Long auctionId, int bidders) {
        registry.gauge("business.auction.room.size",
            List.of(Tag.of("auction_id", String.valueOf(auctionId))),
            bidders);
    }
}
```

## 2.3 SLI / SLO / SLA 设计

这是架构师的必修课，面试必问。

### 概念定义

```
SLI (Service Level Indicator)：服务水平的量化指标
  → "出价接口的 P99 延迟是多少？"
  → 这是一个客观测量值，不带承诺

SLO (Service Level Objective)：SLI 的目标值
  → "出价接口的 P99 延迟不能超过 100ms"
  → 这是团队对内的承诺，做不到要优化

SLA (Service Level Agreement)：基于 SLO 的商业承诺
  → "如果出价接口的 P99 超过 100ms 超过 30 分钟，赔偿用户 100 元代金券"
  → 这是对外（客户/用户）的法律承诺，做不到要赔钱
```

### 竞拍系统的 SLO 设计

| SLI | SLO | 测量窗口 | 为什么定这个值 |
|-----|-----|---------|--------------|
| 出价请求成功率 | > 99.9% | 30 天 | 竞拍是交易核心，失败 = 丢了客户的钱 |
| 出价 P99 延迟 | < 100ms | 30 天 | 车商出价感觉不到延迟的阈值 |
| 推送 P99 延迟 | < 200ms | 30 天 | 比出价略放宽，因为推送涉及多节点广播 |
| 服务可用性 | > 99.99% | 季度 | 全年停机 < 53 分钟 |
| Redis 命中率 | > 95% | 7 天 | 低于这个值说明缓存策略需要优化 |

### SLO 的 Error Budget（错误预算）

```
SLO：出价成功率 > 99.9%
含义：每月允许失败 0.1% 的请求
每月总出价：5000 万次
错误预算：5000 万 × 0.1% = 5 万次失败

用法：
  - 错误预算剩余 80% → 可以按计划发布新版本
  - 错误预算剩余 50% → 谨慎发布，加强预发验证
  - 错误预算剩余 20% → 冻结发布，全力排查和修复
  - 错误预算用完     → 停止所有非紧急发布，oncall 全员排查
```

**面试话术**：
> "SLO 不只是运维的事。我们用 Error Budget 来决定发布节奏——预算充足就大胆迭代，预算紧张就保守。这样运维和开发不再对立，大家都看同一个数字做决策。"

## 2.4 指标设计的常见误区

### 误区 1：只用平均值

```
P50（中位数）比平均值更能代表"典型用户体验"
P99 代表"最差 1% 用户的体验"
平均值会被少数极慢请求拉高，掩盖真实问题

真实案例：竞拍出价接口
  平均延迟：45ms（看起来不错）
  P50：15ms（大部分用户很快）
  P99：350ms（1% 的用户等了 350ms！）
  → 如果只看平均值，永远发现不了 P99 的问题
```

### 误区 2：指标粒度太粗

```
错误率 = 1%  → 看起来还好
但如果只看"总接口错误率 1%"，看不到：
  - /bid/place 接口错误率 20%（某个拍卖品一直在报错）
  - /bid/query 接口错误率 0.01%
  → 必须按接口、按 Tag 下钻
```

### 误区 3：指标没有和业务关联

```
技术指标：CPU 90%
业务方：这是什么？严重吗？

更好的做法：
  技术指标：CPU 90%
  → 关联指标：出价 P99 从 50ms 涨到 200ms
  → 业务影响：出价成功率从 99.9% 降到 98%
  → 老板一眼看懂："哦，有 1%+ 的车商出价会失败"
```

## 2.5 面试准备：指标体系设计三步法

面试官问"你怎么设计监控体系"时，用这三步回答：

```
第一步：分层
  "我设计四层指标：基础设施 → 中间件 → 应用 → 业务"

第二步：每层只选 3-5 个核心指标
  "不是越多越好。出价接口我只关注 3 个：QPS、成功率、P99 延迟"

第三步：关联
  "每层的指标要能下钻。看到业务指标异常，能一路下钻到基础设施"
```
