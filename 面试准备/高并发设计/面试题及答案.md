## 1. Netty 的线程模型是怎样的？主从 Reactor 如何工作？

**面试官考察点**：对 Netty 核心机制的深入理解。

**参考答案**：

**Netty 主从 Reactor 线程模型**：

```
┌─────────────────────────────────────────┐
│              Boss Group                   │
│  ┌─────────┐  ┌─────────┐               │
│  │Reactor 1│  │Reactor 2│  ...           │
│  └────┬─────┘  └────┬─────┘               │
│       │ 监听端口     │ 接收连接             │
│       └──────┬──────┘                     │
│              ▼                            │
│  ┌─────────────────────────────────────┐ │
│  │          Worker Group               │ │
│  │  ┌──────┐ ┌──────┐ ┌──────┐        │ │
│  │  │Reactor│ │Reactor│ │Reactor│ ...   │ │
│  │  │  3    │ │  4    │ │  5    │        │ │
│  │  └──┬───┘ └──┬───┘ └──┬───┘        │ │
│  │     │ 读/写   │ 编解码  │ 业务处理      │ │
│  └─────┴────────┴────────┴─────────────┘ │
└─────────────────────────────────────────┘
```

**职责划分**：
- **Boss Group**：只负责接收 TCP 连接，然后将连接注册到 Worker Group
- **Worker Group**：负责已建立连接的 IO 读写和业务处理
- **EventLoop**：每个 Reactor 线程是一个 EventLoop，绑定一个 Selector，处理绑定在其上的所有 Channel 的 IO 事件

**竞拍系统的 Netty 配置**：
```java
EventLoopGroup bossGroup = new NioEventLoopGroup(2);    // Boss 线程数 = CPU 核数
EventLoopGroup workerGroup = new NioEventLoopGroup(16); // Worker 线程数 = CPU 核数 * 2

ServerBootstrap bootstrap = new ServerBootstrap();
bootstrap.group(bossGroup, workerGroup)
    .channel(NioServerSocketChannel.class)
    .option(ChannelOption.SO_BACKLOG, 1024)          // 全连接队列大小
    .childOption(ChannelOption.SO_KEEPALIVE, true)   // TCP 保活
    .childOption(ChannelOption.TCP_NODELAY, true)    // 禁用 Nagle 算法（低延迟）
    .childHandler(new ChannelInitializer<SocketChannel>() {
        @Override
        protected void initChannel(SocketChannel ch) {
            ch.pipeline()
                .addLast(new ProtobufVarint32FrameDecoder())
                .addLast(new ProtobufDecoder(BidMessage.getDefaultInstance()))
                .addLast(new IdleStateHandler(60, 0, 0))      // 60s 读空闲检测
                .addLast(new BidServerHandler());
        }
    });
```

**关键要点**：
- Boss Group 一般 1-2 个线程就够了（端口数量有限）
- Worker Group 线程数 = CPU 核数 * 2，每个线程一个 Selector
- 不要在执行过程中阻塞 EventLoop——耗时操作要提交到业务线程池

## 2. Netty 的零拷贝是什么意思？有哪些实现方式？

**面试官考察点**：对零拷贝技术栈的深度理解。

**参考答案**：

**Netty 中的"零拷贝"有三层含义**：

**第一层：OS 层面的零拷贝**
```java
// FileRegion：直接将文件数据发送到 Socket，不经过用户空间
FileRegion region = new DefaultFileRegion(fileChannel, 0, file.length());
ctx.writeAndFlush(region);

// 原理：sendfile() 系统调用 → DMA 拷贝，绕过用户空间
```

**第二层：Netty 内部的零拷贝**
```java
// CompositeByteBuf：将多个 ByteBuf 合并，不实际复制数据
CompositeByteBuf composite = Unpooled.compositeBuffer();
composite.addComponent(headerBuf);   // 只添加引用
composite.addComponent(bodyBuf);     // 不复制数据

// Unpooled.wrappedBuffer：包装现有 Buffer，零复制
ByteBuf wrapped = Unpooled.wrappedBuffer(buf1, buf2);
```

**第三层：应用层面的零拷贝**
- 使用 `Unpooled.directBuffer()` 分配直接内存，避免堆内存和直接内存之间的复制
- 使用 `retain()` 来共享 ByteBuf

**传统 IO vs 零拷贝**：
```
传统 IO 路径（4次拷贝，4次上下文切换）：
磁盘 → 内核缓冲区 → 用户缓冲区 → Socket 缓冲区 → 网卡

零拷贝 sendfile() 路径（2次拷贝，2次上下文切换）：
磁盘 → 内核缓冲区 → Socket 缓冲区（DMA）→ 网卡
```

**关键要点**：
- 不要把 Netty 的 CompositeByteBuf 和 Linux 的 sendfile 混为一谈
- 直接内存（Direct Buffer）不是零拷贝，而是避免了堆内到堆外的拷贝

## 3. 如何优化 Netty 以支撑 10 万+ 长连接？

### 实战案例：竞拍系统网关优化

**面试官考察点**：高并发连接场景的实际优化能力。

**参考答案**：

**单机 10 万连接面临的挑战和解决方案**：

**1. 文件描述符限制**
```bash
# /etc/security/limits.conf
* soft nofile 655350
* hard nofile 655350

# /etc/sysctl.conf
fs.file-max = 1000000
```

**2. TCP/IP 协议栈参数调优**
```bash
# /etc/sysctl.conf
net.ipv4.ip_local_port_range = 1024 65535    # 扩大本地端口范围
net.ipv4.tcp_tw_reuse = 1                     # TIME_WAIT 端口复用
net.ipv4.tcp_fin_timeout = 30                 # FIN_WAIT 超时
net.core.somaxconn = 65535                    # 全连接队列大小
net.ipv4.tcp_max_syn_backlog = 65535          # 半连接队列大小

# 内存相关
net.ipv4.tcp_mem = 786432 1048576 1572864
net.ipv4.tcp_rmem = 4096 87380 33554432       # 读缓冲区
net.ipv4.tcp_wmem = 4096 65536 33554432       # 写缓冲区
```

**3. Netty 高低水位线**（防止写缓冲区 OOM）
```java
ServerBootstrap bootstrap = new ServerBootstrap();
// 低水位线：写缓冲区低于此值，恢复可写状态
bootstrap.childOption(ChannelOption.WRITE_BUFFER_WATER_MARK,
    new WriteBufferWaterMark(32 * 1024, 64 * 1024));  // 低:32KB, 高:64KB

// Channel 不可写时，暂停写入避免 OOM
public void channelWritabilityChanged(ChannelHandlerContext ctx) {
    if (ctx.channel().isWritable()) {
        // 恢复消息推送
        resumePush(ctx.channel());
    } else {
        // 暂停消息推送，消息放入队列
        pausePush(ctx.channel());
    }
}
```

**4. 心跳保活与空闲检测**
```java
// 服务端：60s 没有读到数据 → 心跳超时
pipeline.addLast(new IdleStateHandler(60, 0, 0));

// 客户端：30s 发送一次心跳
ctx.writeAndFlush(HeartbeatMessage.getDefaultInstance());
ctx.executor().schedule(() -> sendHeartbeat(ctx), 30, TimeUnit.SECONDS);
```

**5. 内存控制**
```bash
# JVM 参数
-Xms8g -Xmx8g
-XX:MaxDirectMemorySize=4g     # 直接内存（Netty 主要使用直接内存）
-XX:+UseG1GC
```

**效果对比**：
| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| 单机最大连接 | 5000 | 50000+ |
| 连接内存占用 | ~4KB/连接 | ~1KB/连接 |
| GC 频率 | ~20次/min | ~3次/min |
| 连接成功率 | 95% | 99.95% |

## 4. Protobuf vs JSON vs Hessian 序列化选型？

**面试官考察点**：序列化方案的选型能力。

**参考答案**：

| 维度 | Protobuf | JSON | Hessian | Kryo |
|------|----------|------|---------|------|
| 序列化体积 | ★★★★★（最小） | ★★（最大） | ★★★★ | ★★★★ |
| 序列化速度 | ★★★★★（最快） | ★★（最慢） | ★★★ | ★★★★★ |
| 可读性 | ★（二进制） | ★★★★★ | ★（二进制） | ★ |
| 跨语言 | ★★★★★ | ★★★★★ | ★★ | ★★ |
| Schema 演进 | ★★★★★ | ★★ | ★★★ | ★★ |

**竞拍系统的选型**：

```
外部 API → JSON（可读性、调试友好）
内部 RPC → Protobuf（性能最优）
WebSocket 推送 → Protobuf（体积最小，降低网络带宽）
文件存储 → Protobuf（配合 Delta Encoding 极致压缩）
```

**Protobuf 最佳实践**：
```protobuf
syntax = "proto3";

message BidMessage {
    int64 auction_id = 1;
    int64 bidder_id = 2;
    int64 amount = 3;          // 出价金额（分）
    int64 delta_amount = 4;    // 与上次出价的差值（Delta Encoding）
    int64 timestamp = 5;
}
```

**关键要点**：
- 没有最好的序列化方案，只有最适合场景的
- Protobuf 的 Schema 演进（向后兼容）是核心优势

## 5. Delta Encoding（差值传递法）如何节省 80% 带宽？

### 实战案例：竞拍系统推送优化

**面试官考察点**：自定义协议的优化能力。

**参考答案**：

**问题**：竞拍场景中，服务器需要高频率推送"当前最高价"给所有在线车商。每次推送完整的出价信息（出价人、金额、时间等），在 10 万连接下带宽消耗巨大。

**Delta Encoding 原理**：
```
第一次推送：价格 100,000 元 → 传输完整数据（4 字节 int）
第二次推送：价格 100,500 元 → 只传差值 +500（1 字节）
第三次推送：价格 101,500 元 → 只传差值 +1000（2 字节）
...
```

**竞拍场景的数据特征**：
- 出价金额每次都增加（最小加价幅度固定）
- 90% 的出价差值在 ±255 以内（1 字节）
- 出价人变更相对少（Delta 不适用）

**Protobuf + Delta Encoding 实现**：
```java
public class DeltaEncoder {
    private long lastAmount = 0;
    
    public BidMessage encode(Bid current) {
        long delta = current.getAmount() - lastAmount;
        this.lastAmount = current.getAmount();
        
        return BidMessage.newBuilder()
            .setAuctionId(current.getAuctionId())
            .setDeltaAmount(delta)      // 差值，非完整值
            .setTimestamp(current.getTimestamp())
            .build();
    }
}

public class DeltaDecoder {
    private long lastAmount;
    
    public long decode(BidMessage msg) {
        if (msg.hasAbsoluteAmount()) {
            // 首条消息：完整值
            lastAmount = msg.getAbsoluteAmount();
        } else {
            // 后续消息：差值 + 基准值
            lastAmount += msg.getDeltaAmount();
        }
        return lastAmount;
    }
}
```

**效果对比**：
| 推送方式 | 单条消息体积 | 10万连接带宽 | 
|---------|------------|------------|
| JSON 完整 | ~200 bytes | 20 MB/次 |
| Protobuf 完整 | ~50 bytes | 5 MB/次 |
| Protobuf + Delta | ~8 bytes（平均值）| 0.8 MB/次 |

**带宽节省 = 80%**

**关键要点**：
- Delta Encoding 适合"递增"场景（出价递增、库存递减）
- 需要定期发送"全量同步"消息用于校验和断线重连

## 6. "发布-订阅"与"精准路由"结合的混合推送模式

### 实战案例：竞拍系统通知推送

**面试官考察点**：复杂消息推送架构的设计能力。

**参考答案**：

**问题**：竞拍中，车辆价格变化需要通知关注该车辆的车商。如果广播给所有服务器 × 所有车商，复杂度 O(n²)。

**方案一：纯广播（低效）**
```
出价事件 → RocketMQ 广播 → 所有 Netty 节点 → 各节点遍历所有连接 → 判断是否关注 → 推送
问题：10 个节点 × 10 万连接 = 100 万次判断，大量无效 CPU 消耗
```

**方案二：精确路由（低效）**
```
出价事件 → 按车辆 ID 发到唯一节点 → 该节点推送给关注车辆的车商
问题：该节点成为热点，负载不均
```

**方案三：混合模式（竞拍系统方案）**
```
出价事件 → RocketMQ 主题广播 → 所有 Netty 节点收到
    → 各节点根据 ZK 中的"车辆→服务器"映射表判断：
        - 如果本节点有该车辆的车商 → 查询 Redis 获取关注列表 → 精准推送
        - 如果本节点没有 → 丢弃消息
        
时间复杂度：O(节点数 × 该车辆在本节点的关注人数)
```

**实现细节**：
```java
public void onBidEvent(BidEvent event) {
    Long auctionId = event.getAuctionId();
    
    // 1. 从本地缓存获取该车辆在本节点的关注列表
    Set<Long> localFollowers = localFollowerCache.get(auctionId);
    if (localFollowers == null || localFollowers.isEmpty()) {
        return;  // 本节点无关注者，直接丢弃
    }
    
    // 2. 从 Redis 获取最新出价榜 Top10
    List<BidInfo> top10 = redis.zRevRange("bid:rank:" + auctionId, 0, 9);
    
    // 3. 编码推送消息
    BidPushMessage msg = deltaEncode(top10);
    
    // 4. 精准推送给关注者
    for (Long followerId : localFollowers) {
        Channel channel = channelRegistry.get(followerId);
        if (channel != null && channel.isActive()) {
            channel.writeAndFlush(msg);
        }
    }
}
```

**效果**：峰值推送 QPS 提升 10 倍，通知延迟从 800ms 降到 150ms。

## 7. Linux 内核参数调优：你改过哪些关键参数？

**面试官考察点**：操作系统层面的性能调优经验。

**参考答案**：

```bash
# ===== TCP 连接相关 =====
# 全连接队列（ESTABLISHED 但未被 accept 的连接）
net.core.somaxconn = 65535

# 半连接队列（SYN_RECV 状态的连接）
net.ipv4.tcp_max_syn_backlog = 65535

# SYN Cookie：防 SYN Flood 攻击
net.ipv4.tcp_syncookies = 1

# TIME_WAIT 端口复用（客户端）
net.ipv4.tcp_tw_reuse = 1

# 快速回收 TIME_WAIT（不推荐在高并发服务端开启）
# net.ipv4.tcp_tw_recycle = 0

# ===== 缓冲区相关 =====
# TCP 读缓冲区（最小/默认/最大）
net.ipv4.tcp_rmem = 4096 87380 33554432

# TCP 写缓冲区
net.ipv4.tcp_wmem = 4096 65536 33554432

# ===== KeepAlive 相关 =====
net.ipv4.tcp_keepalive_time = 600     # 空闲 10 分钟后开始探测
net.ipv4.tcp_keepalive_intvl = 30     # 探测间隔 30 秒
net.ipv4.tcp_keepalive_probes = 3     # 最多 3 次探测

# ===== 文件描述符 =====
fs.file-max = 1000000
fs.nr_open = 1000000

# ===== 内存相关 =====
vm.swappiness = 1              # 尽量不用 swap（避免内存换出影响延迟）
vm.max_map_count = 262144     # 最大内存映射数（ES/MMap 需要）
```

**关键要点**：
- `tcp_tw_recycle` 在 NAT 环境下有严重问题（时间戳导致丢包），新内核已移除
- `tcp_tw_reuse` 只对客户端（发起连接方）生效
- `somaxconn` 必须和应用的 backlog 配合：`Nginx(backlog=65535) + somaxconn(65535)`

## 8. 系统容量评估怎么做？

**面试官考察点**：架构师的容量规划能力。

**参考答案**：

**容量评估四步法**：

```
1. 业务指标预估
   ├── DAU → 转化成 QPS
   ├── 峰值系数（通常 3-5 倍均值）
   └── 增长率（未来 3-6 个月）

2. 单机容量摸底
   ├── 压测：找单机 QPS 上限
   ├── 记录：CPU/Memory/IO 使用率
   └── 定阈值：上线不超过压测 60%

3. 资源计算
   ├── 节点数 = 峰值 QPS / (单机 QPS × 60%)
   ├── 数据库：QPS / (单库 QPS × 50%)
   └── 缓存：QPS / (单 Redis QPS × 50%)

4. 冗余和容灾
   ├── 至少 30% 冗余
   ├── 跨机房 / 跨可用区
   └── 限流熔断兜底
```

**竞拍系统容量评估实例**：
```
已知：
- 日均拍卖 500 场
- 每场峰值 500 人同时出价
- 峰值 QPS = 500 × 500 × 2（出价+查询）= 50 万 QPS
- 考虑冗余 = 50 万 × 1.3 ≈ 65 万 QPS

单机压测：
- Netty 网关：单机 5 万 QPS
- 业务服务：单机 1 万 QPS（含复杂业务逻辑）
- Redis：单实例 10 万 QPS

资源计划：
- 网关：65 万 / 5 万 = 13 节点（+ 冗余 = 16 节点）
- 业务：65 万 / 1 万 = 65 节点（+ 冗余 = 80 节点）
- Redis：65 万 / 10 万 * 0.5 = 13 实例 → 6主6从
```

## 附录：高并发设计速查表

### 性能优化清单

```
□ 网络层：TCP_NODELAY, SO_KEEPALIVE, SO_BACKLOG
□ 序列化：Protobuf（内部）/ JSON（外部 API）
□ 压缩：gzip / snappy / lz4（根据需要）
□ 连接池：HTTP 连接池、数据库连接池、Redis 连接池
□ 线程模型：Netty Reactor 主从、业务线程池隔离
□ 内存控制：高低水位线、直接内存限制
□ 缓冲：批量处理（攒批）、RingBuffer（Disruptor）
□ 异步：CompletableFuture / Reactor / 协程
□ 无锁：CAS / Atomic / LongAdder
□ 缓存：本地（Caffeine） + 远程（Redis）
```

### 延迟优化的层次

```
第一层（最大收益）：减少 IO
    ├── 缓存 → 不查数据库
    ├── 批量 → 减少 IO 次数
    └── 异步 → 不等待 IO

第二层（中等收益）：减少计算
    ├── 预处理 → 用空间换时间
    ├── 并行 → 多线程加速
    └── 算法 → 优化复杂度

第三层（精细优化）：减少开销
    ├── GC 调优 → 减少停顿
    ├── 序列化 → 减少编解码 CPU
    └── 内存 → 减少分配/回收
```
