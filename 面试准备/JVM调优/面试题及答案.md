# JVM 调优面试题及答案

> 本套面试题针对架构师岗位，结合高并发竞拍系统的实战场景，覆盖 JVM 内存模型、GC 调优、故障排查等核心领域。

---

## 1. 请描述 JVM 运行时数据区，以及各区域可能出现的 OOM

**面试官考察点**：是否真正理解各内存区域的作用和故障模式，而非机械背诵。

**参考答案**：

JVM 运行时数据区分为线程共享和线程私有两大块：

**线程共享区域：**
- **堆（Heap）**：存放对象实例和数组。OOM 表现为 `java.lang.OutOfMemoryError: Java heap space`，常见原因：内存泄漏（如 ThreadLocal 未清理）、大对象分配、GC 跟不上分配速度。
- **元空间（Metaspace，JDK8+）**：存放类元数据。OOM 表现为 `OutOfMemoryError: Metaspace`，常见原因：动态代理/CGLIB 生成大量类、Groovy 脚本热加载未限制、`-XX:MaxMetaspaceSize` 设置过小。

**线程私有区域：**
- **程序计数器（PC Register）**：指向当前线程执行的字节码行号，唯一不会 OOM 的区域。
- **虚拟机栈（VM Stack）**：每个方法执行时创建栈帧。异常表现为 `StackOverflowError`（递归过深）或 `OOM: unable to create new native thread`（线程数过多，每个线程占用约 1MB 栈空间）。
- **本地方法栈（Native Method Stack）**：与虚拟机栈类似，为 Native 方法服务。

**直接内存（非运行时数据区但同样重要）：**
- NIO 的 DirectByteBuffer 分配的堆外内存。OOM 表现为 `OutOfMemoryError: Direct buffer memory`，需要关注 `-XX:MaxDirectMemorySize`。

**关键要点**：
- 说清楚 "OOM 不只是堆内存满了"——Metaspace、直接内存、线程栈都可能 OOM
- 每种 OOM 要说得出典型场景和排查思路

## 2. CMS 和 G1 的对比，什么场景选哪个？

**面试官考察点**：GC 选型能力，是否理解不同 GC 的适用边界。

**参考答案**：

| 维度 | CMS | G1 |
|------|-----|-----|
| 内存模型 | 分代（Young/Old 物理隔离） | 分区（Region，逻辑分代） |
| 回收算法 | 标记-清除（产生碎片） | 标记-整理 + 复制（无碎片） |
| 停顿时间 | 目标低停顿，但 Full GC 时单线程，STW 长 | 可控停顿，`-XX:MaxGCPauseMillis` 设置目标 |
| Full GC 触发 | 碎片化导致 Concurrent Mode Failure → 回退 Serial Old | Mixed GC 先尝试回收，失败才 Full GC |
| 适用堆大小 | 4-8G 以下 | 4G 以上，特别是 8G-64G |
| 可预测性 | 差，容易出现"长停顿" | 好，停顿基本可控 |
| 内存占用 | 较少 | 较多（Remembered Set 占用约 5% 堆） |

**选型建议**：
- **CMS**：JDK8 及以下、堆 < 4G、对吞吐量要求高于延迟、老系统维护
- **G1**：JDK8u40+/JDK11+、堆 > 4G、对 P99 延迟有要求（如在线服务）
- **ZGC/Shenandoah**：JDK11+/JDK17+、堆 > 16G、要求亚毫秒级停顿

**关键要点**：
- 不要只说"G1 比 CMS 好"，要说出具体场景的取舍
- CMS 的碎片化是核心痛点，G1 的 RSet 占用是核心代价

## 3. G1 GC 的 Mixed GC 触发条件是什么？和 Full GC 的区别？

**面试官考察点**：对 G1 工作机制的深入理解，是否有调优经验。

**参考答案**：

**Mixed GC 触发条件**：
1. **IHOP（Initiating Heap Occupancy Percent）**：老年代占用超过 `-XX:InitiatingHeapOccupancyPercent`（默认 45%）时触发并发标记周期
2. 并发标记完成后，G1 根据标记结果选择回收效益最高的 Region 进行 Mixed GC
3. Mixed GC 会同时回收 Young 和部分 Old Region

**Mixed GC vs Full GC**：
| | Mixed GC | Full GC |
|--|----------|---------|
| 回收范围 | Young + 部分 Old Region | 整个堆 |
| 执行方式 | 并发标记 + 并行清理 | 单线程 Serial Old（JDK8）或并行（JDK10+） |
| STW 时长 | 几十到几百毫秒 | 秒级甚至分钟级 |
| 触发时机 | 正常的并发标记后 | Mixed GC 无法跟上分配 / 巨型对象分配失败 / Evacuation Failure |

**G1 Full GC 的常见触发场景**：
- **Evacuation Failure**：Mixed GC 时无空闲 Region 接收存活对象 → to-space exhausted
- **巨型对象分配失败**：对象大小超过单个 Region 的 50%，且找不到连续空闲 Region
- **Concurrent Mode Failure**：并发标记期间老年代被填满

**关键要点**：
- G1 的目标是"避免 Full GC"，调优的核心是让 Mixed GC 能及时回收
- 监控指标：Full GC 次数、Mixed GC 频率、Humongous Allocation 次数

## 4. G1 的 Remembered Set（RSet）是什么？为什么它重要？

**面试官考察点**：是否理解 G1 实现低停顿的核心数据结构。

**参考答案**：

RSet 是 G1 实现"只扫描部分 Region"的关键。每个 Region 都有一个 RSet，记录了**其他 Region 中引用了本 Region 对象的 Card（卡表项）**。

**工作原理**：
- GC 时，G1 不需要扫描整个堆来找 GC Roots，只需要扫描 RSet 中记录的 Card
- 这保证了每次回收的 STW 时间可控，与堆大小解耦

**代价**：
- RSet 本身占用堆内存（约 5%甚至更多）
- 写屏障（Write Barrier）维护 RSet 有额外 CPU 开销
- 这就是为什么 G1 吞吐量通常比 Parallel GC 低 5-10%

**生产问题**：
- 如果 RSet 过大（大量跨 Region 引用），会导致 GC 扫描时间长
- 调优参数：`-XX:G1RSetRegionEntries` 控制 RSet 的初始大小

**关键要点**：
- "G1 停顿与堆大小无关"正是因为 RSet 机制
- 要能说出 RSet 的空间代价和 CPU 代价

## 5. 介绍一次你的 JVM GC 调优实战经历

### 实战案例：竞拍系统 G1 GC 调优

**面试官考察点**：是否真正做过 GC 调优，能否讲清楚调优的逻辑链。

**参考答案**：

**背景**：竞拍系统上线后，大促期间出现间歇性接口超时（> 200ms），Prometheus 监控显示 P99 延迟毛刺严重。

**排查过程**：
1. 查看 GC 日志，发现每 30 秒左右出现一次 Mixed GC，耗时 200-400ms，偶尔出现 Full GC（耗时 2-5s）
2. `jstat -gcutil` 发现老年代使用率持续在 80% 以上
3. 分析业务特征：竞拍期间会产生大量"出价记录对象"，这些对象生命周期约 1-3 分钟（拍卖持续期间需要保留），属于"中长生命周期"对象

**调优方案**：

```bash
# 原始配置
-Xms8g -Xmx8g -XX:+UseG1GC -XX:MaxGCPauseMillis=200

# 优化配置
-Xms12g -Xmx12g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=100
-XX:InitiatingHeapOccupancyPercent=35
-XX:G1HeapRegionSize=4m
-XX:G1NewSizePercent=5
-XX:G1MaxNewSizePercent=60
-XX:ConcGCThreads=4
-XX:ParallelGCThreads=8
-XX:G1ReservePercent=10
```

**调优逻辑**：

| 参数 | 原值 | 新值 | 为什么 |
|------|------|------|--------|
| Heap Size | 8G | 12G | 给 Mixed GC 更多缓冲空间 |
| MaxGCPauseMillis | 200 | 100 | 竞拍场景要更低延迟 |
| IHOP | 45(默认) | 35 | 更早触发并发标记，避免并发标记期间堆满 |
| G1NewSizePercent | 5(默认) | 5(保持) | 新生代下限不变 |
| G1MaxNewSizePercent | 60(默认) | 60(保持) | 保证新生代弹性 |
| G1ReservePercent | 10(默认) | 10(保持) | 预留空间防止 Evacuation Failure |

**效果**：
- Mixed GC 频率从 30s 降到 120s，单次耗时从 200-400ms 降到 80-150ms
- Full GC 完全消除
- P99 延迟从 300ms 降到 50ms 以内

**关键要点**：
- 调优不是猜参数，是基于 GC 日志和业务特征的分析
- IHOP 是最关键的调优参数之一——太晚触发导致 Full GC，太早触发浪费 CPU
- 堆大小的确定 = 活跃数据量 + GC 期间新分配量 + 安全缓冲区

## 6. 如何排查线上 OOM？请描述完整流程

### 实战案例：竞拍系统 OOM 排查

**面试官考察点**：OOM 排查的完整 SOP，工具使用熟练度。

**参考答案**：

**故障现象**：竞拍系统某个节点突然无响应，随后被 K8s 重启。日志中留下 `OutOfMemoryError: Java heap space`。

**排查 SOP**：

**第一步：保留现场**
```bash
# JVM 参数必须预先配置（非故障时才加）
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump/
-XX:+ExitOnOutOfMemoryError  # 竞拍系统选择不退出，触发告警后人工介入
```

**第二步：分析 Dump 文件**
```bash
# 使用 MAT 分析
# 1. 打开 Leak Suspects Report → 定位嫌疑对象
# 2. 查看 Histogram → 按 Retained Heap 排序
# 3. 对嫌疑对象做 Path to GC Roots → 找到引用链
# 4. 查看 Dominator Tree → 确认"大对象"
```

**第三步：定位根因（真实案例）**

MAT 分析发现：
- `HashMap` 占用了 3.2G 堆内存
- 深入查看 HashMap 中存放的是"出价记录"对象
- Path to GC Roots 显示 HashMap 被 ThreadLocal 持有

**根因**：
```java
// 问题代码
public class BidContext {
    private static ThreadLocal<Map<Long, List<BidRecord>>> bidCache = 
        ThreadLocal.withInitial(HashMap::new);
}

// 问题分析：
// 1. 请求线程来自线程池，ThreadLocal 未清理
// 2. Tomcat 线程处理完请求后归还线程池
// 3. 下次请求复用同一线程时，ThreadLocal 里还残留上次的 HashMap
// 4. 日积月累，每个线程的 ThreadLocal 都堆积了大量数据
```

**修复方案**：
```java
// 方案1：finally 清理
try {
    // 业务逻辑
} finally {
    bidCache.remove();
}

// 方案2：使用 FastThreadLocal（Netty 内置，自动清理）
// 方案3：改用请求级别的 Bean（RequestScope）
```

**第四步：验证和预防**
- 增加 JVM 监控：Heap Usage、GC Count/Time、Thread Count
- 增加 ThreadLocal 使用规范：Code Review 检查项
- 定期 MAT 分析：选取高峰期 Dump 做人工分析

**关键要点**：
- OOM 排查的关键是"提前准备好 Dump 参数"
- ThreadLocal 内存泄漏是最常见的 OOM 根因之一
- 会用 MAT 的 Dominator Tree 比会敲 `jmap` 更重要

## 7. CPU 飙高到 100% 如何排查？

**面试官考察点**：线上故障应急处理能力。

**参考答案**：

**标准排查流程**：

```bash
# 1. 找到 CPU 最高的进程
top -H

# 2. 找到 CPU 最高的线程
top -H -p <pid>
# 记录线程 ID（十进制），如 21953

# 3. 线程 ID 转 16 进制
printf "%x\n" 21953
# 输出：55c1

# 4. 查看线程堆栈
jstack <pid> | grep -A 20 0x55c1

# 5. 如果是 GC 线程，看 GC 日志
# 如果是业务线程，结合 Arthas 做进一步定位
```

**Arthas 排查（更高效）**：
```bash
# 一键定位 CPU 最高的线程
thread -n 3

# 查看方法调用耗时
trace com.xxx.service.BidService placeBid -n 5

# 监控方法执行
monitor -c 5 com.xxx.service.BidService placeBid
```

**常见原因与解决**：
| 现象 | 根因 | 解决 |
|------|------|------|
| GC 线程 CPU 高 | 堆内存不足，频繁 GC | 扩堆 / 调 GC 参数 |
| 业务线程 CPU 高 | 死循环 / 正则回溯 / 复杂计算 | 修代码 |
| 多个线程 CPU 均匀高 | 流量增加，正常消耗 | 扩容 |
| C2 编译器线程高 | JIT 编译热点 | 正常现象，过会就好 |

## 8. 类加载机制：双亲委派模型及如何破坏它？

**面试官考察点**：理解类加载机制，是否遇到类加载相关的生产问题。

**参考答案**：

**双亲委派模型**：
```
Bootstrap ClassLoader (加载 rt.jar)
    ↑
Extension ClassLoader (加载 ext/*.jar)
    ↑
Application ClassLoader (加载 classpath)
    ↑
Custom ClassLoader
```

**工作机制**：类加载器收到加载请求后，先委托父加载器加载，父加载器找不到才自己加载。目的是保证核心类的安全（如 `java.lang.String` 不能被自定义类替换）。

**破坏双亲委派的典型场景**：
1. **SPI 机制（JDBC 驱动）**：`ServiceLoader` 使用线程上下文类加载器加载实现类，因为核心类在 Bootstrap 层，实现类在 Classpath 层，按双亲委派模型 Bootstrap 找不到 Classpath 的类
2. **Tomcat 类加载**：每个 WebApp 有独立的 WebAppClassLoader，优先加载自己的类，破坏委派顺序以实现隔离
3. **OSGi**：网状类加载结构，按 Bundle 级别管理
4. **热部署**：动态替换类，需要打破双亲委派

**关键要点**：
- 不要只说 SPI 破坏了双亲委派，要解释"为什么必须破坏"
- `Thread.currentThread().getContextClassLoader()` 是理解 SPI 的关键

## 9. JVM 如何定位和排查 Metaspace OOM？

### 实战案例：规则引擎导致 Metaspace OOM

**面试官考察点**：Metaspace 问题的排查经验。

**参考答案**：

**故障现象**：竞拍系统运行一段时间后，出现 `OutOfMemoryError: Metaspace`。

**排查过程**：
```bash
# 1. 确认 Metaspace 使用情况
jstat -gcutil <pid> 1000
# 查看 MU（Metaspace Used）持续增长

# 2. 查看加载了多少类
jcmd <pid> VM.classloader_stats
# 发现某个 GroovyClassLoader 加载了 20000+ 个类

# 3. Arthas 查看类加载器
classloader -l
```

**根因**：竞拍系统的出价规则使用 Groovy 动态脚本实现，每次请求都创建一个新的 GroovyClassLoader 编译脚本，编译后的 Class 被加载到 Metaspace。由于 ClassLoader 没有被 GC（有引用链），其加载的所有类也无法被卸载。

**修复**：
```java
// 方案1：ClassLoader 缓存
private static final Map<String, GroovyClassLoader> loaderCache = new ConcurrentHashMap<>();

// 方案2：限制 Metaspace 上限 + 开启类卸载
-XX:MaxMetaspaceSize=256m
-XX:+UnloadUnloadingClasses

// 方案3：改用 Aviator/QLExpress 等轻量级表达式引擎替代 Groovy
```

## 10. JIT 编译与逃逸分析是什么？如何利用它们优化性能？

**面试官考察点**：对 JVM 执行引擎的理解深度。

**参考答案**：

**JIT 编译（Just-In-Time）**：
- 解释执行 → C1 编译（Client Compiler，快速编译）→ C2 编译（Server Compiler，深度优化）
- 触发条件：方法调用次数 + 循环回边次数达到阈值（`-XX:CompileThreshold`）

**逃逸分析**：
- 分析对象的作用域，如果对象不会逃逸出方法/线程，则可以：
  1. **栈上分配**：对象分配在栈上，随栈帧销毁自动回收
  2. **标量替换**：将对象的成员变量拆分为基本类型直接在寄存器/栈上操作
  3. **锁消除**：同步块内对象不逃逸，去除锁操作

**生产实践**（竞拍系统）：
```java
// 这段代码中，BidRequest 对象不会逃逸出 placeBid 方法
// JIT 会将它的字段标量替换，避免堆分配
public Result placeBid(BidCommand cmd) {
    BidRequest req = new BidRequest();  // 栈上分配
    req.setAmount(cmd.getAmount());
    req.setBidderId(cmd.getBidderId());
    return processBid(req);
}
```

**验证**：
```bash
-XX:+PrintFlagsFinal | grep EscapeAnalysis  # 默认开启
-XX:+PrintEscapeAnalysis  # 打印逃逸分析结果（debug 版 JDK）
```

**关键要点**：
- 逃逸分析只是一个"分析"，不是一定会做栈上分配——取决于 JIT 的判断
- 减少对象逃逸是代码层面的优化方向

## 11. Arthas 你最常用的命令有哪些？

**面试官考察点**：是否真正在生产中使用过 Arthas。

**参考答案**：

```bash
# 1. 查看 JVM 概况
dashboard  # 实时面板，线程/内存/GC

# 2. CPU 问题定位
thread -n 3  # 查看 CPU 最高的 3 个线程

# 3. 方法调用追踪
trace com.xxx.BidService placeBid '#cost > 50' -n 5  # 追踪耗时超过 50ms 的调用

# 4. 方法执行监控
monitor -c 5 com.xxx.BidService placeBid  # 每 5 秒统计调用量/成功率/RT

# 5. 热修复（线上应急）
retransform /tmp/BidService.class  # 热替换类文件

# 6. 查看方法入参/返回值
watch com.xxx.BidService placeBid '{params, returnObj, throwExp}' -x 3

# 7. 查看静态变量值
getstatic com.xxx.BidConfig maxBidAmount

# 8. 反编译
jad com.xxx.BidService placeBid  # 确认线上运行的代码版本

# 9. OGNL 表达式（最强大）
ognl '@com.xxx.BidConfig@maxBidAmount'
ognl '@System@setProperty("bid.limit", "1000")'

# 10. 火焰图
profiler start  # 启动采样
profiler stop --format html  # 输出火焰图
```

**实战经验**：竞拍系统大促期间，通过 `trace` 定位到某个方法因为加了不必要的分布式锁导致耗时 200ms，通过 OGNL 临时关闭了该锁配置，避免了故障扩大。

## 12. 请设计一个 JVM 性能监控和告警体系

**面试官考察点**：架构师的系统化思维。

**参考答案**：

**三层监控体系**：

```
第一层：JMX 指标采集
├── HeapMemoryUsage (堆使用率 > 85% 告警)
├── NonHeapMemoryUsage (Metaspace > 80% 告警)
├── GC Count/Time (Full GC > 1次/小时 告警)
├── ThreadCount (线程数 > 1000 告警)
└── CPU/Load

第二层：GC 日志分析
├── GCViewer / GCeasy 离线分析
├── Prometheus + jmx_exporter 实时采集
└── 关键告警：单次 GC 耗时 > 500ms

第三层：Dump 文件管理
├── OOM 自动 Dump → 上传 OSS
├── 定期（每周）手动 Dump → MAT 分析
└── 对比分析（发版前后）
```

**关键指标与告警阈值**：
| 指标 | 告警阈值 | 处理优先级 |
|------|---------|-----------|
| Full GC 次数 | > 0 次/小时 | P0 |
| Full GC 耗时 | > 2s | P0 |
| 堆使用率 | > 85% | P1 |
| Young GC 频率 | > 10次/分钟 | P1 |
| GC 总耗时占比 | > 5% | P1 |
| Metaspace 使用率 | > 80% | P1 |
| 线程数 | > 1500 | P2 |

```bash
# 堆设置
-Xms4g -Xmx4g                  # 初始/最大堆（建议相等，避免动态扩缩）
-XX:NewRatio=2                 # 老年代/新生代比例
-XX:SurvivorRatio=8            # Eden/Survivor 比例

# GC 选择
-XX:+UseG1GC                   # G1
-XX:+UseZGC                    # ZGC (JDK11+)

# G1 关键参数
-XX:MaxGCPauseMillis=200       # 预期最大停顿
-XX:InitiatingHeapOccupancyPercent=45  # 并发标记触发阈值
-XX:G1HeapRegionSize=4m        # Region 大小
-XX:G1ReservePercent=10        # 预留空间

# 日志与 Dump
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/path/gc.log
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/dump/
-XX:+PrintFlagsFinal           # 查看所有 JVM 参数默认值

# 容器化
-XX:+UseContainerSupport       # JDK8u191+ 自动感知容器内存限制
-XX:MaxRAMPercentage=75.0      # JVM 使用容器内存的 75%
```

### 排查工具速查

| 问题 | 工具 | 命令/操作 |
|------|------|----------|
| CPU 高 | Arthas | `thread -n 3` |
| 内存泄漏 | MAT | Dominator Tree → Path to GC Roots |
| 死锁 | jstack | `jstack -l <pid>` |
| GC 分析 | GCeasy | 上传 gc.log |
| 类加载 | Arthas | `classloader -l` |
| 方法耗时 | Arthas | `trace ClassName methodName` |
| 火焰图 | Arthas | `profiler start/stop` |
