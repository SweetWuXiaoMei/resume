## 五、模块三：负载均衡

### 5.1 从数据库架构推导 LB 策略

GaussDB 的 CN 是无状态的，每个 CN 都能独立接收和分发 SQL。这决定了**驱动可以在任意 CN 之间做负载均衡**。

但不同 CN 的负载可能不均（某些 CN 被更多应用连接），所以不能用简单的轮询。

### 5.2 加权动态负载均衡算法

```
负载评分 = CPU权重 × 40% + 连接数权重 × 30% + 响应时间权重 × 30%

CN-1: CPU 30% → 40×0.7 = 28 | 连接50/100 → 30×0.5 = 15 | RT 5ms → 30×0.8 = 24 | 总分 = 67
CN-2: CPU 70% → 40×0.3 = 12 | 连接80/100 → 30×0.2 = 6  | RT 20ms → 30×0.2 = 6  | 总分 = 24
CN-3: CPU 50% → 40×0.5 = 20 | 连接30/100 → 30×0.7 = 21 | RT 8ms → 30×0.7 = 21  | 总分 = 62

请求分发比例：CN1:CN2:CN3 ≈ 67:24:62
→ 不是均匀分发，而是"谁闲给谁"
```

### 5.3 实现细节

```java
public class LoadBalancer {
    private final TopologyWatcher watcher;
    private final Map<CNNode, AtomicInteger> activeConnections = new ConcurrentHashMap<>();
    
    // 核心：选择一个 CN 节点
    public CNNode select(List<CNNode> candidates, SQLContext context) {
        // 权重算法：综合 CPU + 连接数 + RT
        List<WeightedNode> weighted = candidates.stream()
            .map(cn -> {
                double cpuWeight = (1 - cn.getCpuUsage()) * 0.4;
                double connWeight = (1 - cn.getConnectionRatio()) * 0.3;
                double rtWeight = normalizeRt(cn.getAvgResponseTime()) * 0.3;
                return new WeightedNode(cn, cpuWeight + connWeight + rtWeight);
            })
            .sorted((a, b) -> Double.compare(b.weight, a.weight))  // 权重高优先
            .collect(Collectors.toList());
        
        // 加权随机选择（避免同一时刻全部请求打到一个节点）
        return weightedRandom(weighted);
    }
    
    // 避免惊群：加权随机代替加权轮询
    private CNNode weightedRandom(List<WeightedNode> nodes) {
        double totalWeight = nodes.stream().mapToDouble(n -> n.weight).sum();
        double random = ThreadLocalRandom.current().nextDouble() * totalWeight;
        
        double cumulative = 0;
        for (WeightedNode node : nodes) {
            cumulative += node.weight;
            if (random <= cumulative) {
                return node.cn;
            }
        }
        return nodes.get(0).cn;  // fallback
    }
}
```

**为什么用加权随机而不用加权轮询？**

> 加权轮询的问题：多个应用实例都从 CN-1 开始轮询 → 同一时刻请求扎堆到 CN-1 → "惊群效应"。加权随机避免了这种同步。

### 5.4 负载信息获取

CN 不会主动推送负载信息给驱动（那是 Agent 的职责）。驱动的做法：

```
方式 1（标准）：定期查询
每 10 秒向每个 CN 发送一条轻量查询
  → SELECT cpu_usage, active_connections, avg_response_time FROM pg_stat_node()
  → 驱动本地缓存 + 滑动窗口平均

方式 2（优化）：Piggyback（搭车）
每当执行 SQL 返回 Response 时，在扩展消息中附带当前 CN 负载
  → 零额外查询，实时性更好
  → 但需要 GaussDB 侧支持（GaussDB 3.0+ 支持）
```

## 六、模块四：故障自动切换（Failover）

### 6.1 故障场景矩阵

| 故障类型 | 现象 | 恢复策略 | 恢复时间目标 |
|---------|------|---------|-------------|
| CN 进程 crash | 连接断开，errno=ECONNRESET | 立即切换 | < 1s |
| CN 网络不可达 | 连接超时，SocketTimeout | 切换 + 熔断 | < 3s |
| CN 响应缓慢 | 查询超时，慢查询 | 降级 + 熔断 | < 5s |
| 整个集群不可用 | 所有 CN 不可达 | 熔断 + 快速失败 | 取决于集群恢复 |

### 6.2 故障切换流程

```
┌─────────────────────────────────────────────────────────┐
│                    故障切换状态机                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  [正常] ──心跳检测(每 5s)──▶ [正常]                       │
│     │                                                      │
│     │ 连接失败 / SocketTimeout / 查询超时                    │
│     ▼                                                      │
│  [故障探测]                                                │
│     │                                                      │
│     ├── retryCount < 3 → 重试同一 CN（可能网络瞬时抖动）      │
│     │                                                      │
│     └── retryCount >= 3 → 确认故障                          │
│            │                                                │
│            ▼                                                │
│  [故障确认]                                                │
│     │                                                      │
│     ├── 标记该 CN 为 UNHEALTHY                              │
│     ├── 加入黑名单(30s 后自动探测恢复)                       │
│     ├── 排干该 CN 的连接池（等待进行中的事务）               │
│     └── 选择备用 CN → 重新执行 SQL（透明重试）               │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 6.3 核心实现

```java
public class FailoverHandler {
    private final BlacklistManager blacklist;
    private final LoadBalancer lb;
    private final RetryPolicy retryPolicy;
    
    public <T> T executeWithFailover(SQLContext ctx, SQLFunction<T> func) 
            throws SQLException {
        int attempts = 0;
        CNNode currentCN = lb.select(ctx);
        
        while (attempts < retryPolicy.getMaxRetries()) {
            try {
                return func.execute(currentCN);
            } catch (SQLException e) {
                attempts++;
                
                if (isRetryable(e)) {  // 连接错误 → 可重试
                    // 标记故障
                    blacklist.mark(currentCN, Duration.ofSeconds(30));
                    
                    // 事务中的请求 → 不能切换！
                    if (ctx.isInTransaction()) {
                        throw new SQLException(
                            "Transaction aborted due to CN failover. " +
                            "Please retry the entire transaction.", e);
                    }
                    
                    // 选择新 CN
                    currentCN = lb.select(
                        ctx, 
                        blacklist.getActiveNodes()  // 排除黑名单
                    );
                    
                    log.warn("Failover: {} → {} (attempt={})", 
                        e.getMessage(), currentCN, attempts);
                    
                } else {  // SQL 错误 → 不重试
                    throw e;
                }
            }
        }
        throw new SQLException("All failover attempts exhausted");
    }
    
    // 判断是否可重试（核心：只有连接/网络错误才重试）
    private boolean isRetryable(SQLException e) {
        String state = e.getSQLState();
        return "08000".equals(state)      // connection exception
            || "08003".equals(state)      // connection does not exist
            || "08006".equals(state)      // connection failure
            || "57P01".equals(state)      // admin shutdown
            || e.getCause() instanceof java.net.SocketTimeoutException;
    }
}
```

### 6.4 关键难点：事务中的故障切换

这是整个 Failover 模块最复杂的部分，也是面试官最可能追问的。

```
场景：事务正在进行中 → CN 挂了

不能做的：
  × 不能在新 CN 上继续事务（全局事务 ID 丢失、锁状态丢失）
  × 不能假装什么都没发生（数据可能不一致）

实际策略：
  ✓ 立即抛异常给应用层：SQLException("Transaction aborted")
  ✓ 应用的连接池收到异常 → 标记所有该 CN 的连接为 broken
  ✓ 应用层需要重试整个事务（这是分布式事务的语义要求）
  ✓ 驱动提供 RetryTemplate 辅助类（Spring Retry 风格）
```

```java
// 驱动内置的事务重试模板
public class TransactionRetryTemplate {
    public <T> T execute(TransactionalCallback<T> callback) throws SQLException {
        int attempts = 0;
        while (attempts < 3) {
            try {
                Connection conn = dataSource.getConnection();
                conn.setAutoCommit(false);
                try {
                    T result = callback.doInTransaction(conn);
                    conn.commit();
                    return result;
                } catch (Exception e) {
                    conn.rollback();
                    throw e;
                }
            } catch (SQLException e) {
                if (isFailoverException(e) && attempts < 3) {
                    attempts++;
                    continue;  // 切换 CN 后重试整个事务
                }
                throw e;
            }
        }
        throw new SQLException("Transaction retry exhausted");
    }
}
```

**面试话术**：
> "事务中的故障切换无法做到完全透明——因为全局事务状态（GTM 分配的 XID、快照版本）在原 CN 上，新 CN 没有这些信息。我们的策略是：**非事务请求透明切换，事务内请求快速失败 + 通知应用层重试**。这也是为什么我们提供了 TransactionRetryTemplate。"

## 七、模块五：读写分离

### 7.1 不是简单的 SELECT → 只读

面试官期望你讲到这一层：

```
简单方案（有坑）：
  SELECT → 路由到只读副本
  INSERT/UPDATE/DELETE → 路由到主库

问题：
  1. SELECT ... FOR UPDATE → 这是读还是写？当然是写！需要加锁。
  2. SELECT nextval('seq') → 序列号操作，必须走主库。
  3. SELECT * FROM func() → 函数内有写操作怎么办？
  4. BEGIN; SELECT ...; UPDATE ...; COMMIT; → 事务中的 SELECT 必须走主库。
```

### 7.2 路由决策引擎

```java
public class ReadWriteRouter {
    private final SQLParser parser;
    
    public RoutingDecision route(String sql, TransactionContext txContext) {
        // 规则 1：事务中的请求 → 全部走主库
        if (txContext.isInTransaction()) {
            return RoutingDecision.MASTER;
        }
        
        // 规则 2：显式 Hint → 尊重用户选择
        if (sql.contains("/*master*/") || sql.contains("/*read*/")) {
            return parseHint(sql);
        }
        
        // 规则 3：SQL 解析判断
        SQLStatement stmt = parser.parse(sql);
        
        if (stmt.isWriteOperation()) {
            return RoutingDecision.MASTER;
        }
        
        if (stmt.isReadOnly()) {
            // 规则 4：特殊检查
            if (stmt.hasForUpdate())      return RoutingDecision.MASTER;
            if (stmt.callsSequence())     return RoutingDecision.MASTER;
            if (stmt.hasVolatileFunc())   return RoutingDecision.MASTER;
            return RoutingDecision.READ_REPLICA;
        }
        
        return RoutingDecision.MASTER;  // 不确定 → 安全起见走主库
    }
}
```

### 7.3 SQL 解析器的选择

```
JSqlParser：完整解析 SQL 语法树，准确判断读写类型
  - 支持复杂 SQL：子查询、CTE、UNION、多表 JOIN
  - 代价：解析 1 条 SQL 约 0.05ms（简单 SQL）~ 0.5ms（复杂 SQL）

正则匹配：只做快速分类，不完整解析
  - INSERT/UPDATE/DELETE → 写、SELECT → 读
  - 代价：~0.001ms
  - 问题：SELECT ... FOR UPDATE 误判为读

两级策略：
  第一级：正则快速分类（命中率 > 90%）
  第二级：JSqlParser 精确判断（正则不确定的 SQL）
  缓存：LRU 缓存解析结果（同一条 SQL 不必重复解析）
```

**面试话术**：
> "我们做了两件事让读写分离更可靠：一是加了 JSqlParser 做精确判断，而不是简单的正则；二是'疑罪从有'——不确定是不是只读的 SQL，一律走主库。宁可多走一次主库，也不能把写操作路由到只读副本。"

## 八、模块六：SQL 执行与结果集处理

### 8.1 流式读取：如何避免大数据量 OOM？

```
传统方式（MySQL JDBC 默认）：
  ResultSet rs = stmt.executeQuery("SELECT * FROM big_table");
  // 此时 500 万行数据全部加载到客户端内存 → OOM!

流式读取（GaussDB JDBC）：
  stmt.setFetchSize(1000);  // 每次只取 1000 行
  ResultSet rs = stmt.executeQuery("SELECT * FROM big_table");
  while (rs.next()) {
      // 处理当前行
      // 遍历到 1001 行时 → 自动从服务端拉取下一批
      // 内存中始终只有 1000 行 → 永不会 OOM
  }
```

### 8.2 流式读取的协议实现

```
客户端                               GaussDB 服务端
  │                                       │
  ├─ Execute(fetchSize=1000) ────────────►│ 执行查询，准备结果
  │                                       │
  │◄──────── DataRow × 1000 ─────────────┤ 发送前 1000 行
  │◄──────── PortalSuspended ────────────┤ 告知"还有更多数据"
  │                                       │
  │ 客户端遍历完 1000 行后：                 │
  ├─ Execute(fetchSize=1000) ────────────►│ 发送下 1000 行（复用 Portal）
  │◄──────── DataRow × 1000 ─────────────┤
  │◄──────── PortalSuspended ────────────┤
  │                                       │
  │ 客户端遍历完最后一批：                     │
  ├─ Close ──────────────────────────────►│ 关闭 Portal，释放服务端资源
  │◄──────── CloseComplete ──────────────┤
```

### 8.3 实现代码

```java
public class GaussDBStreamingResultSet extends GaussDBResultSet {
    private static final int DEFAULT_FETCH_SIZE = 0;   // 0 = 一次性全取
    private int fetchSize;
    private int currentRowInBatch;
    private List<RowData> currentBatch;
    private boolean portalSuspended;
    
    @Override
    public boolean next() throws SQLException {
        // 当前批次还有数据 → 直接返回
        if (currentBatch != null && currentRowInBatch < currentBatch.size()) {
            this.currentRow = currentBatch.get(currentRowInBatch++);
            return true;
        }
        
        // 当前批次用完 → 拉取下一批
        if (portalSuspended) {
            fetchNextBatch();
            if (currentBatch.isEmpty()) {
                return false;  // 没有更多数据
            }
            this.currentRow = currentBatch.get(0);
            currentRowInBatch = 1;
            return true;
        }
        
        return false;  // 结果集结束
    }
    
    private void fetchNextBatch() throws SQLException {
        // 发送 Execute 消息，带上 fetchSize
        protocol.sendExecute(portalName, fetchSize);
        
        // 接收 DataRow 消息，直到 PortalSuspended 或 CommandComplete
        this.currentBatch = protocol.receiveDataRows();
        this.portalSuspended = protocol.isPortalSuspended();
        this.currentRowInBatch = 0;
    }
}
```

**关键设计决策**：

| 决策 | 选择 | 理由 |
|------|------|------|
| fetchSize 默认值 | 0（一次性全取） | 兼容 JDBC 标准行为。大多数查询返回少量行，全取一次网络往返更高效 |
| 何时启用流式 | fetchSize > 0 时 | 由用户显式设置，不给默认值（避免不了解的人误用导致性能问题） |
| 内存控制 | 严格限制当前批次大小 | 即使 fetchSize = 1000，每行数据可能在 Java 堆中有额外开销（String 对象等），需要预留 buffer |

## 九、模块七：PreparedStatement 缓存

### 9.1 为什么需要缓存？

```
不缓存：
每次执行 "SELECT * FROM auction WHERE id = ?"
  → Parse(解析SQL) → Bind(绑定参数) → Execute(执行) → Sync(同步)
  → Parse 是一次网络往返，在简单 SQL 场景下 Parse 耗时占总耗时的 30-50%

缓存：
第一次执行 → Parse + Bind + Execute → 缓存 Statement 名
后续执行 → 直接 Bind(复用已解析的语句) + Execute
  → 减少网络往返 + 减少数据库端 SQL 解析 CPU
```

### 9.2 缓存设计

```java
public class PreparedStatementCache {
    // LRU 缓存：最多缓存 256 个 PreparedStatement
    private final LRUCache<String, CachedStatement> cache;
    
    // 缓存 Key：SQL 文本的 hash
    // 注意：不能用 SQL 文本本身做 Key（内存占用大）
    private static class CacheKey {
        private final String sql;
        private final int hashCode;
        
        public boolean equals(Object o) {
            // 先比较 hash，再比较 SQL 全文（防止 hash 碰撞）
            if (this == o) return true;
            if (hashCode != ((CacheKey) o).hashCode) return false;
            return sql.equals(((CacheKey) o).sql);
        }
    }
    
    public CachedStatement getOrParse(String sql, Connection conn) {
        CacheKey key = new CacheKey(sql);
        CachedStatement cached = cache.get(key);
        
        if (cached != null && cached.isValid(conn)) {
            return cached;  // 缓存命中
        }
        
        // 缓存未命中 → Parse + 缓存
        CachedStatement stmt = conn.parse(sql);
        cache.put(key, stmt);
        return stmt;
    }
    
    // 失效策略
    private class CachedStatement {
        void invalidateIfNeeded(Connection conn) {
            // 1. DDL 变更：ALTER TABLE / DROP TABLE → 失效所有相关缓存
            // 2. 连接断开 → 所有该连接的缓存失效
            // 3. 超过最大缓存数 → LRU 淘汰
            // 4. 超过 TTL（30 分钟无使用）→ 过期
        }
    }
}
```

### 9.3 缓存失效策略（最容易有坑的地方）

```
场景：ALTER TABLE auction ADD COLUMN status VARCHAR(10);

问题：PreparedStatement 缓存中有一句 "SELECT * FROM auction WHERE id = ?"
  之前解析的列数是 10 列，现在表有 11 列了 → 执行时会收到 11 列数据
  如果驱动按照旧的元数据（10 列）解析 → 数据错位！

解决方案：
  1. 监听 DDL 事件 → 消除相关表的 PS 缓存
  2. 执行时校验列数 → 不匹配则重新 Parse
  3. 保守策略：生产环境关闭 PS 缓存（性能换正确性）
```

**面试话术**：
> "PS 缓存的最大风险不是性能，而是 DDL 变更后的缓存失效。我们的方案是：执行时做轻量校验（列数匹配），不匹配时自动重新 Parse。这比监听 DDL 事件更可靠——因为 DDL 可能来自其他连接，驱动不一定能感知。"

## 十、模块八：超时与熔断机制

### 10.1 三层超时体系

```
┌──────────────────────────────────────────────────────┐
│  第一层：连接超时 (connectTimeout)                      │
│  驱动与 CN 建立 TCP 连接的最长等待时间                    │
│  默认：10s，可通过 jdbc:gaussdb://host:port/db?        │
│        connectTimeout=5000 配置                        │
├──────────────────────────────────────────────────────┤
│  第二层：Socket 超时 (socketTimeout)                    │
│  Socket 读取数据的最长等待时间                           │
│  默认：0(无限)，建议配置 30s                            │
│  与 PostgreSQL 的 statement_timeout 不同：              │
│    socketTimeout：客户端超时（网络层面）                 │
│    statement_timeout：服务端超时（SQL 执行层面）          │
├──────────────────────────────────────────────────────┤
│  第三层：查询超时 (queryTimeout)                         │
│  单条 SQL 执行的最长时间                                │
│  通过 Statement.setQueryTimeout(30) 设置               │
│  超时后 → 发送 Cancel 消息给服务端                       │
│         → 服务端终止正在执行的查询                       │
│         → 连接仍可用（不影响连接池）                      │
└──────────────────────────────────────────────────────┘
```

### 10.2 熔断器设计

```
熔断器状态机：
                       ┌──────────┐
        失败次数 < 阈值  │  CLOSED  │
       ◄───────────────┤  (正常)  │
       │                └────┬─────┘
       │                     │ 连续失败 N 次
       │                     ▼
       │                ┌──────────┐
       │                │   OPEN   │
       │                │  (熔断)  │
       │                └────┬─────┘
       │                     │ 休眠时间到 → 进入 HALF_OPEN
       │                     ▼
       │                ┌──────────┐
       │      探测成功   │HALF_OPEN │
       └───────────────┤  (探测)  │
          探测失败 →     └──────────┘
          重新 OPEN
```

```java
public class CircuitBreaker {
    private final int failureThreshold = 5;    // 连续失败 5 次 → 熔断
    private final long sleepWindowMs = 30_000; // 熔断 30 秒
    private final int halfOpenMaxReqs = 3;     // 半开状态最多 3 个探测请求
    
    private volatile CircuitState state = CircuitState.CLOSED;
    private AtomicInteger failureCount = new AtomicInteger(0);
    private AtomicLong lastFailureTime = new AtomicLong(0);
    private AtomicInteger halfOpenCount = new AtomicInteger(0);
    
    public boolean allowRequest() {
        switch (state) {
            case CLOSED:
                return true;
                
            case OPEN:
                // 检查是否到了休眠时间
                if (System.currentTimeMillis() - lastFailureTime.get() > sleepWindowMs) {
                    state = CircuitState.HALF_OPEN;
                    halfOpenCount.set(0);
                    return true;
                }
                // 抛出熔断异常（快速失败，不浪费资源）
                throw new CircuitBreakerOpenException(
                    "Circuit breaker is OPEN. Retry after " + 
                    (sleepWindowMs - (System.currentTimeMillis() - lastFailureTime.get())) / 1000 + "s");
                    
            case HALF_OPEN:
                // 限制探测请求数量
                if (halfOpenCount.incrementAndGet() <= halfOpenMaxReqs) {
                    return true;
                }
                throw new CircuitBreakerOpenException("Circuit breaker is HALF_OPEN, max probe requests reached");
        }
        return false;
    }
    
    public void markSuccess() {
        if (state == CircuitState.HALF_OPEN) {
            state = CircuitState.CLOSED;
            failureCount.set(0);
        }
    }
    
    public void markFailure() {
        lastFailureTime.set(System.currentTimeMillis());
        if (failureCount.incrementAndGet() >= failureThreshold) {
            state = CircuitState.OPEN;
        }
    }
}
```

**面试话术**：
> "熔断器我们设计了两级：CN 级别的熔断（一个 CN 坏了不影响其他 CN）和集群级别的熔断（整个集群不可用时快速失败，不堆积请求）。熔断的触发条件不只是失败次数——我们还加了慢查询比例。如果一个 CN 上 50% 的查询超过 5 秒，即使没报错也要熔断它。"

## 十一、项目排错案例

### 案例 1：连接泄漏导致应用 OOM

**故障现象**：
- 业务应用运行 2 小时后，突然抛出 OutOfMemoryError
- 重启后 2 小时再次 OOM
- MAT 分析发现 PooledConnection 对象占了 80% 堆内存

**排查过程**：
```
1. jmap dump → MAT Dominator Tree → 1200 个 PooledConnection 对象
2. 连接池配置 maxPoolSize=50，为什么会 1200 个？
3. 查代码 → 发现 Statement/ResultSet 未在 finally 中关闭
   → 但连接池的连接关闭不等于物理连接关闭
   → ResultSet 持有 Statement 引用，Statement 持有 Connection 引用
   → Connection 无法回到连接池 → 连接池"以为"连接不够 → 创建新连接
   → 实际物理连接数不断增长

根因：ResultSet 和 Statement 没有正确关闭，导致 Connection 无法归还连接池。
```

**解决方案**：
```java
// 驱动侧：增加泄漏检测
public class ConnectionPool {
    public PooledConnection borrow() {
        PooledConnection conn = pool.borrow();
        conn.setBorrowTimestamp(System.currentTimeMillis());
        conn.setBorrowStack(new Exception("Connection borrow stack"));  // 记录借用栈
        return conn;
    }
}

// 定时扫描：连接借出超过 30 秒未归还 → 打印借用栈 + 告警
scheduler.scheduleAtFixedRate(() -> {
    for (PooledConnection conn : borrowedConnections) {
        if (System.currentTimeMillis() - conn.getBorrowTimestamp() > 30_000) {
            log.error("Connection leak detected! Borrowed at:", conn.getBorrowStack());
        }
    }
}, 10, 10, TimeUnit.SECONDS);
```

### 案例 2：PS 缓存导致数据错位

**故障现象**：
- DBA 执行了 ALTER TABLE ADD COLUMN
- 部分查询结果中，email 字段出现了 phone 的内容
- 数据错位！但重启应用后恢复正常

**排查过程**：
```

2. 驱动日志：查询 "SELECT * FROM user" 使用了缓存的 PS
3. 缓存的 PS 元数据：10 列（phone 是第 5 列，email 是第 6 列）
4. 实际收到数据：11 列（phone→5, new_field→6, email→7）
5. 驱动按旧元数据解析：把 new_field 当 email → 数据错位

根因：DDL 变更后未通知驱动清除 PS 缓存。
```

// 每次执行前做轻量校验
public class CachedStatement {

### 案例 3：Failover 死循环

**故障现象**：
- 某个 CN 故障后，应用日志疯狂打印 Failover 日志
- CPU 飙升，请求全部超时
- 故障节点上的连接全部失败，但驱动不断重试

**排查过程**：
```
1. 重试逻辑：每次重试都选择"新的 CN"
2. 但因为只有 3 个 CN，重试 3 次后所有 CN 都试过了
3. 重试策略的 maxRetries 设置为无限（bug）
4. 驱动在 3 个 CN 之间无限循环重试

根因：maxRetries 没有上限 + 没有 backoff 退避
```

**解决方案**：
```java
// 修改重试策略
public class RetryPolicy {
    private final int maxRetries = 3;  // 最多重试 3 次
    
    public boolean shouldRetry(int attempt, Exception e) {
        if (attempt >= maxRetries) return false;
        if (!isRetryable(e)) return false;
        
        // 指数退避：100ms → 200ms → 400ms
        long backoff = (long) (100 * Math.pow(2, attempt));
        Thread.sleep(backoff);
        
        return true;
    }
}
```
