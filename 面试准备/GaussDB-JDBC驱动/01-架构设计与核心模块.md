## 一、前置知识：GaussDB 分布式架构

### 1.1 为什么需要理解 GaussDB 的架构？

面试官问你"JDBC 驱动怎么做负载均衡"，你如果只会说"轮询"，那是初级回答。架构师的回答必须从**数据库本身的架构**推导出驱动的设计。

### 1.2 GaussDB 核心组件

```
                        ┌──────────────────────┐
                        │       应用层           │
                        │   (你的 JDBC 驱动)     │
                        └──────────┬───────────┘
                                   │ 连接
                        ┌──────────▼───────────┐
                        │    CN (Coordinator)   │  ← 协调节点：接收 SQL、生成分布式执行计划
                        │    无状态、可水平扩展   │
                        └─────┬────────┬────────┘
                              │        │
              ┌───────────────▼──┐ ┌──▼───────────────┐
              │   DN (Data Node) │ │   DN (Data Node)  │  ← 数据节点：存储分片数据
              │   Shard 1        │ │   Shard 2         │
              └──────────────────┘ └───────────────────┘
                              │        │
                        ┌─────▼────────▼─────┐
                        │  GTM (Global TX     │  ← 全局事务管理器：全局事务 ID、全局快照
                        │  Manager)           │
                        └────────────────────┘
```

| 组件 | 职责 | 对驱动设计的影响 |
|------|------|-----------------|
| **CN** | SQL 解析、查询优化、分布式执行计划生成、结果汇聚 | **驱动连接的是 CN**，不是 DN。驱动的负载均衡是对 CN 做负载均衡。 |
| **DN** | 实际数据存储、子查询执行 | 驱动通常不直连 DN（除非特殊场景如批量导入）。**读写分离中"只读副本"也指的是 DN 的只读副本。** |
| **GTM** | 全局事务 ID 分配、全局快照管理 | 驱动需要支持全局事务语义，connection 的隔离级别要和 GTM 配合。 |

### 1.3 驱动设计面临的挑战

```
挑战 1：CN 有多个 → 怎么选？哪个 CN 负载低？ → 负载均衡
挑战 2：某个 CN 挂了 → 连接上的事务怎么办？ → 故障切换
挑战 3：读写混合 → 怎么把读请求路由到只读 DN 副本？ → 读写分离
挑战 4：大查询返回百万行 → 内存爆了怎么办？ → 流式结果集
挑战 5：SQL 频繁执行 → 每次都解析太慢？ → PreparedStatement 缓存
挑战 6：网络抖动/慢查询 → 怎么防止连接泄漏？ → 超时与熔断
```

### 1.4 JDBC 4.2 标准关键接口

```
Driver        → 驱动入口，注册到 DriverManager
Connection    → 数据库连接，事务管理
Statement     → 执行静态 SQL
PreparedStatement → 预编译 SQL，防注入，批量执行
CallableStatement → 调用存储过程
ResultSet     → 结果集，支持可滚动、可更新
DatabaseMetaData → 数据库元数据
```

**面试要点**：你要非常清楚地说出"我实现了 JDBC 4.2 的哪些接口"和"哪些 GaussDB 特性是在标准 JDBC 之上的扩展"。

### 2.3 技术选型决策

| 决策点 | 方案 A | 方案 B | 选择 | 理由 |
|--------|--------|--------|------|------|
| 网络框架 | 原生 Socket + 线程池 | Netty NIO | **Netty** | 原生 Socket 一个连接一个线程，1000 个连接 = 1000 个线程 = 内存爆炸。Netty EventLoop 模型，少量线程管理大量连接。 |
| 协议格式 | 文本协议(类 PostgreSQL) | 纯二进制协议 | **二进制(兼容 PG 协议)** | GaussDB 基于 PostgreSQL 生态，兼容 PG 协议可复用生态工具。但针对 GaussDB 特性(分布式事务/CN 路由)增加扩展消息类型。 |
| 连接池 | 自研连接池 | HikariCP | **自研(借鉴 HikariCP)** | HikariCP 是通用连接池，不理解 CN/DN 拓扑、主从角色。自研连接池可以感知 GaussDB 的集群拓扑变化，做"拓扑感知"的连接管理。 |
| 负载均衡 | 简单轮询 | 加权轮询 + 最少连接数 | **加权动态** | 简单轮询不理解节点负载差异。加权轮询 + 动态权重(CPU/连接数/响应时间)才是 GaussDB CN 集群的正确 LB 策略。 |
| SQL 解析 | 正则匹配 | ANTLR/JSqlParser | **JSqlParser + 正则兜底** | 正则对复杂 SQL(子查询/CTE) 误判率高。JSqlParser 完整解析语法树，准确判断读写类型。简单 SQL 用正则快速路径优化。 |

## 三、模块一：连接管理

### 3.1 为什么需要自研连接池而不是直接用 HikariCP？

面试官一定会追问这个问题。

**HikariCP 的局限**（针对 GaussDB 场景）：

| 场景 | HikariCP 行为 | 需要的 GaussDB 行为 |
|------|--------------|-------------------|
| CN 节点扩容 | 不知道新 CN 加入，连接只分布到旧 CN | **感知拓扑变化**，自动为新 CN 建立连接 |
| CN 节点故障 | 连接池中的连接全部失效，逐个重试 | **批量切换**，把该 CN 的所有连接一次性标记失效并切换到其他 CN |
| 读写分离 | 不支持，所有连接平等对待 | **区分读写连接**，读请求走只读连接，写请求走主连接 |
| 主从切换 | 不知道角色变了 | **感知角色变更**，写连接自动指向新主 |

**面试话术**：

> "我们用 HikariCP 做了原型验证，发现它无法感知 GaussDB 的集群拓扑变化。当 CN 节点扩容或故障时，业务需要重启才能获取新的连接分布。所以我们设计了**拓扑感知连接池**——核心是在 HikariCP 的快速连接管理基础上，叠加了 GaussDB 集群拓扑的感知层。"

### 3.2 连接池架构设计

```
TopologyWatcher (拓扑监听)
  │ 定期(每 10s) 从 CN 获取集群拓扑
  │ 检测变化：新增 CN / CN 下线 / 角色变更
  ▼
ConnectionPoolManager
  │ 为每个 CN 维护一个子连接池
  │ 子连接池大小 = 总连接数 / CN 数量（加权）
  ▼
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│ CN-1 子连接池     │  │ CN-2 子连接池     │  │ CN-3 子连接池     │
│ 权重: 100        │  │ 权重: 100        │  │ 权重: 50         │
│ min=5, max=20   │  │ min=5, max=20   │  │ min=3, max=10   │
│ 活跃: 12         │  │ 活跃: 8          │  │ 活跃: 5          │
│                                          │  (低配节点)       │
└──────────────────┘  └──────────────────┘  └──────────────────┘
```

**关键技术点**：

**① 拓扑感知**：
```java
public class TopologyWatcher {
    private final ScheduledExecutorService scheduler = 
        Executors.newSingleThreadScheduledExecutor();
    
    // 每 10 秒从 CN 查询集群拓扑
    public void start() {
        scheduler.scheduleAtFixedRate(() -> {
            ClusterTopology newTopology = fetchTopology();
            ClusterTopology oldTopology = currentTopology.get();
            
            // 对比变化
            Set<CNNode> added = newTopology.getNodes().stream()
                .filter(n -> !oldTopology.contains(n))
                .collect(Collectors.toSet());
            Set<CNNode> removed = oldTopology.getNodes().stream()
                .filter(n -> !newTopology.contains(n))
                .collect(Collectors.toSet());
            
            // 增量更新：只变更受影响的子连接池
            for (CNNode cn : added) {
                poolManager.addSubPool(cn);
            }
            for (CNNode cn : removed) {
                poolManager.drainAndRemoveSubPool(cn);  // 优雅排干
            }
            
            currentTopology.set(newTopology);
        }, 0, 10, TimeUnit.SECONDS);
    }
}
```

**② 连接健康检查**：
```java
// 不是简单的 SELECT 1，而是验证连接有效性 + 节点角色
public class HealthChecker {
    public HealthStatus check(PooledConnection conn) {
        try {
            // 1. Socket 级别检查
            if (conn.isClosed() || !conn.getSocket().isConnected()) {
                return HealthStatus.DEAD;
            }
            // 2. 协议级别检查：发送 Ping 消息
            conn.sendPing(3000);  // 3s 超时
            // 3. 角色检查：验证节点角色没变
            NodeRole currentRole = conn.queryRole();
            if (currentRole != conn.getExpectedRole()) {
                return HealthStatus.ROLE_CHANGED;  // 触发连接池重建
            }
            return HealthStatus.HEALTHY;
        } catch (Exception e) {
            return HealthStatus.DEAD;
        }
    }
}
```

## 四、模块二：二进制协议编解码

### 4.1 为什么用二进制协议？

```
文本协议：
SELECT * FROM bid WHERE amount > 1000
→ 编码为字符串 "SELECT * FROM bid WHERE amount > 1000\0"
→ 优点：可读、调试方便
→ 缺点：编解码开销大、传输体积大

二进制协议：
Query Message:
  Type: 'Q' (1 byte)
  Length: 42 (4 bytes)  
  Query: [binary encoded SQL] (37 bytes)
→ 优点：紧凑、高效、类型安全
→ 缺点：不可读、调试需要抓包工具
```

**兼容 PostgreSQL 协议**：GaussDB 基于 PG 生态，驱动采用了兼容 PG 前端/后端协议的设计。但 GaussDB 的分布式特性（CN 路由信息、全局事务 ID）需要通过**扩展消息类型**来传递。

### 4.2 消息帧格式设计

```
┌──────────────────────────────────────────────────────┐
│  Type    │  Length   │        Payload                │
│  1 byte  │  4 bytes  │    (Length - 4) bytes         │
├──────────┼───────────┼───────────────────────────────┤
│  'Q'     │  00000045 │   SELECT * FROM ... (binary)  │  ← Query 消息
│  'P'     │  00000030 │   Parse 消息 (Statement名+SQL) │
│  'B'     │  00000040 │   Bind 消息 (参数值)           │
│  'E'     │  00000028 │   Execute 消息 (返回行数限制)  │
│  'D'     │  00000100 │   DataRow 消息 (行数据)        │
│  'C'     │  00000020 │   CommandComplete 消息         │
│  'Z'     │  00000005 │   ReadyForQuery 消息           │
└──────────────────────────────────────────────────────┘

GaussDB 扩展消息类型：
  'G' → GlobalTransactionInfo (全局事务ID)
  'N' → NodeStatus (CN/DN 状态变更通知)
  'R' → ReadOnlyHint (只读路由提示)
```

### 4.3 编解码器实现

```java
public class GaussDBBinaryCodec {
    
    // ===== 编码器：Java 对象 → 字节流 =====
    public ByteBuf encodeQuery(String sql) {
        ByteBuf buf = Unpooled.buffer();
        buf.writeByte('Q');                     // Type
        buf.writeInt(sql.length() + 5);         // Length (含自身 4 字节)
        buf.writeBytes(sql.getBytes(UTF_8));    // Payload
        buf.writeByte(0);                       // 终止符 \0
        return buf;
    }
    
    // ===== 解码器：字节流 → RowData =====
    public RowData decodeDataRow(ByteBuf buf) {
        int fieldCount = buf.readShort();       // 列数
        Object[] values = new Object[fieldCount];
        
        for (int i = 0; i < fieldCount; i++) {
            int colLen = buf.readInt();         // 列值长度
            if (colLen == -1) {
                values[i] = null;               // NULL 值
            } else {
                byte[] data = new byte[colLen];
                buf.readBytes(data);
                // 类型转换：二进制 → Java 类型
                values[i] = typeConverter.convert(data, columnTypes[i]);
            }
        }
        return new RowData(values);
    }
}
```

### 4.4 性能优化：为什么能提升 30%？

面试官会问："你说的 30% 是怎么算出来的？"

**优化前后对比**：

| 优化点 | 优化前 | 优化后 | 提升 |
|--------|--------|--------|------|
| 字符串拼接编码 | `"SELECT" + " *" + " FROM" + ...` → 大量临时对象 | ByteBuf 直接写入 → 零字符串拼接 | GC 压力降低 ~40% |
| 逐字节读取 | 循环 readByte() 逐个读 | bulk read + ByteBuf 批读 | 系统调用减少 ~60% |
| 类型转换 | Object → String → parseInt → Object | 直接二进制 → Java 类型 | 转换开销降低 ~50% |
| 内存分配 | new byte[] 频繁分配 | 对象池复用 ByteBuf | 内存分配次数降低 ~70% |

**压测验证**：
```
场景：100 万行查询，每行 20 个字段
优化前：协议解析耗时 8.2s，GC 暂停 12 次
优化后：协议解析耗时 5.7s，GC 暂停 4 次
性能提升：30.5%
```

**面试话术**：
> "30% 是在标准 TPC-C 查询场景下测得的。核心优化有两点：一是 ByteBuf 批量读写减少了系统调用次数，二是对象池复用减少了 GC 压力。但要注意，这个提升主要体现在大数据量查询场景——对于单行查询，编解码本身就不是瓶颈。"

### 4.5 扩展消息类型设计（GaussDB 特有）

```java
// GaussDB 扩展：全局事务信息
public class GlobalTransactionMessage {
    private long globalXid;       // 全局事务 ID（GTM 分配）
    private long snapshotTs;      // 全局快照时间戳
    private IsolationLevel level; // 全局隔离级别
    
    public void encode(ByteBuf buf) {
        buf.writeByte('G');       // GaussDB 扩展消息类型
        buf.writeInt(28);         // Length
        buf.writeLong(globalXid);
        buf.writeLong(snapshotTs);
        buf.writeInt(level.ordinal());
    }
}
```
