# GaussDB JDBC 驱动 —— 面试问答集

> 针对架构师面试的 15 道核心追问，覆盖架构设计、技术选型、重难点攻克、故障排查。

---

## 架构设计类

### Q1: 请画出 GaussDB JDBC 驱动的整体架构图，并说明各层职责。

**考察目的**：架构设计能力和全局视野。

**参考答案**：

```
应用层：DataSource.getConnection() → Connection → Statement → ResultSet
接口层：实现 JDBC 4.2 全部接口 + GaussDB 扩展（分布式事务/Hint/全局配置）
核心层：连接管理 | 负载均衡 | 故障切换 | 读写分离 | 超时熔断 | PS缓存
协议层：二进制协议编解码（兼容 PG 协议 + GaussDB 扩展消息）
传输层：Netty NIO（少量 EventLoop 线程管理大量连接）
```

纵向看，上层对应用透明，下层封装所有 GaussDB 特性。横向看，核心层的六大模块互相解耦，每个模块都可以独立替换。比如你可以把负载均衡从加权随机改成最少连接数，不影响其他模块。

### Q2: 为什么不直接用 HikariCP，而要自研连接池？

**考察目的**：技术选型的判断力，是否理解"何时该造轮子"。

**参考答案**：

我是 HikariCP 的深度用户，原型阶段确实用了它。但很快发现三个无法解决的问题：

**第一，HikariCP 不理解 GaussDB 的拓扑**。GaussDB 有多个协调节点（CN），CN 可能动态扩缩容。HikariCP 的连接池是扁平的——所有连接平等。但我们需要的是一棵树：总连接池 → CN-1 子池 + CN-2 子池 + CN-3 子池。当 CN-3 扩容时，需要为新 CN 自动创建子池并预热连接。

**第二，HikariCP 不理解节点角色**。读写分离场景下，连接分为"主库连接"和"只读连接"。HikariCP 无法区分。

**第三，故障切换不是换个连接那么简单**。CN 故障时，该 CN 的所有连接都不可用，需要批量标记失效并迁移到备用 CN。而且事务中的连接切换需要特殊处理。

所以我们的设计是：**借鉴 HikariCP 的 ConcurrentBag 和 FastList 等优秀设计，但整体架构围绕 GaussDB 的拓扑模型重建**。

---

### Q3: 讲一个你做的最难的技术决策，当时怎么权衡的？

**考察目的**：Trade-off 思维。

**参考答案**：

事务中的故障切换是否需要做到对应用透明？

方案 A：驱动内部自动在新 CN 上重放事务（像某些 NoSQL 驱动那样）。看起来很美好，应用无感知。

方案 B：驱动直接抛异常，告诉应用"事务被中断，请重试整个事务"。

我选了 B。原因是 GaussDB 的全局事务由 GTM 管理，事务 ID、快照版本、锁状态全部绑定在原 CN 上。新 CN 没有这些上下文，即使重发了所有 SQL，快照隔离性也无法保证——可能读到不同的数据版本。

选了 B 之后，我做了补偿：提供了 TransactionRetryTemplate，让应用层重试事务的成本降到最低。

**教训**：不是所有"对用户透明"都是好设计。有时候，暴露真实情况给应用层，比隐藏复杂性更安全。

## 协议与性能类

### Q4: 二进制协议编解码是怎么设计的？30% 的性能提升是怎么量化的？

**考察目的**：性能优化的量化思维。

**参考答案**：

**设计**：基于 PostgreSQL 前端/后端协议，兼容其消息类型（Query/Parse/Bind/Execute/DataRow 等），但针对 GaussDB 特性增加了扩展消息类型（全局事务信息、节点状态通知、只读路由提示）。

每条消息由 Type(1B) + Length(4B) + Payload 组成。编码时用 Netty 的 ByteBuf 直接写入，避免字符串拼接产生大量临时对象。解码时批量读取而不是逐字节读，减少系统调用。

**量化**：TPC-C 标准查询场景，100 万行查询，每行 20 字段。对比了基于字符串拼接的旧实现和 ByteBuf 批量读写的新实现。协议解析耗时从 8.2s 降到 5.7s，GC 暂停从 12 次降到 4 次。

**但要注意**：线上真实场景的收益会小于压测——因为网络 IO 和数据库执行本身占了大头。协议解析的优化主要是降低了客户端的 CPU 和 GC 压力，在高并发 + 大数据量场景下收益最明显。

### Q5: 流式结果集是怎么实现的？fetchSize 设为多少合适？

**考察目的**：协议层面的理解深度。

**参考答案**：

利用 PostgreSQL 协议的 Portal 机制。执行查询时，驱动发送 Execute 消息并带上 fetchSize。服务端返回最多 fetchSize 行数据 + PortalSuspended 状态（表示还有更多数据）。驱动遍历完当前批次后，再次发送 Execute 消息拉取下一批。

**fetchSize 没有银弹**：
- 100-500：适合行大小较大（> 1KB）的场景，严格控制内存
- 1000-2000：适合一般场景，平衡网络往返次数和内存
- 5000-10000：适合行很小（< 100B）且网络延迟高的场景
- 0（默认）：一次性全取，适合结果集小的 OLTP 查询

**一个坑**：fetchSize 太小（如 10），网络往返次数暴增，总耗时不降反升。我们建议默认 0，让用户根据实际情况显式配置。

### Q6: PreparedStatement 缓存失效问题怎么解决？

**考察目的**：对缓存一致性的深度理解。

**参考答案**：

这是 PS 缓存最隐蔽的坑。DDL 变更后，缓存的 PS 元数据过时，执行时可能数据错位。

我们的方案分两层：

**兜底层（必须）**：每次执行缓存的 PS 前，先发 Describe 消息获取当前服务端的列数，与缓存元数据对比。不匹配 → 自动重新 Parse。这个校验开销极小（~0.1ms），但对正确性至关重要。

**优化层（可选）**：监听 GaussDB 的事件通知机制，收到 DDL 事件时主动失效相关 PS 缓存。这可以减少 Describe 校验的开销，但事件通知可能丢 → 所以兜底层不可省略。

**生产建议**：如果业务有频繁 DDL（如分表日切），建议关闭 PS 缓存或限制缓存数量。

## 高可用类

### Q7: 故障自动切换是怎么做到的？恢复时间为什么是秒级？

**考察目的**：Failover 机制的完整理解。

**参考答案**：

秒级恢复的关键是：不等到"确认故障"才切换，而是在"疑似故障"时就开始准备。

**检测层面**：心跳是 5 秒一次，但真正的故障信号是连接上的操作失败（连接断开/超时）。操作失败的检测是实时的，不需要等心跳周期。

**切换流程**（实际耗时约 500ms-2s）：
```
操作失败(0ms) → 重试 1 次同 CN(100ms) → 确认故障 + 标记黑名单(0ms) 
→ LB 选择新 CN(0ms) → 建立新连接(200-500ms) → 在新 CN 上执行(取决于 SQL)
```

**优化点**：连接池中保持少量到备用 CN 的预热连接，切换时直接取，省去建连的 200-500ms。

**不能快的情况**：事务中的切换必须抛异常给应用层——不是因为技术做不到，而是数据正确性要求。全局事务状态在原 CN 上，新 CN 无法保证事务的隔离性。

### Q8: 读写分离中，SELECT ... FOR UPDATE 怎么处理？

**考察目的**：对读写分离边界 case 的理解。

**参考答案**：

FOR UPDATE 是显式加锁的读操作，必须路由到主库。类似的边界 case 还包括：
- 调用序列号函数（nextval）
- 调用有副作用的函数（需要函数元数据标注）
- 事务中的任何 SQL

我们的路由算法是：**先快速判断（正则），不确定的用 JSqlParser 完整解析语法树，还是不确定的走主库**。"疑罪从有"——把写操作误路由到只读副本是灾难，把读操作路由到主库只影响一点性能。

## 故障排查类

### Q9: 生产环境发现有些查询结果列值对不上，但重启后又正常了，可能是什么原因？

**考察目的**：实际排错经验。

**参考答案**：

这就是经典的 PS 缓存失效问题。原因是 DBA 在执行 ALTER TABLE 后，驱动中的 PS 缓存没有失效，用旧的列元数据解析新的结果集。

排查路径：
1. 对照 DBA 的变更时间和故障开始时间
2. 确认 ALTER TABLE 是否新增/删除了列
3. 检查驱动日志，看 PS 缓存命中情况

修复：加上 Describe 校验（Q6 中描述的）。

---

### Q10: 某天发现连接数一直在涨，最终打满数据库连接上限，怎么排查？

**考察目的**：连接泄漏排查。

**参考答案**：

这是连接泄漏。排查思路：

1. 确认连接池配置（maxPoolSize），对比实际物理连接数
2. 如果物理连接数远超 maxPoolSize → 连接没有正常归还
3. 最可能的原因：应用代码中 Statement 或 ResultSet 没有关闭
4. 开启了驱动的泄漏检测，看哪些连接的借用时间异常长
5. 根据泄漏检测的调用栈定位到具体的应用代码

驱动侧的防护：借出超过阈值（如 30 秒）的连接打印 warn 日志 + 调用栈，方便快速定位。

## 面试官可能问的深度追问

### Q11: 这个驱动和 PostgreSQL JDBC 驱动（pgjdbc）是什么关系？为什么要在它的基础上开发？

**考察目的**：了解你是否理解"站在巨人肩膀上"。

**参考答案**：

GaussDB 兼容 PostgreSQL 生态，通信协议与 PG 高度兼容。所以我们没有从零开始——pgjdbc 经过了 20 年的打磨，稳定性和 JDBC 兼容性都非常成熟。

但我们不只是"fork 改改配置"。我们的核心改动：
1. **连接管理**：pgjdbc 是单节点连接模型，我们改成了多 CN 拓扑感知的连接池
2. **负载均衡**：pgjdbc 完全不存在这个概念，这是我们新增的
3. **故障切换**：pgjdbc 的 failover 只能配一个 standby host，我们做到了多 CN + 黑名单 + 动态恢复
4. **读写分离**：pgjdbc 需要靠 PgPool-II 中间件实现，我们内置了
5. **协议扩展**：增加了 GaussDB 特有的全局事务、节点状态等消息类型

选择基于 pgjdbc 开发是一个战略性决策——把精力集中在 GaussDB 的差异化特性上，而不是重新实现一遍 JDBC 规范。

---

### Q12: 如果让你重新设计这个驱动，你会改变什么？

**考察目的**：复盘能力和架构演进思维。

**参考答案**：

有三件事我会做不同选择：

**第一，连接池的拓扑感知应该更早设计成插件化**。当前拓扑感知和连接池是紧耦合的。如果可以重来，我会把拓扑管理抽象成独立的 TopologyProvider 接口，让连接池依赖注入。这样未来如果 GaussDB 的集群架构变了，只需要换一个 TopologyProvider 实现。

**第二，SQL 解析的性能和准确性需要更好的平衡**。当前用 JSqlParser 对复杂 SQL 的解析有 0.5ms 的开销。对于大多数 OLTP 查询（< 1ms 执行时间），解析开销占比太高了。我会增加一个"快速路径"——对模板化的简单 SQL 用更高效的解析方式。

**第三，应该更早引入可观测性**。当前的 Metrics 是后来加的，不够体系化。如果从一开始就设计好 Metrics 接口（连接池/LB/Failover 各维度的指标），对生产排错会更有帮助。

---

### Q13: 面试官如果质疑"你只是基于 pgjdbc 改了改"，你怎么回应？

**考察目的**：如何捍卫自己的技术贡献。

**话术**：

> "如果只是改改配置，不会有这 5 个模块从 0 到 1 的设计。pgjdbc 给我的是一个单节点的稳定实现，我需要把它变成一个分布式数据库的智能驱动。
>
> 打个比方：pgjdbc 是一辆可靠的燃油车，我的工作是把它改造成一辆智能电动车——底盘（协议层）参考了原有设计，但动力系统（负载均衡/故障切换/读写分离）是全新的。
>
> 如果你看代码量：pgjdbc 核心代码约 15 万行，我们新增和改动的代码约 5 万行，其中完全新增的模块占 3 万行。"
