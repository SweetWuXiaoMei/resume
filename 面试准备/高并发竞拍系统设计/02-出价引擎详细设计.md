# 02 — 出价引擎详细设计

> 这是竞拍系统最核心的模块。面试中 50% 的问题会围绕出价引擎。
> 核心问题：如何在高并发下保证出价的强一致性和公平性？

---

## 2.1 问题定义：为什么出价引擎很难？

### 竞拍出价的本质

```
竞拍出价 = 一个"比较并交换"（Compare-And-Swap）操作：

  1. 读取当前最高价 = 95,000 元
  2. 比较：出价 100,000 元 > 95,000 元？ ✓
  3. 写入：更新最高价为 100,000 元
  4. 扣减：冻结车商的保证金 100,000 元
  5. 排序：将车商加入 Top10 排行榜

问题：如果 10 个人同时出价 100,000 元，怎么保证"先到先得"？
问题：如果步骤 3 成功了但步骤 4 失败了，怎么回滚？
```

### 为什么数据库行锁不行？

```sql
-- 如果用数据库行锁（竞品旧方案）
BEGIN;
SELECT @current_max = MAX(amount) FROM bid_record WHERE auction_id = 67890 FOR UPDATE;
-- 如果 @current_max < 100000
INSERT INTO bid_record (auction_id, bidder_id, amount) VALUES (67890, 12345, 100000);
-- 扣保证金
UPDATE deposit SET amount = amount - 100000 WHERE bidder_id = 12345;
COMMIT;

问题分析：
  1. 行锁争用：10 万 QPS 全部卡在 FOR UPDATE → P99 > 3 秒
  2. 死锁风险：扣保证金需要 bidder_id 锁，查出价榜需要 auction_id 锁
  3. 连接池瓶颈：每个事务占用一个连接，事务排队时连接池耗尽
  4. 排序性能：MAX + ORDER BY 在大表上需要全表扫描或复杂索引
```

---

## 2.2 方案设计：Redis Lua 原子引擎

### 设计思路

```
核心洞察：出价的 4 步操作（校验、比较、排行、扣款）必须在"同一个原子"里完成。
Redis 的 Lua 脚本在服务端单线程执行 → 天然满足原子性。

关键问题变成了：这 4 步操作能不能在一个 Lua 脚本里表达？
答案：可以。Redis 的 Lua 环境提供了 ZSet、String、List 等操作命令。

代价评估：
  Lua 脚本执行期间 Redis 阻塞所有其他命令 → 脚本必须轻量
  单次出价 Lua 脚本平均耗时 5-15ms → 单 Redis 可支撑 1000+ 出价/秒
  不够 → Redis Cluster 分片 → 按 auction_id 分
```

### Lua 脚本完整实现

```lua
-- ============================================
-- 竞拍出价引擎 Lua 脚本（核心中的核心）
-- ============================================
-- KEYS[1]: bid:auction:{auctionId}     -- 出价排行榜 ZSet
-- KEYS[2]: bid:queue:{auctionId}       -- 出价顺序队列 List (FIFO兜底)
-- KEYS[3]: hot:max:{auctionId}         -- 最高价缓存
-- KEYS[4]: balance:{bidderId}          -- 保证金余额
-- KEYS[5]: bid:lock:{auctionId}:{bidderId}  -- 用户出价频率限制
-- ARGV[1]: bidderId                   -- 出价人 ID
-- ARGV[2]: amount                     -- 出价金额（分）
-- ARGV[3]: minIncrement               -- 最小加价幅度（分）
-- ARGV[4]: timestampNs                -- 出价时间戳（纳秒）
-- ARGV[5]: maxDeposit                 -- 最大保证金限制

-- ---- 第一步：校验保证金 ----
local balance = redis.call('GET', KEYS[4])
if not balance then
    return {-1, 'INSUFFICIENT_BALANCE', 0}
end
if tonumber(balance) < tonumber(ARGV[2]) then
    return {-1, 'INSUFFICIENT_BALANCE', 0}
end

-- ---- 第二步：检查加价幅度 ----
local currentMaxScore = redis.call('ZREVRANGE', KEYS[1], 0, 0, 'WITHSCORES')
local currentMaxAmount = 0
if currentMaxScore[2] then
    -- 从 score 中解码出价格（score = price * 10^13 + time_encode）
    currentMaxAmount = math.floor(tonumber(currentMaxScore[2]) / 10000000000000)
end

if tonumber(ARGV[2]) < currentMaxAmount + tonumber(ARGV[3]) then
    return {-2, 'BID_TOO_LOW', currentMaxAmount}
end

-- ---- 第三步：出价频率限制（防刷）----
local lastBidTime = redis.call('GET', KEYS[5])
if lastBidTime then
    -- 同一车商对同一拍卖品，500ms 内只能出价一次
    if tonumber(ARGV[4]) - tonumber(lastBidTime) < 500000000 then
        return {-3, 'BID_TOO_FAST', currentMaxAmount}
    end
end
redis.call('SET', KEYS[5], ARGV[4], 'PX', 1000)

-- ---- 第四步：构造 score 并更新排行榜 ----
-- Score 编码：高 13 位 = 价格，低 13 位 = (10^13 - 1 - 时间戳纳秒)
-- 这样同等价格下，时间戳越早（越小）→ 取反后越大 → 排名越前
local MAX_TIME = 9999999999999  -- 10^13 - 1
local timeEncode = MAX_TIME - tonumber(ARGV[4])
local score = tonumber(ARGV[2]) * 10000000000000 + timeEncode

-- ZADD 更新排行榜
redis.call('ZADD', KEYS[1], score, ARGV[1] .. ':' .. ARGV[2])

-- 只保留 Top100（控制 ZSet 大小）
redis.call('ZREMRANGEBYRANK', KEYS[1], 0, -101)

-- ---- 第五步：FIFO 队列兜底（同纳秒出价）----
redis.call('LPUSH', KEYS[2], ARGV[1] .. ':' .. ARGV[2] .. ':' .. ARGV[4])

-- ---- 第六步：更新最高价缓存 ----
redis.call('SET', KEYS[3], ARGV[2], 'EX', 2)

-- ---- 第七步：扣减保证金 ----
redis.call('DECRBY', KEYS[4], ARGV[2])

-- ---- 返回成功 ----
return {0, 'SUCCESS', currentMaxAmount}
```

### Score 编码详解（面试重点）

面试官会问："同一个价格下，怎么保证先出价的人排前面？"

```
ZSet 的 Score 是 Double（64 位浮点数，52 位尾数精确表示整数）

编码公式：
  score = price × 10^13 + (10^13 - 1 - timestampNs)

举例：
  价格 100000 元 = 10000000 分
  时间戳 A = 1700000000000000000 ns（先出价）
  时间戳 B = 1700000000000000500 ns（后出价，晚了 500ns）

  score_A = 10000000 × 10^13 + (10^13 - 1 - 1700000000000000000)
          = 100000000000000000000 + 8299999999999999
          = 100008299999999999999

  score_B = 10000000 × 10^13 + (10^13 - 1 - 1700000000000000500)
          = 100000000000000000000 + 8299999999999499
          = 100008299999999999499

  score_A > score_B → A 排在 B 前面 ✓

精度分析：
  价格最大 10^9 分（1000万元）× 10^13 = 10^22
  Double 精确整数范围 ≈ 9 × 10^15
  → 价格超过 9 亿分（900 万元）时存在精度风险
  → 竞拍车辆价格通常 < 500 万元 → 安全

  如果真的遇到 900 万+ 的车辆（如超跑）：
  → 降低乘数：price × 10^11 + timeEncode
  → 按拍卖品类型动态调整
```

## 2.3 二级校验机制

```
第一级：出价服务本地缓存（Caffeine）
  ┌─────────────────────────────────┐
  │ 本地缓存：当前最高价              │
  │ Key: auctionId                  │
  │ Value: 最高价 + 刷新时间         │
  │ 刷新策略：每 2 秒从 Redis 同步   │
  │                                │
  │ 逻辑：                          │
  │   if (出价 < 缓存最高价) {      │
  │       return "出价过低";        │  ← 拦截 60% 无效请求
  │   }                            │    不经过 Redis，0.5ms 返回
  │   // 出价 >= 缓存最高价         │
  │   进入第二级 →                  │
  └─────────────────────────────────┘

第二级：Redis Lua 精确校验
  ┌─────────────────────────────────┐
  │ 只有出价高于本地缓存中的最高价     │
  │ 才会进入 Redis Lua 引擎          │
  │ 在 Lua 中做最终精确校验           │
  └─────────────────────────────────┘
```

### 为什么有效？

```
竞拍场景的数据特征：
  - 出价只有 10% 是有效出价（高于当前最高价）
  - 90% 是低于当前最高价的无效出价（车商不知道最新价格，报到旧价格）

二级校验的效果：
  90% 的请求在本地缓存层被拦截（0.5ms 返回）
  只有 10% 的请求进入 Redis（15ms 出价）
  
  平均出价延迟 = 90% × 0.5ms + 10% × 15ms = 1.95ms
  
  如果没有本地缓存：
  平均出价延迟 = 100% × 15ms = 15ms
  
  Redis 压力降低：从 10 万 QPS → 1 万 QPS（降低 90%）
```

## 2.4 公平性保证：三层防护

```
第一层：Score 时间戳编码（主力）
  价格相同时，时间戳早的 score 更大 → 排前面
  覆盖 99.99% 的场景

第二层：FIFO 队列（同纳秒兜底）
  极端情况下同一纳秒有多个出价（Redis 单线程但也可能）
  Lua 脚本中将每次出价 LPUSH 到 FIFO 队列
  查询排名时：先按 ZSet score 排序 → score 相同则按 FIFO 队列位置决定

第三层：防刷机制
  同一车商对同一拍卖品 500ms 内只允许一次出价
  防止脚本自动出价扰乱排名

公平性查询实现：
  // 获取排名时同时查 ZSet 和 FIFO 队列
  ZREVRANGE bid:auction:67890 0 9 WITHSCORES  → 按 score 排序
  LRANGE bid:queue:67890 0 -1                   → 按 FIFO 顺序
  合并两个结果：score 优先 → 同 score 按 FIFO 顺序
```

## 2.5 热点拍卖品处理

### 问题

```
热门车辆（如 Model Y 2025款）的拍卖：
  500 个车商激烈竞价
  出价 QPS 可能达到 5000-10000（远超普通拍卖品的 100-500）

Redis 单实例处理热点 Key：
  bid:auction:67890 这个 ZSet Key 落在 Redis Cluster 的某个 Slot
  该 Slot 所在的 Master 节点 CPU 飙高
  其他 Slot 所在的 Master 节点负载很低 → 集群负载严重不均
```

### 解决方案

```
方案 A：Key 拆分（多副本）
  bid:auction:67890:shard1 → Slot 1000
  bid:auction:67890:shard2 → Slot 2000
  bid:auction:67890:shard3 → Slot 3000
  
  出价时随机选一个 shard 写入
  读取时合并所有 shard 的结果
  
  问题：写不一致 → 需要额外的合并排序逻辑
  结论：竞拍系统不适用（出价需要绝对一致）

方案 B：应用层限流（竞拍系统采用）
  在出价服务层按 auctionId 做限流
  热门拍卖品：每 100ms 一个车商只能出价一次
  Netty 网关层对热门拍卖品做令牌桶限流（5000 QPS / 拍卖品）

方案 C：预排序 + 批处理（兜底）
  如果 Redis 单 Key 扛不住 → 降级为"排队出价"模式
  出价不立即入 ZSet，而是先入 MQ 队列
  消费者批量处理出价，每 100ms 刷新一次排行榜
  延迟从 20ms → 200ms（可接受的有损服务）

实际采用：方案 B（预防）+ 方案 C（兜底）
```

## 2.6 Redis 灾备与恢复

### 故障场景

```
场景：Redis Cluster 中负责热门拍卖品 Slot 的 Master 挂了

流程：
  1. Sentinel 检测到 Master 宕机（5 秒）
  2. 从 Slave 中选新 Master → 提升（3 秒）
  3. 新 Master 开始接受写入
  
  问题：Slave 可能还没同步最新的 Master 数据（异步复制）
        → 最后几条出价可能丢失
```

### 灾备方案

```
第一道防线：AOF + 混合持久化
  appendonly yes
  aof-use-rdb-preamble yes
  appendfsync everysec  → 最多丢 1 秒数据

第二道防线：RocketMQ 异步落库
  每次出价成功后 → 发送事务消息到 RocketMQ
  消费者收到消息 → 写入 MySQL
  Redis 恢复后 → 从 MySQL 回放未同步的出价记录

第三道防线：Redis 挂了但有损服务继续
  出价请求降级为"MQ + DB"模式：
    出价 → 发送到 RocketMQ → 消费者串行处理 → 写入 Redis + DB
    延迟从 20ms → 500ms（有损但可用）
    降级期间：关闭实时排行榜推送，改为 1 秒轮询

Redis 恢复后的数据修复：
  1. 从 MySQL 查出故障期间的所有出价记录
  2. 按 bid_time 排序 → 重新执行出价计算（恢复排行榜最终状态）
  3. 对比 Redis 中的排行榜 → 补全丢失的出价
```

## 2.7 Java 端调用实现

```java
@Service
public class BidEngineService {
    
    private final RedisTemplate<String, Object> redis;
    private final StringRedisTemplate stringRedis;
    
    // Lua 脚本 SHA（首次加载后使用 EVALSHA，减少网络传输）
    private volatile String bidScriptSha;
    
    @PostConstruct
    public void init() {
        String script = loadScriptFromResource("bid_engine.lua");
        this.bidScriptSha = stringRedis.getConnectionFactory()
            .getConnection().scriptLoad(script.getBytes());
    }
    
    public BidResult execute(Long auctionId, Long bidderId, Long amount, 
                            Long minIncrement) {
        long timestampNs = System.nanoTime();
        
        List<String> keys = Arrays.asList(
            "bid:auction:" + auctionId,      // KEYS[1]: ZSet 排行榜
            "bid:queue:" + auctionId,        // KEYS[2]: FIFO 队列
            "hot:max:" + auctionId,          // KEYS[3]: 最高价缓存
            "balance:" + bidderId,           // KEYS[4]: 保证金
            "bid:lock:" + auctionId + ":" + bidderId // KEYS[5]: 频率限制
        );
        
        List<String> args = Arrays.asList(
            String.valueOf(bidderId),
            String.valueOf(amount),
            String.valueOf(minIncrement),
            String.valueOf(timestampNs),
            String.valueOf(maxDeposit)
        );
        
        // 执行 Lua 脚本
        List<Long> result;
        try {
            result = (List<Long>) stringRedis.execute(
                new DefaultRedisScript<>(bidScriptSha, List.class),
                keys,
                args.toArray()
            );
        } catch (RedisConnectionFailureException e) {
            // Redis 不可用 → 降级为 MQ 模式
            return fallbackBidEngine.execute(auctionId, bidderId, amount);
        }
        
        long code = result.get(0);
        long prevMax = result.size() > 2 ? result.get(2) : 0;
        
        return switch ((int) code) {
            case 0  -> {
                // 异步发送 MQ 事件
                mqProducer.sendBidSuccessEvent(auctionId, bidderId, amount, timestampNs);
                yield BidResult.success(prevMax);
            }
            case -1 -> BidResult.insufficientBalance();
            case -2 -> BidResult.bidTooLow(prevMax);
            case -3 -> BidResult.bidTooFast();
            default -> BidResult.unknownError();
        };
    }
}
```
