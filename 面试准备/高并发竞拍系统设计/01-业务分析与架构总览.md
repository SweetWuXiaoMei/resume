## 1.1 业务背景：二手车在线竞拍是怎么玩的？

面试官可能不了解二手车拍卖的业务，你要能用 2 分钟讲清楚。**理解业务是做架构设计的前提**。

### 拍卖流程

```
┌──────────────────────────────────────────────────────────────────┐
│  卖家卖车 → 天天拍车检测(3000+字段检测报告) → 上架拍卖              │
│                                                                  │
│  拍卖开始(倒计时 15 分钟)                                          │
│    │                                                             │
│    ├── 车商 A 出价 80,000 元                                      │
│    ├── 车商 B 出价 81,000 元  →  所有在线车商实时看到 B 排第一     │
│    ├── 车商 C 出价 82,500 元  →  排行榜实时刷新                    │
│    ├── ...                                                       │
│    │                                                             │
│    ▼                                                             │
│  倒计时结束 → 出价最高者获胜 → 进入线下交易流程                     │
└──────────────────────────────────────────────────────────────────┘
```

### 业务特征（影响架构设计的关键）

| 业务特征 | 数值 | 对架构的影响 |
|---------|------|-------------|
| 同时在线车商 | 5-10 万 | 需要长连接，不能短连接轮询 |
| 每场拍卖参与人数 | 200-500 人 | 推送广播范围可控 |
| 同时进行拍卖场次 | 200-500 场 | 需要隔离，A 拍卖不影响 B 拍卖 |
| 出价延迟容忍度 | 车商期望"即点即到" | P99 必须 < 100ms |
| 价格变动频率 | 热门车辆秒级多次出价 | 推送频率极高 |
| 出价金额区间 | 几万到几十万 | 金额精确到分，不能有计算误差 |
| 竞拍公平性 | 法律要求 | 先出价者必须排前面 |

## 1.2 需求拆解

### 功能需求

```
F1: 车商实时出价           → 必须高于当前最高价 + 最小加价幅度
F2: 排行榜实时刷新          → 显示当前 Top10 出价
F3: 出价成功/失败通知       → 实时告知车商出价结果
F4: 保证金冻结/扣减         → 出价需要冻结保证金，防止恶意出价
F5: 历史出价记录            → 拍卖结束后可回溯
```

### 非功能需求（架构师的核心关注点）

```
NF1: 低延迟     → 出价 P99 < 100ms，通知 P99 < 200ms
NF2: 高并发     → 单品峰值 10 万+ QPS
NF3: 强一致性   → 不允许超卖、排序错乱、出价丢失
NF4: 高可用     → 99.99% 可用（全年停机 < 53 分钟）
NF5: 水平扩展   → 拍卖场次增加时直接加机器，不需要改架构
NF6: 公平性     → 同一价格下，先出价者排前面
```

### 非功能需求如何量化？

面试时你说"P99 < 100ms"，面试官会问"这个 100ms 怎么来的？"

```
100ms 是怎么定的？
  - 用户感知研究：200ms 是"感觉有延迟"的阈值，100ms 是"感觉即时"的阈值
  - 竞品对标：二手车拍卖的头部平台出价延迟在 50-150ms 之间
  - 技术可行性：Redis Lua 原子操作 5-20ms + 网络传输 10-30ms + 序列化 2-5ms = 可控制在 100ms 内
  → 设定目标 P99 < 100ms，既满足业务，技术上也可达到
```

## 1.3 架构设计原则

我在设计这个系统时，确立了五条原则：

```
原则 1: 出价链路极简
  "出价请求的路径上，能少一个环节就少一个环节。
   多一个环节 = 多一个延迟 + 多一个故障点。"

原则 2: 状态外移
  "应用服务器不保存拍卖状态。所有状态都在 Redis 中。
   这样服务器可以随时重启、扩缩容，不影响任何拍卖。"

原则 3: 核心路径同步，非核心路径异步
  "出价的'校验+排行+扣款'必须同步原子完成。
   但'通知车商+记录日志+落库'可以异步。"

原则 4: 每层都有兜底
  "不信任任何一个组件。Redis 挂了？MQ 补。MQ 挂了？本地日志补。"

原则 5: 可观测性内建
  "不是事后加监控，而是设计时就定义好每个环节的指标。"
```

### 架构分层和职责

| 层级 | 组件 | 核心职责 | 设计要点 |
|------|------|---------|---------|
| **接入层** | Nginx + Keepalived | L4 负载均衡、SSL 终结 | 不做 L7 路由（WebSocket 升级由 Netty 处理） |
| **网关层** | Netty 集群 | 长连接管理、协议解析、心跳保活、IP 限流 | 无状态，每个节点管理 5 万连接 |
| **服务层** | Dubbo 微服务 | 出价业务、保证金业务、推送调度 | 无状态 + 水平扩展 |
| **引擎层** | Redis Cluster | 出价引擎（Lua）、排行榜（ZSet）、保证金查询 | 有状态，3 主 3 从高可用 |
| **消息层** | RocketMQ | 事件广播、异步解耦、削峰填谷 | 精准路由 + 广播混合模式 |
| **协调层** | ZooKeeper | 路由映射、节点注册、配置管理 | 临时节点自动感知节点上下线 |
| **存储层** | MySQL MGR | 出价记录、保证金流水、对账 | 组复制保证高可用 |

## 1.5 技术选型决策（核心面试内容）

### 决策 1: 为什么用 Netty 而不是 Tomcat/Undertow？

```
Tomcat/Undertow：一个请求一个线程（Servlet 模型）
  10 万长连接 = 10 万线程(或连接等待队列) = 内存爆炸(每线程 ~1MB 栈)
  P99 延迟不可控（线程调度依赖 OS）

Netty：事件驱动 + Reactor 模型
  10 万长连接 = 少量 EventLoop 线程(通常 CPU 核数 × 2 = 16 个)
  所有 IO 操作非阻塞，内存和 CPU 可控
```

### 决策 2: 为什么出价引擎用 Redis Lua 而不是数据库行锁？

```
数据库行锁方案：
  出价 = SELECT FOR UPDATE → 检查金额 → UPDATE → 释放锁
  问题 1：行锁争用 → 10 万 QPS 下 P99 > 3s
  问题 2：死锁（扣保证金 + 查出价榜相互等）
  问题 3：数据库连接池瓶颈

Redis Lua 方案：
  出价 = EVAL 一个 Lua 脚本（校验+排行+扣款，全部原子）
  优势 1：单线程执行 → 天然无竞争 → P99 < 30ms
  优势 2：Lua 内 5 步操作原子 → 彻底杜绝超卖
  代价 1：Redis 挂了一切都挂了（需要灾备方案）
  代价 2：Lua 脚本执行期间 Redis 阻塞（脚本必须轻量）
```

### 决策 3: 为什么用 RocketMQ 广播 + 精准路由，而不是全量广播？

```
全量广播：
  出价事件 → 所有 10 个 Netty 节点 → 每个节点遍历 5 万连接 → 找到关注者
  复杂度：O(10 × 50000) = 50 万次判断 / 每次出价
  CPU 浪费严重

精准路由：
  出价事件 → 只发给"有该车辆关注者"的 Netty 节点
  复杂度：O(该车辆在所有节点上的关注者总数) ≈ O(200-500)
  10 倍效率提升

混合模式：RocketMQ 广播到所有节点 + 各节点本地判断是否需要推送
  好处：不需要额外的路由服务，直接利用 MQ 的广播能力
  过滤：不需要推送的节点在收到消息后 0.01ms 内丢弃
```

### 决策 4: 为什么自建 ZK 路由注册中心，而不是用 Redis？

```
需求：车商进入拍卖间 → 需要知道连接在哪个 Netty 节点上
要求：Netty 节点宕机 → 映射自动清除

ZooKeeper：
  临时节点(EPHEMERAL)：Netty 节点注册后，和 ZK 保持心跳
  Netty 宕机 → 心跳断开 → ZK 自动删除临时节点 → 映射自动更新
  Watch 机制：业务服务可以 Watch 映射变化

Redis：
  需要自己实现心跳和过期，不如 ZK 的临时节点可靠
  Redis 的主从切换可能导致数据丢失
```

## 1.6 核心流程：一次出价的完整旅程

```
  车商 App
    │
    │ ① WebSocket 发送出价请求
    │    {auctionId: 67890, amount: 100000}
    ▼
┌──────────────────────────────────────────────┐
│ Netty 网关                                    │
│ ② IP 限流检查（令牌桶，100次/秒/车商）         │
│ ③ Protobuf 解码                              │
│ ④ 查 ZK → 路由到对应出价服务                   │  耗时: ~3ms
└──────────────────────────────────────────────┘
    │ Dubbo RPC
    ▼
┌──────────────────────────────────────────────┐
│ 出价服务                                      │
│ ⑤ 本地缓存校验：当前最高价 95000 > 出价 80000? │
│    是 → 直接返回"出价过低"，不经过 Redis       │  耗时: ~0.5ms
│    否 → 进入 Redis Lua                        │
└──────────────────────────────────────────────┘
    │ Redis Lua EVAL
    ▼
┌──────────────────────────────────────────────┐
│ Redis Lua 原子脚本                             │
│ ⑥ 检查保证金余额 >= 出价金额                    │
│ ⑦ 检查出价 > 当前最高价                        │
│ ⑧ ZADD 更新排行榜（score = 金额编码）           │  耗时: ~10ms
│ ⑨ DECRBY 扣减保证金                            │
│ ⑩ 返回结果 (success / fail)                    │
└──────────────────────────────────────────────┘
    │ 返回结果
    ▼
┌──────────────────────────────────────────────┐
│ 出价服务（收到结果后）                          │
│ ⑪ 发送 RocketMQ 事务消息(异步落库)              │
│ ⑫ 返回出价结果给 Netty 网关                     │
└──────────────────────────────────────────────┘
    │
    ▼
┌──────────────────────────────────────────────┐
│ Netty 网关                                     │
│ ⑬ Protobuf 编码 + Delta Encoding              │  耗时: ~1ms
│ ⑭ 返回出价结果给车商 App                        │
└──────────────────────────────────────────────┘
    │
    │ 总耗时(车商视角): ~15-20ms
    │
    ▼
  车商 App 看到"出价成功"（几乎即时）

与此同时（异步）：
┌──────────────────────────────────────────────┐
│ RocketMQ 消费端                                │
│ ⑮ 消费出价事件 → 推送服务                       │
│ ⑯ 推送服务查 ZK → 获取该车辆关注者在哪些网关节点 │
│ ⑰ 精准推送：Netty 节点 → WebSocket → 其他车商   │  耗时: ~50ms
│    收到通知"有人出价 10 万，排行榜已更新"        │
└──────────────────────────────────────────────┘
```

### 为什么出价返回和排行榜推送是分开的？

```
"出价返回给这个车商"和"通知其他车商排行榜变化"是两个独立需求：
  - 出价车商需要最快得知出价结果（同步）
  - 其他车商需要看到排行榜更新（可以异步，100ms 内即可）

分开的好处：
  1. 出价链路不因推送慢而变慢
  2. 推送失败不影响出价成功
  3. 推送可以做更多处理（Delta Encoding、批量合并）
```

## 1.7 数据模型设计

### Redis 数据结构

```
# 1. 出价排行榜（每个拍卖品一个 ZSet）
Key:    bid:auction:{auctionId}
Type:   Sorted Set
Member: "{bidderId}"
Score:  {price} * 10^13 + (10^13 - 1 - {timestamp_ns})
        价格编码（高 13 位）+ 时间戳取反编码（低 13 位）
        保证：高价格排前面，同价格先出价排前面
TTL:    拍卖结束后 1 小时

# 2. 保证金余额（每个车商一个）
Key:    balance:{bidderId}
Type:   String (数字)
Value:  当前可用保证金（单位：分）
TTL:    永久

# 3. 出价顺序队列（FIFO 兜底，处理同纳秒出价）
Key:    bid:queue:{auctionId}
Type:   List
Value:  "{bidderId}:{amount}" 按出价时间先后入队
TTL:    同排行榜

# 4. 热点拍卖品最高价缓存（出价服务本地）
Key:    hot:max:{auctionId}
Type:   String
Value:  当前最高价（秒级同步）
TTL:    2 秒
```

### MySQL 表结构

```sql
-- 出价记录表（分库分表：按 auction_id 分片）
CREATE TABLE bid_record (
    id BIGINT PRIMARY KEY,
    auction_id BIGINT NOT NULL,
    bidder_id BIGINT NOT NULL,
    amount BIGINT NOT NULL COMMENT '出价金额(分)',
    bid_time DATETIME(3) NOT NULL COMMENT '出价时间(毫秒精度)',
    result TINYINT NOT NULL COMMENT '1成功 2余额不足 3出价过低',
    INDEX idx_auction_bidder (auction_id, bidder_id),
    INDEX idx_bid_time (bid_time)
) ENGINE=InnoDB;

-- 保证金流水表
CREATE TABLE deposit_record (
    id BIGINT PRIMARY KEY,
    bidder_id BIGINT NOT NULL,
    auction_id BIGINT NOT NULL,
    amount BIGINT NOT NULL COMMENT '变动金额(分，正数为冻结，负数为解冻)',
    type TINYINT NOT NULL COMMENT '1出价冻结 2成交扣除 3失败解冻',
    created_at DATETIME NOT NULL,
    INDEX idx_bidder_time (bidder_id, created_at)
) ENGINE=InnoDB;
```

## 1.8 面试中如何"一句话介绍这个系统"

面试官问："你做过的最有挑战的项目是什么？"

> "天天拍车的核心实时竞价系统。这个系统支撑了公司 90% 以上的交易额，需要在 10 万+ 车商同时在线竞价的场景下，保证出价、排序、通知的强一致性和极低延迟。
>
> 我作为架构师主导了整个系统的设计。核心思路是：Redis Lua 原子脚本做竞价引擎——把出价校验、金额比较、排行榜更新、保证金扣减四步操作在 Lua 里原子完成，彻底消灭了超卖和数据竞争。网络层用 Netty 做长连接网关，单机能扛 5 万连接。通知系统用了 RocketMQ 广播和精准路由结合的混合推送，把推送效率提升了 10 倍。
>
> 最终效果：出价 P99 延迟 75ms，通知延迟 150ms 以内，系统可用性 99.99%。这是我职业生涯中最接近'完美架构'的一次实践。"
