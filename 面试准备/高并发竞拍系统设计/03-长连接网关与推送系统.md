## 3.1 长连接网关设计

### 为什么需要自建网关？

```
竞拍的特性决定了 HTTP 短连接不够：
  1. 服务器需要主动推送（价格变动→通知车商）→ WebSocket 全双工
  2. 车商需要常驻拍卖间（15 分钟以上）→ 长连接比短连接效率高
  3. HTTP 轮询的问题是：轮快了浪费带宽和服务器资源，轮慢了信息滞后

结论：必须用 WebSocket 长连接 + 服务器主动推送
```

### Netty 主从 Reactor 线程模型

### 关键配置

```java
@Configuration
public class NettyGatewayConfig {
    
    @Bean
    public ServerBootstrap serverBootstrap() {
        EventLoopGroup bossGroup = new NioEventLoopGroup(2);
        EventLoopGroup workerGroup = new NioEventLoopGroup(
            Runtime.getRuntime().availableProcessors() * 2
        );
        
        ServerBootstrap bootstrap = new ServerBootstrap();
        bootstrap.group(bossGroup, workerGroup)
            .channel(NioServerSocketChannel.class)
            
            // ===== TCP 参数配置 =====
            // 全连接队列：三次握手完成但未被 accept 的连接
            .option(ChannelOption.SO_BACKLOG, 65535)
            // SO_REUSEADDR：允许重用 TIME_WAIT 的端口
            .option(ChannelOption.SO_REUSEADDR, true)
            
            // ===== 子 Channel 配置 =====
            // TCP_NODELAY：禁用 Nagle 算法（小包立即发送，不等待合并）
            .childOption(ChannelOption.TCP_NODELAY, true)
            // SO_KEEPALIVE：TCP 保活
            .childOption(ChannelOption.SO_KEEPALIVE, true)
            // SO_RCVBUF / SO_SNDBUF：收发缓冲区
            .childOption(ChannelOption.SO_RCVBUF, 65536)
            .childOption(ChannelOption.SO_SNDBUF, 65536)
            // 高低水位线：防止写缓冲区 OOM
            .childOption(ChannelOption.WRITE_BUFFER_WATER_MARK,
                new WriteBufferWaterMark(
                    32 * 1024,   // 低水位：32KB → 恢复可写
                    128 * 1024   // 高水位：128KB → 暂停写入
                ))
            
            .childHandler(new ChannelInitializer<SocketChannel>() {
                @Override
                protected void initChannel(SocketChannel ch) {
                    ChannelPipeline pipeline = ch.pipeline();
                    
                    // 1. Protobuf 编解码（支持变长帧）
                    pipeline.addLast(new ProtobufVarint32FrameDecoder());
                    pipeline.addLast(new ProtobufVarint32LengthFieldPrepender());
                    pipeline.addLast(new ProtobufDecoder(
                        BidProtocol.getDefaultInstance()));
                    pipeline.addLast(new ProtobufEncoder());
                    
                    // 2. 空闲检测：60s 读空闲 → 认为客户端心跳丢失
                    pipeline.addLast(new IdleStateHandler(
                        60,   // 读空闲：60 秒没有收到客户端消息
                        0,    // 写空闲：不检测
                        0     // 读写空闲：不检测
                    ));
                    
                    // 3. 心跳处理器
                    pipeline.addLast(new HeartbeatHandler());
                    
                    // 4. 业务处理器
                    pipeline.addLast(new BidMessageHandler());
                }
            });
        
        return bootstrap;
    }
}
```

### 连接管理

```java
@Component
public class ConnectionRegistry {
    // 车商 ID → WebSocket Channel
    private final ConcurrentHashMap<Long, Channel> bidderChannelMap = 
        new ConcurrentHashMap<>();
    
    // 拍卖品 ID → 关注该拍卖品的车商 ID 集合（本地缓存）
    private final ConcurrentHashMap<Long, Set<Long>> auctionFollowers = 
        new ConcurrentHashMap<>();
    
    // 连接计数（用于负载上报）
    private final AtomicInteger activeConnections = new AtomicInteger(0);
    
    public void register(Long bidderId, Channel channel) {
        bidderChannelMap.put(bidderId, channel);
        activeConnections.incrementAndGet();
        // 注册到 ZK 路由表
        zkRegistry.registerBidder(bidderId, getLocalServerId());
    }
    
    public void unregister(Long bidderId) {
        bidderChannelMap.remove(bidderId);
        activeConnections.decrementAndGet();
        zkRegistry.unregisterBidder(bidderId);
    }
    
    public Channel getChannel(Long bidderId) {
        return bidderChannelMap.get(bidderId);
    }
    
    // 车商进入拍卖间 → 建立关注关系
    public void followAuction(Long bidderId, Long auctionId) {
        auctionFollowers.computeIfAbsent(auctionId, k -> ConcurrentHashMap.newKeySet())
            .add(bidderId);
        // ZK 注册：该拍卖品在该网关节点有关注者
        zkRegistry.addAuctionFollower(auctionId, getLocalServerId());
    }
    
    // 推送消息给关注某个拍卖品的所有本地车商
    public void pushToAuctionFollowers(Long auctionId, BidPushMessage msg) {
        Set<Long> followers = auctionFollowers.get(auctionId);
        if (followers == null) return;
        
        for (Long bidderId : followers) {
            Channel channel = bidderChannelMap.get(bidderId);
            if (channel != null && channel.isActive()) {
                // 高低水位保护
                if (channel.isWritable()) {
                    channel.writeAndFlush(msg);
                } else {
                    // 写缓冲区满了 → 丢弃该消息（推送允许有损）
                    metrics.pushDropped(auctionId, bidderId);
                }
            }
        }
    }
}
```

## 3.2 "车辆-服务器"路由注册中心

### 设计问题

```
问题：推送通知时，怎么知道"关注拍卖品 X 的车商 Y 连接在哪个 Netty 网关节点的机器 C 上"？

朴素方案：广播给所有 Netty 节点 → 每个节点遍历自己的连接找 Y
  问题：10 个节点 × 5 万连接 = 50 万次查找 → 浪费

ZK 路由方案：
  车商 Y 连接在网关节点 C 上 → 在 ZK 上创建临时节点
  /bid/mapping/{auctionId}/{serverId} 
  
  推送时：查 ZK → 知道哪些网关节点有该拍卖品的关注者 → 只推给这些节点
```

### ZooKeeper 路径设计

```
/bid
  ├── /servers
  │     ├── /server-001  [临时节点] {ip: "10.0.0.1", load: 24563, cpu: 45%}
  │     ├── /server-002  [临时节点] {ip: "10.0.0.2", load: 32100, cpu: 52%}
  │     └── /server-003  [临时节点] {ip: "10.0.0.3", load: 18900, cpu: 38%}
  │
  ├── /mapping
  │     ├── /auction-67890
  │     │     ├── /server-001  [临时节点] ← server-001 上有该拍卖的关注者
  │     │     └── /server-003  [临时节点] ← server-003 上也有
  │     └── /auction-67891
  │           └── /server-002  [临时节点]
  │
  └── /bidder
        ├── /bidder-12345  [临时节点] {serverId: "server-001"}
        └── /bidder-12346  [临时节点] {serverId: "server-003"}
```

### 车商进入拍卖间的完整流程

```
1. 车商 App → WebSocket 连接到 Netty 网关
  网关分配连接到 Node-3（通过 Nginx LB 选择）

2. 车商发送"进入拍卖间"消息 {auctionId: 67890}
  
3. Netty Node-3 处理：
   a. 本地注册：ConnectionRegistry.followAuction(bidderId, auctionId)
   b. ZK 注册：创建 /bid/mapping/auction-67890/server-003（临时节点）
   c. ZK 注册：创建 /bid/bidder/bidder-12345（临时节点，记录所在服务器）

4. 当 Node-3 宕机时：
   ZK 自动删除临时节点 → /bid/mapping/auction-67890/server-003 消失
   推送服务 Watch 到变化 → 知道该拍卖品在 Node-3 上不再有关注者
   车商重连 → 连接到新节点 → 重新注册
```

### ZK 路由感知带来的负载均衡

```
车商进入拍卖间时：
  ① 查询 ZK → 获取所有 Netty 节点负载信息
     {server-001: 45%, server-002: 52%, server-003: 38%}
  
  ② 选择负载最低的节点（server-003，38%）
  
  ③ 告诉车商 App：你的 WebSocket 连接到 10.0.0.3:8080
  
  ④ 车商连接到 server-003 → 后续该车商的所有出价和通知都在这条连接上

好处：
  - 热门拍卖品的关注者会分散到多个 Netty 节点（因为不同车商进入时间不同）
  - 不会出现"500 个车商全连在同一个 Netty 节点"的热点
```

## 3.3 混合推送模式

### 推送流程

```
出价成功
  │
  ▼
┌────────────────────────────────────────────────────────────┐
│  出价服务                                                     │
│  ① 发送 RocketMQ 消息                                        │
│     Topic: BID_EVENT                                        │
│     Body: {auctionId, bidderId, amount, deltaAmount, rank}  │
│     Tag: auction_{auctionId % 8}                            │
└──────────────────────┬─────────────────────────────────────┘
                       │ 广播模式：所有推送服务节点都收到
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  推送服务 Node-A  推送服务 Node-B  推送服务 Node-C
        │              │              │
        │ ② 查 ZK：这个拍卖品在哪些网关节点有关注者？
        │    拍卖品 67890 → [网关 Node-1, 网关 Node-3]
        │
        │ ③ 不是本推送服务负责的网关节点 → 发给对应推送服务
        │    或：每个推送服务负责固定的几个网关节点
        │
        ▼
┌────────────────────────────────────────────────────────────┐
│  Netty 网关 Node-1                                           │
│  ④ 查本地关注者：拍卖品 67890 → [车商A, 车商B, ..., 车商Z]   │
│  ⑤ 对每个关注者：                                             │
│     - 检查 Channel 是否活跃                                   │
│     - 检查写缓冲区水位                                         │
│     - Delta Encoding 编码消息                                 │
│     - writeAndFlush() 推送                                    │
└────────────────────────────────────────────────────────────┘
```

### 复杂度分析

```
全量广播方案：
  出价事件 → MQ 广播 → 10 个 Netty 节点 → 每个节点遍历所有 5 万连接
  每次出价 O(10 × 50000) = 50 万次判断
  如果每秒 1000 次出价 → 5 亿次判断/秒

混合推送方案：
  出价事件 → MQ 广播 → 10 个 Netty 节点 → 每个节点查本地关注者（平均 50 人）
  每次出价 O(10 + 50) = 60 次操作
  如果每秒 1000 次出价 → 6 万次操作/秒

提升：50 万 / 60 ≈ 8333 倍（理论值）
实际提升：约 10 倍（还要考虑 MQ 传输、网络、序列化等固定开销）
```

## 3.4 Delta Encoding 极致压缩

### 为什么需要压缩？

```
每场拍卖 500 个在线车商
每次出价都要推送通知给 500 人
每秒 10 次出价 × 500 人 = 5000 次推送/秒

如果不压缩：
  每条推送消息 ≈ 50 字节(Protobuf)
  带宽 = 5000 × 50 = 250 KB/s ≈ 2 Mbps（单场拍卖）
  200 场同时拍卖 = 400 Mbps
  
如果压缩：
  90% 的消息体变小：1 字节(Delta) + 少量元数据 ≈ 10 字节
  带宽 = 500 × 50 + 4500 × 10 = 25 KB/s + 45 KB/s = 70 KB/s
  200 场 = 14 Mbps → 节省 96%
```

### 实现

```java
public class DeltaEncoder {
    private final ConcurrentHashMap<Long, Long> lastAmountMap = 
        new ConcurrentHashMap<>(); // auctionId → 最后一次推送的价格
    
    public BidPushMessage encode(Long auctionId, Long currentAmount, 
                                  int rank, Long timestamp) {
        Long lastAmount = lastAmountMap.get(auctionId);
        
        BidPushMessage.Builder msg = BidPushMessage.newBuilder()
            .setAuctionId(auctionId)
            .setRank(rank)
            .setTimestamp(timestamp);
        
        if (lastAmount == null) {
            // 首次推送：发完整价格
            msg.setAbsoluteAmount(currentAmount);
        } else {
            // 后续推送：发差值
            long delta = currentAmount - lastAmount;
            msg.setDeltaAmount(delta);
        }
        
        lastAmountMap.put(auctionId, currentAmount);
        return msg.build();
    }
}

public class DeltaDecoder {
    private final ConcurrentHashMap<Long, Long> lastAmountMap = 
        new ConcurrentHashMap<>(); // auctionId → 当前显示的价格
    
    public long decode(BidPushMessage msg) {
        long auctionId = msg.getAuctionId();
        
        if (msg.hasAbsoluteAmount()) {
            // 首次接收：用完整价格初始化
            long amount = msg.getAbsoluteAmount();
            lastAmountMap.put(auctionId, amount);
            return amount;
        } else {
            // 接收差值：累加到当前价格
            long current = lastAmountMap.getOrDefault(auctionId, 0L);
            long newAmount = current + msg.getDeltaAmount();
            lastAmountMap.put(auctionId, newAmount);
            return newAmount;
        }
    }
}
```

### 丢包处理

```
问题：如果 Delta 消息丢了，后续所有 Delta 都错位

方案：
  1. 客户端启动时先拉全量快照（初始化 baseline）
  2. 每 100 条 Delta 消息插入一条全量同步消息
  3. 客户端收到全量同步消息时校准本地状态
  4. 如果检测到价格跳变过大（Delta 超过合理范围）→ 主动拉全量快照
```

## 3.5 10 万连接的单机优化清单

| 优化点 | 默认值/问题 | 优化值/方案 | 效果 |
|--------|------------|------------|------|
| 文件描述符 | 1024 | 655350 | 支撑 10 万+ 连接 |
| somaxconn | 128 | 65535 | 全连接队列不丢连接 |
| tcp_tw_reuse | 0 | 1 | TIME_WAIT 端口复用 |
| Netty 高低水位 | 无/默认 | 32KB/128KB | 防止写缓冲区 OOM |
| 心跳空闲检测 | 无 | 60s 读空闲 | 主动剔除死连接 |
| JVM 堆大小 | 默认 | 8-12G | 支撑 5 万连接的 Channel 对象 |
| 直接内存 | 默认 | 4G | Netty Direct Buffer |
| G1 GC | 默认 | MaxGCPauseMillis=100 | 控制 GC 停顿 |
| ByteBuf 分配 | Pooled | Pooled + LeakDetector | 减少内存分配/回收 |
