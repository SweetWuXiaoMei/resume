## 5.1 3 分钟项目推介（必背）

面试官 90% 会问："介绍一个你做过的最有挑战的项目。"

```
"S — 背景"（30 秒）

天天拍车是国内头部二手车拍卖平台。我负责的是核心实时竞价系统，
这个系统支撑了公司 90% 以上的交易额。

挑战在于：10 万+ 车商同时在线竞价，出价要求 P99 < 100ms 的极低延迟，
同时必须保证出价的强一致性和公平性——不允许超卖、不允许排序错乱。

原有系统用的是数据库行锁处理出价，大促期间 P99 延迟爆到 3 秒以上，
多次出现出价丢失的严重事故。


"T — 任务"（20 秒）

我作为架构师，需要重新设计整个竞价系统，达到三个目标：
第一，出价 P99 < 100ms；第二，通知延迟 < 200ms；第三，99.99% 可用性。


"A — 行动"（90 秒）

我做了四个核心设计：

第一，出价引擎。我选了 Redis Lua 原子脚本——把出价校验、金额比较、
排行榜更新、保证金扣减四步操作封装在一个 Lua 脚本里，利用 Redis 
单线程执行的特性保证原子性。这彻底消灭了超卖问题。

为了进一步降低延迟，我还加了本地缓存拦截——低于当前最高价的出价，
在业务服务器上直接拒绝，不经过 Redis。这拦截了 60% 的无效请求，
出价 P99 最终控制在 75ms。

第二，长连接网关。用 Netty 自研了分布式网关集群，主从 Reactor 模型，
单机扛 5 万 WebSocket 连接。通过优化 Linux 内核参数和 Netty 高低水位线，
解决了海量连接的内存和 GC 压力。

第三，通知系统。设计了 RocketMQ 广播和精准路由结合的混合推送——
不是把所有消息广播给所有节点，而是只推给有该车辆关注者的节点。
推送效率提升了 10 倍，通知延迟控制在 150ms 以内。

还有一个小创新：Delta Encoding 差值传递——竞拍价格每次都涨，
只传差值不传全量，90% 的消息体压缩到 1 个字节，带宽省了 80%。

第四，容错和灾备。Redis 挂了的场景也考虑了——出价事件通过 RocketMQ 
落 MySQL，Redis 恢复后从 MySQL 回放重建排行榜状态。


"R — 结果"（20 秒）

上线后：出价 P99 75ms，通知延迟 150ms，可用性 99.99%，大促峰值 
10 万+ 连接稳定运行，零出价丢失、零排序投诉。系统整体吞吐提升 3 倍。
```

## 5.2 常见追问及应答

### 追问 1："为什么用 Redis Lua 而不是直接用 Java 锁？"

> "两个原因。第一，Java 锁只能在单机内保证原子性，但出价需要跨机的一致性——10 个出价服务实例，Java 锁管不到别人。即使用分布式锁，锁的获取和释放本身就有网络开销，10 万 QPS 下锁会成为瓶颈。
>
> 第二，Redis Lua 的原子性是服务端级别的——所有命令在 Redis 主线程中串行执行，天然没有竞争。而且我们把校验、排行、扣款四步放在一个 Lua 脚本里，一次网络往返搞定，延迟极低。
>
> 代价是 Redis 单线程的瓶颈——脚本不能太重。我们的 Lua 脚本控制在 50 行以内，平均执行时间 10ms，单 Redis 实例能支撑 1000 次出价/秒。不够就按 auction_id 分 Cluster。"

### 追问 2："Redis 挂了怎么办？出价数据会丢吗？"

> "这个问题在设计阶段就重点考虑过。我们有三层防护：
>
> 第一层，Redis 自身的 AOF + 混合持久化，appendfsync everysec，最多丢 1 秒数据。
>
> 第二层，每次出价成功后通过 RocketMQ 事务消息异步落 MySQL。Redis 恢复后，从 MySQL 回放故障期间的所有出价记录，重建排行榜状态。
>
> 第三层，Redis 完全不可用时，出价降级为 MQ + DB 模式——延迟会从 20ms 涨到 500ms，但不会丢数据。降级期间关闭实时推送，改为客户端 1 秒轮询。
>
> 上线两年，Redis 故障过 2 次，数据零丢失。"

### 追问 3："10 万连接单机能扛住，你具体改了什么参数？"

> "主要四类优化：
>
> OS 层面：文件描述符上限调到 65 万，somaxconn 调到 65535，TIME_WAIT 端口复用打开。
>
> Netty 层面：SO_BACKLOG 65535，TCP_NODELAY 打开（低延迟），SO_KEEPALIVE 打开（死连接检测）。高低水位线配了 32KB/128KB——某个慢客户端的写缓冲区超过 128KB 就暂停写入，防止拖垮整个节点。
>
> JVM 层面：堆 12G，G1 GC，MaxGCPauseMillis=100，IHOP=35。直接内存 4G（Netty ByteBuf 主要用堆外内存）。
>
> 应用层面：60 秒读空闲检测，主动剔除死连接。WebSocket 心跳 30 秒一次。
>
> 单节点稳定运行 5 万连接，内存占用约 3GB，CPU 30-40%。"

### 追问 4："怎么保证同价格下先出价的人排前面？"

> "用 ZSet 的 Score 编码。Score 是一个 64 位浮点数，我设计了一个分段编码：
>
> 高 13 位放价格（单位分），低 13 位放时间戳的取反值。同一个价格下，时间戳越早，取反后越大，Score 就越大，自然排前面。
>
> 但这里踩过一个坑：一开始用毫秒精度的时间戳，发现同一毫秒内的多笔出价 Score 完全相同，ZSet 会按 member 字典序排——不是 FIFO。后来改成了纳秒精度，同时加了一个 FIFO 队列做兜底。
>
> 另外要注意精度边界——Double 尾数 52 位，精确整数范围约 9×10^15。价格乘 10^13 后，超过 900 万的车需要注意精度。竞拍二手车通常在 500 万以内，安全。"

### 追问 5："你觉得这个系统最大的败笔是什么？"

> "两个地方做得不够好：
>
> 第一，ZooKeeper 的'车辆-服务器'路由映射在流量极大时会成为瓶颈——每个车商进入拍卖间都要写 ZK，ZK 是 CP 系统，写入性能有限。如果重新设计，我会考虑用 Redis + 本地缓存做路由表，ZK 只做配置管理。
>
> 第二，RocketMQ 的广播模式在大促时有尾部延迟问题——最慢的 Consumer 决定了整体的推送延迟。应该给推送消息设置超时，超过 200ms 没消费完就丢弃，反正下一次出价会把更新数据带过去。"

## 5.3 压力题应对话术

### 压力题 1："你这些方案都是抄开源的吧？"

> "我是站在开源社区的肩膀上，但不只是抄。Netty、Redis、RocketMQ 都是开源组件，但怎么把它们组合成一套竞拍系统，这是需要架构判断的。
>
> 比如出价引擎，社区没有一个现成的'Redis Lua 竞拍引擎'可以参考——ZSet 的 Score 编码方案、本地缓存拦截无效出价的二级校验、FIFO 队列兜底同纳秒出价，这些组合方案是我根据竞拍业务的特性设计的。
>
> 架构师的价值从来不是发明新算法，而是在正确的场景使用正确的技术，做出正确的 trade-off。"

### 压力题 2："10 万 QPS 听起来很高，但其实 Redis 单机就能扛，你们是不是过度设计了？"

> "Redis 单机确实能扛 10 万 QPS 的简单读写，但竞拍的瓶颈不是 QPS 总数，而是单个拍卖品的热点。500 个车商对一辆热门车出价，所有请求都打在 bid:auction:67890 这一个 Key 上——这属于热点 Key，Redis 单线程 CPU 会打满。
>
> 我们做本地缓存拦截不是怕 Redis 扛不住，而是怕某一个拍卖品成为热点影响其他拍卖品。架构设计不能只看平均值，要看极端情况。"

### 压力题 3："你说可用性 99.99%，怎么算出来的？"

> "不是拍脑袋。我们定义可用性 = 出价成功率 > 99% 的时间占比。
>
> 过去一年：
> - 计划内维护：4 次 × 2 小时 = 8 小时
> - 非计划故障：2 次 × 1.5 小时 = 3 小时
> - 总计不可用 = 11 小时
> - 可用性 = (365 × 24 - 11) / (365 × 24) = 99.87%
>
> 说实话没到 99.99%，简历上写的是'目标'。实际做到的是 99.95% 左右。但我认为这个数字比虚报更有说服力——我清楚每一次不可用的原因和时长。"

## 5.4 面试官可能深挖的 5 个方向

### 方向 1：架构演进

> "这个系统经历了三个阶段：
>
> V1：数据库行锁 → 单场拍卖 100 QPS
> V2：Redis Lua + Netty 长连接 → 单场拍卖 5000 QPS
> V3：二级校验 + 混合推送 + CDN 静态化 → 单场拍卖 10000+ QPS
>
> 每个阶段不是推翻重来，而是在核心架构上叠加优化。这也是我理解的架构演进——不是做大手术，而是在关键路径上持续做减法。"

### 方向 2：容量规划

> "我们有量化的容量模型：
>
> 单 Netty 节点：5 万连接，1 万出价 QPS
> 单出价服务：5000 出价 QPS（含本地缓存拦截后实际到 Redis 的 2000）
> 单 Redis 实例（热门拍卖品）：1000 出价 QPS
>
> 大促峰值 10 万出价 QPS：
> - Netty：10 万连接 / 5 万 = 2 节点 × 2(冗余) = 4 节点
> - 出价服务：10 万 / 5000 = 20 节点 × 1.5(冗余) = 30 节点
> - Redis：按 auction_id 分片后，单实例 1000 QPS → 10 万 / 1000 = 100 实例
>   实际用 Cluster 6 主 6 从 → 按 auction_id 打散 → 够用"

### 方向 3：数据一致性

> "出价数据的一致性有三级保证：
> - 实时级：Redis Lua 原子操作（出价 → 排行榜，强一致）
> - 近实时级：RocketMQ 事务消息 → MySQL（1-3 秒延迟）
> - 最终级：定时对账任务对比 Redis 排行榜和 MySQL 出价记录（1 分钟一次）"

### 方向 4：可观测性

> "建立了三层监控：
> - 业务层：P99 出价延迟、出价成功率、推送延迟、在线车商数
> - 应用层：每个服务接口的 QPS/RT/错误率
> - 基础设施层：JVM GC、CPU、内存、Redis/MySQL/MQ 核心指标
>
> Grafana 核心面板有 4 个：业务大盘（给老板看）、服务大盘（给开发看）、中间件大盘（给 DBA 和运维）、大促实时大屏。"

### 方向 5：如果重来一次

> "三件事我会做不一样的选择：
>
> 1. 网关和推送服务之间不用 Dubbo RPC，改为直接消费 MQ——减少一跳延迟
> 2. ZK 路由映射改成 Redis + 本地缓存——减轻 ZK 的写入压力
> 3. 早期就引入可观测性，而不是后期补——很多早期故障如果有 Trace，排查时间能缩短一半"

## 5.5 面试应答黄金法则

### 每个技术回答的四要素

```
观点 → 原理 → 案例 → 数据

错了："我们用 Redis Lua 做竞价引擎"（只有观点）

对了："竞价出价必须保证原子性（观点）。Redis Lua 利用单线程执行
      保证原子（原理）。我们把校验、排行、扣款四步封装在一个 Lua 
      脚本里（案例）。上线后出价成功率 100%，P99 从 3 秒降到 75ms（数据）。"
```

### 面试中最加分的 5 句话

```
1. "我们有 A/B/C 三个方案，我选了 A 因为……"
   → 展示选型能力

2. "这个地方踩过一个坑……"
   → 展示真实经验

3. "这个方案最大的代价是……"
   → 展示 trade-off 思维

4. "如果重新设计，我会……"
   → 展示复盘能力

5. "这个数字不是拍脑袋，是这样算出来的……"
   → 展示量化思维
```

### 面试中最减分的 5 句话

```
1. "我们用最流行的技术……"（没有自己的判断）
2. "这个系统没有任何问题"（不真实）
3. "这里我不太清楚，是别人做的"（推卸责任）
4. "理论上是可以的"（没有实战验证）
5. "XXX 技术就是比 YYY 好"（没有场景的绝对判断）
```
