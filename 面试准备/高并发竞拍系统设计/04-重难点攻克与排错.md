## 4.1 五大技术难点

### 难点一：高并发下的出价排序公平性

**问题描述**：
10 万 QPS 并发出价，同一个拍卖品可能有几十个车商在同一时刻出相同价格。如何保证"先到先得"？

**根因分析**：
- 数据库行锁：并发下排队，但 P99 > 3 秒，不可接受
- Redis 单线程：天然解决并发，但如何编码"先后"关系？

**解决方案**（三层防护，详见 02 文件）：

```
第一层：Score 编码（主力）
  ZSet Score = price × 10^13 + (10^13 - 1 - timestampNs)
  同价格下，先出价 → 时间戳小 → 取反后大 → Score 大 → 排前面
  覆盖 99.99% 场景

第二层：FIFO 队列（兜底）
  同一纳秒的出价 → 按 Redis LPUSH 顺序（单线程保证先后）
  查排名时合并 ZSet 和 FIFO 队列

第三层：防刷机制
  同一车商 500ms 内只能出价一次
```

**量化效果**：上线以来零排序投诉。

### 难点二：热门拍卖品 Redis 热点 Key

**问题描述**：
Model Y 2025 款拍卖，500 个车商激烈竞价，bid:auction:67890 成为热点 Key。

**现象**：
- 该 Key 所在 Redis 节点 CPU 使用率飙到 95%
- 同集群的其他 Redis 节点 CPU 只有 20%
- 出价 P99 从 20ms 上升到 200ms

**为什么不能简单地把热点 Key 拆分到多个 Redis 节点？**

```
Key 拆分方案要求"每个 shard 独立判断出价有效性"
但出价要求"全局最高价比较" → 所有 shard 必须知道最新价格
→ 要么写时同步所有 shard（又回到单点）
→ 要么写后异步同步 shard（引入不一致窗口）

结论：出价场景不能用 Key 拆分（和库存扣减不同！）
```

**解决方案**：

```
方案 A：本地缓存拦截（已实现）
  在出价服务层缓存最高价，低于最高价的出价直接拒绝
  效果：拦截 60% 请求，Redis 负载从 10 万 → 4 万 QPS

方案 B：限流控制流量
  对热门拍卖品在网关层做令牌桶限流
  5000 QPS/拍卖品 → 把流量控制在 Redis 单分片可承受范围

方案 C：有损降级（兜底）
  如果 Redis 仍然扛不住 → 降级为"排队出价"模式
  出价不立即入 ZSet → 先入 MQ → 100ms 批处理一次
  延迟从 20ms → 200ms（可接受的有损服务）
```

**决策逻辑**：先用方案 A + B 兜住 99.9% 的场景。方案 C 只在极端流量下触发（大促峰值）。架构师不追求"完美方案"，而是"分层次的应对策略"。

### 难点三：海量长连接的内存控制

**问题描述**：
单台 Netty 节点维持 5 万 WebSocket 连接，每个连接都有关联的内存对象（Channel、Pipeline、Handler、ByteBuf）。JVM 堆内存持续增长，Full GC 频繁。

**排查**：
```
jmap dump → MAT 分析 →
  5 万个 NioSocketChannel 对象（每个 ~2KB）= 100MB
  5 万个 ChannelPipeline 对象（每个 ~1KB）= 50MB
  5 万个 WebSocketFrame 对象（缓冲）= 不定，峰值 500MB
  
  → 总内存占用约 1GB（堆内）+ 2GB（直接内存）
```

**解决方案**：

```java
// 1. 高低水位线控制写缓冲区
bootstrap.childOption(ChannelOption.WRITE_BUFFER_WATER_MARK,
    new WriteBufferWaterMark(32 * 1024, 128 * 1024));
// 作用：当某个连接的写缓冲区超过 128KB 时 → Channel.isWritable() = false
//       → 停止向该 Channel 写入数据 → 数据暂存在 MQ 或丢弃
//       → 等 Channel 的写缓冲区降到 32KB → 恢复写入
// 效果：防止一个慢客户端拖垮整个网关节点

// 2. 直接内存限制
-XX:MaxDirectMemorySize=4g
-Dio.netty.allocator.type=pooled       // 池化 ByteBuf，减少分配
-Dio.netty.leakDetection.level=PARANOID  // 内存泄漏检测

// 3. 空闲连接主动回收
pipeline.addLast(new IdleStateHandler(60, 0, 0));
// 60 秒没有收到客户端消息 → 触发 userEventTriggered → 关闭连接
// 防止死连接（客户端断网但没发 close 帧）占用资源
```

### 难点四：网络带宽瓶颈

**问题描述**：
200 场拍卖同时进行，每秒 1000 次出价，每次推送 500 人 → 50 万条推送/秒。每条 Protobuf 消息 50 字节 → 25 MB/s = 200 Mbps。加上心跳、重连、其他消息 → 峰值 500 Mbps+。

**解决方案**：Delta Encoding（详见 03 文件）。

量化效果：
```
全量推送：500 万条/秒 × 50 字节 = 250 MB/s
Delta Encoding：500 万条/秒 × 10 字节(平均) = 50 MB/s
带宽节省：80%
```

### 难点五：拍卖详情页的性能瓶颈

**问题描述**：
每辆车的检测报告包含 3000+ 字段（车况、事故记录、保养记录等），JSON 序列化后 50-200KB。10 万车商同时打开拍卖详情页 → 服务器每秒要序列化和传输大量 JSON → CPU 和带宽都打满。

**解决方案：静态化 + CDN**

```
方案：预渲染 → 静态 HTML → CDN 分发

流程：
  1. 车辆上架时 → 后台服务预渲染 HTML 页面
     （把 3000+ 字段的 JSON + 模板 → 渲染成完整 HTML）
  
  2. HTML 上传到 OSS/CDN → 分发到全国边缘节点
  
  3. 车商打开拍卖详情 → 从最近的 CDN 节点获取 HTML（延迟 < 50ms）
  
  4. 页面中的动态数据（当前最高价、倒计时、出价按钮）
     通过 WebSocket 推送 → 页面动态更新

效果：
  - 服务器不再处理静态内容的序列化和传输
  - 页面加载时间从 3 秒 → 50ms（CDN 边缘节点）
  - 服务可用性从 99.9% → 99.99%（静态内容挂在 CDN 上几乎不会挂）
  - 服务器 CPU 使用率降低 60%
```

## 4.2 三类故障完整排查

### 故障一：出价排行榜出现排序错乱

**故障现象**：
某场拍卖中，车商 A 出价 10 万在先，车商 B 出价 10 万在后。但排行榜显示 B 排在 A 前面。

**排查过程**：

```
Step 1：确认时间线
  - 查询 MySQL 出价记录：A 的出价时间比 B 早 50ms
  - 确认 A 应该排在 B 前面

Step 2：查 Redis ZSet
  - ZREVRANGE bid:auction:67890 0 9 WITHSCORES
  - 发现 A 和 B 的 score 相同（或 B 的 score 略大于 A）
  
Step 3：分析 Score
  - A 和 B 都是 10 万分（10000000 分）
  - Score = 10000000 × 10^13 + (10^13 - 1 - timestamp)
  - print A 和 B 的 timestamps → 发现 A 的 timestamp 数值反而比 B 大

Step 4：定位根因
  - 时间戳来源：System.currentTimeMillis()（毫秒精度）
  - A 和 B 的出价在同一毫秒内（时间戳相同！）
  - 编码后 score 完全相同 → ZSet 按 member 字典序排列
  - "21345:100000" < "21346:100000" → B 排在 A 前面

根因：毫秒精度不够，同一毫秒内的多次出价 score 相同，ZSet 按字典序排。
```

**修复方案**：
```java
// 改用纳秒精度
long timestampNs = System.nanoTime();  // 替代 System.currentTimeMillis()

// 同时增加 FIFO 队列兜底
redis.call('LPUSH', 'bid:queue:' + auctionId, bidderId + ':' + amount);
// 查排名时：score 优先 → 同 score 按 FIFO 顺序
```

### 故障二：大促期间系统间歇性"卡顿"

**故障现象**：
双十一二手车节期间，车商反映出价偶尔"转圈"1-2 秒才有反应。不是全部车商，是间歇性的。监控显示 P99 延迟出现毛刺。

**排查过程**：

```
Step 1：看监控
  - Grafana 出价 P99 曲线：正常 50ms，每 60 秒出现一次 500ms-2s 的毛刺
  - 毛刺周期稳定（~60 秒一次）

Step 2：关联分析
  - JVM GC 监控：每 60 秒一次 Mixed GC，耗时 200-500ms
  - 毛刺时间点 vs GC 时间点 → 完美重合

Step 3：查 GC 日志
  - G1 Mixed GC 耗时 300-800ms（远超预期的 100ms）
  - GC 原因：IHOP 触发，但 Mixed GC 回收了很少空间
  - 老年代使用率一直在 85% 以上

Step 4：分析根因
  - 大促流量翻倍 → 出价记录对象（BidRecord）分配速率翻倍
  - 这些对象的生命周期 = 单场拍卖时长（15 分钟）
  - 大量对象在 Young GC 后晋升到 Old 区
  - Old 区持续高水位 → Mixed GC 频繁但回收效率低

根因：大促流量下降，对象晋升速率 > Mixed GC 回收速率。
```

**修复方案**：
```
紧急（大促期间）：
  1. 调整 G1 IHOP 从 45 → 35（更早触发并发标记）
  2. 用 Arthas OGNL 热修改限流阈值（稍微降低 QPS）

长期：
  1. 增大堆内存：8G → 16G
  2. 调整 Young 区比例：G1NewSizePercent=10（多给 Young 区）
  3. 优化出价对象：复用 BidRecord 对象池 → 减少对象分配
```

### 故障三：出价成功但排行榜没有更新

**故障现象**：
车商收到"出价成功"的返回，但排行榜上没有看到自己的出价。几秒后又出现了。

**排查过程**：

```
Step 1：确认出价是否真的成功
  - MySQL 出价记录表：出价记录存在 ✓
  - 保证金扣减记录：扣减成功 ✓

Step 2：查 Redis
  - ZREVRANGE bid:auction:67890 0 9 → 排行榜上没有该车商
  - 但 GET balance:12345 → 保证金确实扣了
  - 问题：排行榜和保证金在同一个 Lua 脚本中，怎么可能一个成功一个失败？

Step 3：查 Lua 脚本返回
  - 日志显示 Lua 返回 {0, 'SUCCESS'}
  - 但排行榜就是没有该出价

Step 4：查 Redis 慢日志 + 监控
  - 发现该时间点 Redis 正在进行 AOF Rewrite
  - 同时有其他 Lua 脚本在操作同一个 Key
  - 进一步确认：Lua 脚本中 ZADD 和 DECRBY 都执行了
  - 但 ZSet 被后续的另一个操作覆盖了

根因：另一个管理后台脚本（重置测试数据）在同时操作同一个 ZSet Key，
      ZADD 被后续的 ZREMRANGEBYRANK 误清理。
```

**修复方案**：
```
1. Lua 脚本增加写操作幂等保护
   redis.call('ZADD', KEYS[1], score, member)
   → 确保 ZADD 后立即验证 member 是否在 ZSet 中

2. 管理操作加分布式锁
   任何对生产拍卖数据的后台操作 → 先获取该拍卖的分布式锁

3. 增加对账机制
   定时对比 Redis 排行榜和 MySQL 出价记录 → 不一致告警
```
