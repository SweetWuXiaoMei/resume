### 1. 分布式事务方案：2PC/TCC/SAGA/本地消息表

#### 各方案的核心矛盾

**2PC / XA**：强一致性但同步阻塞
- 原理：两个阶段（Prepare + Commit），协调者收集所有参与者的响应
- 致命问题：协调者单点故障（Prepare 后协调者挂掉 → 所有参与者锁住资源等待）、性能极差（所有参与者串行 Prepare + 阻塞）
- 适用：单服务多数据库（JTA 跨库）、对账系统（非实时链路）
- 实际中基本不用——链路太长，性能无法接受

**TCC（Try-Confirm-Cancel）**：
- Try：预留资源（冻结库存，可用余额减少，冻结金额增加）
- Confirm：确认提交（扣减冻结库存，真正完成）
- Cancel：取消释放（解冻库存，恢复可用）
- 与 2PC 的本质区别：资源不在 Prepare 期间锁住（Try 只冻结，其他事务仍然可以冻结剩余的）
- 业务侵入性极强：每个服务都要实现 3 个接口，业务逻辑散落
- **空回滚问题**：Try 调用失败 → 触发 Cancel，但 Try 可能根本没执行 → Cancel 需要幂等
- **悬挂问题**：Cancel 先于 Try 到达（网络延迟）→ Try 到达后 Cancel 已执行 → 资源处于不一致状态 → 需要 Cancel 记录防止 Try 再次执行

**SAGA**：
- 编舞式（Choreography）：事件驱动，每个服务做自己的事、发事件、下一个响应 → 适合流程简单的短事务
- 编排式（Orchestration）：一个 Saga Manager 按顺序调用服务、失败时执行补偿 → 适合复杂流程
- SAGA 的最大问题：**无隔离性**（A 服务提交后，B 服务能看到 A 的结果，但 SAGA 整体可能被补偿回滚 → B 基于一个"未来会被回滚"的数据做了决策）

**本地消息表**：
- 最朴实但最有效的方案。在同一个本地事务中：（1）执行业务操作（2）写消息表（状态=待发送）
- 后台定时任务扫描消息表 → 发送 MQ → 确认消费成功 → 标记已发送
- 优点：实现简单（不需要第三方协调者）、幂等性天然（消息表有唯一消息 ID）
- 缺点：消息表耦合在业务库中、定时扫描有延迟

#### 实际选择决策树

```
需要强一致性 + 短事务 + 单 DB → 本地事务足够
需要强一致性 + 跨服务 → TCC（资金类）/ 2PC（对账类，非实时）
最终一致性 + 异步解耦 → 本地消息表 + MQ
长事务 + 多步骤 → SAGA
```

### 2. 分布式锁：Redis vs ZooKeeper vs 数据库

#### Redis 分布式锁正确实现

```java
// 加锁：SET 必须带 NX（Not eXists）+ PX（expire 毫秒）
// 两个原子操作为一个命令：SET key value NX PX 30000
String lockKey = "lock:order:" + orderId;
String lockValue = UUID.randomUUID().toString();
Boolean locked = redisTemplate.opsForValue()
    .setIfAbsent(lockKey, lockValue, Duration.ofSeconds(30));

// 解锁：必须用 Lua 脚本保证判断+删除原子
String script = "if redis.call('get', KEYS[1]) == ARGV[1] " +
                "then return redis.call('del', KEYS[1]) " +
                "else return 0 end";
redisTemplate.execute(new DefaultRedisScript<>(script, Long.class),
    Collections.singletonList(lockKey), lockValue);
```

**为什么解锁必须判断 value**：如果不判断，线程 A 的锁 30s 过期 → 线程 B 获取锁 → 线程 A 执行完误删 B 的锁 → B 的临界区不再有锁保护。

**Redisson 的看门狗（Watch Dog）**：锁默认 30s，每 10s 自动续期到 30s。如果 JVM 崩溃，30s 后 Redis 自动释放锁（expire key 删除）。这是目前最成熟的生产解决方案。

**RedLock 算法**：
- 在 N 个独立的 Redis Master 节点上依次获取锁（SET NX PX 同值同超时）
- 超过半数（N/2+1）获取成功 → 锁成功，总耗时 < 锁有效时间
- 否则所有节点释放
- Martin Kleppmann 的质疑：RedLock 依赖多个节点的时间钟同步，GC 停顿导致锁过期比预期早，可能同一锁被两个客户端同时持有
- 结论：大多数场景 Redisson 单实例锁 + 业务幂等兜底已足够

#### ZooKeeper 分布式锁

利用临时顺序节点：在每个线程在 `/lock` 下创建 `临时+顺序` 节点 → 检查自己是不是序号最小的 → 是则获取锁 → 否则 watch 前一个节点 → 前一个释放后收到通知 → 竞争。公平性好（排队了），性能低于 Redis。

**选型建议**：
- 性能敏感、允许极低概率锁失效 → Redis（Redisson）
- 必须绝对公平、不能接受锁失效 → ZooKeeper（Curator）
- 低频场景、不想引入外部依赖 → 数据库乐观锁（version 字段）

### 3. 限流、熔断、削峰的设计思路和实现方案？限流算法（令牌桶、漏桶）、熔断框架（Sentinel）的使用？

#### 是什么

- **限流**：控制「单位时间内通过的请求数」，目的是防止系统被过量请求压垮。你主动说「我只能处理这么多」。
- **熔断**：当下游服务出现故障时，自动切断对它的调用，快速失败，防止故障传播。你被动响应「它已经不行了，我不再调它了」。
- **削峰**：把瞬时的高峰流量平滑成一条平缓的曲线，让系统能以自己的节奏处理。MQ 是最典型的削峰工具。

这三者经常搭配使用：限流挡在最前面，熔断保护调用方，削峰在中间缓冲。

#### 为什么需要

没有限流 → 秒杀时 100 万 QPS 打到支付服务 → 线程池满 → 请求排队超时 → 连接耗尽 → 整个服务雪崩。
没有熔断 → 积分服务慢，支付服务每次调积分都等 5s 超时 → 支付服务的线程全部在等积分服务 → 支付变成不可用。
没有削峰 → 大促开始瞬间，库存扣减请求全部涌入 → 数据库连接打满 → 连正常的查询都被阻塞。

#### 限流算法原理（详细对比）

**① 固定窗口计数器**
- 原理：把时间切成固定窗口（如 1s），窗口内计数，超过阈值拒绝。
- 问题：**临界突变**。第 0.9s 来了 100 个请求（不超），第 1.1s 来了 100 个请求（新窗口，不超），但实际上 0.9s-1.1s 这 200ms 内通过了 200 个请求（两倍限制）。
- 适用：几乎不用于生产（有更好的）。

**② 滑动窗口**
- 原理：把 1s 窗口分成 N 个格子（Sentinel 默认 2 个 500ms 格子），每个格子独立计数。统计窗口 = 最近 N 个格子的和。
- 优点：临界问题大幅缓解（0.9-1.1s 统计了两个格子的和，不会超限）。
- Sentinel 的滑动窗口关键设计：
  1. `LeapArray`（环形数组）：固定长度数组，按时间下标循环覆盖
  2. `WindowWrap<T>`：每个格子 = 时间窗口开始 + 统计数据
  3. 当前时间落在哪个格子 = `time / windowLengthInMs % arrayLength`
  4. 如果当前时间 > 格子的开始时间 → 重置这个格子的统计 → 开始新一轮统计
- 为什么 Sentinel 不是每毫秒一个格子（成本太高），而是 500ms 两个格子？因为统计精度 500ms 在绝大多数场景下够用，且内存和计算都低。

**③ 令牌桶**
- 原理：以固定速率向桶中放令牌。请求来 -> 从桶中取令牌 -> 取到则通过，取不到则拒绝。桶有上限（容量），当桶满时多余的令牌丢弃。
- 优点：允许突发流量（桶里攒了令牌，可以瞬间全部用掉）
- 适用：秒杀、突发流量场景
- Guava RateLimiter 实现：基于 `SmoothBursty` 算法，记录「下一次可获取令牌的时间」，根据时间差计算攒了多少令牌

**④ 漏桶**
- 原理：请求进入桶（队列），以固定速率从桶底漏出（处理）。桶满则拒绝。
- 优点：流量绝对平滑（不管进来多猛，出去都是固定速率）
- 缺点：不允许突发流量（即使系统有空闲容量，也要排队）
- 适用：需要严格控制处理速率的场景（如对外 API，不能把对方打挂）

#### Sentinel 深度解析

**Sentinel 四层规则模型**：
1. **流量控制规则（FlowRule）**：QPS / 线程数 / 慢调用比例。支持直接拒绝、Warm Up（预热）、匀速排队（漏桶）
2. **熔断降级规则（DegradeRule）**：慢调用比例 / 异常比例 / 异常数
3. **热点参数限流（ParamFlowRule）**：针对某个接口的某个参数的特定值限流（如对商品 ID=12345 单独限流）
4. **系统保护规则（SystemRule）**：CPU 使用率 / 平均 RT / 并发线程数 / 入口 QPS → 触发系统保护

**Sentinel 的工作架构**：
```
拦截点(SphU.entry) → ProcessorSlotChain(责任链)
  → NodeSelectorSlot(构建调用树)
  → ClusterBuilderSlot(构建集群节点)
  → StatisticSlot(统计 + 调用下级)
  → FlowSlot(流量控制)
  → DegradeSlot(熔断降级)
  → SystemSlot(系统保护)
```

**热点参数限流的实现**：Sentinel 内部维护一个 LRU 缓存（默认 4000 个），对每个参数值做独立计数。如果某个参数值的 QPS 超过阈值 → 对该值限流 → 不影响其他参数值。

#### 削峰方案

**消息队列削峰**：最经典的方案。请求进入 MQ → Consumer 以自己能承受的速率消费。MQ 相当于一个巨大的缓冲区。
实现细节：Kafka / RocketMQ 的分区模型允许水平扩展 Consumer，积压时增加 Consumer 实例即可。

#### 坑点

1. **Sentinel 规则持久化**：默认规则存在 Dashboard 内存中，Dashboard 重启规则丢失。必须把规则持久化到 Nacos/Apollo
2. **集群限流 vs 单机限流**：单机限流（QPS=1000）→ 3 台实例 = 总共 3000 QPS。如果需要精确到「整个集群 QPS=2000」→ 需要 Sentinel 集群流控（Token Server 模式）
3. **限流不要设在数据库层**：DB 连接池是稀有资源，用限流挡在应用层/网关层，别让请求打到 DB 层才拒绝

### 4. 30+节点集群稳定高可用设计：部署方案、负载均衡、故障自动恢复、容灾备份？

#### 是什么

高可用（HA, High Availability）的本质是：**消除单点故障（SPOF, Single Point of Failure）**。30+ 节点集群的高可用不是「不出问题」，而是「出了任何一台/一个机架/一个机房的问题，业务不受影响」。

#### 多层次的可用性设计

**① 部署层（K8s）**：
```yaml
spec:
  replicas: 3
  affinity:
    podAntiAffinity:  # 反亲和：同一服务的 Pod 不调度到同一台物理机
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchExpressions:
              - key: app
                operator: In
                values: [order-service]
          topologyKey: kubernetes.io/hostname  # 按宿主机打散
```

**② 负载均衡层（Nginx/Gateway + SLB）**：
```
用户 → DNS(GSLB) → SLB(四层) → Nginx(七层) → Gateway → 微服务
```
每一层都有多节点，任何一层单点故障都能自动切换。

**③ 健康检查与故障自动恢复（K8s 自愈）**：
```yaml
livenessProbe:   # 存活探针：容器是否还活着
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
readinessProbe:  # 就绪探针：容器是否准备好接收流量
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
```
- Liveness 失败 → K8s 杀死 Pod → 创建新 Pod
- Readiness 失败 → 从 Service 摘除 → 不再接收新请求
- HPA：`kubectl autoscale deployment order-service --min=3 --max=30 --cpu-percent=70`

**④ 容灾备份三层模型**：
- **同城双活**：两个可用区部署，数据同步（MySQL MGR / Redis Cluster 跨 AZ 节点），一个 AZ 挂了流量切到另一个。RTO < 1 分钟
- **异地灾备**：数据异步复制到异地机房（带宽有限的专线），异地有完整的基础设施但默认冷备。RTO < 30 分钟，RPO < 1 分钟
- **多活（最难）**：多个机房同时提供服务。挑战：数据同步延迟 + 冲突解决（如用户在北京和上海同时下单）。需要全局事务号 + 数据分区

#### 高可用的度量

| 可用性 | 全年故障时间 | 可容忍什么 |
|--------|------------|-----------|
| 99% | 3.65 天 | 非核心业务 |
| 99.9% | 8.76 小时 | 一般业务 |
| 99.99% | 52.56 分钟 | 核心业务（支付） |
| 99.999% | 5.26 分钟 | 金融/电信级 |

#### 坑点

1. **K8s 重启策略**：`restartPolicy: Always` 会在 Pod 失败后不断重启，如果失败了 10 次还在重启 → 说明不是运气问题，是程序问题。配合 `backoffLimit` 限制重启次数
2. **HPA 基于 CPU 的滞后**：CPU 升高到触发扩缩需要 1-2 分钟，突发流量在这期间已经把服务打挂了。解决：基于 QPS 的 HPA（Prometheus Adapter）
3. **优雅上下线没做好**：k8s 直接杀 Pod → Service 还没更新 → 请求打到已死的 Pod → 502

### 5. 分布式系统中的一致性问题（CAP理论、BASE理论），如何权衡？

#### 是什么

CAP 是分布式系统的「不可能三角」。2000 年 Eric Brewer 提出，2002 年 Seth Gilbert 和 Nancy Lynch 用数学严格证明。

- **C（Consistency）一致性**：所有节点在同一时刻看到的数据相同（读到的都是最新写入的值）
- **A（Availability）可用性**：每个请求都能获得非错误的响应（不保证是最新数据）
- **P（Partition Tolerance）分区容错性**：系统在网络分区（消息丢失/延迟）的情况下仍能正常运作

**CAP 只能三选二，但 P 是必须选的**：在分布式系统中，网络分区不可避免（交换机故障、光纤挖断、网络拥塞）。如果你不选 P → 系统在网络分区时停止服务 → 等于放弃了分布式。所以实际选择是 **CP** 还是 **AP**。

#### 为什么 CAP 不是「两阶段提交就是 CP，最终一致就是 AP」

CAP 说的是**网络分区时的行为**。网络正常时，CP 和 AP 系统都能同时提供一致性和可用性。

- **CP 系统**（如 ZooKeeper、Etcd）：网络分区时，少数派拒绝写操作（甚至读操作），等待分区恢复。宁可不可用，也要保证一致。
- **AP 系统**（如 Eureka、Cassandra）：网络分区时，两个分区都能正常读写（数据可能不一致），分区恢复后通过数据同步/冲突解决达成一致。

**CP 的代价**：以 ZooKeeper 为例，如果集群 5 个节点，3 个在机房 A、2 个在机房 B。机房 B 网络断开 → 只剩 2 个节点无法选举 Leader → 整个 ZooKeeper 不可用（虽然机房 A 还有 3 个节点，但 B 的 2 个节点也参与投票，总投票数不满 3 票 → 无 Leader → 停止服务）。

**AP 的代价**：以 Cassandra 为例，两个分区都能写入同一行 → 分区恢复后需要解决冲突（Last-Write-Wins / Vector Clock）。

#### BASE 理论：CAP 的工程折衷

- **BA（Basically Available）基本可用**：系统出现了问题，但还能用（只是比平时慢一点、功能少一点）
- **S（Soft State）软状态**：系统中的数据允许存在中间状态
- **E（Eventually Consistent）最终一致性**：经过一段时间后，数据最终达到一致

BASE 不是放弃一致性，而是放弃了**强一致性**，拥抱**最终一致性**。

#### 实际架构中的权衡

| 场景 | 选择 | 为什么 |
|------|------|--------|
| 银行转账 | CP（强一致） | 钱不能凭空消失或复制 |
| 订单状态查询 | 最终一致 | 等几秒看到最新状态对用户来说无所谓 |
| 注册中心（服务发现） | AP | 宁可拿到旧实例地址导致一次调用失败，也不能全站不可用 |
| 配置中心 | CP | 配置不一致可能导致重大问题（如数据库地址指错了） |
| 秒杀库存扣减 | CP | 超卖是致命的 |

**核心思想**：**大部分业务场景最终一致性就足够了**，不需要为了一致性让整个系统降级到不可用。

### 6. 分布式系统的负载均衡方式？Nginx、LVS、HAProxy的适用场景？

#### 四层 vs 七层负载均衡

**四层（传输层，L4）**：
- 工作在 TCP/IP 层，只看到 IP + 端口，不关心 HTTP 内容
- LVS（Linux Virtual Server）：内核态工作，性能最高，百万级并发
- F5（硬件）：硬件芯片实现，性能最强但贵（几十万/台）
- HAProxy（四层模式）：软件实现，性能好

**七层（应用层，L7）**：
- 工作在 HTTP 层，能看到 URL、Header、Cookie
- Nginx：最常用的七层代理，支持 URL 路由、Cookie 粘滞、请求改写、限流
- Spring Cloud Gateway：微服务原生网关
- HAProxy（七层模式）

#### 为什么需要分层负载均衡

```
用户 → DNS(GSLB，就近接入 + 流量调度)
  → SLB（四层，高可用 + 健康检查）
    → Nginx（七层，URL 路由 + 限流 + 缓存）
      → Gateway（微服务路由 + JWT 校验 + 灰度）
        → 微服务实例
```

每一层都有各自的不可替代性：
- DNS：必须是第一层，把用户导到最近的机房（全球负载）
- 四层：性能最高，只做包转发（修改目标 IP/MAC），适合处理巨大流量
- 七层：能根据业务逻辑路由（`/api/user/*` → 用户服务），能做内容缓存
- 网关：能做服务发现 + 动态路由（Nacos 注册的实例 IP 会变，Nginx 配置是静态的）

#### 负载均衡算法

| 算法 | 原理 | 适用 |
|------|------|------|
| 轮询（Round Robin） | 依次分配 | 无状态服务 |
| 加权轮询 | 按权重分配 | 机器配置不均 |
| 最少连接（Least Connections） | 选活跃连接最少的 | 长连接场景 |
| 一致性哈希（Consistent Hash） | 同一用户始终到同一节点 | 有状态/缓存场景 |
| 随机 + 加权 | 随机选 + 权重 | 简单场景 |

**一致性哈希的实现**：哈希环。节点分布在 2^32 的环上，请求的 key 映射到环上某一点，顺时针找最近的节点。节点增减只影响环上一小段，不影响大部分映射关系。Nginx 的 `consistent_hash` 指令、Dubbo 的 ConsistentHashLoadBalance 都用这个。

### 7. 分布式系统的容灾备份策略？异地多活、主备模式、集群冗余如何落地？容灾演练怎么做？

#### 灾备的三个层级

**Level 1：集群冗余（无灾备，单机房容错）**
- 同机房 3+ 节点，多机架/多交换机组部署
- 只防节点故障，不防机房灾难（火灾、断电、光纤挖断）

**Level 2：主备模式（两地三中心）**
- 主站：提供服务
- 同城灾备：实时数据同步，主站故障秒级切换
- 异地灾备：异步数据复制，作为最后的兜底
- RTO（恢复时间目标）：< 30 分钟
- RPO（恢复点目标）：< 1 分钟（异步复制延迟）

**Level 3：异地多活（最高级）**
- 多个机房同时提供服务，用户就近接入
- 挑战：数据同步 + 冲突解决 + 全局负载均衡
- 代价大、复杂度高，只有少数场景需要（微信、支付宝级别）

#### 数据层灾备

**MySQL**：
- 同城：MGR（MySQL Group Replication，Paxos 协议，强一致，自动选主）
- 异地：异步复制（备机房有最新的 binlog 但不实时 apply）

**Redis**：
- 同城：Redis Cluster 跨 AZ 部署（每个 Shard 的 Slave 在另一个 AZ）
- 异地：AOF 文件定时备份到异地对象存储

**MQ（RocketMQ）**：
- Dledger 模式异地多副本（跨机房 Raft 复制）

#### 容灾演练

**不是「做完就完了」，而是「不知道什么时候会真来」**：
1. 每季度一次：模拟主站挂掉，切换到灾备
2. 验证：流量切换时间是否 < 5 分钟？数据是否有丢失？切回来是否正常？
3. 演练记录：每次演练记录发现的问题 → 下次改进
4. 随机故障注入：不预告，随机选一天搞 Chaos Engineering（K8s 随机 Kill Pod / 网络延迟注入）

### 8. 分布式任务调度框架（XXL-Job、Elastic-Job）原理与使用场景？

#### 是什么

分布式任务调度解决的核心问题：**多个服务实例同时运行，但定时任务只需要一个实例执行**。单机时代 Quartz 自己搞定；集群时代多个 Pod 同时触发同一任务 → 重复执行（如重复发券、重复扣款）。

**XXL-Job 架构**：
- **调度中心（Admin）**：Web UI + 调度逻辑 + 任务配置 + 日志存储。单独部署
- **执行器（Executor）**：嵌入业务服务中的 client，接收 Admin 发来的任务触发请求
- 原理：Admin 定时触发任务 → HTTP 调用执行器的 `/run` 接口 → 执行器异步执行 → 回调 Admin 汇报结果

**路由策略**：轮询、一致性哈希（同一任务固定到一台机器）、最不经常使用、故障转移、分片广播（最关键！）

**分片广播原理**：所有 Executor 实例同时收到任务，但 `shardIndex` 和 `shardTotal` 不同：
```java
@XxlJob("shardingJob")
public void execute() {
    int shardIndex = XxlJobHelper.getShardIndex();  // 0-based
    int shardTotal = XxlJobHelper.getShardTotal();  // 总数
    
    // 每个分片处理自己的数据段
    List<User> users = mapper.selectByShard(shardIndex, shardTotal);
}
```
例如 4 台机器：分片 0 → `id%4=0`，分片 1 → `id%4=1`... 数据并行处理，吞吐量 4 倍。

#### Elastic-Job 与 XXL-Job 对比

| 特性 | XXL-Job | Elastic-Job |
|------|---------|-------------|
| 调度中心 | 独立部署（Admin） | 无需（基于 ZooKeeper 分布式协调） |
| 分片 | HTTP 广播 | ZK 选举 + 分片分配 |
| 运维 | Web UI 管理任务 | 代码中定义任务（无 UI） |
| 适用 | 任务多、需要可视化管理 | 轻量、不想多部署组件 |

#### 使用场景

- 定时对账：每日凌晨 2 点跑所有账户的余额对账
- 数据同步：每 10 分钟同步一次外部系统的订单数据
- 报表生成：每日 6 点生成前一天的日报表（分片并行生成）
- 超时处理：每 5 分钟扫描一次超时未支付订单，自动取消

#### 坑点

1. **任务幂等**：分片广播模式下同一 shardIndex 只会执行一次，但如果任务失败重试 → 需要幂等
2. **Admin 高可用**：Admin 挂了他不会自动切，需要部署多个 Admin + Nginx 反代
3. **阻塞处理策略**：单机串行（默认）→ 运行时间 > 调度周期 → 任务堆积。改为丢弃后续调度或覆盖之前调度

### 9. 分布式系统中的幂等性如何保证？接口幂等、消息幂等？

#### 是什么

幂等性：同一个操作执行一次和多次，产生的结果和副作用完全一样。只读操作（GET）天然幂等；写操作（POST/PUT/DELETE）需要保证幂等。

#### 六种实现方案

**① 数据库唯一约束（最可靠）**
```sql
CREATE UNIQUE INDEX uk_order_no ON orders(order_no);
-- INSERT 时利用唯一约束，重复插入 → DuplicateKeyException → 返回「已存在」
```

**② Token/去重表（防重复提交）**
```
1. 前端先 GET /api/token → 返回 UUID token
2. 提交时带 token
3. 后端：SETNX order:token:<token> 1 EX 600
4. SETNX 返回 1 → 执行业务 + 删除 token
5. SETNX 返回 0 → 「请勿重复提交」
```

**③ 乐观锁（version）**
```sql
UPDATE account SET balance=balance-100, version=version+1 
WHERE id=1 AND version=5;  -- version=5 时更新, 否则影响行数=0
```

**④ 状态机**
订单状态：待支付 → 已支付 → 已发货 → 已完成。已支付不能回退到待支付，任何时候尝试改为已支付（如果已经是）→ 忽略或返回成功。

**⑤ 消息去重表**
Consumer 消费消息前，`INSERT INTO msg_consume_log(msg_id, consumer_id, create_time) VALUES(?, ?, NOW())`。如果 msg_id 重复 → DuplicateEntry → 直接 ack 消息（不处理）。

**⑥ SELECT FOR UPDATE（悲观锁）**
```sql
SELECT * FROM orders WHERE id=1 FOR UPDATE;
-- 检查订单是否已处理 → 已处理则返回，未处理则处理
UPDATE orders SET status='PROCESSED' WHERE id=1;
```

#### 关键认知：幂等的代价

不是所有接口都需要幂等。天然幂等的（查询）不需要做；幂等成本低的（唯一约束）可以做在 DB 层；幂等成本高的（分布式锁 + Redis 去重）只在关键写接口做。

### 10. 分布式系统的限流场景：接口限流、集群限流、热点限流如何实现？

（已在第 3 题详细展开 Sentinel 四层规则 + 滑动窗口 + 热点参数，这里补充集群限流）

**集群限流**：单机 QPS=1000，3 台机器总 QPS=3000。如果需要精确到集群总 QPS=2000 → Sentinel Token Server 模式。Token Server 持有全局令牌桶，Client 向 Token Server 请求令牌 → 获得令牌才放行。代价：Token Server 是性能瓶颈 + 单点风险。

**热点限流**：对热点参数（爆款商品 ID）单独限流。Sentinel 的 `ParamFlowRule` 针对特定参数值限流，不影响非热点值。

### 11. 熔断和降级的区别？在什么场景下需要熔断、降级？如何设计恢复机制？

#### 核心区别

- **熔断**：被动防御。下游出问题 → 你自动切断对它的调用（像电闸跳闸）
- **降级**：主动放弃。你出问题 → 主动关闭非核心功能（像大促时关评论、关推荐）

**熔断是「别人挂了，我保护自己」；降级是「我要挂了，我断臂求生」。**

#### 恢复机制设计

```
CLOSED（正常）→ [慢调用比例 > 50% OR 异常比例 > 50%] → OPEN（熔断）
OPEN → [等待熔断时长] → HALF_OPEN（探测）
HALF_OPEN → [放行 1-3 个请求] → 全部成功 → CLOSED
                               → 任一失败 → OPEN（重新开始熔断计时）
```

关键参数：
- `slowCallDurationThreshold`：慢调用定义（如 200ms 以上就是慢调用）
- `slowCallRateThreshold`：慢调用比例阈值（如 50%）
- `waitDurationInOpenState`：熔断时长（如 10s）
- `permittedNumberOfCallsInHalfOpenState`：HALF_OPEN 放行数量

### 12. 分布式系统数据一致性模型：强一致、弱一致、最终一致？各自适用场景与实现？

- **强一致**：所有节点看到相同数据。实现：2PC/3PC/Paxos/Raft。适用：银行转账、支付
- **弱一致**：不保证何时一致。实现：异步复制 + 过期失效。适用：社交 feed、点赞数
- **最终一致**：经过一段时间后最终一致。实现：消息队列 + 补偿 + 对账。适用：电商库存更新通知、积分系统

最终一致性的实现：本地消息表（同事务写业务 + 消息）→ 定时任务扫消息表 → 发送 MQ → 消费方幂等消费 → 每日对账补差异。

### 15. 分布式系统扩展性设计：水平扩展、垂直扩展、无感知扩展？

- **垂直扩展**（Scale Up）：换更大机器（32G → 128G）。简单但有机房物理上限。
- **水平扩展**（Scale Out）：加更多实例。核心是**无状态化**：Session → Redis，文件 → OSS，缓存 → Redis Cluster。只有无状态的服务才能随便扩。
- **无感知扩展**：K8s HPA 自动扩缩 + ReadinessProbe 延迟接入 + 一致性哈希避免大规模缓存失效
