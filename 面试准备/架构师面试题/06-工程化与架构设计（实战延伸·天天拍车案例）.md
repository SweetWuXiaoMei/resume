## 六、工程化与架构设计（实战延伸·天天拍车真实案例）

> 以下全部以「天天拍车」——国内头部 C2B 二手车拍卖平台为业务背景。
> 核心业务：个人车主卖车 → 上门检测/到店检测 → 生成检测报告 → 上架拍卖 → 全国车商在线竞拍 → 最高价成交 → 签约过户交付。
> 系统核心链路：车辆进件 → 检测评估 → 拍卖场次管理 → 实时竞价 → 成交签约 → 车款支付 → 物流交付。
> 技术栈：Spring Cloud Alibaba + Nacos + Sentinel + RocketMQ + Redis Cluster + MySQL(Sharding-JDBC) + SkyWalking + ELK + K8s。

### 1. Clean Code 与工程化规范落地——天天拍车如何从混乱到有序？

#### 背景与问题

我刚加入天天拍车时，代码仓库的状态是：5 个后端团队维护同一个 Git 仓库（单体应用向微服务迁移过程中），没有统一的代码规范。同一个项目里，有人用 `user_name` 有人用 `userName` 有人用 `user_name_`；有人用 Lombok 有人手写 getter/setter；`pom.xml` 版本号满天飞，升级一个依赖要改 20 个地方。线上故障复盘时发现，有两次 P0 事故的根因竟然是参数校验遗漏和空指针——如果有统一的异常处理和参数校验规范，根本不会发生。

#### 做了什么（三根柱子落地）

**第一根柱子：代码规范自动化**

不是发一封全员邮件让大家"注意代码规范"。直接让规范长在工具链里：

1. **定制化 Checkstyle 配置**：在阿里巴巴 Java 开发手册的基础上，结合我们自己的痛点加了 8 条自定义规则。比如「API 接口的返回值必须用 `Result<T>` 包装，不允许直接返回 `String` / `Map`」「RPC 接口的 DTO 必须实现 `Serializable` 并声明 `serialVersionUID`」。这两个规则是因为之前发生过 Feign 调用返回裸 String 导致下游反序列化失败、以及 DTO 没声明 serialVersionUID 导致的 Dubbo 序列化兼容性问题。

2. **IDE 统一配置**：把 Checkstyle 配置 + IDEA 代码模板 + import 排序规则打包进团队的「脚手架 starter」，新建项目自动继承。IDEA 保存时自动格式化 + import 优化，commit 前触发 Checkstyle 检查。

3. **CI 质量门禁**：SonarQube 质量阈——新增代码覆盖率 < 70%、新增 Bug > 0、新增漏洞 > 0 → 构建直接失败，无法合并到主干。

**第二根柱子：流程规范制度化**

1. **Git 分支模型**：`master`（生产） + `develop`（集成） + `feature/JIRA-序号-简短描述` + `hotfix/JIRA-序号-简短描述`。`master` 和 `develop` 都开启了分支保护。
2. **Commit Message 规范**：`feat:` / `fix:` / `refactor:` / `docs:` / `test:` + Jira 编号。配合 `commitlint` + Git Hook 自动校验，不符合规范的 commit 直接拒绝。为什么要强制 Jira 编号？因为出问题时要能从 Git Blame 反查到当时的需求背景。
3. **MR 评审制度**：至少 2 人 approve 才能合并。Review 时长超过 2 小时没人看的 MR，自动在团队飞书群 @所有人。

**第三根柱子：文化推动**

1. **代码评审文化不是一蹴而就的**。刚开始推行 MR 制度时，大家觉得是负担。我做了两件事：一是前两周我亲自 Review 所有人的 MR，每条 Comment 给出具体建议和理由（不是"写得不好"而是"这个 SQL 如果 `user_id` 为空会全表扫描，建议加前置校验"）；二是每两周评选一次「最佳 CR 评论」，发在团队群，让大家看到好的 Review 长什么样。
2. **技术债务看板**：在 Jira 上开了一个「技术债务」泳道，把 CR 中发现的非紧急但该修复的问题都建 Ticket，让债务看得见。
3. **最佳实践文档**：每遇到一个有代表性的坑（如 ThreadLocal 用了没 remove、事务中调了 RPC），就写一篇「最佳实践」，放进团队的 Confluence。新员工入职的 Onboarding Checklist 第一条就是读完最佳实践。

#### 过程中遇到的额外问题与解决

**问题 1：性能 Jitters——Checkstyle 在 CI 上跑太慢**

一开始 Checkstyle 检查 1000+ 个文件每次 CI 要花 40s。解决方案：只检查本次 MR 变更的文件——用 `git diff --name-only origin/develop...HEAD | grep '\.java$'` 提取变更文件列表，只对变更文件做 Checkstyle。从 40s 降到 2s。

**问题 2：SonarQube 误报太多，团队开始无视**

Sonar 的默认规则有些不适合我们的业务场景（如「方法复杂度超过 10」报 Critical）。Solution：不是关闭规则，而是分级处理——P0 阻塞合并（安全漏洞、空指针），P1 警告但可人工 override（复杂度、代码重复），P2 仅记录不阻塞。给 P1 的 override 加了审批流程（需要 Tech Lead 同意）。

**问题 3：规范推行初期团队抵触**

有人觉得"写代码还要被管，太不自由了"。我采取了"正向激励"策略——不批评不规范代码，而是表扬规范代码。每周站会展示一段"本周最干净的代码"，让大家感受到写好代码是被看见和被认可的。一个月后团队从抵触变成主动维护规范。

### 2. 设计模式在天天拍车的真实运用

#### 案例一：策略模式 + 工厂模式——拍卖出价规则引擎

**业务背景**：天天拍车的拍卖有多种模式：英式拍卖（逐步加价）、荷兰式拍卖（逐步降价）、暗拍（密封出价，一次性最高价成交）。不同品牌/城市的拍卖可能用不同模式，运营还经常新增拍卖玩法。

**初始代码的痛**：最开始所有拍模式逻辑塞在一个 `AuctionService.bid()` 方法里，用 if-else 判断模式：
```java
if ("ENGLISH".equals(auction.getMode())) {
    // 英式拍卖出价逻辑 50 行
} else if ("DUTCH".equals(auction.getMode())) {
    // 荷兰式拍卖出价逻辑 50 行
} else if ("SEALED".equals(auction.getMode())) {
    // 暗拍出价逻辑 50 行
}
```
每次加新模式要改这个类，方法膨胀到 300 行，改一个模式可能搞崩另一个模式（因为用了共享的成员变量做临时计算）。

**重构方案**：
```java
// 定义策略接口
public interface AuctionStrategy {
    /** 出价校验 + 执行 */
    BidResult bid(BidRequest request);
    /** 策略匹配条件 */
    boolean supports(Auction auction);
}

// 英式拍卖
@Component
public class EnglishAuctionStrategy implements AuctionStrategy {
    @Override
    public BidResult bid(BidRequest request) {
        // 1. 校验当前最高价 → 新车商的出价必须 > 当前最高价 + 最小加价幅度
        // 2. 校验车商保证金余额 → 保证金不足拒绝出价
        // 3. 扣减保证金（预冻结）→ 出价写入 Redis ZSet（score=出价）
        // 4. 广播出价事件给所有竞拍者（WebSocket 推送）
    }
    @Override
    public boolean supports(Auction auction) {
        return "ENGLISH".equals(auction.getMode());
    }
}

// 工厂——Spring 自动注入所有策略实现
@Component
public class AuctionStrategyFactory {
    private final List<AuctionStrategy> strategies;
    
    public AuctionStrategyFactory(List<AuctionStrategy> strategies) {
        this.strategies = strategies;
    }
    
    public AuctionStrategy getStrategy(Auction auction) {
        return strategies.stream()
            .filter(s -> s.supports(auction))
            .findFirst()
            .orElseThrow(() -> new BizException("未找到拍卖策略: " + auction.getMode()));
    }
}
```

**解决的问题**：
- 新增「反向荷兰式拍卖」（运营的新需求）→ 加一个 `ReverseDutchAuctionStrategy` 类 + `@Component`，不动任何已有代码。符合开闭原则。
- 每个策略类只关注自己的逻辑 → 类从 300 行瘦身到每个 ~80 行。单一职责。
- 单元测试好写了 → 以前测英式拍卖可能崩荷兰式，现在各测各的。

**实际遇到的问题**：策略模式实现后，发现车商连续出价时，每次 bid 都要走一遍策略匹配（`strategies.stream().filter()`），虽然 O(N) 但 N=4 还好。不过随着策略增多（后来到了 8 个），这个匹配每次请求都做变成了微优化点。解决方法：在 `AuctionStrategyFactory` 里初始化时构建一个 `Map<String, AuctionStrategy>`（key=mode），O(1) 查找：
```java
private final Map<String, AuctionStrategy> strategyMap;

public AuctionStrategyFactory(List<AuctionStrategy> strategies) {
    this.strategyMap = strategies.stream()
        .collect(Collectors.toMap(s -> s.getClass().getAnnotation(StrategyType.class).value(),
                                  Function.identity()));
}
```

#### 案例二：模板方法模式——车辆检测报告生成

**业务背景**：天天拍车的核心价值之一是「标准化检测报告」。一辆二手车进店后，检测师要录入：外观（漆面、钣金）、内饰（磨损、异味）、底盘、发动机、变速箱、路试感受、OBD 故障码等。不同品牌/价格区间的车，检测标准不同（豪华品牌有更多检测项）。

**初始代码的痛**：5 个不同的检测 Service（StandardReportService、LuxuryReportService、EVReportService 等），每个都写了 80% 相同的逻辑（拍照片存 OSS → 生成 HTML 报告 → 推送给车商），唯一的差异是「检测项列表不同」。

**重构方案（模板方法）**：
```java
public abstract class AbstractReportGenerator {
    
    // 模板方法（final！防止子类破坏流程）
    public final Report generate(InspectionData data) {
        // 1. 校验必检项（各子类不同）
        validateMandatoryItems(data);
        // 2. 拍摄关键部位照片（各子类不同）
        List<Photo> photos = takeKeyPhotos(data);
        // 3. 生成评分（各子类不同——豪华车评分维度更多）
        Score score = calculateScore(data, photos);
        // 4. 上传到 OSS（通用逻辑——所有报告同样上传方式）
        List<String> photoUrls = uploadToOss(photos);  // 私有方法，子类不能改
        // 5. 渲染 HTML 模板（通用逻辑）
        String html = renderTemplate(data, score, photoUrls);  // 私有方法
        // 6. 推送给关注的车商（通用逻辑）
        pushToDealers(data.getAuctionId(), html);  // 私有方法
        return new Report(html, score);
    }
    
    protected abstract void validateMandatoryItems(InspectionData data);
    protected abstract List<Photo> takeKeyPhotos(InspectionData data);
    protected abstract Score calculateScore(InspectionData data, List<Photo> photos);
    
    // 通用步骤——私有方法 + final，子类不能改
    private List<String> uploadToOss(List<Photo> photos) { /* 统一 OSS 上传 */ }
    private String renderTemplate(InspectionData data, Score score, List<String> urls) { /* 统一渲染 */ }
    private void pushToDealers(Long auctionId, String html) { /* 统一推送 */ }
}

// 豪华品牌报告
@Component
public class LuxuryReportGenerator extends AbstractReportGenerator {
    @Override
    protected void validateMandatoryItems(InspectionData data) {
        // 豪华品牌多了「真皮内饰磨损等级」「品牌音响功能检测」等
    }
    @Override
    protected List<Photo> takeKeyPhotos(InspectionData data) {
        // 多了底盘升降、空气悬架、ACC 雷达等关键部位拍照
    }
    @Override
    protected Score calculateScore(InspectionData data, List<Photo> photos) {
        // 评分维度：外观 20% + 内饰 15% + 动力 25% + 底盘 20% + 电子系统 20%
    }
}
```

**解决了什么**：
- 报告生成流程统一了（以前 5 个 Service 各有各的上传和推送逻辑，推送到车商的格式不统一）
- 新增新能源车检测报告 → 加一个 `EVReportGenerator` 子类，只实现 3 个抽象方法，其他步骤复用
- 流程步骤有 BUG 只需修父类，不用改 5 个子类

**实际遇到的问题**：模板方法 pattern 上线后，有一次需求变更——运营要求在报告生成后多一步「AI 车况估价」（调 AI 模型接口），这个步骤对所有报告类型都一样。按照模板方法，应该在父类 `generate()` 里加一个步骤 `estimatePriceWithAI()`。但问题来了——AI 模型接口调用耗时 ~2s，如果串行调用整个报告生成从 3s 变成 5s。解决方案：把 `estimatePriceWithAI()` 做成异步（CompletableFuture），在照片上传后立即调 AI（因为 AI 只需要照片，不依赖后续步骤），和模板渲染并行执行，最后用 `allOf()` 等待两个结果。

### 3. Arthas/MAT/SkyWalking 在天天拍车的实战案例

#### 案例一：Arthas 定位拍卖出价接口间歇性超时

**故障现象**：某天下午 3 点，车商投诉"出价按钮点了没反应"。监控显示出价接口 `POST /api/auction/bid` 的 P99 响应时间从 80ms 飙到 12s，错误率 15%。没有 OOM，没有 Full GC，SkyWalking 链路显示大量请求超时在出价服务内部就断了。

**排查过程——Arthas 三步走**：

第一步：`dashboard`
```
ID   NAME                    GROUP          PRIORITY  STATE    %CPU    TIME
23   pool-3-thread-14        main           5         RUNNABLE  99     4m30s
24   pool-3-thread-15        main           5         RUNNABLE  99     4m30s
```
有两个线程 CPU 打满。正常的业务线程池不应该这样。

第二步：`thread -n 5`
```
"pool-3-thread-14" Id=23 RUNNABLE
    at java.util.LinkedList.indexOf(LinkedList.java:543)
    at java.util.LinkedList.contains(LinkedList.java:316)
    at com.ttpc.auction.cache.DealerOnlineCache.isOnline(DealerOnlineCache.java:47)
    at com.ttpc.auction.service.BidService.checkDealerOnline(BidService.java:128)
```
定位到 `DealerOnlineCache.isOnline()` 方法在调 `LinkedList.contains()`！出价请求每次都要校验车商是否在线，而这个"在线车商列表"存在了 `LinkedList` 里，每次 `contains()` 是 O(n)。高峰期在线车商 5000+，每个出价请求的校验步骤耗时 `5000 × 遍历 / 100000 ≈ 50ms`。本身不致命——但是两个线程在同时遍历同一个 LinkedList，触发了并发修改（虽然没有 `ConcurrentModificationException`，但链表结构坏了，contains 死循环）。

第三步：`jad com.ttpc.auction.cache.DealerOnlineCache`
确认代码确实用的 `LinkedList`，而且没有加锁。

**根因链条**：`LinkedList` + 并发读写（没加锁） + 5000 在线车商 = 死循环。

**修复**：
- 短期止血（30 分钟上线）：把 `LinkedList` 换成 `ConcurrentHashMap.newKeySet()`（`Set.remove()` 和 `Set.contains()` 都是 O(1) + 线程安全）。CPU 从 99% 降到 5%，接口恢复正常。
- 长期方案：把「在线车商」状态从应用内存移到 Redis（`SET dealer:online:<id> 1 EX 120`），有状态服务变无状态，方便水平扩展。

**为什么一开始用了 LinkedList**：追查 Git Blame 发现是最初的实习生写的，没人 Review 到这个问题——因为当时只有 50 个车商在线，O(n) 完全没感觉。后来业务增长到 5000 个车商，这个问题才暴露出来。这个教训也推动了我们的 CR 制度——**Review 时要关注数据结构的选型和容量预估**。

#### 案例二：MAT 分析检测报告服务 OOM

**故障现象**：检测报告服务（inspection-report-service）每隔 2-3 天 OOM 重启一次。JVM 参数已经配了 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dump/`，拿到 dump 文件 2.3GB。

**MAT 分析过程**：

1. **Leak Suspects Report**：
   MAT 自动分析报告指出：`java.util.concurrent.ConcurrentHashMap$Node` 占用了 1.8GB（总堆 3G），嫌疑最大。

2. **Dominator Tree**：
   按 Retained Heap 排序，最大的对象是一个 `ConcurrentHashMap` 实例，内部有 42 万个 Entry。

3. **Path to GC Roots**：
   追踪这个 ConcurrentHashMap 的 GC Root 路径：
   ```
   ConcurrentHashMap ← LocalReportCache ← @Component ← Spring 容器 ← 静态引用
   ```
   这是一个单例的 Spring Bean 中的本地缓存，没有容量限制！

4. **查看 Entry 内容**：
   每个 Entry 的 key 是 `reportId`，value 是一个 `byte[]`（2-5MB 不等——检测报告的 PDF 文件）。42 万 × 平均 3MB ≈ 1.2TB？不对，实际只有 ~2GB。继续看发现 value 的 `byte[]` 绝大其实不是真正的 PDF 数据，而是被 `SoftReference` 包装的——这个是后面改的。但 `ConcurrentHashMap` 的 key 和 SoftReference 对象本身仍然占用大量内存。

**根因**：检测报告生成的 PDF 被缓存在 JVM 内存中（一个 `ConcurrentHashMap`），当时的设计思路是"车商经常反复查看检测报告，缓存起来避免反复查询 OSS"。但没有过期策略，没有容量上限。随着每天新增 2000+ 个报告，2-3 天就达到 3G 堆上限。

**修复**：
```java
// 之前（致命）
private final Map<String, byte[]> reportCache = new ConcurrentHashMap<>();

// 修复后（Caffeine 本地缓存）
private final Cache<String, byte[]> reportCache = Caffeine.newBuilder()
    .maximumWeight(500 * 1024 * 1024)  // 最大 500MB 内存（用 weight 而非 count）
    .expireAfterWrite(30, TimeUnit.MINUTES)
    .weigher((key, value) -> value.length)  // 按字节数计算权重
    .removalListener((key, value, cause) -> {
        log.info("报告缓存淘汰: {}, 原因: {}", key, cause);
    })
    .build();
```

**换 Caffeine 后遇到的额外问题**：`weigher` 计算权重时，每次 put/get 都会调 `weigher` 吗？不会——Caffeine 在写入时计算一次并记录权重。但 `byte[].length` 是 O(1) 的，所以没问题。真正的坑是：**`maximumWeight(500MB)` 是在写入时检查的，不是在后台线程定时检查**。如果突然来一堆超大报告（如豪华车检测报告 PDF 50MB × 20 个），一瞬间写入 1GB，Caffeine 无法阻止，只能等写入完成后异步淘汰。这就导致 OOM 仍然可能发生。解决：加了一个前置检查——`if (pdfBytes.length > 10 * 1024 * 1024) { /* 超大报告不缓存，直接存 OSS */ }`。

### 4. 架构从 0 到 1 落地的核心难点——天天拍车微服务改造纪实

#### 背景

我刚接手时天天拍车是一个 Spring Boot 单体应用（200+ 张表，50 万行 Java 代码，构建时间 15 分钟）。业务发展快（从 5 个城市扩展到 30 个城市，车商数从 3000 增长到 5 万），单体架构的瓶颈暴露：
- 一个车商的"我的订单"页面卡顿，全公司所有接口 P99 飙升（线程池被打满）
- 发布一个检测报告的 bugfix，要等整个单体应用构建+测试（30 分钟），打乱其他团队的发布计划
- 数据库单表超 5000 万行（车辆检测数据），查询超时

#### 难点一：服务拆分粒度——拆多少、怎么拆

**不是拍脑袋拆的**。我们花了两周做业务梳理：

第一步：画出业务全景图。和产品、运营、城市经理一起把所有业务流程画出来。发现核心业务域有 6 个：
- 车辆进件域（车主卖车 → 预约检测 → 进店）
- 检测评估域（检测师检测 → 生成报告 → 估价）
- 拍卖交易域（上架 → 场次管理 → 竞价 → 成交）
- 车商管理域（注册 → 认证 → 保证金 → 信用评级）
- 签约过户域（成交后签约 → 过户 → 交付）
- 售后保障域（质保、退换、投诉）

第二步：DDD 限界上下文分析。识别出每个域的「聚合根」：
- 车辆进件域 → `Vehicle`（车辆档案）是聚合根
- 检测评估域 → `InspectionReport`（检测报告）是聚合根
- 拍卖交易域 → `Auction`（拍卖场次）和 `Bid`（出价记录）是两个聚合根

第三步：拆分优先级。先拆「变更频率最高、独立价值最大」的。我们选择了**拍卖交易域**作为第一个试点——因为它是核心赚钱业务，而且每次大促都是瓶颈。

**遇到的额外问题**：DDD 分析做完了，但团队没做过分库。一个服务一个数据库意味着什么？检测评估域要查车辆进件域的车辆信息——怎么能高效地查？团队一开始想"直接 JOIN 对方的数据库"。这就是典型的单体思维。

**解决**：定义了服务间调用的铁律——**绝对不允许一个服务直接连另一个服务的数据库**。车辆信息通过 Feign 调用进件服务的 `/api/vehicle/{id}` 接口获取。为了性能，检测服务在本地 Caffeine 缓存了车辆基础信息（车牌、品牌、车型，变更概率很低）。

#### 难点二：数据迁移——千万级车辆表不中断业务的切库

车辆进件域有 3000 万条车辆记录，拍卖交易域有 8000 万条出价记录。切库需要迁移这些数据，但业务不能停（每天 2000+ 辆车上拍，不能因为迁移停服）。

**迁移方案（6 步渐进式）**：

1. **全量迁移（凌晨）**：凌晨 2 点，老库的车辆表、出价表导出 SQL dump → 导入新库。耗时 2 小时。
2. **Canal 增量订阅**：全量迁移后立刻开启 Canal 订阅老库 binlog → 解析增量变更 → 写入新库。保证全量迁移完成后的增量数据不会丢。
3. **数据校验**：`pt-table-checksum` 对每行数据算 CRC/MD5，对标老库和新库。发现 23 行不一致（全量迁移期间产生的新数据），手动补偿。
4. **双写阶段**：应用层改造——写操作同时写老库 + 新库（异步），读操作优先读新库，新库查不到回退到老库。这个阶段持续 1 周，验证新库性能和数据一致性。
5. **灰度切读**：逐步把读流量从老库切到新库（1% → 10% → 50% → 100%），每步观察 SkyWalking 上的错误率是否有变化。
6. **停写老库**：确认 100% 切读后 3 天无误 → 停掉双写逻辑 → 下线老库。

**实际遇到的问题**：双写阶段，有一次新库的 MySQL 连接池满了（运营在跑一个大 SQL 报表，占用了所有连接），导致所有双写失败。但因为写老库是主路径（双写新库是异步 + 异常不影响主流程），所以业务没受影响。监控发现了「新库写入失败率 100%」的告警，30 分钟内加了新库的连接池限制（最大连接数从 50 调到 200）+ 大 SQL 走只读备库。

#### 难点三：团队从单体思维到分布式思维的转变

**最大障碍不是技术，是思维方式**。团队成员习惯了「改一行代码 → 测一下 → 发版」，突然变成「改一个服务 → 要保证不影响调用方 → 发版要协调多个服务」。

**具体问题和解决**：

- **问题**：第一次拆分拍卖服务后，一个开发改了出价接口的 DTO 字段名（`bidPrice` → `price`），下游的签约服务调这个接口直接 500 了。他没意识到还有别的服务在调他的接口。**解决**：接口变更必须兼容——新增字段不删旧字段，旧字段标记 `@Deprecated`，至少保留 2 个版本再删。

- **问题**：测试环境搭建困难。之前 1 个单体应用 = 1 个测试环境。现在 6 个微服务 = 6 个测试环境？不可能每人配 6 台机器。**解决**：搭建 K8s 开发集群，每个 MR 自动在 K8s 上创建临时的独立环境（namespace 隔离），MR 合并后自动回收。

- **问题**：联调噩梦。开发 A 改检测服务的一个 BUG，需要调进件服务、车商服务的接口来验证，但这两个服务都不是 A 负责的。**解决**：引入 `spring-cloud-contract`，每个服务维护一份 API Contract（接口定义 + Mock 数据）。A 在本地用 Mock 就能联调，不需要依赖别人的真实环境。

#### 难点四：节奏把控——"我们下周大促先把业务顶上去，架构改造往后放放"

这是最头疼的问题。业务压力天天催，架构改造看不到短期价值。

**我的策略——做了三件事**：

1. **用业务语言说话**：不说「我们需要微服务化改造提升系统可用性」，而是说「上次 18 大促支付接口崩了 20 分钟，就是因为单体应用单点故障。改造后，即使支付服务挂了，出价功能还是好的，大促损失至少减少 80%」。
2. **渐进式改造，不一步到位**：第一版只把拍卖服务拆出来（最痛的模块）。其他模块保持单体，新功能全在微服务里开发。相当于「绞杀者模式」——逐步蚕食单体，而不是一刀切。
3. **每个迭代留 20% 时间做技术改造**：不单开一个「技术债务 Sprint」（产品不会批），而是在每个业务迭代中穿插技术改进。比如这个 Sprint 的业务目标是「增加荷兰式拍卖」，我们顺便把拍卖服务中的出价逻辑拆成策略模式 + 独立表。

### 5. 核心业务技术攻关案例——拍卖出价从卡顿到丝滑

#### STAR 完整案例

**S（情境）**：天天拍车的主要营收来源是拍卖成交佣金。某次 618 大促，在线拍卖场次从平时的 200 场同时进行飙到 800 场。出价接口 P99 从 50ms 飙升到 8s，车商反馈"点出价按钮过 10 秒才反应，黄花菜都凉了"。实时竞价的本质是「谁先出到最高价谁赢」，出价延迟意味着车商体验极差、拍卖效率降低、平台收入受损。

**T（任务）**：3 天内把出价接口 P99 从 8s 恢复到 100ms 以内，保证一周后的大促（618 爆发期）不崩。

**A（行动）**：

**第一步：全链路压测 + 瓶颈定位**（半天）

用 JMeter 模拟 800 场拍卖同时进行（3000 个虚拟车商、每秒 500 次出价请求）→ 监控显示：
- 出价服务 CPU 90%（正常）
- 出价服务内存 60%（正常）
- **MySQL 的 CPU 100%！**（瓶颈所在）

SkyWalking 链路分析——每次出价请求的数据库操作：
1. `SELECT * FROM bid WHERE auction_id=? AND dealer_id=?` — 检查是否已出价（3ms）
2. `INSERT INTO bid(auction_id, dealer_id, price, created_at) VALUES(...)` — 写入出价记录（15ms）
3. `UPDATE dealer_account SET frozen_amount = frozen_amount + ? WHERE dealer_id=?` — 冻结保证金（800ms！这里卡了）
4. `UPDATE auction SET current_price=?, current_dealer_id=? WHERE auction_id=?` — 更新当前最高价（15ms）

第三步的 `UPDATE dealer_account` 耗时 800ms！为什么一个简单的 UPDATE 这么慢？EXPLAIN 一看——`dealer_account` 表没有 `dealer_id` 的索引！800 万行全表扫描找 dealer_id。另外这条 UPDATE 走了 `SELECT ... FOR UPDATE`（悲观锁），因为出价时要保证保证金余额乐观。

**第二步：紧急止血**（1 天）

短期方案——不是直接优化 SQL（需要加索引、改代码、重新发版——至少半天），而是采用「削峰 + 异步」：
- 出价请求进入后，先把出价写入 Redis（`ZADD auction:{id}:bids`，score=出价，member=dealerId+price）→ 返回「出价已受理」
- 后台 MQ 消费者 10ms 拉取一次 Redis 中的待处理出价 → 在消费者中串行处理扣保证金 + 写 DB
- 前端车商通过 WebSocket 实时推最高价变化

这样出价接口的响应从 8s 降到 50ms（只写 Redis）。真正的扣保证金变成异步，靠 RocketMQ 削峰。

**第三步：根因修复**（2 天）

- `ALTER TABLE dealer_account ADD INDEX idx_dealer_id(dealer_id)` — 加索引。UPDATE 从 800ms 降到 1ms。
- 保证金冻结从悲观锁改为乐观锁（version 号）：`UPDATE dealer_account SET frozen_amount=frozen_amount+?, version=version+1 WHERE dealer_id=? AND version=?`。失败 → 重试（CAS）。消除了锁等待。
- 出价去重检查从查 MySQL 改为查 Redis Bloom Filter：`BF.EXISTS bid:auction:{id} dealer:{id}` → 不存在才允许出价 → 减少了 MySQL 压力。Bloom Filter 的假阳性（误判为已出价）概率 0.1%，对业务影响极小（极少数车商的首次出价被拒绝，客户无感知）。

**第四步：架构升级**（1 天，为后续大促做准备）

- 出价服务从 2 个实例扩到 8 个（单日出价量 8 万 → 20 万）
- Redis Cluster 扩容（出价数据热点打散）
- Sentinel 对出价接口做限流（单机 QPS 500 → 防止某个车商脚本刷出价）

**R（结果）**：
- 出价接口 P99：8s → 50ms（短期）→ 30ms（长期）
- 618 当天出价总量 15 万次，系统零故障
- 拍卖成交率提升 12%（因为出价延迟低，车商更愿意参与竞价）

**R（反思/学到）**：
1. **不可在数据库中用悲观锁处理高频并发操作**。保证金冻结应该用 Redis + Lua 原子扣减。下个季度我们做了这个优化。
2. **MySQL 索引缺失是性能第一杀手**。800 万行表的一个全表扫描 UPDATE 就能拖垮整个出价链路。事后我们建立了「核心表索引审查」机制——每个核心业务表的索引清单必须由 Tech Lead 审批。
3. **异步化要处理好最终一致性**。出价异步化后，车商出价后立刻查「我的出价列表」可能看不到刚才的出价（还没被异步处理）。解决方案：MyBatis 拦截器做的本地缓存——出价写入 Redis 后立即写入本地 Caffeine 缓存，读时先读 Redis + 本地缓存，没有再查 MySQL。
4. **压测必须模拟真实场景**。之前做过压测，但只压了单次出价——没模拟并发竞争同一拍卖的情况（车商抢拍）。真实拍卖是 50+ 个车商对着同一辆车疯狂出价——锁竞争才是真正的瓶颈。

### 6. 架构演进——从单体到微服务再到领域驱动

#### 天天拍车架构演进三阶段

**第一阶段：单体（2016-2019）**
- 一个 Spring Boot 应用 + 一个 MySQL
- 所有功能在一个进程里：进件、检测、拍卖、支付、报表
- 适合创业阶段：开发快、部署简单、不用处理分布式复杂性
- **触发崩塌的信号**：单表 5000 万行 + 构建 15 分钟 + 1 个模块 CPU 打满拖死全站

**第二阶段：微服务改造（2019-2021）**
- 拆成 6 个独立服务（前面说的进件、检测、拍卖、车商、签约、售后）
- 每个服务独立数据库 + 独立 K8s 部署
- 引入 Nacos、Sentinel、RocketMQ、SkyWalking
- **遇到的典型问题**：服务拆分粒度不够细。拍卖服务从 1 个变成了 3 个（拍卖管理 + 实时竞价 + 成交结算）；检测服务拆成 2 个（检测数据采集 + 报告生成）。拆分的触发因素是团队增长——原先 5 人团队扛 1 个拍卖服务，后来变成 15 人，必须按团队边界再拆。

**第三阶段：领域驱动优化（2021-至今）**
- 不是更细地拆，而是重新审视领域模型。发现"车辆"这个概念分散在进件服务、检测服务、拍卖服务、签约服务四个地方，每个地方都存了一份车辆的冗余信息（车牌、品牌、车型）。
- 做了一次领域模型重构：把「车辆基础档案」收归到进件服务，其他服务只存 `vehicle_id` + 必要的业务字段。车辆信息变更时广播 `VehicleUpdatedEvent`，其他服务响应更新。

#### 平滑演进的关键原则

1. **绞杀者模式**：旧系统只读不写，新功能写微服务。双写过渡期至少 2 周。
2. **接口版本化**：API v1 保留 3 个月再下线，给客户端留升级窗口。
3. **数据库 Schema 只增不减不改**：加列（nullable）→ 代码兼容新旧 schema → 旧代码下线 → 删旧列。
4. **可回滚**：每次架构变更都要有回滚预案。微服务切换时要保持「一键回滚到单体」的能力至少 1 个月。
5. **里程碑驱动，不追求完美**：架构演进分 3 个里程碑，每个里程碑有明确的成功标准（如「拍卖服务 P99 < 100ms」「车辆进件服务独立部署」），达到就庆祝，不追逐"100% 微服务覆盖率"。

### 7. 代码评审的流程和重点——天天拍车如何避免"一个未 Review 的 LinkedList 导致全站故障"

#### 完整的 CR 流程

```
开发自检（本地 Checkstyle + 单元测试）
  → 创建 MR（GitLab，填模板：变更说明 + Jira 关联 + 测试截图）
  → CI 自动检查（编译 + 单元测试 + SonarQube + 覆盖率）
  → CI 通过 → 自动 @ 相关 Reviewer（Code Owner 文件指定）
  → 至少 2 人 Review + Approve
  → 合并到 develop
```

**Code Owner 机制**：每个模块维护一个 `CODEOWNERS` 文件。提交 MR 后 GitLab 自动 @ 该模块的 Owner。比如拍卖模块的 Owner 是我 + 拍卖组组长，所有拍卖相关 MR 必须我俩之一 Review 通过。

**Review 时间承诺**：团队成员承诺「2 小时内给出 Review 反馈」。超过 2 小时没人看 → 飞书群提醒 → 超过 4 小时升级到组长。

#### CR 重点关注清单（天天拍车定制版）

| 维度 | 检查点 | 实际案例 |
|------|--------|---------|
| 设计 | 聚合根是否正确？事务边界是否合理？ | 发现一次 MR 在出价方法里直接调支付服务扣款 → 违反了「事务中不做 RPC」的铁律 |
| 性能 | 是否有 N+1 查询？数据结构选型（HashMap vs LinkedList）？ | 前面 LinkedList 的惨案就是 Review 遗漏导致的 |
| 安全 | SQL 拼接是否用了 `#{}`（MyBatis）？敏感信息（车牌、手机号）是否脱敏？ | 一次 MR 的日志里打印了完整的车主手机号 → Review 发现并要求用 `PhoneUtil.mask(phone)` |
| 并发 | 共享变量是否线程安全？ThreadLocal 是否 remove？ | 出价服务用 ThreadLocal 存车商上下文，Review 发现没有 finally remove |
| 可运维 | 关键逻辑是否上报了监控指标？异常是否打印了足够的上下文？ | 异常只 catch 不 log → Review 要求加 log.error + 上报 Metrics |

#### CR 发现的经典问题——"加了 100 万行日志的拍卖表"

一次 Review 拍卖服务 MR 时，发现开发在出价方法里加了一个 `log.info("出价完成: {}", JSON.toJSONString(bidResult))`，把整个 `bidResult` 对象（包含检测报告摘要、车商信息、车辆信息——总共约 2KB 的 JSON）打到日志里。我问开发为什么加这个日志，他说"方便排查出价失败"。但出价 QPS 高峰期 500/s → 500 × 2KB × 60s × 60min × 24h = 86GB 日志/天 —— Elasticsearch 会被打爆。

**解决方案**：
- 正常出价不打印完整日志，只打印 `bidId + dealerId + price`（50 字节）
- 异常出价才打印完整上下文
- 同时要求加 Metrics 埋点（出价成功/失败的 Counter），监控大盘能看到趋势，不需要去日志里翻

#### 推动 CR 文化落地的实际操作

1. **前两周我亲自示范**：每个 MR 都有我的 Comment，每条 Comment 给理由（"这里用 ArrayBlockingQueue 而不是 LinkedBlockingQueue，因为 xxxx"），让团队看到好的 Review 长什么样
2. **正向激励**：每月评选「最佳 Review」，标准是「发现问题最多、提出的建议最有建设性」，发在团队大群里，带具体例子
3. **老带新**：新人的前 5 个 MR，由两名 Senior 共同 Review。目的不是卡他，而是通过 Review 帮他快速熟悉团队的代码规范
4. **问题回顾**：每次线上事故，复盘时追溯「这个问题的代码有没有被 Review 过？Review 时为什么没发现？」→ 把教训沉淀到 CR Checklist

### 8. 工程化工具集成 CI/CD——天天拍车从手动发版到全自动部署

#### 改造前的困境

我刚接手时，发布流程是这样的：
1. 开发在本地 `mvn clean package` → 把 jar 包用 scp 传到服务器
2. SSH 上去 → `ps aux | grep java` → `kill -9 pid` → `nohup java -jar xxx.jar &`
3. 如果发了 6 个微服务，每个都要手动操作一遍
4. 没有灰度、没有自检、没有回滚（出问题靠人肉 kill、换 jar、重启）
5. 发布当天所有人不敢走（"万一出问题呢"）

#### 改造后的完整 CI/CD 流水线

```
Git Push to develop
  ↓
GitLab CI Trigger
  ↓
Stage 1: Build & Test（并行）
  ├─ mvn clean compile （3 min）
  ├─ mvn test + JaCoCo coverage （5 min）
  ├─ Checkstyle + PMD （30s，只扫描变更文件）
  └─ SonarQube Quality Gate （1 min）
  ↓
Stage 2: Docker Build & Push（2 min）
  ├─ docker build -t ttpc/auction-service:${CI_COMMIT_SHORT_SHA}
  ├─ 推送到 Harbor 私有镜像仓库
  └─ 同时打一个 `latest-dev` 标签
  ↓
Stage 3: Deploy to Dev（1 min）
  ├─ kubectl set image deployment/auction-service auction-service=ttpc/auction-service:${CI_COMMIT_SHORT_SHA} -n dev
  └─ kubectl rollout status deployment/auction-service -n dev（等 30s）
  ↓
Stage 4: Integration Test（5 min）
  ├─ 运行集成测试套件（Spring Boot Test + Testcontainers）
  └─ 调开发环境的真实接口做 smoke test
  ↓
[手动 Approval] —— 测试环境验证通过，QA + Tech Lead 手动点「同意发布」
  ↓
Stage 5: Deploy to Staging（1 min）
  ├─ kubectl set image ... -n staging
  └─ 灰度 5% 真实流量引流（Gateway Header 染色）→ 观察 30 分钟
  ↓
Stage 6: Deploy to Prod - 金丝雀（Canary）
  ├─ kubectl set image ... -n prod（只替换 1 个 Pod 为 v2）
  ├─ Gateway 5% 流量打 v2 → 观察 15 分钟（SkyWalking 错误率 + Grafana 面板）
  └─ 正常 → 扩大 25% → 50% → 100%
  ↓
Stage 7: Post-Deploy Health Check
  ├─ 自动调 /actuator/health/readiness 确认 Pod 就绪
  ├─ 对比新旧版本的错误率（SkyWalking API）
  └─ 异常 → 自动回滚：kubectl rollout undo deployment/auction-service -n prod
```

#### 实际搭建过程中遇到的问题

**问题 1：Docker 镜像太大——每次构建推镜像要 5 分钟**

初始的 Dockerfile 基于 `openjdk:11`（全量 JDK），镜像 650MB。改成多阶段构建：
```dockerfile
# 构建阶段
FROM maven:3.8-jdk-11 AS builder
COPY . /src
WORKDIR /src
RUN mvn clean package -DskipTests

# 运行阶段——用 JRE 而非 JDK
FROM adoptopenjdk/openjdk11:alpine-jre
COPY --from=builder /src/target/auction-service.jar /app/app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```
最后用 `eclipse-temurin:11-jre-alpine`（JRE Alpine），镜像从 650MB 降到 180MB，推镜像时间从 5 分钟降到 30 秒。

**问题 2：K8s 部署后 Pod 启动完了但流量没进来**

新 Pod `readinessProbe` 返回 success → K8s 标记 READY → 但 Gateway 还在路由到旧 Pod？排查发现是 Gateway 的路由缓存（Caffeine）缓存了旧 Pod 的 IP，刷新周期 30 秒。解决：把路由缓存刷新周期从 30s 调到 5s，并配 `speaker.refresh` 基于 Nacos 事件触发（即时）。

**问题 3：集成测试不稳定——时过时不过**

`Testcontainers` 启动 MySQL/Redis 容器需要时间，偶尔因为 test 运行机器的 Docker 慢超时。解决：
- `Testcontainers` 改为 `reuse` 模式（测试之间复用同一个 MySQL 容器）
- 把集成测试从 CI 中拆出来独立运行（不阻塞构建），失败不阻塞发布
- 关键链路的集成测试保留在 CI 中，确保阻塞

**问题 4：金丝雀发布时新旧版本数据库兼容性**

新版本加了字段 `dealer_account.vip_level`。旧版本代码不认识这个字段，`SELECT *` 反序列化时报 Unknown column。解决：
- Schema 变更规范——**先通过 `ALTER TABLE ADD COLUMN ... DEFAULT NULL`** 上线（旧代码能跑，新字段 NULL 不影响）
- 再部署新代码（能识别新字段）
- 确认旧版本全部下线 → `ALTER TABLE ALTER COLUMN vip_level SET NOT NULL DEFAULT 0`

### 9. 系统可扩展性设计——从"一个拍卖模式"到"随时上线新玩法"的演化

#### 天天拍车拍卖业务的扩展性演进

**V1.0：硬编码——只有英式拍卖**
```java
// 所有逻辑写死在 BidService 里
public void bid(BidRequest req) {
    if (req.getPrice() <= currentMaxPrice + minIncrement) {
        throw new BizException("出价必须大于当前最高价 + 最小幅度");
    }
    // ...
}
```
扩展性：零。加新模式 = 改 BidService。

**V2.0：策略模式——支持英式、荷兰式、暗拍**
```java
// 如前面题 2 的设计
interface AuctionStrategy { BidResult bid(BidRequest); }
class EnglishStrategy implements AuctionStrategy { ... }
class DutchStrategy implements AuctionStrategy { ... }
class SealedStrategy implements AuctionStrategy { ... }
```
扩展性：中等。加新模式 = 加一个实现类。但拍卖的生命周期（开始、进行中、倒计时、结束）仍然耦合。

**V3.0：拍卖生命周期插件化——支持完全自定义的拍卖流程**

运营突然提了一个需求：「帮卖模式」——车主设底价，车商暗拍，但车主可以在拍卖过程中降价（一拍没人买，降 5000 二拍）。这个流程和现有的英式/荷兰式/暗拍都不一样——不是出价逻辑不同，而是**整个拍卖的生命周期不同**。

```java
// 拍卖生命周期接口
public interface AuctionLifecycle {
    /** 开拍 */
    void onStart(Auction auction);
    /** 出价 */
    void onBid(Auction auction, Bid bid);
    /** 倒计时（可扩展——比如帮卖模式到了截止时间没人出价自动降价二拍） */
    void onCountdown(Auction auction, int secondsRemaining);
    /** 结束 */
    void onEnd(Auction auction);
    /** 生命周期类型标识 */
    String getType();
}
```

帮卖模式的生命周期：
```java
@Component
public class BangMaiLifecycle implements AuctionLifecycle {
    @Override
    public void onEnd(Auction auction) {
        // 检查是否有有效出价
        if (auction.getHighestBid() == null) {
            // 没人出价 → 自动降价 → 开启二拍
            if (auction.getCurrentRound() < auction.getMaxRounds()) {
                auction.reducePrice(auction.getCurrentPrice() - 5000);
                auction.advanceRound();
                auctionService.restart(auction);
            } else {
                auctionService.markExpired(auction);  // 降价到底也没成交 → 流拍
            }
        } else {
            auctionService.markSold(auction);  // 正常成交
        }
    }
}
```

扩展性：极高。加一个完全新的拍卖业务模式 → 实现两个接口（`AuctionStrategy` + `AuctionLifecycle`），不碰核心框架。之前上线「帮卖模式」只用了 3 天开发 + 1 天测试。

#### 插件化的落地经验

**SPI（Service Provider Interface）机制**：
```java
// 定义扩展点
public interface AuctionPlugin {
    void beforeBid(Auction auction, BidRequest request);
    void afterBid(Auction auction, BidResult result);
}

// 各团队实现自己的插件
@Component
public class RiskControlPlugin implements AuctionPlugin {
    // 风控团队写：出价前校验车商信用分
}

@Component  
public class MarketingPlugin implements AuctionPlugin {
    // 营销团队写：出价后检查是否触发优惠券发放
}
```

**遇到的问题**：插件执行顺序有依赖性。风控插件必须第一个执行（先校验信用），营销插件最后一个。第一版没有排序机制，启动时插件的执行顺序是随机的。

**解决**：用 `@Order` 注解 + `Ordered` 接口：
```java
@Order(Ordered.HIGHEST_PRECEDENCE)  // 最先执行
public class RiskControlPlugin implements AuctionPlugin { ... }

@Order(Ordered.LOWEST_PRECEDENCE)  // 最后执行
public class MarketingPlugin implements AuctionPlugin { ... }
```

还有一次——营销插件有问题抛了异常，导致后续插件也全挂了。解决方案：Spring 的 Plugin Chain 默认 fail-fast，改成 fail-safe——`List<AuctionPlugin>` 遍历，每个插件 try-catch，单插件异常不影响其他插件，只告警不中断。

### 10. 系统安全性设计——天天拍车的多层防护

#### 接口安全

**问题一：车商 API 的防重放攻击**

天天拍车给大车商提供了 API 接口（程序化出价）。有一个车商抓了出价接口的包，用脚本每分钟刷出价——影响拍卖公平性。

**解决方案**：
1. API Key + Secret 签名。每次请求签名 = `HMAC-SHA256(secret, method + path + timestamp + nonce + body)`
2. 服务端校验 timestamp（±5 分钟内有效，防止重放）
3. nonce + timestamp 存入 Redis（`SET nonce:{appId}:{nonce} 1 NX EX 300`），如果 SETNX 失败说明 nonce 已被用过
4. 签名校验不通过 → 返回 401 + 记录到风控日志

**问题二：检测报告强制水印 + 防盗链**

检测报告的 PDF 如果被车商下载后发给别人，就可能绕过了平台的收费机制。解决：
- OSS 设置私有 Bucket + 签名 URL（`?Expires=3600&OSSAccessKeyId=xxx&Signature=xxx`），其他人拿不到
- PDF 内置水印（车商 ID + 手机号 + 时间戳），即使截图也能溯源

#### 数据安全

**车辆 VIN 码（车架号）加密存储**：
VIN 码是车的"身份证"，泄露后可能被用作套牌。数据库中用 AES-256 加密存储：
```java
@TableField(typeHandler = EncryptTypeHandler.class)  // MyBatis Plus 自定义 TypeHandler
private String vin;
```
查询时 TypeHandler 自动解密（内存中），写入时自动加密。密钥管理用 K8s Secret → 环境变量注入，不写死在代码/配置文件里。

#### 权限控制——车商等级体系

天天拍车的车商有不同等级（普通/金牌/钻石），不同等级看到不同范围的车辆、享有不同佣金率、保证金要求不同。

**数据权限实现**（MyBatis 拦截器）：
```java
@Intercepts(@Signature(type = Executor.class, method = "query", args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class}))
public class DealerDataInterceptor implements Interceptor {
    @Override
    public Object intercept(Invocation invocation) throws Throwable {
        // 获取当前车商上下文
        DealerContext ctx = DealerContextHolder.get();
        if (ctx != null && ctx.getLevel() != null) {
            // 拼装 SQL 条件
            BoundSql boundSql = ms.getBoundSql(parameter);
            String oldSql = boundSql.getSql();
            String newSql = oldSql + " AND vehicle_level <= " + ctx.getLevel().getMaxVehicleLevel();
            // 反射替换 BoundSql 中的 sql 字段
            ReflectUtil.setFieldValue(boundSql, "sql", newSql);
        }
        return invocation.proceed();
    }
}
```

#### 实际遇到的安全问题

**问题：内部运维人员的数据库权限过大**

DBA 有生产库的全部权限 → 一次一个运维误操作 `DROP TABLE`（当然是在测试库，但如果是在生产呢？）。解决：生产数据库按「读写分离 + 最小权限」配置。DBA 日常只需要只读权限（查数据），写权限只在执行变更时通过审批流程临时授予（`GRANT ... WITH GRANT OPTION; ... REVOKE ...`）。

### 11. 技术选型的原则——天天拍车的一次关键选型复盘

#### RocketMQ vs Kafka 的选型过程

**背景**：拍卖出价异步化需要消息队列。团队有人提议用 Kafka（社区更活跃、大厂都在用），也有人提议 RocketMQ（阿里系、事务消息功能好）。

**选型决策矩阵**：

| 维度 | 权重 | RocketMQ | Kafka | 得分计算 |
|------|------|---------|-------|---------|
| 业务匹配度——是否支持事务消息？ | 25% | 9（原生事务消息） | 6（需要额外实现） | R:2.25 K:1.5 |
| 团队熟悉度——有没有人深度用过？ | 25% | 7（一人有生产经验） | 5（没用过） | R:1.75 K:1.25 |
| 阿里云托管支持 | 15% | 10（阿里云 MQ 完全兼容） | 7（需要自建或买 Confluent） | R:1.5 K:1.05 |
| 社区活跃度 | 10% | 7 | 10 | R:0.7 K:1.0 |
| 运维成本 | 15% | 8（阿里云托管，零运维） | 6（自建 Kafka 需要专人） | R:1.2 K:0.9 |
| 延迟 | 10% | 8 | 9 | R:0.8 K:0.9 |
| **总分** | 100% | **8.2** | **6.6** | |

**最终选择 RocketMQ 的核心原因**：
1. 业务的**事务消息**是刚需（出价后更新保证金必须在同一事务中）
2. 阿里云提供托管版 RocketMQ（Aliware MQ），运维成本接近零
3. 团队有一人用过（技术风险可控），Kafka 没人有生产经验

#### 选型后踩的坑

**RocketMQ 并不是银弹**。上线后发现了一个问题：我们之前预估的出价消息量是 5 万条/天，但 618 大促当天发到了 30 万条。RocketMQ 的同步刷盘模式（保证消息不丢）在 30 万 TPS 下延迟开始增大（从 5ms 到 20ms）。解决：把非关键消息（出价通知、运营日志）改为异步刷盘，只有「出价确认」（影响保证金）保持同步刷盘。

### 12. 系统性能测试——天天拍车的大促压测体系

#### 压测不是上线前跑一次就完了

我们建立了**三层压测体系**：

**第一层：CI 集成测试中的基准性能测试（每次 MR 自动跑）**
用 JMH（Java Microbenchmark Harness）对关键方法做基准测试：
```java
@Benchmark
public void benchmarkBidValidation() {
    BidRequest req = new BidRequest(1001L, 500000L);  // 车商 ID=1001，出价 50 万
    bidService.validate(req);  // 出价校验
}
```
如果本次 MR 的基准测试耗时比上一次 MR 慢 20%+ → CI 告警 → Review 代码是否有性能回退。

**第二层：每两周的全链路压测（单服务 + 全集群）**
用 JMeter 模拟真实流量模型：
- 500 个虚拟车商
- 200 场同时进行的拍卖
- 每个拍卖 10 个竞价车商
- 出价行为：随机 1-5s 间隔（模拟人点出价的真实频率）

观察：出价接口 P50/P95/P99 + 数据库 CPU + Redis QPS + RPC 调用延迟。

**第三层：大促前的极限压测（摸容量上限）**
增大并发直到系统出现首个错误（CPU > 90% or P99 > 1s or 错误率 > 1%），记录此时的 TPS 作为系统容量上限。目标是在此基础上留 50% 安全余量。

#### 压测中发现的经典问题

**问题 1：JMeter 压测正常但线上大促还是慢**

排查发现 JMeter 模拟的流量是「500 个车商各自出价不同车辆（均匀分布）」，但真实大促场景是「50 个车商对着同一辆热门车疯狂抢拍（热点集中）」。热点集中时 Redis ZSET 的并发写入竞争严重、Lua 脚本执行排队。

**解决**：压测需要两种流量模型——均匀出价（基准性能测量）和热点出价（极限压力测试，50 个线程对同一 `auctionId` 出价）。

**问题 2：压测环境和生产环境配置不一致**

压测环境：32C 64G 物理机，生产：4C 8G K8s Pod。压测环境能扛 5000 TPS，生产只能扛 1200 TPS。

**解决**：压测必须在 K8s 中使用和生产相同的 Pod 规格。用 JMeter 分布式压测（多个 JMeter slave Pod + 1 个 master）。

### 14. 微服务架构下的日志收集和分析——ELK 在天天拍车的落地

#### 从零散的日志到统一可搜索

**改造前的问题**：
- 6 个微服务各自 print 日志到本地文件 → 出问题要 SSH 到 6 个 Pod 上分别 `tail -f` 翻日志
- 日志格式不统一（有的用 `[]` 有的用 `-` 有的用空格分隔）
- 没有 traceId → 一个出价请求跨了 4 个服务 → 无法串联
- Spring Boot 默认日志输出是文本格式不是 JSON → Logstash 解析困难

**改造方案（EFK）：Filebeat + Kafka + Elasticsearch + Kibana**

```
Pod 内的应用日志(stdout/stderr)
  → Filebeat DaemonSet（每个 K8s Node 一个，采集该节点所有 Pod 日志）
    → Kafka（缓冲，削峰，防止 ES 被日志洪水打挂）
      → Logstash（解析 + 增强 + 结构化）
        → Elasticsearch（索引 + 存储）
          → Kibana（检索 + Dashboard + 告警）
```

**统一日志格式**（自定义 `ttpc-log-spring-boot-starter`，基于 Logback JSON Encoder）：
```json
{
  "timestamp": "2024-06-18T14:30:25.123Z",
  "level": "INFO",
  "logger": "com.ttpc.auction.service.BidService",
  "thread": "http-nio-8080-exec-15",
  "traceId": "5f7a3c1e9b2d4f8a",
  "spanId": "bid-service-1",
  "msg": "出价成功",
  "app": "auction-service",
  "instance": "auction-service-7d8f9-abc123",
  "env": "prod",
  "context": {
    "dealerId": 10086,
    "auctionId": 500123,
    "bidId": 900456,
    "price": 185000
  }
}
```

关键设计：
- `traceId`：在 Gateway 层生成 UUID → MDC 注入 → Feign Interceptor 透传 → 下游 MDC → 全链路可追踪
- `context`：业务字段单独结构（不是混在 msg 字符串里），方便 Kibana 按字段筛选（如 `context.dealerId:10086`）
- `app` / `instance`：区分是哪个服务、哪个 Pod，K8s 环境下 Pod 名会变

#### 实际落地的坑

**坑 1：Filebeat 把 Node 的磁盘塞满了**

Filebeat 采集日志后转发给 Kafka，但如果 Kafka 挂了 → Filebeat 把日志缓存在本地磁盘 → 缓存越积越多 → Node 磁盘打满 → K8s 驱逐 Pod。解决：Filebeat `queue.mem` 限制内存队列大小 + `output.kafka.max_retries=3` 快速失败 + Node 磁盘告警 > 80%。

**坑 2：Logstash Grok 解析性能差**

一开始用 Grok 正则解析 Spring Boot 的默认文本日志格式，每天 5000 万条日志 → Logstash CPU 打满。解决：应用层直接输出 JSON 格式（Logback JSON Encoder），Logstash 不需要解析只用 `json` filter。CPU 降了 80%。

**坑 3：Elasticsearch 索引膨胀**

6 个微服务按天建索引 → ES 磁盘每周增长 200GB。解决方案：
- 索引生命周期管理（ILM）：Hot（7 天 SSD）→ Warm（30 天 HDD）→ Cold（90 天对象存储）→ Delete
- ERROR 日志保留 90 天，INFO 日志保留 14 天（不同的 ILM 策略）
- 按 `level` 字段差异化保留

#### 实际排查案例

**场景**：某车商投诉"我明明出价 18.5 万，为什么最后显示是 18 万？"

在 ELK 中搜索：
```
traceId: "从车商 APP 的 Response Header 中拿到" AND app: "auction-service" AND context.dealerId: 10086
```
3 秒内找到完整的出价链路：
- 车商发起出价 18.5 万 → auction-service 收到 → 校验通过
- 写入 Redis ZSet: score=185000 → 成功
- 广播 WebSocket 给其他车商时，price 字段被 `Integer.parseInt()` 取了整数（因为前端用整数显示）→ 其他车商看到的是 18 万

根因：序列化时精度丢失。修复后加了自动化测试——所有涉及价格的字段必须用 `BigDecimal`，不能在中间转 `int` / `double`。

### 15. SOLID 原则——天天拍车真实代码中的体现

#### 单一职责原则（SRP）——"订单事件处理上帝类"的拆分

**背景**：拍卖成交后触发一个 `AuctionSoldEvent`，由一个 `AuctionSoldHandler` 处理所有成交后逻辑。这个 Handler 做了：
- 生成成交合同
- 扣减车商保证金
- 发送成交短信
- 通知检测师
- 更新车商统计数据
- 触发生成发票
- 发送内部运营报表
- ...

750 行代码的上帝类。每次成交逻辑有变动，都要改这个类。关键是——这些操作之间没有顺序依赖，完全可以并行。

**重构**：
```java
// 成交合同
@EventListener
public void generateContract(AuctionSoldEvent event) { ... }

// 保证金扣减
@EventListener
@Order(Ordered.HIGHEST_PRECEDENCE) // 必须第一个执行
public void deductDeposit(AuctionSoldEvent event) { ... }

// 通知（异步，不阻塞主流程）
@EventListener
@Async("notificationExecutor")
public void sendNotifications(AuctionSoldEvent event) { ... }

// 车商统计
@EventListener
@Async("statsExecutor")
public void updateDealerStats(AuctionSoldEvent event) { ... }
```

**解决了什么**：
- 每个 Listener 一个职责，类从 750 行降到 50-80 行
- 新增「成交后自动评价」→ 加一个 Listener，不动已有代码（开闭原则）
- 异步执行的 Listener 不阻塞主流程，保证金扣减（最高优先级）先执行

#### 开闭原则（OCP）——拍卖策略的新增

前面题 2 和题 9 已详细展开。新增拍卖模式 / 支付渠道 / 报告类型 = 加一个新类实现接口，不改已有代码。

#### 里氏替换原则（LSP）——车商认证的继承陷阱

**反面案例**：我们曾经设计了一个 `BaseDealer` 父类和 `PersonalDealer`（个人车商）、`CompanyDealer`（企业车商）子类。

```java
public class BaseDealer {
    public void freezeDeposit(BigDecimal amount) {
        this.frozenAmount = this.frozenAmount.add(amount);
        this.availableAmount = this.availableAmount.subtract(amount);
    }
}

public class CompanyDealer extends BaseDealer {
    @Override
    public void freezeDeposit(BigDecimal amount) {
        // 企业车商多了银行保函模式——不是冻结自己的钱，而是锁定额度
        if (hasBankGuarantee) {
            this.guaranteeUsed.add(amount);  // 只记账，不冻结
        } else {
            super.freezeDeposit(amount);
        }
    }
}
```

问题：调用方不知道 `freezeDeposit()` 的具体行为——传入相同的保证金金额，个人车商被冻结了保证金，企业车商只是减了银行保函额度。如果你写了一个逻辑"冻结后保证金总额减少"——对 `CompanyDealer` 这是错的（银行保函额度不等于保证金）。

**教训**：不是所有的"is-a"关系都能用继承。`CompanyDealer` 有不一样的保证金行为 → 应该用组合而非继承：
```java
public interface DepositStrategy { void freeze(BigDecimal amount); }
public class CashDeposit implements DepositStrategy { ... }
public class BankGuaranteeDeposit implements DepositStrategy { ... }

public class CompanyDealer {
    private DepositStrategy depositStrategy;  // 组合
}
```

#### 依赖倒置原则（DIP）——Spring 的日常

天天拍车所有 Service 层依赖接口不是实现类：
```java
@Autowired private VehicleRepository vehicleRepository;  // 接口
// 实际注入：MyBatisVehicleRepository（MyBatis 实现）
// 如果换 JPA: JpaVehicleRepository implements VehicleRepository
// Service 层不用改任何代码
```

#### 接口隔离原则（ISP）——避免"胖接口"

车商信息的查询接口最初是一个大接口：
```java
interface DealerService {
    Dealer findById(Long id);
    List<Dealer> findByCity(String city);
    void updateDealer(Dealer dealer);
    void updateCreditScore(Long dealerId, int score);  // 只有风控服务才用
    void updateDeposit(Long dealerId, BigDecimal amount);  // 只有拍卖服务才用
}
```

风控服务和拍卖服务都用 `DealerService`，但它们实际需要的只是其中 1-2 个方法——依赖了全部方法。重构：
```java
// 只读接口
interface DealerQueryService {
    Dealer findById(Long id);
    List<Dealer> findByCity(String city);
}
// 信用接口（只有风控用）
interface DealerCreditService {
    void updateCreditScore(Long dealerId, int score);
}
// 保证金接口（只有拍卖用）
interface DealerDepositService {
    void updateDeposit(Long dealerId, BigDecimal amount);
}
```

**解决了什么**：风控服务以后不需要关心保证金接口的变化；拍卖服务不需要关心信用评分的实现。
