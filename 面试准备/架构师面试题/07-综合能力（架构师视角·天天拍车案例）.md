## 七、综合能力（架构师视角·天天拍车实战案例）

> 以下全部以「天天拍车」为背景，涵盖技术选型、业务平衡、团队建设、Roadmap 制定、跨团队协作、成本控制、架构师素质等方面。

### 1. 作为Java架构师，你如何进行技术选型？考虑哪些因素？

#### 是什么——技术选型的本质

技术选型不是「哪个火选哪个」，也不是「哪个我熟选哪个」。本质是**在多重约束下寻找最优解**——约束包括：业务需求、团队能力、时间窗口、成本预算、公司技术栈战略。

#### 天天拍车三次关键选型复盘

**选型一：消息队列——RocketMQ vs Kafka**

这是前面第六部分第 11 题详细讲过的案例。核心决策点：业务需要事务消息（出价 + 保证金冻结必须原子操作）→ RocketMQ 原生支持，Kafka 需要额外实现 → 事务消息这个「刚需」压倒其他所有维度的差异。

**选型二：前端拍卖实时推送——WebSocket 长连接 vs 短轮询 vs SSE**

业务场景：车商在拍卖页面需要实时看到最新出价（延迟要求 < 1s），200 场拍卖同时进行，每场 50+ 个车商在线，总计 ~10000 并发长连接。

| 维度 | 权重 | WebSocket | 短轮询(3s) | SSE |
|------|------|----------|-----------|-----|
| 实时性 | 30% | 9（push 即时） | 5（最多迟 3s） | 9 |
| 浏览器兼容 | 10% | 9（所有现代浏览器） | 10 | 7（IE 不支持） |
| 服务端复杂度 | 20% | 7（Netty 管理连接） | 9（无状态 HTTP） | 8 |
| 车商 APP 兼容 | 15% | 8（需要 WebSocket SDK） | 10（HTTP 天然支持） | 7 |
| 带宽消耗 | 15% | 9（只推变更） | 4（每次请求 HTTP 头 ~1KB × 万人 × 3s） | 9 |
| 扩缩容难度 | 10% | 6（长连接重连风暴） | 10（无状态随便扩） | 6 |
| **加权总分** | | **8.05** | **7.4** | **8.1** |

选型结果：WebSocket。因为实时性是核心体验（车商 3s 延迟就可能错过出价窗口），无法妥协。

上线后的坑与解决：
- **连接数暴涨导致 Netty 文件描述符耗尽**：初次上线时，Node 的文件描述符限制是 1024 → WebSocket 连接 5000 后报 `Too many open files`。解决：`ulimit -n 65535` + K8s Node 级别配置 `fs.file-max`
- **Pod 重启导致万级重连风暴**：一个 WebSocket Pod 重启 → 5000 个客户端同时重连 → CPU 打满。解决：客户端加随机延迟重连（`Math.random() * 5000ms`）+ 最少连接数预热
- **车商网络切换（WiFi→4G）连接断开**：客户端心跳 30s 一次，断开后到检测到需要 30s → 车商在这 30s 内看不到出价更新。解决：客户端加网络状态监听（`navigator.onLine` + `NetworkInformation API`），网络变化后立即重连

**选型三：配置中心——Nacos vs Apollo**

天天拍车当时的情况：微服务改造已上线 4 个服务，预计年底到 15 个。技术负责人（我）需要选一个配置中心。

团队背景：运维团队 2 人，后端开发 30 人，没有专门的中间件团队。如果用 Apollo，需要单独部署 Apollo Portal + Admin Service + Config Service + MySQL，运维成本至少 0.5 人。Nacos 本身已用作注册中心，配置功能是内置的——不需要额外部署。

决策对比：
| 维度 | Nacos | Apollo |
|------|-------|--------|
| 部署复杂度 | 零（已在用） | 高（4 个组件 + 1 个 DB） |
| 配置灰度 | 基础（按 IP） | 完善（按 AppId、IP、标签） |
| 配置审计 | 基础 | 完善（每次变更记录） |
| 团队运维成本 | 0 人天 | ~5 人天/月 |

选 Nacos。当时有人质疑「Nacos 配置管理不如 Apollo 专业，将来业务复杂了怎么办？」我的回答：「等需要 Apollo 级别的配置灰度时，我们已经能承担运维成本了。现在的瓶颈不是配置管理不够精细，而是团队没精力维护多一套系统。」这个权衡是对的——两年后团队扩张到 80 人时，我们迁移到了 Apollo，但 Nacos 的 2 年节省了约 120 人天的运维成本。

#### 技术选型的 6 条铁律（总结）

1. **业务需求权重最高**：技术是为业务服务的，不是反过来
2. **团队能力决定上限**：选团队能驾驭的技术，不是最先进的技术
3. **不要过早优化**：当前够用就行，预留扩展点而不是一步到位
4. **评估运维成本**：开源不等于免费，维护的人天是真实成本
5. **做 POC 验证**：纸上对比三个月不如花三天写一个 Demo
6. **记录决策过程（ADR）**：以后被质疑时能回溯为什么这么选

### 2. 如何平衡技术理想与业务需求？当业务要求快速上线，技术有更优但耗时更长的方案时，如何决策？

#### 天天拍车真实冲突案例——"帮卖模式"上线之争

**背景**：运营团队提出「帮卖模式」——车主挂牌后如果 24h 无人出价，系统自动降价 5000 元进入二拍。运营要求 5 月底上线（赶上 618）。

**技术理想方案（我提出的）**：完全配置化的拍卖生命周期引擎——任何拍卖模式（英式、荷兰式、帮卖、闪拍）通过配置实现，不需要写代码。预估开发时间：4 周。

**业务要求的方案**：先硬编码帮卖逻辑上线（1 周），后面再配置化。

**冲突点**：我觉得硬编码是技术债务，将来改起来更贵。业务说「没有帮卖模式，618 少 30% 的车源，这是几千万 GMV 的事」。

#### 我的决策过程

**第一步：算账——用业务语言翻译技术选择**

```
方案 A（硬编码，1 周上线）：
  开发成本：5 人天
  618 GMV 预估：+3000 万（帮卖模式多带车源）
  技术债务：预估 10 人天（2 个月后配置化重构）
  
方案 B（配置化，4 周上线）：
  开发成本：20 人天
  618 GMV：0（来不及上线）
  错过 618 窗口，下次大促是双 11
```

算完账，方案 A 的账很清晰——先上帮卖，618 赚 GMV，之后 10 天还债。方案 B 虽然技术优美，但错过了业务窗口，技术上再优雅也没有价值。

**第二步：承认并显性化技术债务**

我没有假装不管技术债务，而是立刻在 Jira 上建了一个 Task：「帮卖模式配置化改造」，排到下个迭代。所有人可见——债务可见了，就不会被遗忘。

**第三步：硬编码也要写得"好拆"**

虽然是硬编码，但我要求开发用策略模式的接口：
```java
// 即使现在只有一个帮卖实现，也要用接口隔离
interface AuctionLifecycle {
    void onEnd(Auction auction);
}
class BangMaiLifecycle implements AuctionLifecycle { ... }

// 不要直接 new BangMaiLifecycle()，而是通过工厂获取
// → 将来加新模式直接改工厂，不碰业务逻辑
```

**结果**：帮卖模式 5 月底上线，618 带了 4000+ 车源。两个迭代后（7 月中旬）完成配置化改造，技术债务还清。全程没有线上故障。

#### 平衡技术理想与业务的三条原则

1. **用业务 ROI 做决策，不用技术偏好**：把技术方案翻译成业务影响（GMV、转化率、人天），让决策基于数据
2. **分期交付——快上线，慢优化**：MVP 快速上线验证业务价值 → 观察真实用户行为 → 针对性优化。不要一开始就做最优方案
3. **显性化技术债务**：不是「先欠着后面再说」（后面永远不会说），而是建 Jira Ticket + 排入 Sprint Backlog + 明确偿还时间

#### 我踩过的坑

**反例——一次技术理想主义导致的事故**：刚加入天天拍车时，我坚持要把缓存从 Guava Cache 换成 Redis Cluster，理由非常充分（多实例共享、过期策略统一、无状态更好扩缩容）。但这个改造花了 2 周，期间因为 Redis Cluster 配置不当（没有设密码 + 公网端口误开），被扫到了 Redis 挖矿脚本，把拍卖出价的缓存全清了。如果当初先保持 Guava Cache（虽然不完美但够用），线上不会挂。

**教训**：不是所有技术优化都要立刻做。判断标准：当前的「不完美」真的在造成业务损失吗？如果不是，优化可以往后排。

### 3. 你如何带领团队进行技术攻关、代码评审？如何提升团队的技术能力？

#### 在天天拍车带团队的三个阶段

**阶段一：我扛旗（前 3 个月）——建立信任和标准**

初到团队时，团队 15 人，中级工程师为主，只有 2 个 Senior。团队之前没有架构师，技术决策靠组长拍脑袋。

第一件事不是推规范，而是**用一次线上故障证明专业价值**：拍卖出价接口间歇性超时（就是前面讲过的 `LinkedList` 并发死循环），从发现到恢复我只用了 30 分钟（Arthas 定位 + 修复）。这次事故的复盘会上，团队才真正认同 Arthas 的价值、CR 的价值、数据结构和并发安全的重要性。

之后推行 CR 制度和代码规范（第六部分第 1 题详细讲过），从硬推变成了团队主动要求——"这个 LinkedList 变更有被 Review 过吗？"

**阶段二：带团队做技术攻关（6-12 个月）——从"告诉答案"到"引导思考"**

拍卖出价性能优化（出价 P99 从 8s 到 30ms）是我主导的第一次全团队攻关。我的做法：

第一，把问题分解成子任务：
- 子任务 A：分析 SkyWalking 找出最慢的环节（1 天）→ 分配给中级工程师
- 子任务 B：EXPLAIN 分析慢 SQL + 初步优化建议（1 天）→ 分配给另一个中级
- 子任务 C：研究 Redis 缓存方案（竞品调研）（1 天）→ 分配给主动想学 Redis 的新人
- 子任务 D：整体方案设计 + 评审（我主导）

第二，方案评审时不是我一个人讲：
- 每个子任务的负责人先讲自己的发现和建议
- 大家讨论权衡（为什么用 Redis 而不是本地缓存？为什么用 Bloom Filter？）
- 我负责补充他们没考虑到的点（如 Bloom Filter 的假阳性如何影响业务）

第三，攻关后的复盘：
- AAR（After Action Review）：做了什么 → 什么做对了 → 什么可以更好 → 下次怎么做
- 复盘文档化（Confluence），标题：「出价性能优化——从中可以复用的排查方法」
- 分享给全公司（不止后端团队，前端、测试也能学到全链路排查的思路）

**阶段三：放权培养（12 个月之后）——让别人成长**

团队从 15 人增长到 40 人，我不可能所有决策都自己做。做了三件事：

1. **定义 Tech Lead 角色**：每个微服务配一个 Tech Lead，负责该服务的架构设计和 CR 把关。我负责跨服务的决策 + 培训 Tech Lead

2. **Tech Lead 轮值制**：每个季度换一次 Tech Lead，让更多人有架构决策的经验。第一周我会旁听 Tech Lead 的方案评审，之后逐步放手

3. **能力模型透明化**：
```
L5 高级工程师：独立负责一个模块，能写出团队认可的代码
L6 资深工程师：独立负责一个微服务，能做技术方案设计，能带新人
L7 架构师：跨服务架构决策，技术选型，团队技术方向规划
```
每个级别有明确的行为指标（不是"工作 5 年自动升级"，而是"主导过至少 1 次线上故障排查 + 1 次跨服务架构设计 + 带过 2 个新人"）。

#### 如何提升团队技术能力

1. **每周技术分享**：轮值制，主题不限。好的分享包括：「我是怎么用 Arthas 排查那次 OOM 的——现场重演 15 分钟」「RocketMQ 事务消息的坑——从源码解析到线上排查」「设计模式不是面试题——拍卖策略模式重构全过程」

2. **结对编程（不是全程，而是关键节点）**：新人在做第一个 DB 设计或第一个复杂 SQL 时，和 Senior 结对写。不是 Senior 写让新人看，而是新人写让 Senior Review，发现问题当场讨论。

3. **外部学习**：每季度每人有 2 天「自我提升日」——可以去参加技术大会、研究一个开源项目、或学一个新技术做 Demo。回来要分享（1 小时以上），不能私自享用。

4. **内外开源**：内部把通用组件（日志 Starter、鉴权 Starter）开源到团队私有 GitLab，鼓励贡献 PR。好的工具推送到 Maven Central（如我们的 `ttpc-log-spring-boot-starter`，被公司其他部门也使用了）。

### 4. 未来3-5年，Java架构师需要重点关注哪些技术方向？如何保持技术迭代？

#### 结合天天拍车的业务展望

**方向一：AI 与业务系统的深度融合**

天天拍车已经在尝试：AI 车况估价（检测报告 + 车辆图片 → AI 模型预估成交价）、AI 智能客服（车商问题自动应答）、OCR 识别（行驶证/登记证自动录入）。

架构师的职责不是训练模型，而是**设计 AI 能力的集成架构**：
- RAG（检索增强生成）：把天天拍车的历史成交数据、检测标准、政策文档向量化存储（Milvus），LLM 查询时检索相关文档增强回答
- AI Agent：定义 Agent 的工具接口（查询订单、查询车辆信息、查询保证金余额），LLM 作为推理引擎选择工具
- MCP 协议：把天天拍车的业务 API 封装为 MCP Tool，无缝对接各种 LLM 平台
- 向量数据库选型：Milvus vs Qdrant vs pgvector，天天拍车的数据量（3000 万车辆 + 5000 万检测数据）需要分布式向量存储

**方向二：Java Virtual Threads（JDK 21）对微服务架构的颠覆**

天天拍车当前最大的性能瓶颈之一——线程池。拍卖出价的线程池（200 线程）在大促期间被打满，导致请求排队。Virtual Threads 让每个线程占 ~300 bytes 栈（传统线程 ~1MB），出价服务可以开 10000 个虚拟线程而不会 OOM。

但 Virtual Threads 不是银弹。我们做了 POC：在 Virtual Threads 中调 `synchronized` 会导致 pinning（线程固定在 OS 线程上），反而更差。需要把所有 `synchronized` 换成 `ReentrantLock`。这对存量代码是巨大的迁移成本。

**方向三：GraalVM Native Image——冷启动从秒到毫秒**

天天拍车的 K8s Pod 启动时间 ~40 秒（Spring Boot + 依赖注入 + 连接池初始化），HPA 扩缩容有滞后。GraalVM Native Image 可以把启动时间降到 < 1s，让扩缩容的响应速度从分钟级降到秒级。

但 Native Image 的限制也很实际：不支持 `@RefreshScope`（需要编译期确定）、不支持动态代理（CGLIB/JDK Proxy 需要配置）、反射需要声明。Spring Boot 3.x 的 AOT（Ahead-of-Time）编译已支持大部分场景，但第三方库的兼容性仍然是大问题。

**方向四：可观测性升级——eBPF 的零侵入监控**

SkyWalking Agent 虽然已接近零侵入，但 eBPF 更进一步——不需要改 JVM 参数、不需要 Agent，直接从 Linux 内核层面追踪系统调用、网络包。天天拍车的痛点：某些老服务 Agent 版本不兼容、某些第三方 SDK 无法追踪。eBPF 在容器网络层面的追踪可以补上这些盲区。

#### 如何保持技术迭代

1. **20% 时间做技术预研**：每个季度抽 1-2 天做一个新技术的 POC。比如「Virtual Threads 替换线程池——出价服务 Demo」跑一下，看性能变化，写一篇内部报告
2. **读论文 > 读博客**：论文是一手资料，博客是二手理解。Raft、Spanner、DynamoDB 的经典论文值得每 2 年重读一次
3. **参加社区**：开源项目的 Issue/PR 讨论是最好的学习材料。2024 年跟着 Spring AI 和 LangChain4j 的 MCP 实现看了很多设计思想
4. **写 > 读**：写技术博客、做内部分享，输出是最好的输入。讲不清楚 = 没搞清楚

### 5. 当项目出现技术瓶颈时，如何分析问题、制定解决方案、推动方案落地？

（第六部分的出价性能优化案例已详细阐述完整的 STAR 过程，这里补充「推动方案落地」的通用方法论）

#### 推动方案落地的四步法

**第一步：量化——让问题可见**

不说「出价很慢」，用数据：「出价接口 P99 = 8s，P50 = 3s，错误率 15%，车商客诉量本周 87 次（上周 3 次）」。

把技术指标翻译成业务损失：「错误率 15% 意味着每天约 300 次出价失败，按照出价到成交转化率 8% 算，每天损失 24 笔成交，约 48 万 GMV。」这个数字在周会上报给业务负责人看，方案审批就顺畅了。

**第二步：方案对比——给人选择感**

不给「唯一方案」，给 A/B/C 三个方案：
```
方案 A（削峰异步，1 天）：P99 恢复但最终一致性，有 1s 延迟
方案 B（加索引+乐观锁，2 天）：P99 恢复且强一致，但需要停服 10 分钟加索引
方案 C（Redis+Lua，3 天）：P99 永久优化，但需要额外的 QA 测试

推荐：A（止血） + B（根治），C 排下个迭代做长期优化
```

**第三步：灰度验证——让小部分用户先吃螃蟹**

不是"全量发布"，是"1% → 10% → 50% → 100%"渐进式发布。每一步观察 SkyWalking 错误率、P99 延迟、业务指标（成交率）。

**第四步：复盘——把个人经验变成团队资产**

故障复盘 = 时间线 + 根因 + 修复 + Action Items + 下次如何避免。关键不是「找到谁的责任」，而是「找到下次不再发生的机制」。比如 LinkedList 事故的 Action Item 是"核心数据结构选型加入 CR Checklist"，不是"实习生下次注意"。

### 6. 你如何与产品、测试、运维等团队协作？

#### 天天拍车的跨团队协作案例

**和产品的协作——「一键降价」需求的沟通**

产品提了一个需求：「帮卖模式中，车主可以在 App 上一键降价 5000」。技术上这个不难——一个 API 调 `update auction set current_price = current_price - 5000` 就行。

但在需求评审时，我追问了三个问题，发现产品没考虑到：
1. 「一键降价」有没有次数限制？如果车主每分钟点一次，拍卖永远不结束怎么办？→ 产品补充：每轮只能降一次，最多降 3 轮
2. 降价后是否需要通知已出价的车商？→ 产品补充：需要 WebSocket 推「车主降价至 XXX 万」
3. 降价时如果有人正在出价怎么办？→ 技术上需要 Redis 锁，防止并发冲突

这三个问题让一个"简单需求"变成了一个有完整边界的设计。产品经理后来说这次评审让他知道了「以后提需求时会先想清楚边界条件」。

**和测试的协作——把测试从瓶颈变成赋能**

天天拍车早期测试流程：开发自测 → 扔给 QA → QA 手工测 → 提 bug → 开发修 → QA 回归。一个 MR 从提测到上线平均 3 天。

我的推动：
- **让测试左移**：开发写单元测试 + 集成测试（Spring Boot Test + Testcontainers），覆盖率 > 70% 才给 QA。QA 不用再测基本的逻辑正确性，聚焦业务场景和边界条件
- **让测试右移**：线上流量录制回放。用 SkyWalking 录制真实请求 → 在 CI 环境中回放 → 对比新旧版本响应差异。发现了一次 MR 把出价精度从 BigDecimal 改成了 double（精度丢失），在测试环境就被拦截
- **联合共建**：我写了第一个 Testcontainers 的测试示例（MySQL + Redis Mock），QA 团队在此基础上扩展了完整的集成测试套件

**和运维的协作——从我修 bug 到我写手册**

天天拍车初期没有运维团队，后端开发兼任运维。后来有了 2 个运维，但他们不熟悉我们的业务代码。出问题时运维只能重启 Pod，不能定位根因。

我的做法：
- **可运维性设计**：所有服务暴露 `/actuator/health` + `/actuator/metrics` + `/actuator/prometheus`。运维能在 Grafana 上看到 QPS/RT/错误率
- **提供排查手册**：写了一份《常见线上问题排查手册》给运维——「问题：出价接口 5xx → 1. 看 SkyWalking 哪个服务报错 → 2. 如果是 DB 超时，看 `SHOW ENGINE INNODB STATUS` → 3. 如果是 Redis 不可用，看 Redis 集群状态」
- **建立 on-call 值班制度**：后端和运维轮流 on-call。on-call 遇到解决不了的问题 15 分钟内升级到 Tech Lead
- **事后复盘共同参与**：不是运维的锅自己扛，开发的锅甩给运维，而是一起复盘，找到机制的改进点

#### 跨团队协作的核心原则

1. **说话用对方的语言**：和产品聊用 GMV、转化率；和运维聊用 MTTR、可用率；和测试聊用覆盖率、缺陷率
2. **主动承担责任边界之外的半步**：我写的代码，运维不了解 → 我写排查手册。测试需要 Mock 数据 → 我提供数据构造工具
3. **用共同的目标拉齐**：不是「我要做微服务改造」，而是「我们一起把系统可用性从 99.9% 提升到 99.99%」

### 8. 工作中遇到的最大的技术挑战是什么？如何解决的？从中学到了什么？

#### 天天拍车最大的技术挑战——交易数据迁移（不中断业务的 8000 万行出价表切库）

这是我在天天拍车面临的最大技术挑战，比性能优化更复杂——因为它涉及**不中断业务的数据迁移**，出了错要么丢数据、要么业务中断。

**挑战的规模**：
- 出价表 8000 万行（每天新增 30 万）
- 车辆表 3000 万行
- 保证金账户表 800 万行
- 读写 QPS 高峰期 ~5000（不能停机迁移）
- 目标：从老库（自建 MySQL 5.6）迁移到新库（云数据库 PolarDB 8.0）

**最难的三个问题**：

**难点一：全量迁移 8000 万行期间产生的增量数据怎么追**

全量导出 8000 万行需要 4 小时。导出过程中新出的价怎么办？

解决：全量导出前记录 binlog 位点 → 导出完成后从该位点开始增量追（Canal 订阅 binlog → 解析 INSERT/UPDATE/DELETE → 回放到新库）。追了 3 轮增量（每轮追差距越来越小），最后差距 < 100 条时进行最终切换。

**难点二：切换瞬间怎么保证数据不断**

切换不是「停老库 → 启新库」，而是渐进式切流。

解决：Gateway 层实现流量染色。写了一个 Gateway Filter，根据 `dealer_id % 100` 逐步把读流量从老库切到新库。每切 5%（观察 30 分钟 → 确认无异常 → 再切 5%）。

切到 80% 时出现了一次异常——新库一个 SQL 突然走错了索引（优化器用错了执行计划），P99 涨到 500ms。立即暂停切流（停在了 80%），DBA 强制执行计划（`FORCE INDEX`），恢复后再继续。

**难点三：双写一致性——写老库成功写新库失败怎么处理**

双写阶段：应用层写操作先写老库（主路径），再异步写新库。如果写新库失败怎么办？

解决：
1. 写新库失败不阻塞主流程（catch 异常 + 告警）
2. 失败的消息写入消息表（queue 机制，不是 MQ——因为切换期间要保证处理有序）
3. 后台 Worker 重试消息表（指数退避：1s → 2s → 4s → 8s → 16s）
4. 超过 16s 还没写成功 → 人工介入（非常罕见，只在 Canal 断连时出现过一次）
5. 数据一致性校验：`pt-table-checksum` 每 2 小时全量校验一次，发现不一致 → 立即补偿

**从这次挑战中学到的**：

1. **数据迁移的核心不是技术，是流程和回溯**。每个步骤有明确的回滚方案，每一步迁移是可逆的
2. **Canal binlog 解析有坑**——`TIMESTAMP` 类型在 ROW 模式下，binlog 中是 UTC 时间，Canal 默认不转时区 → 比实际时间差 8 小时。排查了 3 天才发现是时区问题
3. **`pt-table-checksum` 在大表上会锁表**——之前的经验在 1000 万行内没问题，8000 万行时 checksum 本身就需要 20 分钟，期间大量表级共享锁。解决：在凌晨 2-5 点执行 + `--chunk-size-limit` 限制每个 chunk 大小
4. **数据切换要和业务低峰对齐**：不是技术什么时候准备好就切，而是和运营确认"什么时候出价量最低"（凌晨 3-5 点）

### 9. 如何评估一个系统的架构设计是否合理？有哪些评估指标？

#### 天天拍车的架构评估体系

**不是一次性评估，而是持续评估**。每季度用以下框架做一次全系统架构评估：

| 评估维度 | 指标 | 天天拍车 2023Q3 实际情况 | 目标 | 差距 |
|---------|------|------------------------|------|------|
| 性能 | 核心链路 P99 | 出价 120ms, 详情 350ms | 出价 < 100ms | 轻微差距 |
| 可用性 | 近 90 天故障时间 | 35 分钟（3 次 P1） | < 15 分钟 | 需改进 |
| 可扩展性 | 新增一个城市上线需改多少代码 | 只改配置（达标） | 只改配置 | OK |
| 可维护性 | 新人独立上手时间 | 1.5 周 | 1 周 | 轻微差距 |
| 安全性 | 渗透测试高危漏洞 | 1 个（API 鉴权遗漏） | 0 | 需修复 |
| 可观测性 | MTTR（平均故障恢复时间） | 25 分钟 | < 15 分钟 | 需改进 |
| 成本 | 单次出价的云资源成本 | 0.003 元 | < 0.005 元 | OK |

**Q3 评估结论**：可用性和 MTTR 需要重点改进（Q4 目标：新增自动故障转移演练 + 故障排查手册升级）。

#### 评估案例——天天拍车一次"看起来不错"但实际有问题的设计

**场景**：出价服务依赖车商服务的 RPC 获取「车商信用分」，如果信用分不达标，不允许出价。

这个设计在正常运行状态下没问题。但评估时我发现了一个隐患：**出价服务和车商服务是同步 RPC 调用**。如果车商服务挂了或者变慢，出价服务每个请求都等 RPC 超时（3s），100 个并发请求全部卡死 → 线程池满 → 出价服务不可用。

评估指标体现：**MTTF（Mean Time To Failure）**——如果把车商服务停了，出价服务在 3s 后就会无法响应。这不符合「核心链路不能依赖非核心服务」的原则。

改进方案：把信用分校验改为本地缓存 + 异步更新。信用分变更不频繁（一天可能只变一次），在出价服务本地 Caffeine 缓存（TTL 5 分钟）。即使车商服务挂了，出价服务用本地缓存照样能运行。

**这个案例说明**：架构评估不能只看「功能是否正确」，还要评估「依赖健康度」。如果核心服务依赖了一个非核心服务，且是同步依赖 → 就是一个潜在的架构风险。

### 10. 如何看待技术债务？在项目中如何避免产生技术债务，如何偿还已有的技术债务？

#### 天天拍车技术债务的四个真实案例

**债务一（低利率——可缓还）：检测报告 HTML 模板硬编码**

2018 年写的检测报告生成代码，HTML 模板直接写在 Java 类里（StringBuilder 拼接）。没人愿意动它——"能动就行，改了怕出 bug"。这个小模块 4 年没更新过，也不影响核心业务。

处理：**不主动还**。除非业务需要改模板（如新增新能源车检测项），顺便重构。不要让低利率债务占据核心精力。

**债务二（高利率——必须还）：保证金冻结的 `SELECT ... FOR UPDATE`**

所有出价都要对车商的保证金账户做 `SELECT ... FOR UPDATE`（悲观锁），高并发下锁冲突严重——每天都有死锁告警。

处理：**优先偿还**。用乐观锁（version 号）+ CAS 重试替代了悲观锁。还债用了 3 天，之后死锁告警降为零。

**债务三（突发债务——事故后的修复）：车商登录的 Session 共享**

早期用 Spring Session + Redis 实现 Session 共享，但 Redis 集群的一次网络抖动导致所有车商被迫重新登录（Session 全丢）。事故后我们把登录状态改成了 JWT（无状态），不再依赖 Redis Session。

处理：**事故驱动偿还**。有些债务只有在出了事之后才会被重视——这种时候不要只修 bug，要从架构层面消除 bug 的根源。

**债务四（隐形债务——团队不知道的坑）：`@Transactional` 使用不当**

全项目用了 300+ 个 `@Transactional`，但因为同类方法调用失效 + checked 异常不回滚，估计有 10-20 个地方事务没有生效。但因为都是低 QPS 的边缘逻辑（管理后台、报表导出），一直没有暴露。

处理：**技术债台账 + 渐进修复**。在 Jira 建了「事务注解问题修复」Epic，每次迭代修 3-4 个，3 个迭代修完。不专门排 Sprint，而是在业务开发中顺便修。

#### 如何避免产生技术债务

1. **CR 是防火墙**：发现"能用但不好"的代码，CI 不拦截但 CR 拦截，要求"至少写成好拆解的结构"
2. **技术债台账**：Jira 专门一个「技术债务」泳道，所有在 CR/故障复盘/周报中发现的问题进泳道，排优先级
3. **每个迭代留 15-20% 还债额度**：不单开 Sprint，而是融入日常。这个 Sprint 做了业务需求 A，顺便还了相关的债务 B
4. **Boy Scout Rule**：离开代码时让它比来时更干净。加新功能时发现旁边的旧代码有坑 → 顺手修（但要单独提 MR，别和新功能混在一起）

### 11. 当团队成员对技术方案有不同意见时，你如何协调和决策？

#### 天天拍车真实争议案例——"出价去重用 Redis 还是 MySQL"

**背景**：出价前需要校验「这个车商在这场拍卖中出过价没有」（防止出一价后又出一价）。

**工程师 A（Senior）方案——MySQL**：
```sql
SELECT COUNT(*) FROM bid WHERE auction_id=? AND dealer_id=?
```
理由：简单可靠，MySQL 已有去重逻辑，不需要引入新组件。

**工程师 B（中层）方案——Redis Bloom Filter**：
```
BF.EXISTS bid:auction:123 dealer:456
```
理由：极低延迟（< 1ms），减少 MySQL 压力，之前 MySQL 被打满就是因为这类查询。

**争论焦点**：
- A：Bloom Filter 有假阳性，误判概率 0.1% 可能导致车商的首拍被拒，这会影响成交！
- B：0.1% × 10 万次出价 = 100 次误判。但 MySQL 去重查询高峰期占用 30% CPU 导致全局变慢，影响的是所有出价！
- A：那为什么不用 Redis SET（精确去重，无假阳性）？
- B：SET 存 8000 万条出价记录要 30GB+ 内存，Bloom Filter 只要 ~200MB。

**我的协调方法**：

第一步：冷静分析，把争论转为数据对比。

我让 A 和 B 各花半天做 Benchmark：
- MySQL 方案：单次去重查询 3ms，并发 500 → CPU 30%
- Bloom Filter 方案：单次 < 1ms，假阳性 0.1%，内存 200MB
- Redis SET 方案：单次 < 1ms，0 假阳性，但需要 30GB 内存 × 3 个分片 → 每月 2000 元云资源

第二步：引入业务视角。

和产品确认："如果一个车商的第一次出价因为技术原因被拒绝，他会有什么感受？"产品说"他会马上再出一次价——以前这种情况也有过，车商反馈就是多点一次按钮"。

第三步：决策。

Bloom Filter 方案。理由：
- 0.1% 的假阳性对业务影响极小（车商多点一次按钮即可）
- 30% 的 CPU 降低对系统的稳定性提升巨大
- 200MB vs 30GB 的成本差异不可忽视

**关键**：我不是强行拍板，而是通过数据 + 业务视角 + 成本分析让所有人认同。决策后 A 虽然选了不是自己的方案，但认同这是正确的选择。

#### 处理技术分歧的原则

1. **数据 > 直觉**：不凭感觉争论，花半天做 POC/Benchmark 验证
2. **业务视角 > 技术偏好**：回到业务场景判断——哪个方案对用户体验/业务收入的影响最小
3. **决策框架**：多维度打分（性能、成本、复杂性、风险），设定每个维度的权重
4. **决策前充分讨论，决策后一致执行**：一旦做出决策，所有人都要支持，不允许"我早就说这方案不行"的马后炮
5. **鼓励不同意见**：会上不发言的人，会后可能会有更大的意见。主动邀请安静的人发言，不让强势的人主导讨论

### 12. 架构设计中如何考虑成本控制？

#### 天天拍车的云资源成本优化实战

**第一阶段：云计算账单审计——"我们真的需要这么多资源吗？"**

我们做了一次全面审计，发现大量浪费：
```
拍卖服务：8C16G × 8 Pod，日常 CPU 平均 15%
报表服务：16C32G × 4 Pod，CPU 5%，只在凌晨跑报表时到 80%
Redis Cluster：16GB × 6 分片，内存使用率 40%
MySQL：8C32G × 2（主+从），CPU 15%
```
每月云资源费用 12 万元——其中至少 5 万是浪费的。

**第二阶段：对症下药——四项降本动作**

**① 水平伸缩替代固定规格——HPA + KEDA**
```
之前：拍卖服务固定 8 个 Pod（为峰值准备）
改造：HPA min=2 max=12，CPU > 60% → 扩容
      凌晨 2-6 点: min=1（KEDA Cron Scaler）
```
降本：平均 Pod 数从 8 降到 2.5，年省 ~3 万元。

**② 报表服务改为异步 + Spot 实例**
- 报表不需要实时，凌晨 3-6 点批量生成
- 改造：从同步大 SQL 改为 Spark 异步任务（XXL-Job 触发生成 → OSS 存储 → 第二天下载）
- 报表服务改用 Spot 实例（可被回收的廉价实例，价格是标准实例的 20%）
降本：报表服务从 4 × 16C32G 改为 0.5C1G Spot 实例 × 投机扩容，年省 ~5 万元。

**③ 热冷数据分离——不是所有数据都要用 SSD**
- 出价记录：近 3 个月的出价（热数据，SSD）→ 3 个月前的出价（冷数据，归档到 OSS Parquet）
- 检测报告 PDF：存 OSS 标准存储（3 个月），之后转低频存储（1 年），再转归档存储（永久）
- 日志：ES Hot-Warm-Cold ILM 策略（7 天 SSD → 30 天 HDD → 90 天 OSS）

**④ 技术栈统一降低隐形成本**
- 之前：Config 用 Apollo + Discovery 用 Eureka + Gateway 用 Zuul，三个组件三个团队维护
- 统一到 Spring Cloud Alibaba：Nacos（Config + Discovery）+ Gateway + Sentinel，一套生态一个团队维护
- 隐形成本（学习成本、运维成本、迁移成本）远大于显性的云资源成本

**第三阶段：建立成本意识——"谁的资源谁负责"**

- 每个服务标注 Owner，每月拉取该服务的云资源账单 → 发到 Owner 邮箱
- 资源浪费排行榜：月会展示「CPU 使用率 < 10% 的服务」→ 排名第一的 Owner 会自觉缩容
- 成本预算制：团队每月有固定的云资源预算，超预算需要申请（自然就会关注优化）

#### 成本控制的核心原则

```
显性成本（云账单） + 隐性成本（运维人力 + 学习成本 + 迁移风险）
              = 真正的 TCO

不要为了省 2000 元的云资源，花费 2 万元的工程师时间。
```

### 13. 一个优秀的 Java 架构师应该具备哪些素质？如何提升自己的这些素质？

#### 在天天拍车我对"好架构师"标准的演进

**刚成为架构师时以为的素质**：
- 技术够深（能讲清楚 JVM 原理、能看源码）
- 写过足够的代码（能解决复杂 bug）

**做了两年架构师后认识到真正的素质**：

**① 业务翻译能力——把"帮卖模式"翻译成"拍卖生命周期接口"**

产品说的「车主挂牌后没人竞价，自动降价 5000 重新开拍」。在架构师脑子里应该拆成：
- 一个状态机：待拍卖 → 一拍进行中 → 一拍未成交 → 自动降价 → 二拍开始
- 一个事件：`CountdownTimeoutEvent` → 检查是否有出价 → 无出价 → `ReducePriceEvent`
- 一个接口：`AuctionLifecycle.onCountdown(auction, secondsRemaining)`
- 一个可扩展点：将来"荷兰式拍卖的倒计时"和"帮卖模式的倒计时"行为不同，需要策略分离

能不能把一个模糊的业务需求翻译成清晰的、可扩展的、团队能落地的技术方案——这是架构师最重要的能力。

**② 权衡能力——没有完美方案，只有最适合当前阶段的取舍**

- 用 Nacos 配置中心（功能不够强大但运维成本低）vs Apollo（功能完善但要多人维护）
- 先硬编码帮卖（快速上线赚 GMV）vs 完美配置化（错过业务窗口）
- 用 Bloom Filter（0.1% 假阳性但 200MB）vs Redis SET（精确但 30GB）

架构师每天都在做权衡。关键不是选「最好的」，而是选「在当前约束下最合适的」——当前约束包括团队能力、时间窗口、业务需求、成本预算。

**③ 沟通能力——三种语言**

- 对老板/业务：用**业务语言**。「系统可用性从 99.9% 提升到 99.99%」→ 翻译：「一年故障时间从 8 小时降到 52 分钟，上次那种导致 50 万 GMV 损失的大事故不会再发生」
- 对团队：用**技术语言**。「为什么选 RocketMQ 而不是 Kafka？因为它的事务消息能解决我们出价 + 保证金原子操作的刚需，Kafka 需要自己实现这个逻辑增加 2 周开发量」
- 对外部（面试/分享/开源）：用**故事语言**。「我们碰到了什么问题 → 尝试了什么 → 最后怎么解决的 → 从中学到了什么」

**④ 务实精神——用最简单的方案解决最复杂的问题**

天天拍车出价性能优化，技术方案有一大堆可以炫的（Service Mesh、CQRS、Event Sourcing），但最后选了最简单的：加索引 + 缓存 + 异步削峰。不是因为我不会更复杂的技术，而是**简单方案够用、好维护、风险低**。

好的架构师不炫技。**越简单的方案越考功力**——因为简单方案需要理解业务本质，才知道哪里该删、哪里该留。

#### 我如何提升这些素质

**关于业务理解**：
- 每周参加产品的周例会（即使不需要我），听懂业务在讨论什么
- 大促期间跟着运营值班（亲自看车商出价的真实操作流程）
- 写技术方案前先和产品/运营聊一小时，确保我真正理解了需求

**关于权衡能力**：
- 每次做决策都给自己的方案找 3 个缺点（强迫自己不只看到好处）
- 看别人的架构决策（GitHub 上优秀的开源项目 ADR），想"如果是我，我会怎么选？"
- 和不同团队的架构师定期交流（跨公司、跨行业），扩展视野

**关于沟通能力**：
- 写技术文档时假设读者完全不了解背景（新人、产品都能看懂）
- 做分享前找非技术同事试讲——能让他听懂，说明我真的理解了
- 每次故障复盘写两个版本：技术版本（给团队）和业务版本（给老板）

**关于务实精神**：
- 拿到一个问题，先问自己「最简方案是什么？」（不用新组件、不改架构、只改代码能不能解决？）
- 如果最简方案能解决问题 → 就用最简方案。不因为「面子上不够高级」就选复杂方案
- 定期回顾自己做过的决策——哪些是真正需要复杂方案的？哪些是炫技的？诚实面对自己
